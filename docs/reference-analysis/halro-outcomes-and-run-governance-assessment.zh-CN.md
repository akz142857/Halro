# 业务结果究竟是什么，以及 Halro 是否适合扩展相关能力

日期：2026-09-04。状态：分析与设计建议，未实施。源码基线：`381743f6613607dc256828f4776b52af8bdd232c`。

对应的完整开发规格见：[Run 治理、业务结果关联与单位结果成本 PRD](/Users/ziy/Code/ClayCosmos/Halro/docs/prd/prd-run-governance-and-business-outcomes.zh-CN.md)。

本文独立评估数据归因、任务预算、结果接收及经营分析。判断依据为实际数据位置、已有机制、接入负担和维护成本；“网关”或“轻量”这样的名称不单独构成赞成或反对理由。

## 1. 对原图的修正

原图中的“业务验收结果发送到 FinOps”是职责示意，表达不够准确。FinOps 是一套管理实践，不是一个规定了接收协议的软件服务，也不表示数据要发给微软或 FinOps Foundation。

实际接收方可以是企业的数据分析系统，也可以是 Halro 内的可选成本分析模块。接收的是结构化业务结果及其来源，用来回答“这些费用最终完成了多少有用工作”。完整聊天、代码或工具输出通常不是计算这个指标所必需的数据。

FinOps Foundation 区分资源效率指标和业务单位指标，例如每 Token 成本与每个已解决工单成本，并要求说明指标定义、数据来源和成本范围。[Unit Economics](https://www.finops.org/framework/capabilities/unit-economics/)

## 2. 到底发送什么内容

假设客服 Agent 处理一个工单，先研究问题、生成答复，第一次未通过验证，第二次运行后解决。业务系统可以回传如下事件；字段只是建议，当前 Halro 没有这个接口：

```json
{
  "event_id": "result_4821_r2",
  "work_unit_id": "ticket_4821",
  "related_run_ids": ["run_research_1", "run_retry_2"],
  "metric_definition": "support.resolved_without_handoff.v1",
  "outcome": "accepted",
  "accepted_units": 1,
  "unit": "ticket",
  "human_intervention": false,
  "evaluator": "support_workflow_validator",
  "evidence_ref": "support_validation_973",
  "observed_at": "2026-09-04T08:15:00Z",
  "revision": 2
}
```

| 信息 | 意义 |
| --- | --- |
| `work_unit_id` | 稳定的业务工作单位；重跑两次仍然只是一张工单 |
| `related_run_ids` | 完成这项工作所涉及的执行过程，便于归集第一次失败和后续重试费用 |
| `metric_definition` | “通过”的具体定义和版本；不同任务不能把各自的通过率直接混合 |
| `outcome` / `accepted_units` | 当前结论与通过的业务单位数；也应允许 pending、rejected、unknown |
| `evaluator` / `evidence_ref` | 谁依据什么作出判断，支持事后核对 |
| `human_intervention` | 区分自主完成与经人工介入后完成 |
| 时间、事件 ID、版本 | 支持延迟到达、重复投递、结果修订和观察窗口 |

Project 与上报者身份应由服务端凭据校验；客户端填写的 `evaluator` 名称本身不构成可信身份。若数据跨项目涉及同一业务对象，必须有显式归属和权限约定。

业务结果可能晚于模型调用几小时或几天出现，也可能被后续证据修订。因此接收应与推理响应解耦。某个任务没有结果，应显示“未知/待验收”，不能自动计入成功或失败。已验收、拒绝、未验收的覆盖率应同时展示。

### 谁来判定

| 使用场景 | 可选的验收方 | 需要保留的限制 |
| --- | --- | --- |
| 结构化抽取 | schema 与业务约束验证器；人工或标注集检查内容正确性 | 结构通过不等于字段值正确 |
| 编程任务 | CI、验收测试与代码审查系统 | 测试通过、审查批准、实际业务改善属于不同证据 |
| 客服任务 | 工单状态机、人工质检或一定观察期后的业务规则 | “已关闭”未必代表真正解决，需要约定重开与接管口径 |
| 开放式回答 | 人工评分、用户反馈或独立模型评价 | 评分属于测量信号，不能自动当成客观正确性 |

LLM 评价可以参与判断，但应保留评价方法与版本，避免把执行 Agent 自己声称完成作为唯一依据。若没有稳定验收标准，仍可先做 Run 费用与预算，不必强行产生“价值分数”。

已有工具也采用这种分离方式：Langfuse 可将外部 API、人工或评价器产生的 Score 关联到 trace/session 等对象。这说明接收评价数据与运行评价器可以成为不同接入路径。[Langfuse Scores 数据模型](https://langfuse.com/docs/evaluation/scores/data-model)

## 3. 接收以后如何使用

建议的关联层次为：

```text
业务工作单位 → 一次或多次 Run → 一次或多次模型 Request → Provider Attempts
```

网关内部 fallback 产生多个 Attempt；应用因结果不合格再次请求则产生新的 Request；整项任务重新执行可能产生新的 Run。这些费用都应归入同一业务工作单位，最终成功单位只计一次。一个 Run 服务多个业务对象时，需要单独的分摊规则，不能把其全部费用给每个对象重复计算。

示例：两种方案处理相同难度、相同验收标准的 100 张工单，已完成观察窗口且所有结果均已知。金额均为虚构示例。

| 指标 | 方案 A | 方案 B |
| --- | --- | --- |
| 全部尝试的模型费用 | $10 | $14 |
| 无人工接管且通过验收的工单 | 40 | 80 |
| 每次尝试平均模型费用（此例每张工单一次尝试） | $0.10 | $0.14 |
| 全部模型费用 / 验收通过工单数 | $0.25 | $0.175 |
| 无人工接管验收率 | 40% | 80% |

在这个限定口径下，B 的平均调用支出更高，但每个合格结果所分摊的模型支出更低。这是业务结果回传能支持的决策。分子包含全部失败与重试成本；无法归属或尚未结算的费用需要显式披露。

这张表只能说明模型消费效率。工具、沙箱、人工处理、错误损失等成本尚未包含，不能标成总成本或 ROI。“节约了多少钱”还需要可信的人工/旧系统基线、相同任务难度和归因方法。

时间上还应区分：按费用发生日看支出；按业务任务批次及观察截止时间看成功率。直接用“今天的费用 / 今天收到的成功通知”会把不同任务批次混在一起。

## 4. Halro 当前有哪些有利条件

### 4.1 它拥有实际模型调用的计量位置

Halro 的账本已经关联 Request、Attempt、Project、Key、Provider 和 Deployment，并保留价格快照、用量来源及估算状态。这适合补充业务关联标识，也有利于把重试和 fallback 纳入任务成本。[Ledger Event](/Users/ziy/Code/ClayCosmos/Halro/internal/ledger/event.go:45)

不过 Halro 记录的是其定义范围内的调用费用，部分为估算；它无法仅凭这套账本得知未经过网关的工具开销和最终供应商发票总额。

### 4.2 它已经解决了预算控制中较难的一部分

`Manager.admit` 在 Project 锁下将已结算、已预留和待落账的预留同时纳入检查；持久写入不持有该锁。恢复路径区分未开始与可能已经到达上游的调用，后者按保守规则结算。[准入实现](/Users/ziy/Code/ClayCosmos/Halro/internal/budget/manager.go:276)、[恢复实现](/Users/ziy/Code/ClayCosmos/Halro/internal/budget/manager.go:696)

因此任务预算是对既有机制的扩展，具有架构连续性。多个 Agent 即使在不同进程或机器上运行，只要其相关模型请求汇聚到一个 Halro，就可以在一个预算权威下控制这些请求；这不要求先建设 Halro 多副本集群。

### 4.3 结果展示不要求引入业务执行框架

接收一个有归属、定义版本、结论及证据引用的事件，可以是一项通用功能；存储和查询这些事件不要求 Halro 执行工具、保存完整对话或理解每种业务的验收算法。

如果使用 Halro 的用户希望少部署一个分析系统，内置基础结果统计具有实际使用价值。是否建设复杂分析，应由查询需求和数据量决定，不能仅凭“网关不做业务”否决。

## 5. 当前结构不能直接复用的部分

### 5.1 单维度汇总不能承担任务级精确关联

当前每日 rollup 是单维度边际汇总，每个维度最多保留 200 个独立值，后续值折入 `__other__`。摘要接口明确拒绝同时按 Project 过滤再按其他维度分组，因为汇总没有保存交叉数据。[维度与容量](/Users/ziy/Code/ClayCosmos/Halro/internal/domain/usage_rollup.go:22)、[查询限制](/Users/ziy/Code/ClayCosmos/Halro/internal/app/admin_usage_summary.go:105)

把 Run 直接作为新 rollup 维度会丢失大量任务的精确身份，也不能回答“这个项目、这个任务版本、通过验收的工作花了多少钱”。应新增受控的 Run 明细索引与结果关联读模型；大范围、多维度探索可使用外部分析系统。这是存储模型的具体缺口，不是单进程架构原则上做不到。

### 5.2 日预算和任务全程预算具有不同生命周期

现有 `BalanceKey` 是 Project、账期、时区版本；Request 在准入时固定所属账期。[余额键](/Users/ziy/Code/ClayCosmos/Halro/internal/ledger/event.go:293)、[Request 账期](/Users/ziy/Code/ClayCosmos/Halro/internal/budget/manager.go:50)

一次任务可能跨天、暂停并恢复。新增任务预算必须同时满足当前 Request 的 Project 日预算和任务累计预算；不能每天自动重置任务额度。恢复、取消及过期也不能悄悄退回已经可能花掉的资金。

如果将所有 Run 限定在单一 Project 内，可优先研究在同一 Project 准入决策中检查两个额度，避免一开始引入跨项目多锁和多权威事务。若要跨 Project 或跨 Halro 实例共享预算，那是明显更大的扩展。

### 5.3 费用事实与外部结果事实需要不同的信任规则

费用账本说明 Halro 观察到了哪些调用并如何计量；结果事件说明某个业务方对某个任务作出了什么判断。可信上报者也可能犯错或修订结论，因此“已鉴权”不等于“判断绝对正确”。

建议把外部结果保存为独立、可追踪版本的记录，再与费用读模型关联。结果修订不改写已发生的模型费用，不自动返还预算；结果缺失或上报失败不阻塞正常推理。两者可以在一个二进制中实现，仍然保持权限和故障路径分离。

### 5.4 面向应用的管理权限尚需补齐

当前 Usage 路由使用管理员鉴权，并非供应用持 Gateway Key 自助查询或提交结果的专用接口。[Usage 路由](/Users/ziy/Code/ClayCosmos/Halro/internal/app/runtime.go:1597)

新增能力应区分调用权限、预算创建/调整权限、费用读取权限与结果上报权限。调用方自填 Run ID 可以用于关联，不能自动获得创建新预算的权力；任意换 ID 不应消除已有消费或绕过上级限制。

### 5.5 容量与历史兼容还需要实测

唯一 Run 数量会随业务量持续增长；结果事件还可能迟到和修订。需要限制活跃 Run、关联条数、字段长度及保留期，并处理明细过期后仍需解释报表的情况。费用关联若进入持久化事件，还影响回放、checkpoint、导出和备份契约。

本次只做源码与文档分析，没有执行性能或恢复试验。可以判断设计适配程度，但不能把它变成某个 QPS、并发量或保留天数下的容量保证。

## 6. 分项结论

| 能力 | 适配判断 | 主要收益 | 主要工作量或前提 |
| --- | --- | --- | --- |
| Run 与业务成本归因 | 高，建议优先设计 | 回答具体任务和重试花了多少 | 标识传播、作用域授权、持久关联、明细查询 |
| 单 Project 内的 Run 预算 | 高，值得建设 | 在项目总额度内隔离单个任务的失控消耗 | 双额度原子准入、跨天生命周期、恢复与过期 |
| 外部结果接收、查看与基础统计 | 中高，有合理产品价值 | 连接费用与验收率，减少接入系统数量 | 独立权限、版本化结果、去重、覆盖率和专用读模型 |
| 指定场景的验收器接入 | 中，依赖明确场景 | 自动获得可信度更高的结果信号 | 业务方负责标准，适配器或外部验证器负责执行 |
| 根据结果自动调整实时预算或路由 | 当前证据不足 | 有机会改善单位结果成本 | 稳定样本、评价质量、反馈延迟及误判成本；应先离线评估 |
| 通用评测执行平台 | 当前适配较低 | 全流程评测与实验 | 数据集、执行环境、标注、模型评价费用等新增子系统 |
| 企业级完整 FinOps 平台 | 当前适配较低 | 全口径采购、分摊、预测及经营决策 | 模型以外的大量数据、治理流程与分析能力 |

“适配高”表示值得做进一步设计，不表示只是加一个字段即可上线。完整平台目前优先级较低，是因为核心数据与责任大量位于网关之外、建设投入明显增加；这个判断不否定轻量结果接收和统计。

## 7. 推荐推进方式与停止条件

1. **先验证使用价值。**选择一个真实业务流程，约定工作单位、验收标准和目前要改善的决策。用一个业务周期观察其重试费用、结果覆盖率与人工接管；没有业务样本时，市场需求和收益仍未知。
2. **成本关联与结果回传可独立试点。**已有响应 `X-Request-ID` 与 Usage 的 Request 查询提供初步关联入口，但网络中断可能丢失响应标识，不能据此声称完整归因。可先由可信后台保存关联；生产接入再明确补偿与专用服务权限。[响应标识](/Users/ziy/Code/ClayCosmos/Halro/internal/gatewayapi/handler.go:821)、[Request 过滤](/Users/ziy/Code/ClayCosmos/Halro/internal/app/admin_usage.go:385)
3. **预算需求明确时，单独设计 Run 预算。**先限单 Project、单 Halro 权威；停止语义从拒绝后续模型调用开始，应用处理收尾。若痛点就是 Agent 失控费用，这一步可先于结果分析，不必等验收体系完备。
4. **结果报告按需求选择部署位置。**基础查询可以内置、可选开启；已经有数据仓库或评测系统的用户可只消费导出。无需为简单指标强制新增服务，也无需为复杂分析强行扩张本地查询引擎。
5. **验证再考虑自动反馈。**如果结果覆盖率低、标准持续变化或关联不完整，继续改善测量，不启动“按成功率自动分配预算”。如果可靠性试验显示多额度准入或结果存储拖累调用路径，先修复隔离与恢复问题。

建议的首批验收问题：能否精确关联一次失败重试后的成本与一个最终结果；并发 Agent 是否共享同一任务额度；任务跨天和进程重启后是否保留正确余额；结果重复、迟到或撤回是否改变统计而不改写消费；结果报告不可用时是否保持既有模型调用服务边界。

**总体判断：Halro 适合扩展“有成本归因、任务预算和可选结果关联的调用治理能力”。当前代码提供了良好的记账与准入基础，需要补齐 Run 生命周期、精确查询和应用权限。对完整 FinOps 或评测平台的判断，应在这些具体能力产生真实使用价值之后另行作出。**
