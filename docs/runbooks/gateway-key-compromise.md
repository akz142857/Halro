# Gateway Key 泄露处置 Runbook

一个 `gw_...` Gateway Key 出现在它不该出现的地方 —— 聊天记录、工单、CI 日志、截图、共享文档 —— 之后的处置流程。

这是最可能真实发生的凭据事故：Gateway Key 是唯一会被交到应用开发者手里的凭据，而 Provider Credential 和 Master Key 都不会离开 Halro。

**不要为了「先确认影响面」而推迟撤销。** 撤销是即时且可逆的（重新签发一个新 key 即可），而每推迟一分钟，泄露的 key 就多一分钟可用。先撤销，再调查。

## 1. 语义边界

先读这一节。事故中最容易走错的判断都在这里。

- **Key 只以 SHA-256 存储。** 明文在创建时显示一次，之后 Halro 不再持有它。因此「找回」不存在，唯一的动作是作废并重新签发。
- **撤销是软删除。** `DELETE .../keys/{keyID}` 把记录置为 `Enabled=false` 并写入 `DeletedAt`，记录本身保留为墓碑。控制台里看不到它，但它在数据目录中仍然存在 —— 这是**正常的**，墓碑是审计链的一部分。
- **正常路径下撤销在响应前生效。** 删除请求先提交存储事务，随后重建认证快照（`auth.Refresh`），把带 `DeletedAt` 的 key 从内存映射中剔除，**然后才返回 `204`**。拿到 204 就意味着该 key 的后续请求立即得到 `401 invalid_api_key`。
  **但这两步不在同一个事务里**，因此存在一个必须知道的失败态，见下一条。
- **收到 `503` 时不要判定「撤销失败」。** 删除的三步是「提交存储 → 重建认证快照 → 写审计」，后两步失败都返回 `503`，而**存储提交已经生效且不会回滚**：
  - `{"error":"metadata unavailable"}` —— 墓碑已落库，但**内存快照还持有那把 key，它仍然可用**。Halro 没有周期性刷新，这个窗口只在下一次成功的管理变更或**进程重启**后关闭。见 §2.2 的处置。
  - `{"error":"audit unavailable"}` —— key 已经真正撤销且已从内存剔除，只是**没有留下审计记录**。
  两种情况的方向都是安全的（已撤销，而非未撤销），但都需要收尾动作。**重试删除会得到 `404`**（墓碑对 Admin 读接口不可见），那不是「撤销没生效」的证据。
- **记录数归零不等于撤销过。** 如果某个数据目录的 `gateway_keys` 中一条记录都没有，那说明这个目录被**重建**过（`make reset` 或全新 `init`），而不是有人撤销了 key —— 撤销会留下墓碑。事故复盘时把「零记录」读成「已处置」是个常见误判。
- **撤销只作用于一个数据目录。** Halro 是单实例、单数据目录。任何其他实例、任何早于撤销时间的备份，只要它的数据目录里还有那条记录，泄露的 key 在**那里**依然有效。这是本 Runbook 中唯一无法由一条命令解决的部分，见 §3。

## 2. 立即处置

### 2.0 选择通道

三条路都能止血，按你当前手上有什么选：

| 通道 | 前提 | 效果 | 何时用 |
| --- | --- | --- | --- |
| 控制台「停用」 | 管理员会话 | `Enabled=false`，立即 `401` | **最快**；拿不到 TOTP 时用这条 |
| Admin API `DELETE`（§2.2） | 会话 + 密码 + TOTP | 停用并写入墓碑 | 标准处置 |
| `halro key disable`（§2.5） | 能停机、能登主机 | `Enabled=false`，**不留墓碑** | 控制台与 API 都不可用时的 break-glass |

**先用能立刻执行的那条止血，之后再补齐标准处置。** 控制台的停用只需要 `If-Match`，不需要二次验证，因此它也是被盗会话能做到的事 —— §2.2 的「被盗会话不足以撤销 key」只对**删除**成立，对**停用**不成立。对攻击者而言停用是等效的拒绝服务，这一点在评估事故影响时要算进去。

### 2.1 定位记录

先找到 Project，再列出它的全部 key：

```http
GET /admin/api/v1/projects
GET /admin/api/v1/projects/{projectID}/keys
```

响应只包含元数据，不包含 key 材料。按 `name` 与 `created_at` 定位。

**不要用 `last_used_at` 对时间。** 该字段目前**从未被写入**，在每个响应里都是缺省的，控制台也因此把每把 key 显示成「从未使用」。要判断泄露窗口内的实际行为，用 §3 的审计与 Usage 数据。

### 2.2 撤销

```http
DELETE /admin/api/v1/projects/{projectID}/keys/{keyID}
If-Match: "<revision>"
Content-Type: application/json

{ "current_password": "...", "totp_code": "..." }
```

三道保护都是必需的，不要试图绕开：

1. **`If-Match` 修订号** —— 缺失返回 `428`，不匹配返回 `412`。它保证你撤销的是你刚才看到的那一条，而不是在你阅读期间被改动过的另一个状态。
2. **破坏性操作二次验证** —— **材料放在请求体里**，不是请求头。需要管理员密码（Argon2id）；**账号启用了 MFA 时 `totp_code` 也是必需的**。没有请求体的 DELETE 直接返回 `401 recent_reauth_required`。失败有**每分钟 5 次**的限流，慌乱中连错五次会撞上 60 秒的墙，所以第一次就把密码和验证码准备好。
3. **审计** —— 写入 `gateway_key.delete`，记录管理员身份与目标 key ID。

**收到 `503` 时按 §1 的分支处置：**

- `metadata unavailable` —— 墓碑已落库但内存快照未刷新，**那把 key 仍然可用**。立即执行任意一次会成功的管理变更（例如在控制台停用另一把测试 key），或**重启 Halro**，以强制重建认证快照。然后回到 §2.3 验证。
- `audit unavailable` —— key 已撤销，但审计链里没有这条。**手工记录**该次撤销的时间、执行人与 key ID，并在事故报告中说明审计缺失的原因；不要因为查不到 `gateway_key.delete` 就重做一次撤销。

控制台里对应的是密钥列表中的删除操作，会依次要求确认和重新输入密码（路径：项目 → 目标项目 → 密钥列表）。

### 2.3 验证

三项都要做，不要只做第一项：

1. 用泄露的 key 发一个请求，确认返回 `401 invalid_api_key`。**这一项不能省** —— 它是唯一能证明内存快照确实刷新了的检查，也正是 `metadata unavailable` 分支要靠它兜底的地方；
2. 在审计中确认存在对应的 `gateway_key.delete`（若走的是 §2.5 的 CLI，事件名是 `gateway_key.disable`）；
3. 确认应用侧已经换用新 key —— 否则你会在业务中断中才发现漏了一个消费方。

**关于查审计：目前只能翻页，不能检索。** `GET /admin/api/v1/audit` 只接受 `cursor` 与 `limit` 两个参数，任何 `action=` 之类的过滤都会被拒绝；它按时间倒序返回，所以刚写入的记录在第一页。CLI 侧 `halro audit` 只有 `verify` / `verify-anchor`，那是完整性校验，不是查询工具。事故中不要指望 grep 审计，直接翻第一页。

### 2.4 重新签发

```http
POST /admin/api/v1/projects/{projectID}/keys
Idempotency-Key: <任意唯一串，≤256 字节>
Content-Type: application/json

{ "name": "...", "expires_at": "...", "current_password": "...", "totp_code": "..." }
```

**`Idempotency-Key` 请求头是必需的**，缺失或超长返回 `400 idempotency_key_required`。它让重试落成存储冲突，而不是悄悄多出一把没人知道的活凭据。二次验证材料与 §2.2 相同。

**新 key 只显示一次。** 交付给应用方时不要走泄露发生的那个渠道 —— 让对方准备一个 `chmod 600` 的文件，把 key 写进去，不要粘贴到聊天、工单或任何会被保存的地方。

### 2.5 Break-glass：CLI 停用

控制台与 Admin API 都不可用时：

```bash
halro key disable --key-id <keyID>
```

用之前必须知道三件事：

- **它会取数据目录锁，因此 Halro 必须先停机。** 这是 break-glass 通道，不是更快的通道 —— 单看止血速度，控制台的停用远快于「停机 + 执行 + 启动」。
- **它只置 `Enabled=false`，不写 `DeletedAt`**，因此不留墓碑。事后仍应按 §2.2 补一次标准撤销。
- **它写入的审计事件是 `gateway_key.disable`，不是 `gateway_key.delete`。** §2.3 第 2 步要按这个名字找，否则会误判成「没有审计记录」。

## 3. 影响面评估

撤销完成之后再做这些。

**其他实例。** 逐一确认所有运行中的 Halro 实例。任何数据目录建立时间早于该 key 创建时间的实例，都仍然持有这条记录并会接受它。对每一个都执行 §2。

**备份。** 任何在撤销之前创建的 `.hmbk` 归档都包含这条记录。**从这类备份恢复会让 key 复活**，且恢复过程不会有任何提示 —— 恢复会使管理员会话失效，但**不会对 Gateway Key 做任何等价处理**。要么把这些归档从可恢复集合中移除，要么在恢复流程中加入一步「恢复后立即重新执行 §2」。这一条必须写进你的恢复清单，而不是依赖记忆。

**已发生的用量。** 用审计与 Usage 数据核对该 key 在泄露窗口内的行为：请求量是否异常、成本是否偏离基线。Project 级的 RPM/TPM/预算上限限制了最坏情况 —— 但要注意**这些字段为 0 表示不限制，不是不允许**，所以「配置过」和「有上限」不是一回事，确认时看的是非零值。另外这些上限是与正常消费方**共享**的，泄露的 key 打满上限本身就是一次业务中断。

**同渠道的其他凭据。** 一个 key 出现在聊天记录里，通常意味着那个渠道还有别的东西。检查同一渠道是否还暴露了 Provider Credential、Admin 密码或 Master Key 材料 —— 后两者的处置流程不同，见
[`m11-kms-key-lifecycle.md`](m11-kms-key-lifecycle.md) 与 [`m11-kms-disaster-recovery.md`](m11-kms-disaster-recovery.md)。

## 4. 预防

- **不要为了调试把 key 粘进任何会被保存的地方。** 需要用真实 key 验证时（例如账务写入路径只有真实 Gateway 请求才会产生事件），把它写进 `chmod 600` 的文件，让工具从文件读取。
- **给 key 设置 `expires_at`。** 调试用途的 key 尤其应当设，它把「忘了撤销」的后果限制在一个已知窗口内。该字段在认证期强制生效，过期 key 与被撤销的 key 一样返回 `401 invalid_api_key`。
- **一个消费方一个 key。** 共用 key 会让撤销变成一次业务中断，而中断的代价会促使人推迟撤销 —— 这正是要避免的动机。
- **key 的名字要能在事故中定位它。** 「工作台调试 2026-08-08 10:06:57」是个好名字：它说明了用途和时间。「test」不是 —— 尤其在 `last_used_at` 不可用的情况下，名字是唯一的定位线索。
