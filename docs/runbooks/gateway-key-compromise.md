# Gateway Key 泄露处置 Runbook

一个 `gw_...` Gateway Key 出现在它不该出现的地方 —— 聊天记录、工单、CI 日志、截图、共享文档 —— 之后的处置流程。

这是最可能真实发生的凭据事故：Gateway Key 是唯一会被交到应用开发者手里的凭据，而 Provider Credential 和 Master Key 都不会离开 Halro。

**不要为了「先确认影响面」而推迟撤销。** 撤销是即时且可逆的（重新签发一个新 key 即可），而每推迟一分钟，泄露的 key 就多一分钟可用。先撤销，再调查。

## 1. 语义边界

先读这一节。事故中最容易走错的判断都在这里。

- **Key 只以 SHA-256 存储。** 明文在创建时显示一次，之后 Halro 不再持有它。因此「找回」不存在，唯一的动作是作废并重新签发。
- **撤销是软删除。** `DELETE .../keys/{keyID}` 把记录置为 `Enabled=false` 并写入 `DeletedAt`,记录本身保留为墓碑。控制台里看不到它，但它在数据目录中仍然存在 —— 这是**正常的**,墓碑是审计链的一部分。
- **撤销即时生效。** 删除请求在同一个事务内重建认证快照（`auth.Refresh`），把带 `DeletedAt` 的 key 从内存映射中剔除，**然后才返回 `204`**。不存在「已删除但还能用一会儿」的窗口。返回 204 之后，该 key 的请求立即得到 `401 invalid_api_key`。
- **记录数归零不等于撤销过。** 如果某个数据目录的 `gateway_keys` 中一条记录都没有，那说明这个目录被**重建**过（`make reset` 或全新 `init`），而不是有人撤销了 key —— 撤销会留下墓碑。事故复盘时把「零记录」读成「已处置」是个常见误判。
- **撤销只作用于一个数据目录。** Halro 是单实例、单数据目录。任何其他实例、任何早于撤销时间的备份，只要它的数据目录里还有那条记录，泄露的 key 在**那里**依然有效。这是本 Runbook 中唯一无法由一条命令解决的部分，见 §3。

## 2. 立即处置

### 2.1 定位记录

Gateway Key 属于 Project,列出该 Project 的全部 key:

```http
GET /admin/api/v1/projects/{projectID}/keys
```

响应只包含元数据，不包含 key 材料。按 `name` 定位；若名称不足以区分，用 `created_at` 与 `last_used_at` 对照泄露发生的时间。

### 2.2 撤销

```http
DELETE /admin/api/v1/projects/{projectID}/keys/{keyID}
If-Match: "<revision>"
```

三道保护都是必需的，不要试图绕开：

1. **`If-Match` 修订号** —— 缺失返回 `428`。它保证你撤销的是你刚才看到的那一条，而不是在你阅读期间被改动过的另一个状态。
2. **破坏性操作二次验证** —— 需要重新校验管理员密码（Argon2id）。被盗的会话本身不足以撤销 key。
3. **审计** —— 写入 `gateway_key.delete`,记录管理员身份与目标 key ID。审计写入失败会导致整个请求失败，不会出现「撤销了但没有记录」。

控制台里对应的是密钥列表中的删除操作，会依次要求确认和重新输入密码。

### 2.3 验证

三项都要做，不要只做第一项：

1. 用泄露的 key 发一个请求，确认返回 `401 invalid_api_key`;
2. 在审计中确认存在对应的 `gateway_key.delete`;
3. 确认应用侧已经换用新 key —— 否则你会在业务中断中才发现漏了一个消费方。

### 2.4 重新签发

```http
POST /admin/api/v1/projects/{projectID}/keys
```

**新 key 只显示一次。** 交付给应用方时不要走泄露发生的那个渠道 —— 让对方准备一个 `chmod 600` 的文件，把 key 写进去，不要粘贴到聊天、工单或任何会被保存的地方。

## 3. 影响面评估

撤销完成之后再做这些。

**其他实例。** 逐一确认所有运行中的 Halro 实例。任何数据目录建立时间早于该 key 创建时间的实例，都仍然持有这条记录并会接受它。对每一个都执行 §2。

**备份。** 任何在撤销之前创建的 `.hmbk` 归档都包含这条记录。**从这类备份恢复会让 key 复活**,且恢复过程不会有任何提示。要么把这些归档从可恢复集合中移除，要么在恢复流程中加入一步「恢复后立即重新执行 §2」。这一条必须写进你的恢复清单，而不是依赖记忆。

**已发生的用量。** 用审计与 Usage 数据核对该 key 在泄露窗口内的行为：请求量是否异常、是否出现新的来源 IP 段、成本是否偏离基线。Project 级的 RPM/TPM/预算上限限制了最坏情况 —— 确认这些上限当时确实是配置好的，而不是事后才补的。

**同渠道的其他凭据。** 一个 key 出现在聊天记录里，通常意味着那个渠道还有别的东西。检查同一渠道是否还暴露了 Provider Credential、Admin 密码或 Master Key 材料 —— 后两者的处置流程不同，见
[`m11-kms-key-lifecycle.md`](m11-kms-key-lifecycle.md) 与 [`m11-kms-disaster-recovery.md`](m11-kms-disaster-recovery.md)。

## 4. 预防

- **不要为了调试把 key 粘进任何会被保存的地方。** 需要用真实 key 验证时（例如账务写入路径只有真实 Gateway 请求才会产生事件），把它写进 `chmod 600` 的文件，让工具从文件读取。
- **给 key 设置 `expires_at`。** 调试用途的 key 尤其应当设，它把「忘了撤销」的后果限制在一个已知窗口内。
- **一个消费方一个 key。** 共用 key 会让撤销变成一次业务中断，而中断的代价会促使人推迟撤销 —— 这正是要避免的动机。
- **key 的名字要能在事故中定位它。** 「工作台调试 2026-08-08 10:06:57」是个好名字：它说明了用途和时间。「test」不是。
