## 1. 要回答的运维问题

1. **客户端现在能否完成关键写？** Primary 存在、客户端入口可达、启动裁决完成、复制确认仍可用，必须分别显示。`/health/ready` 成功不代表需要副本确认的写一定成功；全部 Replica 不可达时，Primary 仍可 ready，但这类写会返回 `503 replication_unavailable`。
2. **集群是否仍保持安全边界？** 成员是否属于同一 cluster/incarnation、term 与 promised term 是否相容、是否出现多个自称 Primary、是否有身份或 schema 不兼容。任何不一致都不能被“其余节点在线”掩盖。
3. **每个节点发生了什么？** 存活、ready、角色、维护、认证会话、复制状态、持久/确认/应用水位、元数据投影、最近观测时间及数据来源。
4. **复制卡在哪里？** 区分 Primary 本地 durable→confirmed、Replica 接收 durable、Replica confirmed→applied，以及对端会话中断；区分“没有新写所以曲线平坦”和“有新写但追不上”。
5. **故障时哪个节点可能成为候选？** 给出待核查条件和缺失证据，绝不自动标记“可直接提升”。合法提升还要新 term 的 durable promise、精确 `(last_frame_term, index)` 前缀比较、旧 Primary 的外部 fencing 与命令重新校验；仅凭图表无法完成这些步骤。

## 3. 页面信息架构

主入口是独立监控故障域中的受控 HA 健康页；现有「集群状态」页面继续显示本地事实，可在部署提供受控入口 URL 后增加链接。页面不依赖 Primary Admin 的 HTML/session 服务；Primary 宕机、启动等待裁决时仍须可访问。监控入口的身份验证、授权、TLS、审计、部署与故障演练是 P0 验收条件；不能直接公开 Prometheus UI/API。页首固定显示环境、cluster ID、incarnation、观测时间、采集覆盖 `已获取/配置成员数`、数据新鲜度和“当前状态仅供观察”提示。所有状态卡点击后定位到能解释它的数据；对应分区提供受控 HA 运维手册入口。独立服务可选配置经认证审计的 HTTPS 文档根地址；未配置时只显示仓库路径，不假定目标环境可直达文档。

| 区域 | 视觉组件 | 主要信息与交互 |
|---|---|---|
| 集群总览 | 四张状态卡 + 简化拓扑 | 客户端入口、关键写确认能力、安全一致性、追平节点观察数；拓扑显示唯一 Primary → 各 Replica 的认证连接与最近观测，不把连线等同于同步成功。2 节点常驻说明“故障提升后仍需另一成员才能确认关键写”。 |
| 节点健康 | 可排序节点表、节点详情抽屉 | 角色/term/promised term、逐节点 HTTP live/ready、维护、startup ready、身份一致性、三个本地 index、投影水位、peer 会话、最近抓取成功时间与失败原因。未配置直接探针、离线或状态不可读显示 `未知`，不显示 0；节点 ready 不代表客户端 Service 可达。 |
| 数据同步 | 三条同轴 index 阶梯线 + 节点差值表 | 每节点 durable/confirmed/applied 历史，Primary durable−confirmed、每个 Replica 的 durable−applied 与“相对 Primary confirmed 的数值差”；图上标 term/incarnation 变化、维护、断连、提升事件。跨节点 index 差只是位置比较，不证明前缀相同。 |
| 请求影响 | 五分钟结果分布与事件列表 | 客户端探针可用性、服务端写路由 HTTP 2xx/4xx、`not_primary`、其他 503、超时、其他 5xx、取消和写出失败。503 不自动归因为复制阻断。每个预期成员必须同时具备八类新鲜当前序列和八类可计算的五分钟增量，才汇总分布；缺报时标未观测。重试会重复计数，流式 2xx 可能随后失败，不能当作客户端完整成功；最终客户端可见结果仍需端到端来源。 |
| 事件和诊断 | 告警时间线、证据抽屉 | 告警开始/恢复时间、影响、触发条件、原始样本时间、关联 runbook；提供逐节点状态快照导出，供人工决策留证。当前实现的抽屉只能提供活动告警的求值结果、当前加载规则及最近成员样本，各来源时间可能不同；历史原始触发样本的还原仍需目标环境验证和补充。 |

默认时间窗 1 小时，可切 15 分钟、6 小时、24 小时。图表在 term 或 incarnation 改变处断线并注释，不跨任期计算速率或差值；缺失样本画空洞，不补零、不前向填充。提供“当前 / 历史”切换；历史不替代实时状态。

### 3.1 四个顶层状态的判定

| 卡片 | 健康 | 降级 / 危险 / 未知 |
|---|---|---|
| 客户端入口 | 从**客户端 Service**执行有界无计费根路径探针，最终到达所配置 cluster ID 的 Primary；实际写入仍按 SDK 契约重试 | 根路径命中 Replica 时预期返回带身份的 200，探针继续尝试；实际写请求单次遇到 `503 not_primary` 是默认 Service 的正常路由结果，不单独作故障。只采到同集群 Replica 或探针传输失败为未知，不能由随机路由推断无 Primary；路由到其他 cluster ID、持续返回非预期错误或成员事实证明无 Primary 为危险。缺失集群标识不能显示健康。不得调用真实 Provider。 |
| 关键写确认能力 | 唯一 Primary 完成启动裁决，且稳定任期内近期有需确认 Ledger/metadata 屏障成功；这证明内部必需 ACK 路径成功，不等于最终客户端响应成功 | `replication_unavailable=1` 表示已知阻断；值为 0 只表示未发现内部阻断，**不能推出确认能力健康**。无必需确认证据时为未知，不能用连接数或普通 confirmed index 增长代替。 |
| 安全一致性 | 全部新鲜的成员身份一致、恰一个 Primary、无更高 promised term 冲突、无不兼容信号 | 多 Primary、incarnation 冲突为危险并立即升级；成员缺报则未知，不宣称安全。term 差异可发生在正常切换期间，短暂标“切换中”，超过窗口或伴随冲突才告警。 |
| 追平节点观察 | 至少一个 Replica 新鲜、无维护/不兼容、本地三个水位相等，且其 applied index 数值与最近观测的 Primary confirmed index 相等 | 0 个为降级；仅部分采集时为未知。若同任期且采样相近的 Replica 数值超过 Primary confirmed，视为采样或状态待核查，安全卡未知，即使另一节点恰好相等也不显示绿色综合状态。显示“观察到追平，前缀未验证”，**不是提升资格判定**。 |

总状态优先级：安全冲突或无客户端 Primary 为 `危险`；已知关键写不可用、没有观察到追平节点为 `降级`；必需观测缺失或确认能力缺少正向证据为 `未知`，不得显示绿灯；只有四项都健康才显示 `健康`。计划维护可抑制预期的节点离线告警，但不抑制多 Primary、身份冲突或关键写不可用。

关键写确认卡定位到独立依据区，显示稳定任期查询的状态、匹配节点、近五分钟 Prometheus 估算增量和样本时间。没有新鲜样本、查询失败或出现多个候选序列都保持未知；普通 index 曲线不能代替此证据。即便该增量为正，仍只证明内部屏障返回而非客户端完整收到响应。

## 4. 采集与计算契约

### 4.1 拓扑

P0 沿用 Prometheus 逐成员抓取 `/metrics`，另从客户端 Service 做无计费、具有正常 Replica 重试语义的探针。独立的受控监控入口查询 Prometheus 的受限只读查询通道，不能依赖 Primary 存活，也不能给浏览器暴露 scrape token 或开放 Prometheus 管理 API。P0 仅展示 Metrics 真能提供的成员身份和水位；缺少状态采集时投影细节标未知。P1 逐成员状态采集已使用 Metrics 监听器上的机器只读 `/ha/status`，以独立版本化 bearer 与客户端 mTLS 认证，并提供轮换、撤销、限流和到达应用后的读取审计；目标环境仍须验证 Secret 管理、证书生命周期、网络限制和握手前拒绝日志。人工 `/admin/api/v1/cluster/status` 的 `requireAdmin` Cookie 登录（含可能的 TOTP）不作为采集凭据，不得把人工管理员口令或 TOTP 秘密存入采集器。

机器状态响应中的 `peers[]` 必须恰好列出受控成员清单中的其他节点；缺失、重复、自指或清单外 Peer 会使该节点状态证据无效并阻止绿色综合状态。此检查只验证拓扑身份，不以连接状态推断对端同步或提升资格。

同一成员的新鲜 Metrics 与机器状态若在 incarnation、角色、term、promised term、startup ready 或复制阻断状态上不一致，标记 `metrics_disagreement`，安全卡及总览不得为绿色。两种采集并非原子快照；切换瞬间的差异应标为待核查，而不能仅凭该差异断言出现了双 Primary 或前缀冲突。持续差异需要核对采样时间、目标身份和实际成员状态。

逐节点 HTTP live/ready 可在机器状态清单中成对配置固定 HTTPS URL，要求与该成员 `/ha/status` 使用同一主机名，可使用不同端口。采集器用受信 CA 和客户端证书直连成员网关，不向这两个健康路径发送机器 bearer token，也不跟随重定向。200 表示该路径本次成功，503 表示明确不健康，其他状态、超时和传输失败是探针未知；两条路径的结果与认证状态采集结果分别保留。Primary 明确不 ready 会使综合状态降级，探针未知阻止绿色综合状态。Replica ready 受本地追平和接收器状态影响，不代替集群候选资格，也不把节点 ready 当作客户端 Service 或关键写成功。

成员列表来自受控部署清单；发现的陌生节点和配置节点缺报都作为异常。采样记录必须保存 `environment`、`cluster_id`、`incarnation`、`node_id`、`role`、`term`、抓取时间、数据源和成功/错误状态。Prometheus 的 `environment/cluster/instance` 由采集侧加标签，成员查询还固定限定 `job="halro",expected_target="true"`；其他 job 即使带相同环境和集群标签也不能补足 HA 覆盖。应用另以低基数 `halro_cluster_member_info{cluster_id,node_id}` 回报自身配置，监控页须核对 `cluster_id=cluster`、`node_id=instance`，错标或缺失都不能显示绿色。清单外 instance 若有近期成功抓取或成员指标，安全卡判危险；仅有失败、陈旧或无效样本时判未知并保留名称与时间，均不显示绿色。应用指标不放地址、密钥、凭据、Project、请求 ID 或对象字节。metrics 非 loopback 暴露遵循现有 credential file + 专用 mTLS 契约；Admin 状态采集使用受限只读凭据和最小网络访问。

成员指标解析对布尔 gauge 只接受 0/1，对 term 与 index 只接受可精确表示的非负整数；样本格式无效、同一字段矛盾、Peer 不在受控清单或 Peer 指向自身均标识为异常，不能由同轮其他正常序列覆盖为绿色。认证 Peer 会话只参与连接观察，不构成已追平或可提升证据。

建议 10–15 秒采样一次、30 秒内判为新鲜；**第一次失败即显示采集异常，任何必需成员有失败就不显示绿色总状态**。仓库中的 `HalroTargetDown` 在静态配置目标 `up=0` 持续 2 分钟后触发，成员仍可被抓取但缺少身份或角色指标时另由对应的 1 分钟规则告警；超过 30 秒的页面观测转未知。目标环境可按故障预算校准规则持续时间，但不得把抓取失败解释为 index 0、角色消失或成员健康。历史观测标记“最后更新于…”，超过新鲜度阈值灰化受影响卡片。

### 4.2 数据定义

| 信号 | 来源与公式 | 用途 / 限制 |
|---|---|---|
| 本地持久/确认/应用 index | 每成员认证 status 或 `halro_replication_index{kind=…}` | 同一成员须满足 `durable ≥ confirmed ≥ applied`；任意一对已观测相邻水位逆序即为危险，不能因第三个水位缺报而掩盖。index 是帧序号，不是字节或秒。 |
| Primary 确认缺口 | Primary `durable − confirmed`，现有 `halro_replication_confirmation_lag` | 反映本地已持久但尚未满足确认规则的帧；不能直接说会丢多少笔请求。 |
| Replica 应用积压 | Replica `durable − applied`，现有 `halro_replication_apply_backlog_frames` | 区分接收后应用慢；另展示 `confirmed − applied`，其含义是该**成员本地**确认前缀的应用缺口。 |
| 相对 Primary 的 index 数值差 | 在同 cluster/incarnation/term、采样足够接近时，`Primary.confirmed − Replica.applied`（保留正负号） | 仅观察位置差；异任期或缺报时不计算。负值需要人工调查，不截成 0。当前接口没有跨节点 ordering head，数值相等不证明同一前缀，更不能单凭此判定可提升。 |
| peer 连接 | 成员 status `peers[].connected` 或 `halro_replication_peer_connected{peer}` | 仅代表已认证数据会话，不能证明对端 durable/applied、投影或服务可用。 |
| 维护与不兼容 | `halro_cluster_maintenance`、`halro_replication_member_incompatible{reason}` | 维护是预期状态而非在线候选；不兼容需按 schema/key/SPKI 分类诊断。当前不兼容 gauge 表示进程启动以来见过事件，不等同于当前连接仍不兼容。 |
| 客户端可用性 | 独立 Service 探针 + 角色核对 | 单独计算，不由 `/health/ready` 推断；应覆盖 LB/endpoints 翻转。 |

P0 就要整理现有 HA 指标的指标契约与 reference，并迁移现有 Prometheus HA 告警及其 rule tests，使监控页和告警共用同一判定定义。P1 增加有界枚举的角色/复制阶段状态迁移事件、需确认写的最终客户端结果计数、ACK/fsync/apply 时延直方图、最近成功确认时间，以及认证的 `(last_frame_term, ordering head)` 摘要供诊断。新增指标先冻结命名、HELP 和标签，再做兼容迁移。已实现的内部必需确认等待计数只覆盖到屏障返回，不能推出最终客户端成功、超时或拒绝。**不**以“现在－进程启动时间”生成 lag seconds，也不以固定平均帧大小生成 lag bytes；要提供这些量，先补准确采样和定义。播种离线期间由作业/操作记录事件，不能要求已停进程导出 seed duration。

最终客户端结果需要调用方在完整响应消费后记录；入口层只有在负责重试且收到调用方应用层完成回执时才能提供同等证据，并按一次逻辑操作而非每次重试归类。固定结果枚举为成功、超时、拒绝、传输失败、取消和流式响应未完整结束；Prometheus 只允许环境、区域、集群与固定操作类别等低基数标签，不能放请求 ID、密钥、模型、地址或原始错误。来源必须在 Primary 宕机时仍可观测，并在目标环境按真实 SDK 重试、幂等与流终止语义验证。当前仓库只有服务端 HTTP 终态和内部屏障计数，**没有**上述客户端最终来源；完整接入条件见[部署契约](../observability/ha-health-service.md#client-final-result-boundary)，因此页面不得给出客户端完整成功率。

当前健康页已从 Prometheus 角色、term、incarnation、复制阶段历史样本生成最多 200 条**采样变化记录**。它只比较同一节点相隔不超过 45 秒的相邻样本，显示变化前一次和变化后首次的观测时刻；采样间短暂变化可能漏掉，因此不能把这张表称为精确状态迁移事件或 Audit 记录。机器状态入口另返回本进程 `StatePublisher` 在认证状态文件成功发布后产生的角色/term/promise **真实迁移事件**，以及 Primary coordinator `replicating`/`unavailable` 的真实边界事件。Replica 另记录接收持久化故障与应用失败/重试恢复导致的 `ready`/`blocked` 边界；固定原因不含任意错误文本，目标 index 是尝试值而非持久水位，取消操作不会被记成失败。三类事件各有进程内递增序号、发布时间与最近 128 条保留；Replica 阶段无事件不能证明持续接收或已追平。可选的独立监控事件文件每 15 秒采集固定成员，原子落盘最近 1000 条记录，在健康服务重启后保留已采到的事件，并显式记录首次观测、采集失败、成员事件源变化、incarnation 变化、环淘汰及序号倒退缺口。页面与证据导出单列此来源和保留淘汰数；配置后文件写入失败、采集陈旧或成员状态部分缺失均使综合状态不能为绿色。成员在两次采集间崩溃或重启、事件环先行淘汰时仍无法补齐所有事件，因此不是完整持久 Audit；若要求全链，仍需在不阻断 HA 状态发布的前提下提供更强的持久来源。

现有 `cluster.promote` Audit 帧也不能填平这个缺口：离线提升先将新 term 发布到 `state.json`，随后才追加 Audit；两步之间崩溃时，新状态可能已持久而事件尚未落盘。在线更高任期 Promise 同样先经 `StatePublisher` 持久发布，当前真实迁移事件只写入内存环。完整跨重启链需要事件与状态的可恢复持久化协议；[持久迁移证据契约](../contracts/ha-transition-durability.md)已规定写前记录、状态对账、旧版本迁移、保留和故障注入门禁。v3 状态、成员写前日志、认证分页与独立追赶已实现，成员与采集端均已追加分段并保留旧段，但尚无归档交接及目标环境故障与容量验收。该协议会给 Promise/提升路径增加一次持久写入，须量测延迟和磁盘故障下的可用性；不能把现有 Audit、内存环或 15 秒轮询文件任一个单独宣称为完整来源。

历史查询另纳入维护与逐 Peer 认证会话的固定 Prometheus 序列；只在同一节点相邻且不超过 45 秒的有效样本之间产生变化记录。同一时刻重复 term 序列值不同、枚举 gauge 同一标签的 0/1 互相矛盾，或字段出现非法值时，不生成该字段事件；清单外 Peer 被忽略。水位图最多标出最近 80 组首次观测位置；角色从 Replica 变为 Primary 只作为**采样提升标记**，并不证明提升程序合法。页面提供“当前 / 历史”切换，实时状态卡始终保留。

客户端最终结果的拟议外部指标、互斥结果语义、观测者清单、缺报门限和目标环境演练已另列为[客户端最终结果集成契约](../contracts/ha-client-final-result.md)。该契约尚无生产端实现；仓库已提供清单门禁的只读页面消费端，未配置清单时保持“未接入”，配置后仍须在完整来源、窗口覆盖与目标环境验收证明下才显示结果分布。服务端 HTTP 结果及内部屏障仍单独显示。

### 4.3 P1 机器只读采集入口（仓库已实现，待目标环境验收）

Admin 状态接口经人工 Cookie session 和角色/MFA 守卫。仓库新增逐成员 Metrics 监听器 `GET /ha/status`，复用该接口的安全字段响应，但使用 `metrics.ha_status.credential_file` 中独立的版本化 bearer 凭据，并要求经过验证的客户端 mTLS 证书。启用条件是 HA 模式、Metrics mTLS 和认证均开启。持有 Metrics token 不得读取 HA 状态，持有 HA 状态 token 不得访问 `/metrics` 或 Admin 变更接口。每次到达应用的读取记录证书 SPKI 指纹、目标节点、结果与时间，不记录 token；TLS 握手前拒绝的请求须由前置 TLS/网络日志审计。`halro ha-status rotate|revoke|list|verify-audit` 承接有审计的重叠轮换与永久撤销，凭据文件须按 Secret 管理。接口用并发上限保护且不缓存；具体部署见[独立健康服务契约](../observability/ha-health-service.md)。

采集器通过受控 JSON 成员清单逐节点请求，不走随机客户端 Service；限定固定 HTTPS 路径、禁止重定向、4 秒超时和最多三个成员并发，逐次重读 token 与客户端证书，拒绝响应中的 cluster/node 身份不匹配。认证失败、证书失效、成员离线、超时、响应格式变化都按该节点 `未知` 处理，并保留错误类别及采集时间；已启用状态采集而失败时综合状态不能显示绿色。新增入口默认只暴露人工状态接口已经公开的安全字段。显式启用 `metrics.ha_status.include_prefix_digest` 后，机器接口另返回**状态文件当前 durable index 对应的认证 ordering 记录**之 `last_frame_term` 和 `SHA-256(ordering head MAC)`，不返回原始 MAC、密钥或地址；同一份状态与 ordering 记录不一致时拒绝提供该证据。采集清单可逐节点要求前缀证据；同 cluster/incarnation/index 的摘要冲突使安全卡与总状态为危险，缺失使总状态未知。摘要相等仍不能授权提升。目标环境须验证轮换、撤销、TLS 失效和 Primary 停机时的持续采集。

## 5. 告警与处置

告警由独立监控抓取全部成员；应用内 webhook 仍只由 Primary 发送。规则必须限定 environment/cluster，并按 cluster/incarnation/term 去重，防止旧 incarnation 的残留序列污染当前集群。阈值在生产验收前用正常写峰值、网络抖动和 72 小时 soak 校准；下面的时长只是初始建议。

| 告警 | 初始触发 | 级别与操作 |
|---|---|---|
| 无 Primary / 客户端入口失败 | 仓库 `HalroNoPrimary` 在全部预期目标和角色观测完整且无 Primary 持续 2 分钟后触发。页面的客户端 Service 探针单轮限时 4 秒并重试 Replica；其结果只进入页面，不生成 Prometheus 告警。独立 `halro-deadman` 新增可选 `ha_client_root` 模式，可在监控故障域之外持续探测同一客户端 Service，并以持久 down/up 状态送到独立接收者；目标环境仍须配置、演练送达与恢复。目标或角色缺报时，页面保持未知，由目标/身份采集告警负责暴露缺口 | 紧急；核对抓取完整性、Service endpoints、外部 fencing，按 [HA 运维手册](../runbooks/ha-operations.md#unplanned-manual-promotion) 处理。 |
| 多 Primary / 身份冲突 | 同 incarnation 两个成员自称 Primary；或同 cluster 的在线成员 incarnation 不同 | 紧急；先隔离流量与核验 Audit/节点来源，不由 UI 选择胜者。 |
| 复制内部阻断 / 确认能力未知 | Primary `halro_replication_unavailable=1` 连续 2 次为已知阻断；无近期确认结果为未知，另以独立信号告警 | 高；查 peer、ACK、存储与 term。`unavailable=0` 不可作为告警恢复和确认能力健康的唯一证据。无副作用关键写探针须先有正确实现才启用。 |
| Replica 应用停滞 / 积压风险 | 分别按同任期的滑窗入流速率、Replica applied 速率及积压绝对量/增长率判定；无新写时不推断停滞 | 中/高；区分“稳定非零积压”“apply 停止”“持续追不上”，不单凭积压告警称节点失去提升资格。阈值由目标环境定。 |
| 节点不可观测 / 维护超时 | 静态配置目标 `up=0` 持续 2 分钟触发 `HalroTargetDown`；页面在本轮缺报时即转未知。维护超出批准窗口的告警需要目标环境的维护计划来源，仓库尚未提供批准窗口指标或规则 | 中；首先检查采集链路，再看进程、网络、PVC。未知不等于节点故障。 |
| 成员 HA 指标缺失 | `HalroMemberHASignalMissing` 要求维护、term、promised term、durable/confirmed/applied 三类索引、启动裁决、复制阻断、三种不兼容原因及配置 Peer 指标的原始采样时间与本轮成功 `up` 一致；三类索引各恰好一条。同轮不完整持续 1 分钟后触发，不受即时查询旧样本的回看窗口推迟。页面首次缺报即判未知并在节点详情列出缺项 | 中；对照原始 `/metrics`、目标清单和 relabeling 修复。Peer 数量相等仍需核对具体名称。 |
| 成员重复采集来源 | `HalroMemberDuplicateScrapeSource` 在同一环境、区域、集群、`instance` 有两条以上预期 `up` 序列时立即触发；页面按逻辑指标唯一性标来源冲突，安全/总览不绿。HA 告警先按成员聚合同轮 `up` 原始时间，比较类规则排除重复来源；稳定任期要求五分钟内 term、incarnation、`up` 各只有一个来源，避免双份原始序列使规则求值出错或误报双 Primary | 紧急；冻结两套完整目标标签与原始样本时间，修正清单或 relabeling。分别核对页面 45 秒窗口、告警回看期和全部规则健康，不能把双份抓取直接解释成双 Primary。 |
| 成员不兼容 / 启动等待裁决 | 不兼容信号新出现；startup ready 长时间为 0 或角色为 `awaiting_decision` | 高；按架构 §8.2/§15 核对证书、schema、key 与更高 term，人工裁决。 |
| 水位倒退 / 本地顺序违反 | 同 incarnation/term 本地 index 回退，或 `durable < confirmed` / `confirmed < applied` | 紧急；保存原始状态和盘证据，停止依赖该成员，不自动修正。合法新 incarnation 切换另起序列。 |

状态页展示告警的**观测证据**：哪些节点、抓取时刻、原值、计算公式、连续时长、对应 runbook。当前告警抽屉提供活动告警求值向量、加载规则和最近成员样本；它们并非同一时刻的触发原始样本，连续时长也只能取规则 `for` 与活动告警开始时间，不能还原通知或恢复历史。告警规则与卡片应共享判定依据，目标环境仍须核对规则投递与页面状态的一致性。维护静默由目标环境的告警系统配置并审计到期时间，当前健康页没有静默控制；安全冲突即使静默也不允许显示绿色。

Runbook 入口增量验证：独立服务新增可选 `-runbook-base-url`，只接受无凭据、查询与片段的 HTTPS 文档根地址；页面各诊断分区链接到 HA 运维手册，当前告警只把固定 operations runbook 路径及受限片段转成链接，其余注解保留文本。未配置文档地址时显示仓库路径，不生成外部链接。Go URL/渲染测试、页面交互测试、脚本语法、`go vet` 与独立健康服务全包 `-race` 通过；目标环境仍需核查受控文档路由、认证审计和实际锚点可达。

告警证据抽屉增量验证：点击当前告警后，页面展示 Prometheus 活动告警的求值向量值、开始时间、影响节点，按需读取当前加载的 `halro-alerts` 规则表达式、`for` 持续条件、规则健康及最近求值时间，并列出最近成员观测值与各自采样时间。仅接受固定规则组中唯一匹配的规则；缺失、重名、格式异常或规则接口失败均明示证据不可用。Go 路由与范围校验、页面交互测试覆盖成功与缺失；抽屉明确这些来源不是同一时刻的原始样本，不声称还原触发瞬间或 Alertmanager 通知。目标环境仍须核查实际 Prometheus 版本和历史原始样本关联。

缺报与陈旧判定修订：安全卡只用新鲜成员观测判定当前冲突；某成员角色指标缺报时保持未知，而非把零个已观察 Primary 误判为已证实无 Primary。新鲜成员的水位逆序仍在其他成员缺报时立即判为危险。`HalroNoPrimary` 告警要求预期 `up` 目标均成功且**同一 instance** 恰有一个角色观测；目标离线由 `HalroTargetDown` 报告，成功抓取但缺角色由新增 `HalroMemberRoleMissing` 报告，同一成员角色重复由新增 `HalroMemberRoleAmbiguous` 立即报告。评估器定向测试及 promtool 规则夹具覆盖完整无 Primary、缺角色、重复角色、清单外角色不能补足预期成员、目标离线及缺角色恢复场景；目标环境仍须检查真实 scrape 的 target 清单和时间戳语义。

清单外证据分级增量验证：独立查询只接受预期 Halro scrape job 的成员指标和 `up`；清单外 instance 另携带 `observed` 与样本时间。近期成功抓取或成员指标使安全卡危险；只有失败、陈旧或格式异常样本时安全卡未知，页面列出名称及证据状态；两者均不能显示绿色。评估器、查询选择器、清单外分类及页面交互定向测试覆盖上述情况。目标环境仍须验证真实 Prometheus relabeling 确实保留固定 job/expected_target 标签，且 30 秒新鲜度契约与抓取间隔一致。

HA 规则来源隔离增量验证：`halro-alerts` 中各项 HA 成员指标和 `halro:ha_epoch_stable:bool` 的原始输入统一限定 `job="halro",expected_target="true"`；启动裁决与复制阻断关联使用环境、区域、集群和 instance，避免跨集群同名节点串联。Promtool 夹具补齐真实 scrape 标签，并证明其他 job 的 Primary、身份、角色、term/incarnation 不能抑制缺失告警或提供稳定任期。目标环境仍须验证所有预期成员确实在该 job 下抓取，规则重载成功且旧规则实例退出。

配置与门禁回填：方案已改用仓库实际实现的机器专用 `/ha/status`，并把客户端入口告警、维护超时、静默和历史触发样本中尚需目标环境来源的部分明确标出。新增配置已写入中英文完整参考和首次运行模板；HA 状态认证、并发限制与拒绝计数归入一个 Runtime 子结构，服务端写路由结果计数独立保留。首次全仓 `go test -count=1 ./...` 仅 `internal/app` 的配置参考和 Runtime 宽度门禁失败；修订后 `internal/app` 全包 `-count=1`、`internal/config`、`cmd/halro`、`cmd/halro-ha-health` 和受影响的 HA 状态 `-race` 定向测试均通过，其他 Go 包在首次全仓运行中通过。前端 typecheck、48 个测试文件的 691 项测试、生产构建与嵌入 bundle 漂移检查通过；`go vet ./...`、受影响包修订后的 `go vet`、观测配置及 promtool rule tests、`git diff --check` 通过。这是仓库验证，不代替真实 Service、成员 mTLS、告警投递与 G0–G7 验收。

历史证据抗矛盾修订：同一节点、同一采样时刻的 term 重复序列若数值不同，或角色、incarnation、复制阶段的同标签 0/1 序列矛盾，采样事件不再采用最后读取值制造状态变化；非法 term、枚举 gauge、维护值及已配置 Peer 的连接值也使对应字段事件失效。定向用例验证 term 序列顺序不同及角色重复值冲突均不能产生假事件，后续有效相邻 term 样本仍可生成真实采样变化。`cmd/halro-ha-health` 全包 `-count=1`、`go vet` 与 `git diff --check` 通过；这仍是采样变化证据，不能还原采样间的短暂状态。

三节点前缀冲突标注修订：同一 cluster/incarnation/index 上只要一个认证前缀摘要或 `last_frame_term` 与其他成员不同，所有参与该位置比较的成员状态都标 `prefix_conflict`，而不是仅标第一对冲突节点。三成员 A/B/A 回归用例验证第三个节点也显示冲突，不同 index 仍不比较；独立健康服务全包 `-count=1`、`go vet` 与 `git diff --check` 通过。此标注是同位置矛盾诊断，不选择正确前缀，也不授权提升。

机器状态 Peer 清单校验：独立服务从固定成员清单为每个 `/ha/status` 采集器生成预期 Peer 集合；响应缺失、重复、自指或出现清单外 Peer 时返回 `peer_inventory`，该节点机器状态证据不可用并阻止绿色综合状态。定向测试覆盖三成员有效集合及四类异常；独立健康服务全包 `-race -count=1`、`go vet` 和格式检查通过。真实成员配置与部署清单一致性仍须在目标环境检查。

跨来源状态核对：当同一节点的新鲜 Metrics 与认证机器状态的角色、term、promised term、启动裁决或复制阻断不一致时，安全卡和总览转未知，机器状态标 `metrics_disagreement`；原有危险信号仍保留更高优先级。定向 API 测试覆盖五类差异，独立健康服务全包 `-race -count=1`、`go vet` 和格式检查通过。比较只用于阻止假绿，不要求两个异步采样点数值完全同步，也不以差异自动判定提升非法。

请求影响窗口覆盖修订：`/api/impact` 不再用单一 `http_2xx` 当前序列代表整节点，也不再用全局 `sum by (outcome)` 掩盖某节点缺失的窗口样本。现在分别验证每个预期成员的八类当前计数和八类五分钟 `increase`，全部新鲜、唯一、非负后才求和；任一节点缺一类、重复或陈旧均显示未观测。定向测试覆盖完整分布、单节点缺成员/缺类别、仅有当前计数无窗口增量、重复和陈旧结果；独立健康服务全包 `-count=1`、`go vet` 和格式检查通过。该分布仍是服务端观察，不能声明客户端最终成功。

事件留存清单修订：独立事件文件每次轮询再次按固定 `-members` 校验采集器返回值；缺失、重复或清单外节点标为 `partial`，列出问题节点，不让这轮采集伪装成完整。已观测来源的采集失败仍写入缺口记录，清单恢复后状态才回到 `ok`。定向事件留存测试与 `-race`、`go vet`、格式检查通过；目标环境仍须核对真实清单与身份边界。

指标新鲜度修订：Prometheus 即时查询可返回回看期内的旧值，其响应时间不是原始抓取时间。健康页的当前 HA 成员与 `up` 改查固定 45 秒原始范围向量，取每条序列最后一个真实样本并仍按 30 秒门限判定；同一成员最早和最晚的指标样本还须与该成员最新 `up` 样本相差不超过 1 秒，避免本次成功抓取漏掉一项指标而上次 15 秒前的值继续显示健康。节点表同步标“本轮指标缺报”，详情列出三种原始样本时间，证据导出保留这些时间。服务端在响应前再按当前时间核对成员与必需确认证据，避免等待其他只读来源期间旧绿灯过期；`/api/health` 返回该服务端 `observed_at`。浏览器用该时间加上自请求开始的单调经过时间保守计算节点新鲜度和旧卡片过期，超过 30 秒才返回的健康响应直接丢弃，不使用操作员电脑的墙上时间判定。请求影响的八类当前计数也使用原始范围向量，避免部分成员停止更新后仍因即时查询求值时间而显示完整。定向测试覆盖单成员 15/40 秒旧样本、原始样本顺序异常、即时向量拒绝、浏览器时钟偏差与慢响应、页面节点文案及请求影响的陈旧覆盖；目标环境须校准真实 scrape 间隔和时间同步。

确认能力来源补强：稳定任期内五分钟必需确认成功增量还须同时满足当前 Primary 的 Ledger 与 metadata 两条 `confirmed` 计数均有唯一且不超过 30 秒的原始抓取样本、稳定任期记录规则有唯一新鲜原始样本，并排除五分钟内计数器重置的窗口。证据响应分别保留两类计数中最旧的 `sampled_at` 和记录规则的 `epoch_sampled_at`；服务端响应前复查两者，任一来源先过期都使确认卡转未知。旧进程成功、规则停评、部分指标缺失或重复不能把重启后的确认卡变绿。定向测试覆盖陈旧计数、缺失/重复/额外 store、陈旧或矛盾记录规则及旧成员样本；独立健康服务全包 `-count=1`、`go vet` 和格式检查通过。目标环境须用真实重启及写负载校验 Prometheus 的重置语义。

固定 PromQL 实验：使用部署锁定的 Prometheus 镜像启动临时单容器自抓取，当前成员的 45 秒原始选择器返回 `matrix`、`up` 与原始采样时间；确认卡 `increase`/`resets`/稳定任期组合表达式解析成功（无 HA 计数时结果为空，符合预期）。后续 2 秒自抓取再核对 `up` 与 `prometheus_build_info` 同轮样本时间完全一致，支持成员指标与 `up` 按轮对齐的假设。容器均已清理。这验证查询语法、响应类型和自抓取时间戳，不替代真实三节点抓取、规则加载或重启语义验收。

成员 HA 信号覆盖修订：安全卡现在要求每个新鲜成员同时上报维护、启动裁决、复制阻断、`schema`/`key_challenge`/`spki` 三种不兼容原因，以及对清单中每个其他成员的 Peer 连接值。无已知危险时，任意一条缺报均为未知，节点详情列出具体缺失项；任一成员明确维护、未完成启动裁决或复制不可用则为降级。更高 promised term 等已知危险优先于另一信号缺报，清单外不兼容原因与矛盾值会标成冲突。新增 `HalroMemberHASignalMissing` 在成功抓取但上述固定指标数量不完整持续 1 分钟后告警；promtool 夹具覆盖完整成员不触发、缺原因/Peer 触发及恢复。Peer 数量相等不能证明名称正确，页面仍按清单逐一核对。评估器及独立健康服务定向/全包测试、页面交互测试覆盖缺报、降级和危险优先级。仓库只观察服务端 HTTP 终态与内部确认；兼容性 SDK 测试关闭自动重试，没有可代表真实调用方完成重试并消费整段流的生产入口，因此客户端最终结果仍须由外部客户端，或取得调用方完成回执的入口层接入并在目标环境验证。

外部客户端最终结果契约修订：单独定义拟议的逻辑操作结果计数和观测者可用性指标、六种互斥结果的优先级、重试去重与流终止条件、完整观测者清单和窗口覆盖门限，列出真实 SDK、幂等、断流、重启和 Primary 停机的验收场景。该文档明确是**待接入的 P1 契约**，当前没有生产端；健康页消费端新增 `-client-final-manifest` 清单门禁和五分钟完整采样校验，缺失、断点、重置或未对账均不显示分布。指标 reference 仍仅列实际导出的成员指标，默认页面显示“客户端最终逻辑操作结果：未接入”，不能因此生成客户端完整成功率。

客户端最终结果消费端验证：清单要求版本、验收记录 ID、逐观测者区域/实例/责任方/覆盖范围和固定操作类别；未配置时 `/api/client-final` 返回 `not_configured`。启用后四组原始序列用同一 Prometheus 求值时刻覆盖完整五分钟，逐轮与 `up` 时间对齐，再检查零重置和每类 `increase`。定向用例覆盖完整采样、缺观测者/类别、单轮缺项、采集断点、陈旧、重复、额外标签、观测者故障、未对账、原始或 Prometheus 报告的重置及空窗口；任一异常均不返回计数。`cmd/halro-ha-health` 完整包 `-count=1` 与 `-race -count=1`、`go vet`、独立二进制构建和页面 16 项定向测试通过。验收记录字段只表示部署方声明，不能替代真实生产端、调用方回执和流量清单核对；这些仍为目标环境 `NOT_RUN`。消费端复核后把六条查询按原始覆盖与窗口计算分两轮并行执行，所有查询仍固定在同一 Prometheus 求值时刻，避免串行查询超过健康服务写超时；导出证据加入客户端最终状态、计数及部署声明 ID，但原始样本与调用方回执仍须单独保留。使用部署锁定的 Prometheus 镜像短时自抓取验证：固定求值时刻的 `up[6m]` 与同目标 `prometheus_build_info[6m]` 均返回 matrix、保留指标名，最近四轮原始时间戳逐一相同；验证容器已清理。这只证明查询响应形状和自抓取同轮时间戳，不代替客户端观测者生产指标与目标环境采集验收。

消费端清单加载增量加固：启动时先核对清单解析后的文件为非空普通文件、不可由组或其他用户写入且不超过 64 KiB，再按上限读取并比对已打开文件身份；兼容指向普通文件的 Kubernetes ConfigMap 投射链接。目录、可写清单及超限文件拒绝测试和受影响 Go 包全包测试通过。该加固不构成外部客户端最终结果生产端验收。

客户端观测者告警增量验证：新增 `HalroClientObserverDown` 与 `HalroClientObserverCoverageIncomplete`，分别对已配置目标的抓取失败和就绪/未对账覆盖缺口持续一分钟告警。规则只在 `job="halro-client-observer",expected_client_observer="true"` 已有目标时生效；未部署来源不产生虚假的全局缺失告警。规则要求就绪与未对账 gauge 的原始时间戳和该目标 `up` 同轮，避免 Prometheus 回看旧值掩盖单轮漏报；promtool 夹具覆盖无来源、目标失联与恢复、观测者不就绪、未对账、两类 gauge 缺报、跨 job 伪证据和单轮漏报后的触发/恢复；锁定镜像的配置与规则测试通过。完全未写入 Prometheus 配置的预期目标仍须以健康页清单、独立流量清单和目标环境巡检发现，不能由该规则证明不存在。
