# 异步提交与延迟取回（`background: true`）

适用范围：`POST /v1/responses`。契约见 [ADR 0024](../adr/0024-deferred-response-tier.md)，
机器可读清单见 [`endpoint-manifests.json`](../compatibility/endpoint-manifests.json)
中的 `openai.responses.create.v1`、`openai.responses.get.v1`、
`openai.responses.cancel.v1`、`openai.responses.delete.v1`。

## 一句话

提交时立刻返回一个 `queued` 的 Response 对象，连接可以马上断开；稍后凭同一个 id 取回结果。
上游看到的仍然是一次普通的同步生成调用——它不知道 Halro 把答案留到后面才给。

## 先决条件

**默认关闭，按项目开启。** 控制台「项目 → 延迟取回」勾选「允许异步提交」。

之所以要显式开启：打开它会改变这个实例的数据目录里有什么。在此之前，调用方自己写的内容
只在一个地方落盘（失败捕获，默认也是关的）；打开延迟取回之后，**成功请求的完整回答**也会
落盘，而且是常态而非尾部。回答以主密钥密封，绑定到 (记录 id, 项目 id)，最长保留 24 小时。

## 提交

```http
POST /v1/responses
Authorization: Bearer gw_...
Idempotency-Key: <可选，强烈建议>

{"model": "my-alias", "input": "...", "background": true}
```

立即返回：

```json
{"id": "resp_...", "object": "response", "status": "queued", "background": true,
 "model": "my-alias", "output": [], "usage": null}
```

- `background: true` 与 `stream: true` 互斥：延迟取回承诺的是一个最终答案，不是一段可重放的
  事件流。
- `store: true` 仍然被拒绝，即使与 `background` 同时出现。OpenAI 语义里 `store` 意思是
  「服务商替你存」，而 Halro 的上游什么都没存——接受它等于对调用方声称一件不成立的事。
- 提交会占用一个 RPM 名额（它确实是一次请求），但**不**占用并发名额（排队中的请求没有在跑）。
- 队列有上限（默认 100）。队满返回 `429`，带 `Retry-After`。

## 取回

```http
GET /v1/responses/resp_...
```

| status | 含义 | 响应头 |
| --- | --- | --- |
| `queued` | 已受理，还没轮到 | `Retry-After` |
| `in_progress` | 正在调上游 | `Retry-After` |
| `completed` | 成功，`output` 与 `usage` 完整 | — |
| `failed` | 失败，`error` 说明原因 | — |
| `cancelled` | 被取消 | — |

轮询节奏由服务端在 `Retry-After` 头里给（1–10 秒，按已等待时长递增）。这个值不放进 Response
对象里：那个对象有 SDK 契约，塞非标准字段会让某些客户端解析失败。

**轮询不产生任何账务事件，也不打上游。** 结果已经在本地磁盘上。批处理的 `GET /v1/batches/{id}`
不是这样——它必须问上游才知道状态，所以每次轮询都是一次真实请求并按请求计账。两者的差别是
有没有上游句柄，不是端点风格。

记录不存在、不属于本项目、或已过冷却期，一律返回 `404`。

## 取消与删除

```http
POST   /v1/responses/{id}/cancel
DELETE /v1/responses/{id}
```

- 取消一个 `queued` 的请求是确定的：什么都没发出去。
- 取消一个 `in_progress` 的请求是尽力而为的：上游调用可能已经发生。这种情况按 ADR 0011 保守
  结算，终态记录会明确写出「可能已在上游产生费用」。
- 已经终态的请求取消返回 `409`。
- `DELETE` 删除记录与它的两个密封对象；它不撤销已经发生的账务。还欠着答案的请求删除返回
  `409`——先取消。

## 项目到达 TPM 或并发上限时

请求留在 `queued`，不会失败——这正是队列存在的理由。等待只受两件事约束：队列深度，和 24 小时
TTL。排到 TTL 都没轮上的请求会变成 `failed`，错误码 `deferred_response_expired`。

## 单次执行的时间上限

一次延迟执行受 `route_total_timeout`（默认 2 分钟）约束，与同步请求相同。超时的请求变成
`failed`（`deferred_response_timeout`），并且**同样可能已经计费**。没有这个上限的话，延迟路径
会比它声称等同的同步路径更松：SafeTransport 只约束建连与响应头，一个逐字节返回的响应体不受任何
约束，而它会一直占住数量很少的 worker 之一。

## 回答体积上限

单条延迟回答上限 1 MiB。超过的请求变成 `failed`（`deferred_response_too_large`），**但这次上游
调用真的发生过、也真的计费了**——上限约束的是「能留下多少」，而没有任何办法在上游产出之前量出
一个回答有多大。需要更长的回答时，走同步路径。

## 脱敏发生在生成时，不是取回时

回答在写入磁盘之前就已经走完出站脱敏，用的是**当时**生效的脱敏策略。之后修改项目的脱敏策略，
不会追溯改写已经存下来的回答——这与同步路径一致（同步路径也是在响应时脱敏），但因为延迟回答会
在磁盘上停留最长 24 小时，这件事值得单独说明。收紧策略之后如果需要立刻生效于已存的回答，用
`DELETE` 删掉它们。

## 保留期

- TTL 24 小时（与失败捕获的保留期一致：存的是同一类材料，不该活得更久）。
- 首次成功取回后进入 15 分钟冷却期，冷却期内可以重复取回。**一个 HTTP 200 离开 Halro 不等于
  调用方收到了它**，所以不是「取回即删」。
- 冷却期结束、TTL 到期、显式 `DELETE`，三条路都会清掉记录和对象。

## 必须写进你的重试逻辑的一条

**`in_progress` 的请求不跨重启存活。** Halro 重启后，正在执行的延迟请求一律变成 `failed`，
错误信息会说明它可能已经在上游计费、答案无法取回。

原因不是实现偷懒。批处理在上游有句柄，重启后可以继续查；一次延迟生成在上游只是一次普通的同步
HTTP 调用，进程死掉时套接字跟着死了——Halro 无法确认它是否完成、是否计费、答案是什么。ADR 0011
对「谁也无法判定的结果」的处理是保守结算，唯一诚实的状态就是 `failed`。

排队中（`queued`）的请求不受影响：它们没发出去过，重启后会重新入队执行。

## 账务

一次 background 请求在 ledger 里与同一个请求走同步路径**逐字相同**：同样的预留、同样的尝试
阶梯、同样的结算顺序。这是因为出队之后执行的就是同一段代码，而不是一份平行实现。

预留发生在出队时（打上游之前），不是提交时。所以一个排了十分钟队的请求不会占住十分钟的日预算
额度；代价是超预算的提交会被受理，稍后以 `failed` 告知。
