## Defect and review disposition

No defect reports were opened against the range. Two items are worth recording
because they were found and closed inside it:

- The `npm audit` conflation (#311) was found by main going red on `dab04526`, a
  docs-only commit. Root cause was external — the registry retired
  `/security/audits/quick` while `/advisories/bulk` answered 503 — but the gate's
  inability to tell that from a finding was ours. Fixed, with a contract test that
  refuses any `npm audit` outside the gate.
- The HA design (#310) was rewritten after two rounds of multi-role review. It is a
  proposal for unimplemented work; it changes no shipped behaviour and appears in
  this range only as documentation.

## Invariants and upgrade impact

No Go source under `internal/` changed in this range, so every runtime invariant is
untouched rather than argued:

1. **Single-writer / single data dir** — untouched.
2. **Ledger WAL is the accounting authority** — untouched.
3. **Fail-closed** — untouched at runtime. The one fail-closed change is in CI, not
   the product: the release workflow now refuses to publish when the npm advisory
   endpoint cannot be reached (`--require-endpoint`), which moves a gate toward
   fail-closed rather than away from it.
4. **No secrets in logs/errors/metrics/audit** — Gateway 401 bodies were checked for
   echoed key material and carry none; the web bundle secret-canary scan passes on
   29 files.
5. **Determinism on replay** — untouched.
6. **Bounded retry/fallback** — untouched.
7. **Capability filtering rejects, never drops** — untouched.
8. **Compatibility manifests** — untouched; no northbound facade behaviour changed.
9. **Config semantics** — no configuration key was added or changed.

**Upgrade impact.** Re-initialisation is **not** required, no configuration edit is
required, and this release places **no rollback fence**: metadata schema is 38
before and after, and the previous released binary was verified to reopen a
directory the candidate had used. A verified pre-upgrade backup remains standing
practice.

The only operator-visible product change is the console's attempt log under Usage.
It reads the same data; no API, no schema and no configuration moved.

## Evidence boundaries

No billable real-Provider request, production KMS/PKI, contact-point delivery,
clean-host package installation or 24-hour soak was run. Benchmarks were not re-run
because the range touches no hot path — no `internal/` Go source at all — which is
a scoping decision under §0, not a waived result. The formal workflow must still
repeat its container scans, SDK compatibility, SSE stress, reproducible packaging,
SBOM, signature, provenance and pre-publication verification. Production admission
remains unverified; `docs/verification/production-validation-run-260918.zh-CN.md`
records that conclusion in full.

**One boundary is specific to this release.** It is the first dispatched with
`publish_packages=true`, so `downstream-package-repositories` — the step that sends
`halro-release-published` to Homebrew and APT — executes for the first time. Both
downstream workflows were exercised on 2026-09-18 through their own
`workflow_dispatch` entries and both work end to end; the untested part is exactly
the dispatch seam between them. Its payload (`client_payload.version` / `.commit`)
matches what both downstream workflows read, but that is a reading, not a run.
Failure there is bounded by design: the tag and Release are already published
before it runs, and a downstream failure delays a channel without retracting
anything. Watch it; `docs/guides/releasing.md` carries the paragraph to delete once
it has succeeded.

A second, smaller one: the frontend redesign was verified by its test suite (624
tests) and the production build, not by a browser pass over the redesigned page.
The range contains no browser-driven evidence.

## Publication verdict

**GO**, for GitHub, GHCR, Homebrew and APT.

The range carries no runtime code change, the full gate passed clean on the first
run, the candidate binary reads and writes a directory the previous release
created, and the previous release reads it back. The risk this release actually
carries is not in the product: it is the first exercise of the downstream dispatch
seam, which is bounded, observable, and cannot retract what has already been
published.
