## 2 Performance

- Benchmarks, HEAD vs v0.3.0 built from the same tree, same host, back-to-back
  (`-benchtime=1s`): **no regression.** Strict redaction 67.7µs/32 allocs vs 68.2µs/32 allocs;
  rolling redaction 15.6µs/79 allocs vs 15.4µs/79 allocs; Token Guard fixed 153.8ns/2 allocs
  vs 154.6ns/2 allocs; EWMA 169.5ns vs 166.2ns. Allocation counts identical throughout.
- The range moved redaction and token estimation onto the semantic request, trading two
  whole-message traversals for per-content-part work. A new `BenchmarkOutboundGenerateResultManyParts`
  measures that directly: 2.3µs/18 allocs at one part, 19.0µs/130 at eight, 148.8µs/1028 at
  sixty-four — **linear in parts, no superlinear term.** HEAD-only baseline; v0.3.0 has no
  semantic traversal to compare against.
- No new locks, channels, or single-goroutine funnels on the request path.
- Frontend bundle: no drift; embedded `internal/webui/dist` is what `web/src` builds.
- Finding carried from v0.3.0: `performance-baseline.md` (2026-07-31) is still stale for route
  resolution and should be re-measured and re-dated.

## 3 Invariants

1. **Single-writer / single data dir** — untouched. No new path writes the data dir outside
   the owning process.
2. **Ledger WAL is the accounting authority** — touched, and this is where the range's one
   real defect was. Reservation is still durable before any Provider request; settlement is
   still atomic; ambiguous outcomes are still conservatively accounted and never refunded.
   What was wrong was the *outcome label*: a request whose answer could not be rendered was
   finalized as `success` while the caller was told 502. Fixed: every outbound refusal now
   runs before `run.finalize`, and the record and the answer agree. Regression-tested and
   reverse-verified.
3. **Fail-closed** — holds. New failure paths refuse: the redaction traversal's `default`
   branch refuses an unknown content kind rather than passing it through; capability records
   that cannot be read are withheld; the schema gate refused both directions across the
   version boundary in the real-binary run.
4. **No secrets in logs/errors/metrics/audit** — holds, and was widened. `Detail` and `Status`
   were the two remaining string members no pass on the outbound traversal looked at; both now
   go through the mandatory baseline. Web bundle canary scan passes.
5. **Determinism on replay** — untouched.
6. **Bounded retry/fallback** — untouched by the range. Noted for the record: a deterministic
   502 has no idempotency key on the inference path, so an official SDK's own retry can bill
   the project several times for one broken answer. The fix in §1 removes the failure that
   made this reachable; the underlying absence of inference-path idempotency is unchanged
   (issue #12).
7. **Capability filtering rejects, never drops** — holds, and improved. The range replaced a
   silent drop (v0.3.0 discarded reasoning content and answered 200) with an explicit refusal.
   `provider_executed_tools` is off by default structurally — via the Defaults list and the
   `Clamp` at `admin_deployments.go:1064` — not by nothing declaring it; verified by
   constructing a catalog entry that does declare it and watching it fail to open.
8. **Compatibility manifests** — `endpoint-manifests.json` matches the implementation
   (23 declared rejections checked against code). The capability dictionary rename is not
   visible to gateway clients (wire validation byte-identical across the change; error codes
   and envelope shape unchanged); it *is* visible on the Admin API, which pre-1.0 permits and
   the changelog must state.
9. **Config semantics** — no new config keys in range.

## 4 Design

- **Fix-in-place discipline**: clean. `json_mode` was replaced, not kept beside its successors;
  migration 32 moves stored records rather than teaching a reader two vocabularies.
- **Format versions**: bbolt 31→32, detector contract v5, capability dictionary v2 — each
  bumped, each refusing stale state rather than misreading it (verified in both directions
  with real binaries).
- **One-way doors**: the new `openai.responses.v1` profile ID, the `json_object` /
  `structured_outputs` capability names, and the new `redaction_policy_error` error code.
- **ADRs**: none required by the range.
- **Threat surface**: `web_search` means the upstream originates network calls that do not pass
  through `safetransport`. It is off by default, gated on an explicit capability, and warned
  about in the console — but this trust boundary is not written into
  `docs/architecture/threat-model.md`, whose SSRF line still names SafeTransport as the only
  egress control. Non-blocking; listed for the docs pass.

**Re-init required: no** (verified with a real v0.3.0-written data directory).
**Stated in release notes: NOT YET — see below.**

## 5 Verdict

**Open blocker (documentation, not code):** `CHANGELOG.md` `[Unreleased]` must carry this
range's user-visible changes, including the capability-rollback loss list. Migration 32 turns
both halves of the split capability off for every stored deployment, and the operator gets no
signal that says so: the startup log mentions the migration nowhere, `doctor` reports
"catalog capabilities available for review" (which says the opposite of what happened, and only
for catalog-covered models), and the console says the same. Until the operator re-ticks, every
request carrying `response_format: json_object` or `json_schema` is refused with 400
`unsupported_feature`. That is a visible service interruption and it must be planned for, not
discovered.

`release.yml`'s `prepare` job also refuses to start without a changelog section for the version,
so this is a hard gate as well as a substantive one.

**Not verified** (must not be replaced by static inference): real-account Provider smoke for
every affected profile (owner decision: not run); the real shape of a `web_search` answer;
that migration 32 clears the detection buckets on a real data directory (package-level evidence
only); signed remote catalogue end to end.
