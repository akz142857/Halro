## Quality and recovery evidence

Implementation [main CI](https://github.com/akz142857/Halro/actions/runs/45656695684)
passed its Go test/race/vet, frontend, compatibility SDK, fuzz, container and
observability jobs. The [candidate image scan](https://github.com/akz142857/Halro/actions/runs/45657565353)
passed. Local implementation verification covered 68 Go packages, targeted
races, 893 frontend tests, the embedded asset comparison, three release command
builds and local SDK contract tests. The exact preparation merge will run the
same ordinary CI as a workflow precondition.

The checksummed published v0.17.0 Linux ARM64 binary seeded a scratch Standalone
data directory against an isolated TLS Provider fixture. The release candidate
started on that directory, handled a successful inference request, and passed
readiness, doctor, Ledger and Usage verification. The v0.17.0 reader refused
both active epoch-6 data and a sealed epoch-6 ledger. The candidate created and
restored a verified encrypted backup, and v0.17.0 restored and served the
verified pre-upgrade backup into an empty directory. The only four requests
went to the fixture. There was no production data or network path in the test.

Six same-host macOS ARM64 samples per side used Go 1.26.11 and
`GOMAXPROCS=4`. Request lifecycle comparisons at 8 and 64 workers found no
significant slowdown. Populated 100,000-record WAL replay was 831.4 ms versus
774.5 ms (p=0.818). Price-pin geometric mean moved from 5.107 ms to 5.314 ms
with no significant per-worker change. Initial route and limited admission
samples were noisy. The longer six-sample recheck measured routing at
4.946 µs versus 4.950 µs (p=1.000, 41 allocations) and limited admission at
133.0 ns versus 133.2 ns (p=0.818, five allocations). Routing uses 0.78%
more bytes per operation from the expanded accounting target. Token Guard and
redaction showed no significant slowdown. The initial console bundle grew
from 258,827 to 259,635 gzip bytes (+0.31%).

The v0.18.0 metadata bump passed the locked Node 22.23.5 suite (893 tests),
typecheck, build and embedded bundle drift gate. Config snapshot checks and
release tooling completed (44 tooling cases, one environment-dependent skip).

## Invariants and upgrade impact

1. Standalone keeps the data-directory lock. HA uses the existing replicated write authority.
2. The Ledger owns balances. Batch and asynchronous jobs use the original project, period and priced hold. Terminal settlement is idempotent.
3. Provider I/O follows the durable dispatch boundary. Definitive pre-send refusals release the hold. Uncertain outcomes retain or conservatively settle it.
4. Billing evidence records result classes and counts rather than credential values, prompts or Provider result bodies. The bundle scans for embedded secrets.
5. Replay uses recorded prices, token provenance and accounting period. The new Ledger reader can replay authenticated epochs 4 and 5.
6. Streaming does not start another Provider after response bytes. Background reconciliation has a per-job deadline and runs independently of object retention.
7. Batch validates each item against the pinned target and requires a generation limit before creating the upstream job. Existing profile availability is preserved.
8. The generated endpoint manifest documents bounded Batch input, budget reservation, settlement, and resource status semantics.
9. The effective configuration defaults and metadata schema 43 are unchanged. Usage exports read earlier partitions and write schema 11 for new data.

Standalone data re-initialisation is unnecessary. HA requires one offline
maintenance window for all members. Once the new Ledger is written, v0.17.0
rollback requires a verified pre-upgrade backup. The epoch and sealed manifest
fences prevent a silent binary-only downgrade.

## Evidence boundaries

No real-Provider/KMS account, production cluster, or production data was used
in preflight. The old and new formats use the same authenticated frame layout;
the paired populated-WAL replay test checks the changed reader. The historical
10 GiB recovery measurement is not a new timing guarantee.
