ordinary CI and the formal dry-run and publishing release gates on the exact
release commit.** Homebrew and APT stay out of scope for the same reason they
were excluded from v0.8.2 — the package-channel App credential was not

## Defect and review disposition

- The two new configuration keys (`admin.setup_token_file`,
  `admin.setup_token_ttl`) are optional. This was the upgrade risk worth
  checking, because configuration is validated key by key and never merged with
  built-in defaults: a required new key would have refused every existing
  `config.yaml`. Verified directly, not reasoned about — see §1d below.
- `halro serve` now fails closed when an instance with **no administrator yet**
  is reachable beyond loopback and has no setup-token file. Verified against the
  binary rather than read off the changelog, because the blast radius is what an
  operator needs to know: the gate is `adminCount == 0 && setupRequiresToken(cfg)`
  (`internal/app/runtime.go:241`), and the zero-administrator half is decisive.
  Two runs of `serve` on the same configuration — `external_origin` set, no
  token file — differed only in whether an administrator existed: the first
  refused, the second bound all three listeners. `halro start` passes
  `AllowGeneratedSetupToken: true` and still prints a generated one-time token
  instead of refusing; `serve` passes `false` because it is the container
  entrypoint with no console to print to.
- The visual-system commit changed no Go behaviour. Its four user-visible fixes
  (disabled contrast, unknown-versus-partial status, link affordance, page
  gutter) are recorded in the changelog's Fixed section.
- One correction was made during this range's own review: an earlier finding
  claimed nine disabled controls carried by `opacity`. There are five, and four
  already cleared 4:1. The finding's substance held — one control at 1.90:1 on
  Light, and an idiom whose contrast cannot be read off the rule — but its size
  did not, and the record was rewritten to the measured values.

frontend suite, TypeScript checking, production build, artifact/secret scan,

## Invariants and upgrade impact

1. **Single-writer / single data dir** — unchanged. The bootstrap completion
   marker is written inside the existing owning transaction.
2. **Ledger WAL is the accounting authority** — untouched by this range.
3. **Fail-closed** — strengthened. Zero-administrator remote startup without a
   setup-token file now refuses instead of exposing an open setup path.
4. **No secrets in logs/errors/metrics/audit** — the setup token is written to
   a private file and never printed; the CLI generates it without echoing it.
   Invalid-key Gateway errors were checked for echoed material and carry none.
   The web bundle secret-canary scan passes.
5. **Determinism on replay** — untouched.
6. **Bounded retry/fallback** — untouched.
7. **Capability filtering rejects, never drops** — untouched.
8. **Compatibility manifests** — no facade behaviour changed.
9. **Config semantics** — the two new keys are optional with defaults present
   in `default.yaml`; absence is distinguished from empty, and an existing
   configuration file is accepted unedited.

**Upgrade impact.** Re-initialisation is **not** required. An existing
`config.yaml` needs no edit. Metadata schema is unchanged at 38, so a v0.8.2
binary can still read a v0.8.3 directory — unlike the v0.8.1→v0.8.2 step, this
release places no rollback fence. A verified pre-upgrade backup remains
required as standing practice.

The one operator action this release can force, stated by blast radius: an
instance started with `serve`, reachable beyond loopback, that has **never had
an administrator created**, must configure `admin.setup_token_file` or complete
the offline `halro admin bootstrap` flow before upgrading. In practice that is a
deployment sitting at an unfinished first-run setup. Every instance that already
has an administrator, every loopback instance, and every `halro start` invocation
is unaffected. The refusal is the intended fail-closed outcome, not a defect.

## Evidence boundaries

No billable real-Provider request, production KMS/PKI, contact-point delivery,
clean-host package installation or 24-hour soak was run. Benchmarks were not
re-run because the range touches no hot path; that is a scoping decision under
§0, not a waived result. Homebrew and APT acceptance is deliberately outside
this publication. The formal workflow must still repeat its container scans,
SDK compatibility, SSE stress, reproducible packaging, SBOM, signature,
provenance and pre-publication verification. Production admission remains
unverified.
