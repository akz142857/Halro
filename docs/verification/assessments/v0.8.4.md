## Defect and review disposition

- **The release-artifact defect this range fixes was confirmed against the
  published releases, not read off the diff.** `gh release view v0.8.3` lists
  `halro_0.8.3-1_amd64.deb` and `halro_0.8.3-1_arm64.deb` as the only two assets
  with no `.sigstore.json` sibling, while every `halro-deadman_*.deb` has one.
  Debian's underscore naming is why: the `halro-*` globs in the checksum, signing
  and verify steps never matched the gateway package. SLSA provenance globs
  `release/*.deb` and covered them throughout, so it was the single surviving
  binding, not an unbound artifact.
- **This release is the first to run the corrected lists**, which makes the
  non-publishing rehearsal load-bearing: the checksum, signing and
  `gh attestation verify` steps all execute in a dry run, so a mistake in the
  new globs fails the rehearsal rather than the publication.
- **Token guards changed behaviour, and the change widens.** A Deployment
  created without explicit `max_context_tokens` / `max_output_tokens` no longer
  inherits a catalog or provider number as a hidden minimum; an unset guard now
  means the upstream's own limit applies, which is what the Admin console has
  always displayed ("upstream applies"). Existing Deployments keep their stored
  values and those values are still enforced. Capability snapshots taken before
  this release keep their numbers on disk; nothing reads them as a claim.
  Recorded here because it is the one change in the range an operator could be
  surprised by after upgrading.
- **Admin API semantics changed for one case**: omitting `capabilities` on a
  Deployment update now means "leave them unchanged" rather than restoring
  catalog defaults. The console always sends the complete set, so the console is
  unaffected; an API client that relied on the old behaviour was being silently
  widened and is now not. Saving from a capability detection with no
  `capabilities` answers `capability_detection_capabilities_required` instead of
  the target-mismatch error, which described the wrong problem.
- **The verify-command wording change relaxed no gate**, which is the thing
  worth checking about it. Both commands still exit non-zero on an empty
  directory. Confirmed by running them: see below.

## Invariants and upgrade impact

1. **Single-writer / single data dir** — untouched.
2. **Ledger WAL is the accounting authority** — untouched. `ChainReport.HoldsFrames`
   is a read-side predicate over a report the verifier already produced; no new
   path treats a derivative as a balance source.
3. **Fail-closed** — preserved. Both verify commands still exit non-zero on the
   state they now describe more precisely; the empty and erased cases are
   byte-identical on disk and deliberately share a refusal.
4. **No secrets in logs/errors/metrics/audit** — the three new shutdown lines
   carry a duration and an error string; Gateway 401 bodies were checked for
   echoed key material and carry none. The web bundle secret-canary scan passes.
5. **Determinism on replay** — untouched.
6. **Bounded retry/fallback** — untouched.
7. **Capability filtering rejects, never drops** — preserved and tightened: a
   capability-detection save that names no retained capabilities is now rejected
   with its own code rather than resolved to something the operator did not ask
   for.
8. **Compatibility manifests** — no northbound facade behaviour changed. The
   Admin API change is described above and in the changelog.
9. **Config semantics** — no configuration key was added or changed.

**Upgrade impact.** Re-initialisation is **not** required, no configuration edit
is required, and this release places no rollback fence: metadata schema is 38
before and after, and the previous released binary was verified to reopen a
directory the candidate had used. A verified pre-upgrade backup remains standing
practice.

The one behaviour change an operator should read before upgrading is the token
guard ownership above: Deployment-level `max_context_tokens` /
`max_output_tokens` are now the only Halro-side windows, and a Deployment that
never had one set gets no Halro-side guard rather than the catalog's number.

clean-host package installation or 24-hour soak was run. Benchmarks were not
