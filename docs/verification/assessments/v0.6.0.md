## 2 Performance

**Follow-up: the missing comparison is supplied.** The original round did not
measure performance because 260901 **P14** identified an obsolete baseline.
The follow-up measures v0.5.0 and the corrected candidate on the same Apple M4
host with Go 1.26.6, identical benchmark fixtures and eight samples per version.
[Raw evidence and method](../performance/2026-09-03-v0.6.0/README.md) and the
[full table](../performance-baseline.md) replace that gap.

Routing is 5.198 → 5.233 µs with no significant difference. Unlimited project
admission is +9.82% (100.8 → 110.8 ns), limited admission +6.30%, and WAL replay
has no significant time change but +5.58% cumulative allocation. No measured
median time increase exceeds 10%; the unlimited limiter result is near that
threshold and its candidate interval is ±13%. These are bounded component
measurements, not an end-to-end capacity guarantee. P14 is closed as an evidence
gap; the [follow-up verdict](v0.6.0-followup.md) preserves the measured costs.

Two capacity facts from the original code review still belong in the release
notes. The historical 10 GiB measurement below was not repeated by this follow-up:

- The first start after upgrade replays the whole WAL twice (the usage
  checkpoint is discarded by migration 35), against the published bound of
  68.578 s for a 10 GiB WAL.
- For the first maintenance interval (default 1 h) the console aggregate holds
  every attempt in the instance's history, not `console_window_days` — window
  trimming does not begin until one successful export has run.

| New binary against the v0.5.0 config | Accepted (`config check` exit 0); new keys default to off |

| Offline usage commands after P10 remediation | Require the master key / primary KMS slot and current metadata for authentication. Refuse old schema without migration; use the old binary for pre-upgrade backup and verification |

## 4 Security

No new leak or bypass in the log surface or the Kimi platform: the new
`FailureDescriptor` carries only enumerations and narrowed identifiers, the
errors-only sink sits inside `safelog` rather than beside it, and all three Kimi
profiles go through the shared SafeTransport client with a single accepted
credential header.

The two new stores of caller-written material are cryptographically sound —
per-scope HKDF, length-prefixed AAD binding `(resource id, project id)`,
128-bit random filenames, explicit path-traversal guards, and the sweep that
survives the feature being switched off. What did not keep up is everything
around them:

- Sealed orphan objects have no sweep at all, and two comments claim one exists
  (P2, confirmed and downgraded).
- The payload endpoint is the first admin GET in this repository that returns
  what a caller wrote, and `read_only` reaches it — the role model's stated
  premise ("every admin GET is a view of Halro's own metadata") was broken this
  round without the model being revisited (confirmed by live reproduction).
- That same endpoint writes its audit record and then returns the body **even
  when the audit write failed** — fail-open on the one read that hands back a
  prompt.

## 5 Verdict

**As filed: no-go for the tag as it stands.** Close A1–A4 first; A1 needs a decision, not
an edit. The six P1 items should be triaged before the tag and can ship in
v0.6.1 if the owner accepts them explicitly, with one exception: B5 (the audit
fail-open) touches a stated invariant and is cheap to fix.

The code in this range is in better shape than the release contract around it.
Zero new dependencies, 1.48 % binary growth for roughly 12k lines of Go, the
accounting authority and its derivatives changed together without the
derivatives becoming a second truth, and the sealing design holds. What is not
ready is what an operator would be handed: a changelog missing half the release,
a manual describing gates that do not exist, and an upgrade path where the first
command the manual tells you to run is the one that closes your way back.
