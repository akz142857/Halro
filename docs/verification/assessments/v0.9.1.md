## Defect and review disposition

The full `v0.9.0..01ef631e` diff was reviewed by this assessor. No independent
second-review claim is made. No blocking finding was identified:

- All history/archive transactions and statistics accesses use the wrapper;
  `Reopen` cannot exchange the handle underneath an active transaction.
- Shutdown stops and joins maintenance before closing the stores. A deliberately
  closed wrapper cannot be reopened by a later call.
- Reopen failure leaves the handle unavailable. The minute maintenance tick
  retries failed files; usage catch-up continues to use the Ledger as authority.
- A replacement filesystem identity is rejected. Page-write counters carry
  across successful reopens rather than restarting the exported counters.
- The concurrency regression test now checks idle success between bounded
  concurrent batches; it no longer requires the scheduler to create an idle
  window inside 500 ms. It also checks accumulated rows after each reopen.

The repository had no open issues labelled `bug` when queried on 2026-10-20.
No new unfinished-code marker was found in the changed source files. Existing
known limitations recorded in the v0.9.0 assessment remain; this patch does not
claim to fix pricing quarantine lifting, history retention, snapshot heap
amplification, or the diagnostic coverage gaps.

## Invariants and upgrade impact

1. **Single writer / data directory:** preserved. Both files remain owned by the
   same process and its existing data-directory lock.
2. **Ledger authority:** preserved. Reopen changes a file handle, not accounting
   decisions; failed history writes recover through Ledger catch-up.
3. **Fail closed:** touched and preserved. An unsuccessful reopen makes every
   transaction return the stored error until recovery; a different file identity
   is refused.
4. **Secret handling:** unchanged. New operational logs contain store labels and
   filesystem errors; no Provider key, prompt, response, or source IP is added.
5. **Replay determinism:** unchanged. The maintenance timer only reopens a file;
   it does not create or modify replayed accounting events.
6. **Bounded retries/fallback:** unchanged on requests. Maintenance performs one
   attempt per selected file per tick, with no retry loop.
7. **Capability filtering:** untouched.
8. **Compatibility manifests:** untouched; no northbound or Provider protocol
   behavior changes.
9. **Configuration:** no new key, default, or schema. The v0.9.1 configuration
   snapshot is byte-identical to the previous release's default.

Re-initialisation required from v0.9.0: **no**. No additional format-version or
rollback fence is introduced. The v0.9.0 upgrade requirements still apply to
older versions and remain linked from the new release notes.

Design review: one shared wrapper replaces the raw bbolt handles; no parallel
legacy implementation, new public identifier, outbound call, or endpoint is
introduced. No architectural rule changes requiring a new ADR were identified.

## Evidence boundaries

- No billable Provider/KMS run: no corresponding wire or custody change.
- No new long-duration soak or same-host throughput benchmark is claimed.
  The memory regression is covered by the existing 300,000-row heap test and

- Reopen is best-effort: it skips an active transaction and retries on a later
