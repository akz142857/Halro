# v0.17.0 pre-release assessment

Date: 2026-11-19

Implementation base: `09c96300566bc9c5d04a542647c401b9f95c8282` plus the release preparation corrections.

## Scope and review

GitHub PRs #524 and #525 change upstream retry interpretation, route suspension
persistence, and the idempotency lifecycle on the request path. There are no
console source, configuration-default, database-schema, or WAL-format changes.
The release bumps version metadata and snapshots the existing defaults.

The release review found that a deadline previously persisted by v0.16.0
escaped the new 15-minute limit on restore, and a failed retryable reclaim
could be described as a live competing call. Preparation clamps and rewrites
the legacy deadline from its recorded observation and reclassifies the key
after a failed reservation write. Regression tests exercise both cases. The
read-side check preserves the existing 503 when a fresh or reclaimable key
cannot be written, and a competing request gets the applicable 409 result.

## Verification

Fresh Go tests ran on Linux ARM64 with Go 1.26.11. One unmodified Ledger
snapshot timing test failed on tmpfs and reproduced twice in 16 v0.16.0
baseline iterations. The complete Ledger package passed on disk with the same
shuffle seed. The full Linux race suite, Go vet, 889 frontend tests, type check,
production build, bundle drift check, and observability validation passed.
The Go scan found no reachable vulnerabilities. Release tooling tests passed
with one host-dependent skip. Ordinary CI must pass on the exact merge commit.

The SHA-256-verified v0.16.0 Linux ARM64 binary wrote a scratch data directory
against an isolated TLS Provider fixture. It wrote a completed key, a lost
outcome, and a 24-hour upstream cooldown. The candidate reused the directory,
returned a 900-second bound without a Provider call, and preserved the completed
and lost outcome refusals while the alias was suspended. A new 12-second hint
did not survive restart. A same-key retry then completed once. Readiness, HTTP,
doctor, Ledger and Usage verification passed through upgrade, restart, candidate
backup restore, and v0.16.0 rollback from a verified backup.

Same-host benchmarks use six interleaved samples per version and Go 1.26.11.
The request lifecycle geometric mean was 5.025 ms versus 5.082 ms. Routing
rechecked at 6.402 μs versus 6.769 μs (p=0.818), both with 41 allocations.
The price-pin rerun moved from 5.081 ms to 4.965 ms geometric mean.
The contended admission benchmark varied from 346.6 ns to 401.3 ns, but the
two trimpath limiter test binaries are byte-identical. The difference is
host measurement variation. Other benchmark families showed no statistically
significant timing regressions in the sampled runs.

## Invariants and compatibility

1. Standalone retains its exclusive data-dir lock. The replicated write path
   still waits for the required dispatch confirmation.
2. Reservations and dispatch marks precede upstream work. Explicit pre-execution
   refusals can be reclaimed after settlement. An uncertain result stays held.
3. Expiry restarts on a durable reclaim. Failed writes and unreadable records
   fail closed. The secondary classification does not reserve or dispatch.
4. Stable error codes carry no upstream response text, keys, or account identity.
5. Existing journal, audit, and Ledger encodings remain in use. The route
   deadline uses its stored observation time, so a restart does not extend it.
6. Upstream hints are bounded and persisted for long ordinary rate limits.
   Route and attempt deadlines still apply to retries and fallback.
7. Capability and policy checks still precede dispatch.
8. HTTP status for a protected repeat stays 409. Clients branching on error code
   must handle `idempotency_outcome_unknown` separately from a live request.
   The generated Chat and Embeddings contracts reflect the distinction.
9. Metadata schema 43 and all configuration defaults remain compatible with
   v0.16.0. Standalone needs no reinitialization. Restore the pre-upgrade backup
   with v0.16.0 for rollback.

No new public configuration, data shape, or externally exposed metric name was
introduced. The new error code and lifecycle meaning are recorded in the
idempotency contract. No billable real-Provider or production HA test was used.
