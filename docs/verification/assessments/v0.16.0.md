## Quality, recovery, and performance evidence

The local Node 22 `make full-check` passed, including fresh Go and race tests,
vet, 889 frontend tests, type checking, the production build, observability
provisioning, and embedded bundle drift validation. The embedded assets are
byte-identical to v0.15.0. Strict npm audits passed for the console and Node
SDK lockfiles. The Go vulnerability scan found no reachable vulnerabilities.
The release tooling tests passed with one host-dependent fixture skipped.
Ordinary CI must pass on the exact merge commit before dispatch.

The published v0.15.0 Linux ARM64 binary was checked against the published
SHA-256 and wrote a scratch data directory through a successful HTTP inference
against a local TLS fixture. The candidate started from the same directory and
refused a repeat of the old completed key. It persisted an explicit 429 cooldown
across a restart, avoided a Provider call during that window, accepted the
original key after the cooldown and refused a subsequent completed duplicate.
Readiness, HTTP inference, doctor, Ledger verification and Usage verification
passed on both binaries, the candidate restart, a restore of a candidate
backup, and a separate v0.15.0 rollback restored from the pre-upgrade backup.
Both backup archives passed verification.

Same-host Go 1.26.11 benchmarks used six interleaved samples per version.
Request lifecycle geometric mean moved from 8.839 ms to 8.031 ms. Registry
resolution was 5.050 μs versus 5.548 μs (p=0.937), with 41 allocations on
both revisions. WAL replay, redaction, Token Guard and Project admission did
not show statistically significant timing changes. The first price-pin
single-worker result was 27% slower with wide timing variation. An interleaved
Linux ARM64 rerun was 25.84 ms versus 25.06 ms (p=0.818). The pricing pin path
does not call the changed inference-claim writer.

The local Mantle fallback fixture passed. On a Linux ARM64 data volume the
same capacity fixture improved the 60-request fast-group p95 from 16.07 s
(v0.15.0) to 233 ms (candidate) amid variable disk synchronization latency.
The candidate held 60 requests in flight for 65 seconds and recorded all
300 settlements with zero Project 429s and no pending work. This run did
not reproduce the 200 ms latency target on disk. A separate tmpfs run
passed all phases, with a 60 ms fast-group p95. The tmpfs result isolates
the request path from physical storage synchronization. The previous Linux acceptance result and its test
conditions are retained in [Opsique batch B](../opsique-batch-b.zh-CN.md).

## Invariants and design

1. Data-directory fencing still owns the writes. Standalone batching uses the
   existing store batch facility and returns after durable commit. The
   replicated path retains the existing per-request confirmation.
2. Reservations and durable dispatch marks precede Provider execution.
   Refusals become retryable only after dispatch evidence and accounting allow
   it. Ambiguous execution continues to hold the original key.
3. If storing the retryable outcome fails, the caller receives
   `503 resource_store_unavailable` and the record remains protected.
4. Caller errors expose a stable code and a recovery delay. No new error body
   copies credentials, request text, or Provider-account identity.
5. Cooldown deadlines are stored using the existing suspension record. The
   existing journal records mutations and revision updates for replay.
6. Attempts stay bounded by the route deadline and attempt limits. Retry
   hints belong to the candidate that returned them.
7. Configured candidates are filtered by capability and request limits before
   temporary suspensions are used to explain exhaustion.
8. The generated compatibility manifest records the change to non-streaming
   Chat Completions. The bilingual guides cover fallback, 429 and idempotency.
9. Configuration defaults and WAL encoding match v0.15.0. Metadata remains
   schema 43. `retryable_refused` is an additive value in the existing
   inference record. Older binaries had treated unknown states conservatively.
   Use the verified pre-upgrade backup with v0.15.0 to roll back.

The new lifecycle value and error behavior are documented in the existing
idempotency and Gateway correctness contracts. The patch adds no public field,
endpoint, configuration key, or metrics identifier.
