## 总结论

**这个范围的主体是稳的，但它把一处结构性缺陷从半闭合状态暴露成了全貌。**

范围内最要紧的两件事各有下场。**能力词表拆分**（`json_mode` → `json_object` + `structured_outputs`）
的动机与实现都成立：一个开关同时承诺"能出 JSON"与"能守 schema"，勾上其一即被路由到另一半、在预算
预留之后被上游拒绝——拆开是对的。迁移 32 的 COW 纪律、中断回滚、幂等性、清理面完整性全部实测通过，
**不需要重新初始化数据目录**。**新增的 `openai.responses.v1` 档案**同样成立：`web_search` 的默认关闭
是结构性的而非"恰好没人声明"（V5 实证证伪了相反的判断），`code_interpreter`/`file_search` 在 wire 与
语义两层于 I/O 之前双重拒绝，跨项目隔离与凭据不外泄未见缺口。

问题集中在一个模式上，而且是三个互不知情的角色从三个方向同时指到的：**渲染或校验失败发生在账目
提交之后**。#231 修的是这个模式的一个实例（引用 span 的那一半），模式本身还在，并且在本轮被两条
独立路径重新触发——一条来自脱敏策略（`$1` 模板清空 citation URL），一条来自内容种类（wire 承载不了
reasoning 或非法 tool JSON）。实测形态是：`attempt outcome="success", http_status=200,
committed_micros_usd=20`，而调用方收到 502 `provider_error`。钱没算错、没有退款、网关侧没有无界
重试——但**账本记的是一句假话，而且把网关自己的缺陷归因给了上游**。V3 还补上了最贵的一层：
推理链上没有幂等键，确定性的 502 会被官方 SDK 自动重试，于是按重试上限倍数产生真实费用。

## 对抗验证：五条里三条的归因或复现路径被推翻，结论只推翻一条

本仓 260805 / 260807 / 260814 三轮评审的最严重发现无一条原样成立，本轮延续这条规律。

| 原发现 | 裁决 | 被改写的是什么 |

| A1-4 出站渲染在 finalize 之后 | **CONFIRMED** | 触发面全错（原报告点名的 citations 不可达，真正可达的是 reasoning 与非法 tool JSON）；"本轮新增"只对一半成立 |

**这一环的价值在这一轮特别清楚**：三条 CONFIRMED 里没有一条的原始描述是准确的。发现型角色擅长
指出"这段代码有问题"，不擅长回答"这条路径真能走到吗"、"它是这一轮引入的吗"。V3 甚至发现本轮把
v0.3.0 的一次**静默丢弃**（reasoning 被无声丢掉并 200 返回）换成了一次响亮失败——按 B4 方向是对的，
只是失败发生的位置不对。

## 整改（五处，全部带回归测试与反向验证）

1. **出站失败移到账目关闭之前**（A2-4 + A1-4 + A1-16）。`generate` 收 render 回调，出站脱敏之后、
   `run.finalize` 之前依次做语义校验与 wire 渲染，任一失败都决定 outcome。新增错误码
   `redaction_policy_error`(500)：策略没有"拒绝"答案，是把它**改坏**了——说清这点才能让运维去查
   自己的规则，而 `provider_error` 会把他们支到上游。覆盖 Chat、Responses、Messages 三条链。
2. **识别阶段探针预算分母**（A5-1）。抽出共用的 runnable 计数，主循环与识别路径共用一份——两份
   重复的计算正是漂移成因。修后 Mantle 得 60s、OpenAI chat 得 45s（此前均为 10s）。
3. **替换模板不得引用不存在的捕获组**（V2 建议，窄化后采纳）。只拒越界引用；可选组与纯 `$1` 是
   合法写法，继续放行，由第 1 项兜住后果。
4. **`Detail` 与 `Status` 纳入强制基线**（A2-2 + A2-3）。`Status` 尤其要紧：出站方向、上游填写、
   原样抵达调用方——#231 修 `action.query` 的理由逐字适用于它，只是漏了一个成员。
5. **`Messages` 门面的两次渲染进入请求内**（A1-16）。抽 `chatWithRender`，**不**拆掉 Chat 中转
   （那条中转正是把 portable Messages 约束在 Chat wire 能表达范围内的限制）。

反向验证全部实际执行，每次退回前先断言编辑真的落地（防 gofmt 重排导致的假验证）。三条失败文案
分别给出了 `14.99s`（与 V4 算式吻合）、`the request was already finalized as … when the render ran`、
`the ledger recorded success for a request the caller saw fail`——最后一条把 A1-16 从 PARTIAL 推成
实证坐实。

**修复后 `make check` 仍 exit 0。**

## 运行时结论：H1 有了完整答案

真实二进制、真实数据目录（v0.3.0 建链 → HEAD 打开）实测：

- **不需要重新初始化数据目录**，31→32 干净迁移，迁移后 doctor healthy。
- **迁移完全静默**：26 行启动日志里提到 migration / schema / capability 的行数是 **0**；
  `json_mode` 字节 2→0，新词表各 6。
- 迁移后 doctor 多出 `capability_drift warn`，但措辞是"**有目录能力可供复核**"，
  不是"你的两半 JSON 能力被关掉了"——**方向说反了**。且这条 warn 只对**目录内**的模型出现；
  A7 用不在目录内的自声明模型验过，那种部署**零信号**。

合起来：升级后到运维重新勾选之前，所有走 `response_format: json_object` / `json_schema` 的存量
流量会被 400 拒绝，而运维在日志里看不到、在 doctor 里看到的是一句说反了的话、在控制台里看到的
（W11）也是"目录变多了"。**这是本轮唯一有对外影响的事，它不是代码缺陷，是发布说明的责任。**
