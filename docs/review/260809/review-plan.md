# Halro 上线前评审与评估方案（2026-08-09）

> 本文件是**方案**，不是报告。执行后的结论落在同目录 `260809.md`（格式参照 [`260807/260807.md`](../260807/260807.md)），整改进度落在 `progress.md`（参照 [`260807/progress.md`](../260807/progress.md)）。
> 评审框架（角色定义、选择指南、方法论）见 [`docs/review/README.md`](../README.md)。本文件只做"这一轮该怎么跑"的具体化，不重复定义角色；对框架的两处扩充在第 4.4 节单独说明。

## 1. 本轮的性质：这是放行评审，不是又一次周期评审

前两轮的产出是**问题清单**。本轮的产出必须是**一个放行判断**：v1.0.0 能不能发、如果不能，差什么、差的每一项由谁在什么条件下关闭。问题清单是达成这个判断的手段，不是终点。

这个差别决定了三件事，贯穿全文：

1. **每个角色都要回答"这条发现是否阻塞发布"**，而不只是给 P0/P1/P2。严重但可用运维手段绕过的，和不严重但发出去就收不回的（格式、契约、公开接口），优先级次序与周期评审不同。
2. **证据链本身是评审对象。** `docs/verification/` 下的七份证据文档、release workflow 的门禁、能力选择的 §15 门禁清单，都不是"背景材料"而是被审对象——上线前最典型的失败模式是"每份文档都说自己通过了，但没人对着真东西跑过一遍"。
3. **必须产出一份"已知限制"清单**并进入发布说明。1.0.0 明确是单写者、单数据目录、无 HA（[milestone 记录](../../todo/halro-ha-architecture.zh-CN.md) 已定 HA 归 1.1.0）——这些不是缺陷，但如果不写进发布说明，第一个把它跑成两副本的运维就是我们的责任。

### 2.2 上一轮之后新增的面

按需要独立评审对象的粒度归并，主要是五块：

1. **模型能力目录与能力选择（Phase 0~2，约 30 个提交）**——`internal/modelcatalog` 是新包；Deployment 保存能力快照、来源与证据；能力漂移在启动核对与 `halro doctor` 中可见；漂移 fail-closed 扣留路由；能力收窄前给出 Route 预检；新增审计事件与指标；bbolt schema 迁移 20~23。这是本轮**最大的新增面**，且直接改动了"什么能力能被路由到上游"这条链路——属于 CLAUDE.md 点名的"能力过滤发生在 Provider I/O 之前"不变量的实现本体。
2. **预算记账写路径重构（[ADR 0018](../../adr/0018-project-admission-and-the-accounting-write-path.md)，提交 `bae8f83`）**——项目锁不再覆盖 Ledger 持久化 append，只覆盖准入决策；"已准入但尚未持久化"的额度改为按项目、按 balance 周期在内存中跟踪。这**直接触及 CLAUDE.md 最高优先级不变量之一**："预算预留必须在 Provider 请求发出之前持久化"。提交信息本身给出了正确性论证（额度在任一瞬间被记在两处之一、绝不两处皆无），这个论证是否成立必须由独立角色复核，而不是采信作者自述。
3. **可观测性与容量自省**——写路径插桩、`make stats`、无 Prometheus 也能读出本实例吞吐上限、`halro_accounting_project_lock_*` 系列指标。这是为 #13（Linux/NVMe 容量基线，#110 的门禁）铺的路，本轮第一次具备做"性能与容量"角色的条件（前两轮都因无压测环境而记为待办）。
4. **前端重构与首次运行体验**——SettingsPage 按模块拆分、有效配置独立面板、能力选择 UI、首次运行 checklist 改为服务端 onboarding readiness 驱动、诊断页多处修复。1.0.0 的第一印象在这里。
5. **改名 Heimdall → Halro（`0814cac`）**——**已核实无残留**：全仓 `*.go/*.ts/*.tsx/*.yaml/*.yml/*.json` 无大小写不敏感的 `heimdall` 命中；指标前缀在 `deploy/observability` 与 `docs/contracts/metrics-reference.md` 中 152 处全部为 `halro_`。**故本项从风险面移除，不给任何角色派为重点问题**，仅在可用性角色通读文档时顺带确认对外文案。此处记录该核实，是为了让后续读者知道它被查过而不是被忘了。

### 2.4 发布流水线自身的未解问题

`v1.0.0-rc.1` 标签存在，但其 publish job 从未产出 Release。已核实的机制事实：`.github/workflows/release.yml` 的 `publish` job 带 `environment: v1-release`，并在发布前强制校验 `secrets.M11_RELEASE_EVIDENCE_JSON`（`release.yml:247-277`）。**未验证**的是这两者中哪一个（GitHub Environment 未配置/未审批，还是 secret 未设置）导致 job 未完成，或 job 是否根本没被触发。这是"供应链与发布工程"角色的第一号问题——在解决它之前，任何"我们准备好发版了"的结论都是空的。

### 2.5 已裁决：模型能力自动探测进入本轮范围

写这份方案时，工作区里有一批未跟踪的 Go 文件实现"模型能力自动探测"，而该功能在 2026-08-09 曾经五角色评审后决定为 Deferred。两者不对齐会让评审对着一棵没人会发布的树进行，所以当时把它列为开工前必须裁决的事项。

**裁决结果：Deferred 决定已被撤销，代码已合入 `main`（PR #144，merge commit `481d1c9`）**，`docs/todo/model-capability-auto-detection.zh-CN.md` 的状态行同步改为 "Implemented — 待用户验收"。因此这块**作为第六个新增面进入本轮范围**，与 2.2 节列的五块同等对待——它已经在第 3 节定义的基线区间之内，不需要额外纳入动作。

它是本轮**优先级最高的新增面**，理由是当初支持 Deferred 的那条最强论据在实现里只兑现了一半：

- **已兑现**：每次 Provider 调用在请求发出前把 `reserved → running` 两次持久化落盘，启动恢复把两种在途状态都判为 UNKNOWN 且从不重放。崩溃不能绕过调用次数预算，也不能假装一次可能计费的请求没发生过。
- **未兑现**：这笔花费**没有进 Ledger**——记的是调用计数（`ProviderCalls`），不是 token 与成本，不出现在余额、预算或用量账目里。这是第一批不走网关记账路径的计费 Provider 调用。

当初记下的解除条件原文是"任何复活必须先把这笔支出纳入与网关流量同一套记账纪律，在 I/O 之前持久化"——持久化那一半做了，记账那一半没做。**这个缺口是否阻塞 1.0.0，是本轮必须给出的裁决之一**，已收进第 5 节的不允许空白清单。

对应的角色分工：A1（核心逻辑）判断这笔账该不该进 Ledger、不进的后果是什么；A2/A3（安全）看探测新增的 Admin 端点面与出网面；A4（测试盲区）看崩溃恢复的三态是否有负面测试。

### 2.6 一条发布门禁按构造有约一半概率变红，而没人查过

写这份方案期间，`deploy/observability/smoke.sh` 在一个纯文档 PR 上失败了。查下来与改动无关，而且是同一个 commit 的两次并发 CI 一个通过一个失败——同一棵树给出不同结果。

根因量出来了，不是推断的。Watchdog 等待的预算是 60 次 ×1s；而 Alertmanager 的 Watchdog 路由设了 `group_interval: 1m`，第一次派发没赶上的通知要整整一分钟后才重试。本机反复运行测得的等待时间**只有 0s 和恰好 60s 两个值，中间没有别的取值**——告警通常在等待开始前就已投递，没赶上就落在一个 `group_interval` 之后。60s 预算正好压在这条边界上，成败取决于循环开销的抖动而不是投递是否正常。修复见 PR #146（预算提到 150s，并在超时分支打印两端实际状态）。

**这件事本身不重要，它暴露的东西才重要**，而且正好落在本轮的两个判据上：

1. **一个按构造约有一半概率变红的发布门禁，长期没有被当作信号。** 它不是最近才坏的——预算和路由配置都不是新写的。这说明 CI 红灯在这个仓库里已经被默认为噪声。G3（`make check` 与 CI 全绿）如果只看"这次跑绿了没有"，是量不出这个问题的；要问的是**红灯出现时有没有人查**。
2. **预算是照着名义路径设的，没照着重试路径设。** 名义链路 ≤15s（`vector(1)` 无 `for:`、`group_wait: 0s`），60s 看着像四倍余量——但它对重试路径是零余量。**同一类错误可能不止这一处**：C2（可观测性）应当检查其余等待与超时是按名义耗时设的，还是按最坏投递路径设的。

这条不需要单独的角色，已并入 C2 的范围，并作为 G3 判定时的一条具体检验项。

## 3. 范围界定

- **基线区间**：`8868e85`（260807 评审基线的 HEAD）→ 评审启动时的 `main` HEAD（当前为 `33bc13b`，启动时以实际为准并记录在报告首页）。角色应优先通读该区间 diff 覆盖的文件。
- **全仓性角色例外**：架构、可用性、供应链、运维演练四个角色**不受 diff 限制**——它们判断的是整体形状与可操作性，只看增量会得出错误结论。
- **证据文档纳入被审范围**：`docs/verification/` 七份、`docs/runbooks/`、`docs/contracts/`、`docs/milestones/release-notes-v1.0.0.md`、`docs/todo/model-aware-capability-selection.zh-CN.md` §15/§17.4 门禁表。**特别注意** `docs/verification/security-review-v1.md` 自称"final v1 release remains blocked on the M10 recovery, soak, packaging, and release-signing gates"——这句话是否仍然成立，本身就是一条要裁决的发现。
- **无可排除的依赖噪声**：与 260807 那一轮不同，本区间内**没有任何依赖升级提交**（0 个），93 个非 merge 提交全是功能与修复——这也是本轮增量密度高于上一轮的原因之一。"供应链"角色仍须整体核对依赖树与 `docs/verification/dependency-license-review.md` 是否一致，但不是因为本轮改过依赖，而是因为该文档自上次核对后可能已过期。
- **排除**：已在 260805/260807 走查且本轮无改动的代码不重新通读。

## 4. 角色选择

### 4.1 选择依据

README 的选择指南给出两个相关档位——"大型功能合并前"（架构 + 核心逻辑 + 安全 + 测试盲区 + BUG）和"发版前"（可用性 + API 兼容性 + 供应链 + 数据迁移）。本轮**两个档位同时成立**：既有 23.5k 行未评过的新代码，又要发 GA。因此取两者并集，再按第 1 节"放行评审"的性质补充一档上线后可运维视角。

共 **15 个发现型角色**，分四档。这是三轮中规模最大的一次，理由是它也是最后一次——1.0.0 发出去之后，同样的问题修起来要多一个兼容性维度。

### 4.3 模型分配与拒答处置

本轮首次按角色分配模型，理由不是"贵的更好"，而是三条模型侧的事实各自决定了一批角色的归属。

#### 分配依据

| 模型 | 角色 | 依据 |
|---|---|---|
| **Fable 5** | A1、A6、B2、B4、C3 + 部分对抗验证 | 深度推理密集、需要把 23.5k 行增量整体装进上下文（1M 窗口）、且不带安全框架。这些正是它的强项区间 |
| **Opus 5** | A2、A3、A4、A5、B1、B3、C1、C2 + 安全类对抗验证 | 两类：(a) 落在 Fable 5 分类器目标区的安全角色；(b) 以实操与核对为主而非深推理的角色，付两倍单价没有对应收益 |
| **Sonnet** | D1、D2 | 前端模式一致性核对，不需要顶配 |

#### 安全角色为什么必须避开 Fable 5

Fable 5 的安全分类器**针对研究生物学与大部分网络安全内容**——官方定位是不适用于这些领域，且明确说明它在找 bug 上的能力提升**不包括以安全为焦点的分析**，因为 cyber 分类器在那里生效。良性的安全工具类工作会产生误判，本项目正是典型场景。

被拒时的表现值得特别注意：**返回的是 HTTP 200 加 `stop_reason: "refusal"`**，不是报错。也就是说一个安全角色可能"顺利完成"却交回空结论，而汇总时看起来只是这个角色没发现问题。因此：

- A2、A3、A5、C1 一律走 Opus 5，不做尝试。
- 汇总时对任何"未发现问题"的角色结论做一次真伪核对——区分"查过没发现"与"根本没查"。

#### 万一 Fable 5 角色仍被拒

- 服务端 `fallbacks` 参数（cyber 类拒答自动路由到 Opus 4.8）是 API 层能力，评审执行环境用不上，不要指望。
- 处置就是把该角色重新派给 Opus 5 跑一遍。角色本来就互不知情、独立产出，代价是一个角色重跑，不是整轮作废。
- 提示词中如实说明"这是对自有代码库的授权防御性安全评审"——这是准确的上下文而非规避话术，能降低误判率但不保证。

#### 开工前必须确认的两件事

1. **数据保留策略。** Fable 5 要求 30 天数据保留，**零数据保留（ZDR）组织下每个请求都返回 400**，与内容无关。先用一个 Fable 5 角色试跑验证可用性，再按本表铺开。
2. **成本。** Fable 5 是 $10/$50 每百万 token，Opus 5 是 $5/$25。按上表分配，15 个角色中 5 个吃两倍单价。若需压缩，B2 与 B4 可降到 Opus 5，A1、A6、C3 不建议动。

#### 提示词写法：Fable 5 角色是"目标 + 下限"，不是清单

为早期模型写的提示词对 Fable 5 往往**过于规定性，反而降低产出质量**。因此 §4.2 中 Fable 5 那五个角色的交付内容已改写为：给目标与约束、由角色自行划定范围与方法，原先的重点问题降级为"不允许空白的下限"。Opus 5 与 Sonnet 角色保留原有的枚举式写法——这对它们仍然有效。

这条差异是本轮的一个观察点：同一份评审里两种提示词风格并行，收尾时值得记录哪一种产出更好，作为下一轮的输入。

### 4.5 对评审框架的两处扩充（建议回写 README）

1. **新增"运维就绪与 Runbook 演练"角色**（C1）。它与"可用性"的区别是：可用性看**首次使用者**能不能上手，运维就绪看**事故中的运维**能不能自救；与"可观测性"的区别是：后者看信号是否存在，前者看拿到信号之后的动作是否可执行。`fd3e522`（runbook 三处说法代码并不支持）证明这个视角是必要的——文档评审看不出这类问题，只有实操能。

## 6. 对抗验证

沿用 README 的方法沉淀，本轮**不缩减**这一环：发现型角色产出后，对最严重的 5~7 条各派一个独立"证伪型"角色，默认 finding 为错，要求在代码里复现完整路径或找出已有拦截防御，裁决 CONFIRMED / REFUTED / PARTIAL。

两轮历史数据支持这个投入：260805 六条最严重发现无一原样成立（一条头号安全 P0 被完全 REFUTED）；260807 五条中四条 CONFIRMED、一条 PARTIAL（紧急程度高估约两档）。**在放行评审里这一步比以往更重要**——一条被误判为 P0 的发现会无谓地推迟发布，一条被误判为已缓解的发现会带着上线。

预期的对抗对象集中在第 5 节表格的 1、2、3 三项，以及 A5 报出的最严重 BUG。

**证伪型角色的模型按被验证的 finding 分配**，而不是统一一个：记账/架构/迁移类 finding（如第 5 节第 1 项 ADR 0018 额度不变量）走 Fable 5——复现一条并发时序需要的正是它的推理深度；安全类 finding（第 2、3 项及 A5 的安全向 BUG）走 Opus 5，理由同 §4.3。这里尤其不能出错：**一个被 cyber 分类器拒答的证伪角色会返回空结论，而空结论在裁决表里长得像 REFUTED**——那等于把一条真漏洞判成误报带着上线。
