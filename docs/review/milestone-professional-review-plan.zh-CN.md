# Halro 里程碑专业评审计划

> 文档性质：常设评审程序与执行模板  
> 适用对象：产品、架构、研发、数据、安全、测试、运维、发布及业务类里程碑  
> 计划版本：1.1  
> 制定日期：2026-09-18  
> 上次修订：2026-09-18（对齐既有证据阶梯、角色体系、目录规范与 pre-1.0.0 政策）  
> 适用仓库版本区间：`v0.1.0` — `v0.x`（pre-1.0.0）；进入 `1.0.0` 后第 7.5、10.2 节的
> 重新初始化豁免必须重新审查  
> 状态：待具体里程碑实例化后执行

本文件定义 Halro 里程碑的统一专业评审方法。它回答“这个里程碑是否按承诺完成、风险是否可接受、
是否允许进入下一阶段”，但不自动构成版本发布、生产部署或真实 Provider 调用授权。

每次执行必须先复制本计划，填写具体的里程碑编号、范围、候选提交、负责人、时间与证据位置。
未绑定精确候选 SHA、只有口头说明或沿用旧版本测试结果的评审，不得给出 `GO`。

## 1. 评审目标与结论边界

### 1.1 评审目标

一次完整评审必须形成以下六个可审计结论：

1. **价值完成度**：承诺的用户、业务与运营结果是否实现，而不只是任务是否关闭；
2. **范围完整性**：需求、设计、代码、配置、数据、文档和交付物是否属于同一个候选范围；
3. **工程正确性**：关键不变量、失败路径、并发、恢复、升级和兼容行为是否有证据；
4. **风险可接受性**：安全、隐私、账务、合规、供应链和运维风险是否已关闭或被明确接受；
5. **可交付性**：构建、部署、监控、回滚、支持和发布流程能否由非作者重复执行；
6. **决策可追溯性**：谁基于哪些证据，在什么时间批准、附条件批准或拒绝进入下一阶段。

### 1.2 三类结论必须分开

| 结论 | 核心问题 | 典型证据 | 不代表 |
| --- | --- | --- | --- |
| 里程碑完成 | 约定范围与验收条件是否完成 | 需求追踪、实现、定向测试、评审记录 | 可以正式发布 |
| 发布就绪 | 精确候选能否安全构建、验证和分发 | 全量门禁、升级、制品、SBOM、签名、dry run | 已具备生产运行证据 |
| 生产就绪 | 目标环境中的容量、恢复、安全和运营闭环是否成立 | 真实环境演练、长稳、告警、值班、RTO/RPO、签署 | 所有未来场景均无风险 |

评审报告必须明确本次裁决属于哪一类。不得以“里程碑完成”替代“发布就绪”，也不得以本地或
模拟环境通过替代生产就绪。

### 1.3 默认禁止事项

除非另有明确授权，评审不得：

- 创建或推送正式 tag、发布 Release、部署生产环境；
- 使用真实客户数据、生产密钥或不可逆修改生产状态；
- 调用计费的真实 Provider、真实 KMS 或外部告警接收端；
- 把模拟器、fixture、静态代码阅读或旧 CI 结果描述成真实环境证据；
- 为了让门禁通过而降低既有安全、账务、恢复或兼容标准。

## 3. 评审原则

1. **证据优先**：结论必须能追溯到候选 SHA、命令、日志、截图、数据或明确的代码位置；
2. **作者与裁决分离**：作者可以说明设计，但不能单独关闭自己的高风险发现；
3. **发现与证伪分离**：P0/P1 及有争议问题由非原作者从入口到结果重新复现；
4. **风险驱动**：验证深度由影响面决定，不以代码行数或排期压力决定；
5. **失败路径优先**：除成功路径外，必须覆盖拒绝、超时、取消、重试、重启、损坏与资源耗尽；
6. **事实与判断分离**：先记录观察事实，再记录影响、严重度与建议，未知即标记 `UNVERIFIED`；
7. **上游事实来自上游**：模型、区域、版本和能力等不得因本地 adapter 沉默而被臆测；
8. **一次候选一次结论**：所有签字绑定同一 SHA；代码变化后按影响面失效并复验；
9. **评分不能覆盖硬门禁**：高分不能抵消账务错误、越权、密钥泄漏、数据损坏或不可回滚；
10. **最小充分验证**：迭代阶段先跑能看见改动的检查，发布前在最终候选上只跑一次完整门禁。

### 4.4 独立性与利益冲突

- P0/P1、账务、认证授权、持久化、恢复和发布链问题必须由非代码作者复核；
- 同一人可以承担多个角色，但报告必须标明角色合并，不能声称“独立交叉验证”；
- 业务 Owner 可以接受业务取舍，不能接受安全、合规或数据完整性风险；
- 无法取得独立评审时，相关结论最多为 `CONDITIONAL GO`，并记录残余风险与补审期限。

### 4.5 独立评审人可以是 agent

本仓库的日常形态是少数几位维护者加 agent 驱动的评审，历史评审（260805、260807、260905、
260913）的发现型与证伪型角色都是这样执行的。因此“非作者复核”在本仓库以 agent 承担是合法的，
条件是全部满足：

1. **独立上下文**：复核 agent 不继承产出该改动或该 finding 的会话上下文；
2. **不读结论先复现**：先从公开入口（HTTP 端点、CLI、Admin 界面、真实数据目录）自行走通路径，
   再对照原报告，不以“原文说有问题”作为前提；
3. **裁决绑定证据**：给出入口、前置条件、经过的防线、可观察结果，而不是复述代码阅读；
4. **角色披露**：报告写明该角色由 agent 执行、使用的模型/工具类别与人类复核范围。

不满足上述任一条时，该复核记为 `UNVERIFIED`，不能用来关闭 P0/P1。人类决策人仍是 GO/NO-GO 的
唯一签字方，agent 不能签署风险接受。

## 5. 准入条件

下列条件全部满足后才进入正式评审：

- [ ] 目标、非目标、验收标准、用户旅程和成功指标已书面化；
- [ ] 候选范围可由上一基线和候选 SHA 唯一重建；
- [ ] 需求、Issue、PR、ADR、代码、测试和文档间有追踪关系；
- [ ] 关键设计决策与被拒方案有记录；
- [ ] 已知限制、依赖、假设、外部授权和开放问题已列出；
- [ ] 测试环境、样本数据、工具版本与证据目录可用；
- [ ] 真实账户、真实 KMS、计费调用和生产变更的授权边界已明确；
- [ ] 本次分层（Tier-0/1/2）、评分阈值与不可裁剪项已按第 14.1 节确定并写入 `review-plan.md`；
- [ ] 每个触发专项已有责任人，P0/P1 已指定独立复核人（由 agent 承担时满足第 4.5 节条件）；
- [ ] 第 2.1 节列出的既有未关闭队列已逐一核对，遗留项要么关闭要么显式纳入本次范围；
- [ ] 现有工作区状态可解释，不会把无关改动混入候选；
- [ ] 评审期间的范围变化和紧急修复流程已约定。

任一关键条件不满足时，状态为 `NOT READY FOR REVIEW`，不能用评审会议替代准备工作。

| 阶段 | 建议时间 | 主要工作 | 退出条件 |

| S0 启动与冻结 | T-10～T-8 | 冻结范围、候选、角色、门禁和环境 | 范围表与证据计划获确认 |
| S1 独立桌面评审 | T-8～T-6 | 各角色独立读需求、设计、diff 和测试 | 每个角色提交发现或无发现依据 |
| S2 定向验证 | T-6～T-4 | 运行受影响测试、契约、升级、性能和浏览器检查 | 所有结果绑定候选 SHA |
| S3 实机与故障验证 | T-5～T-3 | 二进制、恢复、回滚、故障注入、兼容与演练 | 高风险运行证据完整 |
| S4 对抗裁决 | T-3～T-2 | 非作者证伪 P0/P1 和争议发现 | 每项有标准裁决与严重度 |
| S5 整改与复验 | T-2～T-1 | 修复、回归、更新文档与证据 | 阻断项清零，例外获批准 |
| S6 决策与归档 | T0 | 最终门禁、签署、GO/NO-GO | 决策绑定唯一 SHA |
| S7 上线后验证 | T+1～T+N | 观察指标、用户反馈、事故与复盘 | 验证退出条件满足并归档 |

S2 与 S3 的时间区间**故意重叠，表示并行**：S3 的实机、升级和故障验证通常需要更长的准备与
运行时间，一旦候选二进制可用即可启动，不必等 S2 的全部定向测试收敛。两者的退出条件互相独立；
若 S2 发现改动面扩大，S3 必须按新范围补跑，而不是沿用先启动时的证据。

### 6.2 S0：启动与冻结

输出（文件名见第 12 节，与本目录既有实践一致）：

- `review-plan.md`：本计划实例化版本，含本次采用的分层（第 14.1 节）与阈值；
- `scope-and-baseline.md`：基线、候选 SHA、提交/文件/接口/格式/依赖和风险面；
- `coverage-matrix.md`：目标 → 需求 → 设计 → 实现 → 测试 → 证据；
- `evidence/environment.json`：证据编号、责任人、环境、工具链版本与计划完成时间。

### 6.3 S1：独立专业评审

各角色在首次汇总前独立工作，避免早期结论锚定。每份角色报告至少包含：

1. 已审范围与未审范围；
2. 通过项及其证据；
3. 发现项、严重度、完整可达路径与最小复现；
4. 尚未验证的假设；
5. 建议的额外测试或运行实验；
6. 本角色结论：`PASS / PASS WITH CONDITIONS / FAIL / UNVERIFIED`。

### 6.4 S2：定向验证

执行顺序遵循仓库 `AGENTS.md`：先运行能看见改动的最窄检查，再逐层扩大。

- Go 逻辑先跑具体测试，再跑受影响包；作为通过证据时使用 `-count=1`；
- 只有并发、goroutine、共享状态或生命周期改变时，对受影响包执行 `-race`；
- 前端逻辑先跑直接相关 Vitest，TypeScript 类型或组件逻辑变化时跑 typecheck；
- 纯 CSS、文案和视觉层级变更采用聚焦视觉检查；设计系统/样式变更运行其专属测试；
- `web/` 变化后重建并校验 `internal/webui/dist`，生成物与源代码同一提交交付；
- 最终候选在 push 或正式交付前只运行一次完整门禁，不重复无意义的全量套件；
- 不通过管道读取关键命令退出码，不把缓存结果视为当前候选证据。

### 6.5 S3：实机、升级与故障验证

按适用性选择：

- 构建真实二进制，从空数据目录完成启动、核心旅程、doctor 和优雅停止；
- 使用上一已发布版本写入的 populated 数据副本执行升级；
- 验证旧版本回滚行为：安全兼容或明确 fail closed，不允许静默误读；
- 执行备份、校验、在隔离目录恢复、从恢复结果启动并核对关键数据；
- 对超时、取消、重启、磁盘/配额不足、损坏输入和依赖不可用做受控故障注入；
- 对受影响热路径做同机同工具链性能对比，记录原始样本而非只留摘要；
- 用受控上游（`httptest` fake server、`internal/compatibility` 的 transport fixture、
  `internal/kms/fakekms`）完成端到端；真实 Provider 仅在授权后补充，且单独标记；
- 用生产构建的内嵌前端完成真实浏览器旅程，不以 jsdom 结果替代浏览器证据；
- 计费的真实 Provider 调用按 [`docs/verification/provider-real-matrix.md`](../verification/provider-real-matrix.md)
  取得授权后才执行，证据单独标记等级与账户归属，不与受控 Provider 结果混排。

#### Halro 专属运行证据（适用即必跑）

二进制本身是诊断工具。下列只读命令在候选二进制、真实数据目录上执行，输出连同退出码入档；
它们的兄弟命令（`ledger seal`、`usage compact|prune`、`backup restore`）会改状态，只在隔离
副本上执行：

```bash
./bin/halro doctor        --config config.yaml
./bin/halro config check  --config config.yaml
./bin/halro ledger verify --config config.yaml
./bin/halro audit verify  --config config.yaml
./bin/halro usage verify  --config config.yaml
./bin/halro backup verify ...
git diff --exit-code -- internal/webui/dist   # web/ 变更后生成物漂移门禁
```

同时逐项确认本仓库的硬不变量在候选上仍成立，任一项证据缺失即记 `UNVERIFIED`，不得默认通过：

| 不变量 | 验证方式 |
| --- | --- |
| 单写者、单数据目录（含 Docker/K8s 单副本、`Recreate`） | 并发启动被锁拒绝；部署清单复核 |
| Ledger WAL 是账务权威，bbolt/Parquet 只是派生 | `ledger verify` + 从 WAL 重建后比对聚合 |
| `internal/safetransport` 是 Provider/webhook 的唯一出网路径 | 新增出网调用的代码审查 + 允许列表、无重定向、无 env proxy 行为验证 |
| `internal/failurecapture` 是 secret 留存的唯一例外 | 日志、指标、审计、备份与前端 bundle 的 secret canary 扫描 |
| Withheld profile 写路径拒绝、读路径不阻塞启动 | `domain.IsWithheldProfile` 相关测试 + 持有该连接的实例仍能启动与删除 |
| fuzz 目标与 CI 名单同步 | 新增/改名的 fuzz 目标已登记进 `.github/workflows/ci.yml`（未登记 = 静默不 fuzz） |
| 重试/回退有界，且响应字节可见后不再切换 Provider | 中途故障注入下的流式行为 |

### 6.6 S4：对抗裁决

对抗评审人默认发现可能不成立，从公开入口重新验证完整链路，不只检查被指出的局部代码。

| 裁决 | 定义 |
| --- | --- |
| `CONFIRMED` | 可达条件、影响和严重度基本成立 |
| `PARTIAL` | 问题存在，但范围、影响或严重度需收窄/改写 |
| `REFUTED` | 现有防线阻断攻击链或事实前提不成立 |
| `UNVERIFIED` | 缺少环境、权限、数据或可重复证据，不能判断 |

裁决必须说明入口、前置条件、经过的防线、可观察结果和建议回归测试。`UNVERIFIED` 不是通过。

### 6.7 S5：整改与复验

- 每项整改绑定 finding ID、Owner、目标提交、验证方法与截止时间；
- 修复后由原发现人或独立复核人确认，不以开发者自报“已修”关闭；
- 只重跑能受该修复影响的检查；若修复改变候选的其他风险面，补相应专项；
- 所有 P0/P1 清零后，才可形成最终候选并运行完整门禁；
- P2/P3 延后必须有风险接受人、期限、跟踪 Issue 和用户可见影响说明。

### 6.8 S6：决策与归档

决策会议只处理已准备好的证据与争议，不现场第一次阅读材料。最终记录至少包含：

- 精确候选 SHA、基线、环境和完整门禁结果；
- 各角色结论、评分、对抗裁决和未验证项；
- 未关闭风险、例外、补偿控制、Owner 与到期时间；
- `GO / CONDITIONAL GO / NO-GO` 及理由；
- 若为发布/生产结论，记录制品摘要、部署/回滚负责人和观察窗口。

### 6.9 S7：上线后验证

若里程碑进入发布或部署：

- 在约定观察窗口核对错误率、延迟、账务差异、资源、告警和关键业务指标；
- 验证支持渠道、回滚条件和升级问题没有新增高风险信号；
- 发现门禁遗漏时在 `completion-audit.md` 记录“评审逃逸项”，补充测试或流程，并开跟踪 Issue，
  而不只修一次缺陷；
- 完成复盘，更新常设检查表、Runbook、基线和后续里程碑输入。

## 7. 专业评审检查域

### 7.1 产品与业务价值

- 目标用户、核心问题、替代方案和不做的内容是否明确；
- 验收指标是否有口径、数据源、基线、目标值、观察窗口与责任人；
- 成功、部分成功、失败、取消和回退的用户结果是否定义；
- 是否存在“功能完成但用户无法发现、配置或验证”的断点；
- 计价、订阅、权益或限制是否以用户可理解的方式呈现；
- Beta/实验性/生产可用等标签是否与真实证据一致；
- 已知限制、迁移影响和支持范围是否进入发布说明与用户文档。

### 7.2 架构与领域模型

- 领域对象、标识符、状态机、事实源和派生数据是否唯一；
- 管理面、数据面、控制面和持久化边界是否清晰；
- 新抽象是否有至少两个真实需求支撑，是否引入第二权威或并行旧路径；
- 模块依赖是否保持单向，是否出现循环、跨层调用或隐式全局状态；
- 一次性里程碑代号是否泄漏进长期 API、类型、指标或存储格式；
- 不可逆的公共名称、事件编号、配置键和格式版本是否经过专门审查；
- 架构变化是否需要 ADR，现有 ADR、图和实现是否一致。

### 7.3 核心逻辑、账务与并发

- reservation 是否在 Provider I/O 前持久化，settlement 是否原子；
- Ledger 是否仍是账务权威，聚合库或 Parquet 是否只作为派生视图；
- 幂等键、重试、回退、取消和不明结果是否保持保守且有界；
- 跨租户、跨 Project、跨 Provider、跨 Region 的状态是否可能串联；
- 共享状态、锁顺序、pending 窗口、goroutine 生命周期和关闭流程是否正确；
- 时间、随机数、价格、能力和配置等重放输入是否被冻结而非重新解释；
- 错误分类、展示字段和指标是否不会反向改变执行或结算语义。

### 7.4 安全、隐私与合规

- 每个入口的认证、授权、租户归属、角色与对象级权限是否完整；
- Gateway Key、Provider credential、Master Key、session 和恢复密钥的生命周期是否受控；
- 日志、错误、指标、审计、前端 bundle、备份和故障捕获是否通过 secret canary；
- prompt、response、IP、标识符等敏感数据是否有最小化、加密、留存和删除规则；
- redaction / contentscan 在递归 JSON、tool args 和**分块流边界**上是否仍正确，且不通过
  无界缓冲整个流来实现；`internal/sse` 的解析与写出是否保持有界；
- 自定义 endpoint、重定向、代理、DNS、IPv4/IPv6 和云元数据地址是否守住出网边界；
- 解析器、模板、命令、路径和序列化是否存在注入、遍历或资源放大；
- 安全失败是否 fail closed，且不会通过告警洪泛、磁盘耗尽等方式反噬可用性；
- 许可证、NOTICE、数据处理和第三方条款是否与实际依赖及功能一致。

### 7.5 数据、迁移、备份与恢复

- durable format 变化是否有明确版本、兼容矩阵和拒绝策略；
- 升级使用真实 populated 旧版本数据，而非只用新代码生成的 fixture；
- 迁移中断、重复执行、空间不足和损坏输入是否幂等或 fail closed；
- 备份 manifest 是否覆盖全部权威日志、密钥描述、派生状态和版本信息；
- 恢复后是否执行完整性验证、重放、关键查询和真实启动；
- 回滚边界是否写进发布说明，单向迁移不得伪装成可回滚；
- RPO/RTO、最大数据规模和恢复内存上界是否有测量依据。

#### pre-1.0.0 的重新初始化豁免

仓库政策（见 `CLAUDE.md`“Pre-1.0.0: fix in place, do not accumulate compatibility”）是：在版本
低于 `1.0.0` 期间不承诺兼容，durable schema 就地修改，操作者重新初始化自己的实例，而不是被迁移。
因此 **“本次变更要求重新初始化数据目录”是合法处置，不构成 NO-GO**，条件是三项全部成立：

1. **拒绝而非误读**：旧格式被 format version 检查明确拒绝，fail closed，不存在静默按新语义解释
   旧字节的路径；版本检查是可接受区间，不是精确相等（仓库已被精确相等咬过多次）。
2. **明写且可计划**：发布说明、升级文档和 CHANGELOG 明确写出“需要重新初始化数据目录”，
   以及会丢失什么、如何先备份。
3. **备份与恢复仍需真实演练**：即使不提供迁移，备份、校验、隔离目录恢复和从恢复结果启动
   仍必须有 E3 证据——重新初始化不豁免数据可取回性。

三项任一不成立，则回到第 10.2 节的硬门禁。进入 `1.0.0` 后本豁免自动失效，必须提供迁移或
明确的长期兼容承诺。

### 7.6 Provider、API 与兼容性

- 在写 decoder 前是否读取真实响应或权威规范，而不是只写理想化 fixture；
- 上游枚举回答“谁存在”，能力证据回答“能做什么”，两者是否保持分离；
- 未知或手填模型是否保持 unknown，不能从名称或 endpoint 虚构能力；
- 请求字段、响应、SSE、usage、错误 envelope、request ID 与官方 SDK 是否一致；
- 认证 header、host、path、地域、产品和凭据是否可能交叉使用；
- 新 Provider 分支是否污染共享 adapter 下的其他 Provider；
- 真实账户未验证时是否诚实标记，而非把 fake-provider 结果升级为真实兼容声明。

### 7.7 测试与质量证据

- 每项需求和不变量是否至少有一项能失败的验证；
- 测试是否会在实现被移除或错误时变红，而非只检查字符串/快照存在；
- 是否覆盖边界、拒绝、超时、取消、并发、重启、损坏和权限负向路径；
- mock 是否保留真实协议、故障和时序特征，还是屏蔽了核心风险；
- flaky、skip、TODO、被删除测试和缓存通过是否被显式记录；
- 测试结果是否绑定候选 SHA、环境、命令、退出码和日志；
- 发现的每个已确认缺陷是否新增了能防止复发的回归测试。

### 7.8 前端、交互与可访问性

- 核心用户旅程是否能从入口到结果闭环，包括空态、慢请求和错误恢复；
- 前端展示、筛选、权限和状态是否与服务端事实一致，服务端仍是最终权威；
- 危险操作是否有清晰影响、确认、处理中、成功和失败反馈；
- Light/Dark、中英文、窄屏、200% 缩放、键盘、焦点和语义标签是否可用；
- 未知成本、未知能力和部分数据是否显示 unknown/partial，而不是错误地显示为零；
- 浏览器前进后退、深链接、过期会话、重复提交和并发编辑是否可预测；
- 设计系统变化是否解决系统级原因，避免堆叠页面局部补丁。

### 7.9 性能、容量与可靠性

- 基线和候选是否在同机、同工具链、同 fixture、同参数下对比；
- 热路径延迟、吞吐、分配、锁竞争和 I/O 是否在预算内；
- 新 map、队列、缓存、日志、指标标签和重试是否有硬上限与清理策略；
- 恢复、启动、升级和大数据查询是否在目标规模下满足 RTO/SLO；
- 前端 bundle 或二进制体积异常增长是否有解释；
- 性能下降是否来自必要的正确性/安全成本，并被量化和接受；
- 长稳和容量结论是否区分短时实验、模拟环境与真实生产证据。

### 7.10 SRE、可观测性与运营

- 关键 SLI、错误预算、指标、日志和审计是否能回答“谁、何时、什么、影响多大”；
- 标签是否低基数、有界且不含秘密或上游原文；
- 告警是否有明确阈值、持续时间、严重度、Owner 和可执行 Runbook；
- Runbook 是否由非作者在隔离环境演练，包括回滚、恢复和 break-glass 撤权；
- doctor、health、readiness 是否检查真实依赖，不制造虚假绿色；
- 配置变更、密钥轮换、备份失败、磁盘容量和依赖退化是否可被发现；
- 值班、升级、支持和事故沟通责任是否明确。

### 7.11 供应链与发布工程

- 依赖变化、许可证、NOTICE、漏洞和作用域是否与锁文件一致；
- 干净环境能否构建，源码与生成 bundle 是否零漂移；
- 制品、容器、SBOM、checksum、provenance 和签名是否绑定同一 SHA；
- 外部使用者能否按文档独立验签，而不依赖内部上下文；
- CI 权限、secret、Environment 审批和发布身份是否最小化且职责分离；
- dry run 是否覆盖正式流程的主要图，未覆盖差异是否有人工前置检查；
- 版本号、CHANGELOG、文档、二进制和 release notes 是否一致。

### 7.12 文档、支持与变更管理

- README、用户指南、Operator Guide、API/配置参考、Runbook 是否同步；
- 升级、回滚、备份、已知限制和破坏性变化是否清晰；
- 错误信息是否可行动，支持人员能否从症状定位到检查步骤；
- 示例命令是否安全、可复制、使用明确占位符且不泄露秘密；
- 文档中的状态、版本、路径、测试名和截图是否仍真实存在；
- 面向用户的术语、i18n 与产品界面是否一致；
- 培训、公告、迁移支持和反馈渠道是否与影响范围匹配。

## 8. 证据标准

### 8.1 证据分级

E1–E4 的定义**直接沿用**
[`docs/verification/production-validation-plan.zh-CN.md` 第 2 节](../verification/production-validation-plan.zh-CN.md)，
本计划不另行定义，避免同一标签两套含义。本计划只补一个更低档的 E0：

| 等级 | 含义 | 可支持的结论 |
| --- | --- | --- |
| E0 声明 | 作者描述、计划或推断，无可重复材料（本计划补充） | 不能用于通过 |
| E1 | 文档、设计和静态检查 | 设计意图存在 |
| E2 | 单元、集成、契约和故障注入测试 | 仓库内实现满足契约 |
| E3 | 本机、容器或托管 CI 的端到端运行 | 可重复构建和集成 |
| E4 | 目标生产形态中的真实依赖、身份、网络和故障演练 | 生产准入证据 |

注意 E2/E3 的边界按上表：**普通 CI 的端到端运行属于 E3，不是 E2**；而单机跑的单元、契约和
故障注入测试属于 E2。真实二进制在本机完成的启动、升级、备份恢复和浏览器旅程属于 E3；只有目标
生产形态中的真实 Provider、真实 KMS、真实网络与真实故障演练才是 E4。

低等级不能冒充高等级。需要 E4 但尚无授权或环境时，结论必须为 `UNVERIFIED` 或降级承诺。
若上述被引用文档修订了阶梯定义，以它为准，本表随之更新。

### 8.2 每份证据的最小元数据

- 证据 ID、生成时间、执行人；
- 完整候选 SHA、分支/tag、工作区状态；
- 操作系统、架构、工具链和关键依赖版本；
- 完整命令、输入/fixture、环境变量类别（秘密值须脱敏）；
- 起止时间、退出码、原始日志或制品路径；
- 预期结果、实际结果、限制和复现方法；
- 对二进制、数据集和外部文件记录摘要或不可变标识。

## 9. 发现项管理与严重度

### 9.1 发现编号与模板

finding ID 必须**跨里程碑唯一**，形如 `<里程碑标识>-F-<两位序号>`，例如 `260918-M12-F-03`；
里程碑标识与证据目录名一致。序号一经分配不再复用，即使该发现最终被 `REFUTED`。既有评审的
`PHIL-A04` 这类前缀式编号保持原样，不回溯改名。

每个 P0/P1 发现必须绑定一个 GitHub Issue（标题以 finding ID 开头），整改 PR 在描述中引用该
Issue；P2/P3 若被延后接受，同样需要 Issue 承载 Owner 与到期时间。没有 Issue 的延后等同于
无期限 TODO，按第 9.3 节禁止。

```markdown
## <里程碑标识>-F-<序号> · <简短标题>

- 角色：R<编号>
- 严重度：P0 / P1 / P2 / P3
- 状态：OPEN / IN REVIEW / REMEDIATED / ACCEPTED / CLOSED
- 证据等级：E1 / E2 / E3 / E4
- 影响面：<用户/账务/安全/数据/兼容/运维/发布>
- 入口与前置条件：<如何到达>
- 观察事实：<文件:行号、命令、日志、截图或响应>
- 预期行为：<契约或不变量>
- 实际行为：<可重复结果>
- 最坏可信影响：<不要用纯理论极值夸大>
- 建议修复：<优先给最小正确修复>
- 建议回归：<会因缺陷复发而失败的测试>
- Owner / 截止时间：<责任人 / 日期>
- 跟踪 Issue：<GitHub Issue 链接；P0/P1 必填>
- 对抗裁决：CONFIRMED / PARTIAL / REFUTED / UNVERIFIED
```

### 9.2 严重度定义

| 级别 | 定义 | 决策影响 | 关闭要求 |
| --- | --- | --- | --- |
| P0 致命 | 可造成广泛数据/资金错误、关键越权、秘密泄漏、不可恢复损坏或发布链失守 | 立即停止，强制 NO-GO | 修复、独立复现、回归、全影响面复验 |
| P1 高 | 核心用户旅程失败、账务/安全/迁移重大缺陷、无安全回滚或高概率事故 | 阻断里程碑/发布 | 修复并由非作者复核 |
| P2 中 | 有界功能缺陷、可观测/运维/兼容缺口，有可靠补偿控制 | 可条件放行 | Owner、期限、风险接受与跟踪 Issue |
| P3 低 | 文案、一致性、维护性或低风险优化 | 不阻断 | 排期或明确不做 |

严重度由“影响 × 可达性 × 暴露范围 × 可恢复性”共同决定。未知可达性不得直接夸大为 P0，
但涉及关键边界且缺少证据时，也不得自动降为通过。

### 9.3 生命周期

`OPEN → TRIAGED → IN REMEDIATION → READY FOR VERIFY → CLOSED`

另有两个终态：

- `ACCEPTED`：由具备权限的风险接受人批准，包含补偿控制和到期时间；
- `REFUTED`：经对抗复核证明前提不成立，并保留复核证据。

禁止以 `WONTFIX`、无截止时间的 TODO 或会议口头同意代替风险接受。

## 10. 评分卡与硬门禁

### 10.1 评分方法

每个域按 0–5 分评分：

- `5`：范围完整，E3/E4 证据充分，无重要缺口；
- `4`：主要目标完成，存在少量有界且已接受的 P2/P3；
- `3`：基本可用，但证据或运营闭环不完整；
- `2`：多项关键条件未证明，存在明显返工；
- `1`：核心目标大多未完成或结论主要依赖声明；
- `0`：未评审、不可用或已证明违反核心约束。

| 评分域 | 权重 |
| --- | ---: |
| 产品价值与范围 | 8% |
| 架构与领域模型 | 10% |
| 核心逻辑与账务 | 14% |
| 安全、隐私与合规 | 14% |
| 数据、迁移与恢复 | 10% |
| 测试与质量证据 | 10% |
| Provider/API 兼容性 | 7% |
| 前端、交互与可访问性 | 6% |
| 性能与容量 | 7% |
| SRE 与可观测性 | 6% |
| 供应链与发布 | 5% |
| 文档、支持与变更管理 | 3% |
| **合计** | **100%** |

#### 覆盖率、不适用域与 `UNVERIFIED`

沿用 260913 方案的做法，避免用重新分配权重的方式把缺口稀释掉：

- **不适用的域**必须说明理由并记为 `N/A`，其权重从分母中扣除；不得记满分，也不得把权重
  摊给其余域（摊权重会让“没评审”看起来像“评审通过”）。
- **评分覆盖率 = 已给出结论的域权重之和 ÷ 100%（不含 `N/A` 扣除部分）**。覆盖率低于 **80%**
  时不输出数值总分，只输出阶段性诊断与未覆盖清单，结论最高为 `NOT READY`。
- **`UNVERIFIED` 的域最高记 3 分**：证据缺失不能靠“看起来没问题”补齐。若该域属于下方的关键
  域，`UNVERIFIED` 直接阻断 `GO`。

#### 关键域

以下三个域为**关键域**，第 10.3 节的 `GO` 要求它们各自 ≥ 4：

1. 核心逻辑与账务；
2. 安全、隐私与合规；
3. 数据、迁移与恢复。

若某次里程碑判定某个关键域 `N/A`（例如纯文档里程碑不触及账务），必须在决策记录中写明理由，
并由决策人确认——关键域的 `N/A` 是一次显式决定，不是默认值。

### 10.2 硬门禁

出现下列任一情况，综合得分无论多高都不得 `GO`：

- 存在未关闭的 P0 或 P1；
- 候选 SHA 不唯一，或最终证据来自不同候选且未复验；
- 账务不正确、可绕过预算、未知结果被自动退款或出现第二账务权威；
- 认证/授权 fail-open、跨租户访问、密钥/秘密泄漏；
- 既有数据可能**静默误读**、不可恢复，或格式变化没有安全拒绝路径；
  （pre-1.0.0 下“要求重新初始化数据目录”不命中本条，前提是满足第 7.5 节豁免的三项条件）
- 重试、队列、缓存、日志、指标基数或资源增长无上界；
- Provider 能力静默丢弃/虚构，或在响应开始后跨 Provider 回退；
- 关键升级、恢复、回滚或制品验证从未由非作者走通；
- 发布/生产结论所需的完整门禁、SBOM、签名、演练或授权证据缺失；
- 已知事实与对外文档、版本状态或“production-ready”声明相冲突。

### 10.3 决策规则

| 结论 | 必须满足 |
| --- | --- |
| `GO` | 无硬门禁；P0/P1 为零；覆盖率 ≥ 80%；总分 ≥ 85；三个关键域均 ≥ 4；无过期风险接受 |
| `CONDITIONAL GO` | 无硬门禁；覆盖率 ≥ 80%；总分 ≥ 75；仅剩有补偿控制、Owner 和期限的 P2/证据缺口；决策人明确接受 |
| `NO-GO` | 命中任一硬门禁、存在 P0/P1、总分 < 75，或关键域证据不足 |
| `NOT READY` | 范围、候选、角色、环境或基础材料尚未满足准入条件，或评分覆盖率 < 80% |

85 / 75 是**约定阈值，不是测量得出的常数**。决策人可按里程碑类别（例如纯文档、纯前端、
含账务或密钥面）在 S0 冻结时调整并把理由写进 `review-plan.md`；一旦冻结，评审期内不得为了
让候选通过而下调。硬门禁不可调整。

条件放行必须写清“允许进入哪个阶段”，不能用它模糊授权正式发布或生产部署。

### 10.4 裁决词汇与既有文档的映射

260913 的设计哲学评估使用另一套终态词汇。同一候选被两套流程评审时，按下表对齐，报告中
不得混用：

| 本计划 | 260913 设计哲学评估 | 含义 |
| --- | --- | --- |
| `GO` | `HEALTHY`（无红线、覆盖率达标） | 允许进入下一阶段 |
| `CONDITIONAL GO` | `REMEDIATION REQUIRED`（有界、有 Owner 与期限） | 带条件放行 |
| `NO-GO` | `UNSAFE` 或命中红线的 `REMEDIATION REQUIRED` | 阻断 |
| `NOT READY` | 覆盖率不足，仅输出阶段性诊断 | 尚不能裁决 |

对抗裁决的四值（`CONFIRMED` / `PARTIAL` / `REFUTED` / `UNVERIFIED`）两份文档一致，直接通用。

## 11. 会议设计

### 11.1 启动会（45–60 分钟）

1. 目标、非目标和目标结论；
2. 候选范围与变更地图；
3. 成功标准、硬门禁和证据等级；
4. 角色分工、独立性和外部授权；
5. 日程、沟通渠道、升级与范围变更规则。

### 11.2 发现汇总会（60–90 分钟）

只做事实去重、严重度初判和复核分派，不投票决定技术事实。多个角色独立发现同一问题时标记
“交叉证实”，但仍需验证完整可达路径。

### 11.3 GO/NO-GO 会（45–60 分钟）

建议议程：

- 5 分钟：候选 SHA 与范围是否仍冻结；
- 10 分钟：硬门禁逐项确认；
- 15 分钟：P0/P1 裁决及 P2 风险接受；
- 10 分钟：评分、未验证项和残余风险；
- 10 分钟：决策、Owner、回滚/观察窗口和签字。

会议结束时只能产生一个明确结论；“基本可以”“原则通过”“之后再补”不是有效裁决。

## 14. 分层裁剪、人员与工作量

### 14.1 三个分层

全套 S0–S7 只适用于最高分层。**默认从 Tier-1 起判，按触发条件上浮**；分层在 S0 冻结时确定并
写进 `review-plan.md`。这与 `review/README.md` 的“分层选择”和 `AGENTS.md` 的“最小充分验证”
是同一条原则：验证深度由影响面决定，不由流程完整性决定。

| | Tier-0 轻量 | Tier-1 标准 | Tier-2 完整 |
| --- | --- | --- | --- |
| 适用 | 文档、注释、i18n 文案、纯 CSS/视觉、不改行为的重构 | 常规功能、前端页面、非关键路径改动 | 触发第 2.2 节任一触发矩阵项 |
| 阶段 | S0（精简）+ S2 + S6 | S0 + S1 + S2 + S4 + S5 + S6 | S0–S7 全部 |
| 角色 | 1 个相关角色 + 1 名复核人 | README 核心档中相关的 3–5 个 + 对抗评审 | 全角色 + ≥2 名对抗评审 + 证据管理员 |
| 评分卡 | 不出总分，只记结论与证据 | 出总分，可将明显不适用的域记 `N/A` | 出总分，覆盖率 ≥ 80% |
| 实机证据 | 不要求 | 受影响面的 E3 | 完整 E3，外部主张需 E4 |
| 产物 | `review-plan.md` + `findings.md` | 加 `scope-and-baseline.md`、`adversarial-verdicts.md`、`scorecard.md`、`progress.md` | 第 12 节全套 |
| 参考投入 | 0.5 人日以内 | 2–5 人日 | 8–15+ 人日 |

**强制上浮**：无论初判为哪一层，命中下列任一项即至少 Tier-2——账务/Ledger、认证授权/密钥、
durable format、备份恢复、出网边界、发布链与制品、Provider 能力面。降层需要决策人书面同意
并记录理由，不能因排期压力降层。

**不可裁剪项**（任何分层都必须做）：候选 SHA 冻结、第 10.2 节硬门禁逐项确认、P0/P1 的独立
复核、最终候选上跑一次完整门禁。

### 14.2 人员配置参考

| 里程碑规模 | 推荐配置 | 参考投入 |
| --- | --- | --- |
| 小型、低风险、无持久格式/安全面 | Owner + 2–3 个相关角色 + 1 名复核人 | 1–2 人日 |
| 中型、跨后端与前端或含兼容变化 | 主持人 + 5–8 个角色 + 独立对抗评审 | 4–8 人日 |
| 大型、含账务/安全/迁移/发布/生产 | 全角色覆盖，至少 2 名对抗评审，专门证据管理员 | 8–15+ 人日 |

角色可由 agent 承担，条件见第 4.5 节。工作量不包含缺陷整改、等待真实账户/生产窗口、
24 小时以上长稳或外部合规审批。

## 15. 完成定义

只有以下条件全部成立，评审任务本身才算完成：

- [ ] 候选范围、目标结论、采用的分层和全部角色覆盖已记录；
- [ ] 每个适用域都有明确结论和证据等级；
- [ ] 所有 P0/P1 已关闭并完成独立复验；
- [ ] P2/P3 已修复或有正式风险接受、Owner 和期限；
- [ ] 所有对抗裁决均有复现路径，`UNVERIFIED` 未被误记为通过，且评分覆盖率满足第 10.1 节门槛；
- [ ] 若本次要求重新初始化数据目录，第 7.5 节豁免的三项条件均有证据；
- [ ] 最终门禁绑定唯一候选 SHA，且无后续影响结果的代码变化；
- [ ] 用户文档、运维文档、已知限制和发布说明与实现一致；
- [ ] 决策人给出明确裁决，条件与授权边界无歧义；
- [ ] 原始证据、评分、签署和会议决议已归档且可由非作者读取；
- [ ] 若已部署，完成观察窗口与复盘，并将流程逃逸项转为可执行改进。

本计划的最终目的不是制造更多会议或文档，而是让里程碑的价值、工程事实、风险和授权边界在
进入下一阶段前被同一套可重复证据说明清楚。
