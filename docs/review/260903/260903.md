## 一、结论

**代码这一侧可以发,发布契约这一侧不能发。**

工程面是这几轮里最好的一次:零新增依赖(两侧 `go list -m all` 都是 57),约 +12k 行
Go 只换来 1.48% 的二进制增长,fuzz 清单与代码一一对应且带防改名守卫,ledger 分代封存
不删除任何字节、段清单缺一代就拒绝启动,记账权威与两个派生物同时改动而派生物没有变成
第二真相 —— 最后这一条是本轮最大的风险,核心逻辑角色逐行核对后确认它没有发生,并列出
了守护它的测试。

阻断发布的四条,没有一条在业务逻辑里:

1. **发布管线与它的手册不是同一个东西。** `docs/guides/releasing.md` 承诺的
   Environment 审批、`release-governance` 前置作业、annotated tag 签名校验、M11 证据包
   校验,在 `.github/workflows/release.yml` 里**一条都不存在**(六个关键词命中数全部
   为 0,主持方实测)。按手册发版的人会等一个永不出现的审批,同时准备一份没人校验的
   证据包;而 tag 一推,产物直接发出去。
2. **CHANGELOG 覆盖了六个提交里的 2.5 个。** 缺 Kimi(#253)全部、延迟取回(#258)
   全部、留存后续项(#257)全部。更要紧的是**元数据 schema 从 33 跳到 35 一字未提**,
   且没有 `### Operator impact` 段 —— 而 v0.5.0 的那一段正是 260901 **P16** 的全部缓解
   措施。不补,缓解就断。
3. **升级路径上有一条会静默关闭回滚的命令。** 主持方实测:对一个 v0.5.0 的数据目录跑
   `halro ledger verify`,命令**以失败退出码结束**,同时已经把 schema 迁到 35。运维读到
   的是「验证失败,先别升级」,实际是「已经迁完了,回不去了」。这是 260901 P16 的原样
   复发,且本轮的迁移 35 会删除 usage checkpoint 与 rollup,后果比 v0.5.0 时代那次只加
   字段的迁移重得多。
4. **一个配置项的合法范围收紧,会导致拒启。** `usage.retention_days` 下限从 1 提到 7,
   写了 1–6 的实例换二进制后直接起不来。

失败诊断这一整个特性还有一处自我矛盾:它把「一个计数」变成「一个解释」,而在
「回退后成功、随后渲染失败」这条路径上,给出的解释指向**一次成功的上游调用**
(V1,已实测复现)。本轮刚在日志侧修掉同一个缺陷,读侧没跟上 —— 而且结构上不可能
跟上,因为日志侧的修法落在进程内内存,读侧从 ledger 重建,ledger 里没有区分这两种
`provider_error` 的标记。

## 六、这一轮的方法学观察

**运行时证据产出了两条 P1,而它们不是读代码能得出的。** A4(`ledger verify` 静默迁移)
和 B3(`retention_days` 拒启)都来自真二进制跑真数据目录。七个角色里有两个独立读到了
迁移代码,但「跑一条只读语义的命令会关闭回滚路径」这件事,要把命令真的跑一遍才会发现。

**对抗验证第三次证明了它的价值,而且这次的价值在两个方向上。** 一条头号安全发现被
**证伪**(V4:project 级授权是既定边界);一条三重交叉证实的发现被**下调并说得更准**
(V2:找到把行为锁成契约的测试)。如果没有这一步,前者会作为漏洞进入发布评估,后者
会以错误的严重度和错误的性质描述被记录。

**「注释声称的守卫不存在」在本轮出现了两次,形状相同。** 密封孤儿的清扫、
un-withholding 的测试守卫 —— 都是代码里写着「这件事由 X 拦住」,而 X 不存在或不做
那件事。这类说法比缺失更危险:缺失会被下一个人发现,而一句自信的注释会让他不去看。
建议把「注释里点名的守卫必须存在」变成一条可机械检查的规则(注释里出现
`Test[A-Z]\w+` 时,该函数必须在仓库中存在),这是 grep 就能做到的。

主持方已经跑了一遍这条规则。全仓非测试代码的注释里点名了 1834 个疑似测试名,实际
存在 1821 个;剔除测试辅助类型名(`TestAdapter`、`TestRuntime` 之类)的误报后,**三处**
真正踩中,而且分成两种性质:

| 注释点名 | 位置 | 实际情况 |
|---|---|---|
| `TestEveryProfileIsRegistered` | `internal/compatibility/provider_fields.go:38` | 守卫在,名字漂了 —— 真实函数是 `TestEveryProfileRegistersItsOwnFieldRules` |
| `TestStreamMatchesUnaryRedaction` | `internal/redaction/engine.go:478` | 守卫疑似在,名字漂了 —— 最近似的是 `TestRollingStreamMasksMatchSplitAcrossEveryChunkAndFlushesBeforeFinish` |
| `TestNoEndpointIsServedByATargetThatReasonsUnasked` | `internal/modelcatalog/builtin.go:468,552`、`catalog.go:262`、`compatibility/reasoning_reachability.go:25` + 三处文档 | **守卫不存在**。实测翻转确认(见第四节「说法与实现不符」第 2 条) |

前两种是无害的名字漂移,一次改名就修好,而且正是这条规则最擅长抓的东西。第三种是本轮
发现的那一条 —— 一个从未存在过的守卫被四处代码注释和三处文档反复引用。这条规则的成本
是一次 grep,收益是让第三种不可能再出现。
