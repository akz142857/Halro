# 260903 评审方案

发布前评审,目标版本 v0.6.0。基线 `v0.5.0` → `ff12842`。

## 为什么做这一轮

`docs/review/README.md` 的选择指南把「发版前」定为**可用性 + API 兼容性 + 供应链 + 数据迁移**四个角色。本轮在此之上加了三个,理由是改动性质而非规模:

- **安全威胁建模**:这一轮第一次让调用方写的字节落盘——`gateway.failure_capture`
  与延迟取回。在此之前 Halro 持久化的全部是它自己产生的元数据,「prompt 与响应体
  不落盘」是一条无例外的规则,现在有了两个例外,每个例外都带密封、绑定、限量、
  过期、审计五组约束。新的信任边界要用攻击者视角看一遍。
- **核心逻辑**:`internal/ledger` +2043 与 `internal/usage` +2512 同时改动,即记账
  权威与它的两个可重建派生物在同一轮里一起动。这正是派生物悄悄变成第二真相的时机。
- **测试盲区**:上一轮(260901)的经验是,已知高危缺陷之所以存活,是因为守护它的
  测试不存在。本轮新增三个特性、六个新持久面,需要一份盲区地图而不是覆盖率数字。

「性能与容量」按 README 的建议**未跑**:它要求压测环境,而 260901 的 P14 已记录
`performance-baseline.md` 对路由解析差 12 倍、不能再作回归判据。在那份基线被修正
之前,任何性能数字都无从比较——这一点写进了 `runtime-evidence.md` 的「未能取得的
证据」,而不是留白。

## 执行方式

七个发现型角色**并行、互不知情**,各自独立通读,共同起点只有 `range-map.md`
(范围、改动量、四个由改动决定的高危区、上一轮仍开着的条目)。任何角色都不知道
别人在看什么,交叉证实因此是独立事件而非互相印证。

角色与产出:

| 角色 | 覆盖 |
|---|---|
| 安全威胁建模 | 两个新留存面、新北向端点族的授权、新 Admin 端点、日志新面、Kimi 平台 |
| 核心逻辑 | 延迟取回的记账时序、ledger/usage 同时改动、失败诊断口径、有界化 |
| API 兼容性契约 | 四条新端点 ↔ manifest ↔ 契约文档、北向端点清单自查、Kimi 字段规则、新错误码 |
| 测试盲区 | 每个新源文件的守护测试、四类必测路径(负向/并发/崩溃恢复/回滚) |
| 数据迁移与升级 | v0.5.0 数据目录升级后会怎样、回滚、配置兼容、发布说明需要写什么 |
| 可用性 + 供应链 | 配置项文档、CHANGELOG 对照、`make help`、依赖、fuzz 清单、发布管线 |
| BUG 排查 | 高危区逐文件,只报有代码证据且写得出触发场景的 |

主持方(本文件作者)另做一件角色做不了的事:**运行时证据**。真二进制、真数据目录、
真升级与回滚,结论在 `runtime-evidence.md`。这一步的必要性由 CLAUDE.md 的「Verify,
never assume」规定,而它在本轮直接产出了两条 P1——都不是读代码能得出的。

## 对抗验证

README 的方法沉淀要求:发现型角色产出后,对最严重的若干条**各派一个独立证伪角色**,
默认 finding 为错,要求在代码里复现完整路径或找出拦截防御,裁决
CONFIRMED / REFUTED / PARTIAL。

本轮送去证伪的五条,以及为什么是它们:

| # | finding | 为什么需要证伪 |
|---|---|---|
| 1 | 同 project 内任意 Gateway Key 可取回/取消/删除他人的延迟结果 | 取决于「这是设计选择还是疏忽」,而 ADR 0024 通篇未声明这条边界 |
| 2 | 失败列表把成功那次尝试的 `provider_request_id` 展示给运维 | 单一角色提出、未经交叉,且断言了一个具体时序 |
| 3 | 密封孤儿对象永不清扫 | 三角色交叉证实,正因如此更要有人专门去找「其实存在的清扫路径」 |
| 4 | `read_only` 管理员可读客户 prompt | 断言的是「设计含义漂移」,需要有人验证本轮之前是否真的没有先例 |
| 5 | 全局 FIFO + 硬编码 4 worker 可跨项目饿死 | 纯代码事实,由主持方直接核验而非派角色 |

交叉证实提高的是「代码可疑」的置信度,不等于「这条路径真能走到」。这一步的价值在
260805 与 260901 两轮都被验证过:最严重的几条 finding 没有一条原样成立。
