# Halro 全面工程评审计划（2026-09-05）

> 状态：2026-09-05 用户授权的 S0–S4 评审已完成；见 [评审报告](review-report.md) 与 [完成核对](completion-audit.md)。结论带明确证据限制，S5 修复未开始。本文原有风险、场景和检查项本身不是已确认缺陷，以 findings 与裁决为准。
> 制定基线：`main`，`381743f6613607dc256828f4776b52af8bdd232c`；制定时工作区干净。
> 评审对象：当前 Halro 全仓实现及其构建、部署、运维与使用契约。官网只检查与本仓承诺的一致性，不在本轮修改范围内。

## 1. 目标与决策用途

本轮从架构设计、代码逻辑、BUG、安全、数据可靠性、API、前端和工程交付八个方面，回答以下问题：

1. 当前实现是否符合“小型、可靠、可嵌入、协议中立的 AI 基础设施”定位？单进程、单写者和最少运行依赖的边界是否被实际代码维持？
2. 请求从认证、策略判断、上游执行到计费、留存和恢复，是否存在可到达的错误路径？
3. 故障、取消、重启、并发与恶意输入下，安全边界和账务不变量是否仍成立？
4. 文档、API 契约、控制台和实际二进制是否描述同一产品？
5. 哪些问题应阻断后续发布，哪些进入有责任人与验收条件的整改队列？

交付物必须允许未参与评审的人复现结论。不得用综合评分、测试总数或行覆盖率代替安全与正确性判断；不得声称“没有 BUG”，只能报告范围、发现和证据局限。

### 2.3 边界

- 初始授权是制定计划；2026-09-05 用户追加授权执行 S0–S4 评审。实现修复与发布仍不在本轮范围内。
- 后续运行默认使用隔离数据目录、测试凭据和本地可控上游；不对现有业务数据执行 reset、迁移、故障注入或恢复。
- 计费真实 Provider smoke 必须得到用户明确请求；无真实响应样本时，将适配器真实性列为未验证，不能用自制 fixture 替代上游证据。
- Realtime 属架构设计范围，HA 属提案范围；不得把尚未实现的能力按已上线功能验收，也不得把当前单写者设计本身当成 BUG。
- 真实 KMS、云部署、官网与外部观测平台验证若缺环境，记录阻塞与所需条件；本地测试通过不等于生产验收。

## 3. 组织方式与阶段安排

采用发现、证伪、裁决分离的方式。可由多人或独立 Agent 执行；人员不足则串行覆盖，并明确“未取得独立复核”，不可声称多角色独立验证。

| 阶段 | 建议工作量 | 工作内容 | 退出条件 |
| --- | --- | --- | --- |
| S0 基线与范围冻结 | 0.5–1 人日 | SHA、工作区、工具链、模块/路由/数据清单、历史未结问题 | 全部生产模块有归属；范围和环境可复现 |
| S1 架构与威胁建模 | 1–2 人日 | 依赖图、信任边界、数据权威、状态机、不变量 | 高风险链路均有图或时序表及验证入口 |
| S2 独立专项评审 | 4–7 人日 | 按下表分工进行源码与定向实验 | 每项检查有状态、证据或阻塞原因 |
| S3 对抗验证与端到端实验 | 2–3 人日 | 证伪严重问题、崩溃恢复、浏览器和 SDK 验证 | 所有候选 P0/P1 有裁决或明确待验证项 |
| S4 汇总与整改排期 | 0.5–1 人日 | 去重、定级、盲区图、整改责任与发布建议 | 报告可复现；每项未结风险有处置 |
| S5 修复后复验（另行安排） | 按确认缺陷估算 | 回归用例、定向验证、必要最终门禁 | 达到第 9 节关闭条件 |

S0–S4 合计约 8–14 人日，3–4 人并行可按 4–6 个工作日排期；依赖环境准备、长稳实验和发现数量调整，不作为硬性完成承诺。S1 后可并行 S2；S3 依赖候选发现，最终裁决必须在证据完成后进行。

## 4. 架构与关键不变量

### 4.1 架构设计检查

- 画出入口 → 认证/授权 → 治理 → 上游 → 结算/审计/留存的实际调用图，以及 Admin 配置变更到运行快照的路径。
- 检查包依赖方向、领域层是否依赖传输细节、`internal/app` 是否承担过多业务逻辑、不同协议是否复制策略实现。
- 检查新抽象是否有实际调用方；识别循环依赖、逃逸的全局状态、隐式初始化、死代码和多份业务规则。
- 检查一致性边界和事务边界是否重合；画出 bbolt、Ledger、Audit、Usage、Provider 对象之间的写入与恢复次序。
- 检查取消、超时、重载、停止时的所有权：谁创建 worker，谁关闭，谁释放额度，谁完成最终结算。
- 检查后续扩展是否仍保持核心小而可靠；Agent 工作流、记忆、Skill 执行等应用职责若进入核心，必须说明必要性与隔离方案。
- 对架构建议给出当前代价、最小改善、兼容性影响和验证方式，不以文件长度或个人风格单独判定缺陷。

### 4.2 必须逐项证明的不变量

| ID | 不变量/审查命题 | 最低证据 |
| --- | --- | --- |
| INV-01 | 同一数据目录只能有一个写者，初始化、诊断、备份与恢复不绕过锁 | 双进程竞争与离线命令行为 |
| INV-02 | Ledger 是账务权威，未经认证的输入不能更新持久化派生物 | 篡改/截断/缺失输入，重建前后摘要对比 |
| INV-03 | 每次 attempt 的资金预留、确认、释放、未知结果处理符合契约，不能重复或遗漏结算 | 成功、取消、未知结果、重试与重启的余额/事件对照 |
| INV-04 | 无授权的调用不能通过替代端点、资源 ID 或缓存跨越项目边界 | 双项目与同项目不同 Key、管理员角色矩阵 |
| INV-05 | 模型存在性与能力证据分离；手填 ID 不得获得虚构的 `provider_metadata` 能力 | 枚举、手填、unknown、过期证据、刷新失败用例 |
| INV-06 | 上游结果不确定时，重试/回退遵循既定策略，不能放大重复执行风险 | 发送前失败、发送后断链、首 token 前后失败的分界证据 |
| INV-07 | 留存对象受访问、密封、配额、过期和删除约束；崩溃不产生永久孤儿 | 写入/登记间中断，清扫与重启验证 |
| INV-08 | 限流、并发、队列、缓存、日志及流缓冲在压力下有边界 | 上限、超限行为、释放和跨项目公平性实验 |
| INV-09 | 密钥轮换、恢复与升级失败后仍可解释并恢复，不静默接受损坏状态 | 阶段中断矩阵、完整快照恢复和错误退出证据 |
| INV-10 | UI、API、路由注册和 manifest 对功能状态与权限含义一致 | 合约对照与实际浏览器旅程 |

若不变量存在合法例外，应先引用契约并明确边界，再设计测试；未知结果的保守结算不能仅因“用户未收到回答”被误报为重复收费。

## 5. 专项审查清单

### 5.1 代码逻辑与 BUG

- 检查 nil/空集合、数值溢出、负值、金额精度、时间边界、时区和跨日定价；明确错误码与最终业务结果。
- 检查锁顺序、读写竞争、共享 map、原子操作、事务内回调、goroutine/文件描述符/HTTP body 泄漏。
- 检查 context 传播、取消与结算脱钩、重复回调、幂等键冲突及异常清理；不同项目相同幂等键应按契约隔离。
- 检查熔断 half-open、fallback 候选耗尽、权限过滤与能力过滤的次序，避免不合规请求进入上游。
- 检查 deferred response 的提交、排队、执行、取消、完成、过期与删除竞态；审查 Files/Batches 的本地与上游对象一致性。
- 检查定价快照固定、输入/输出/cache/reasoning usage 映射；总请求与各次 attempt 的展示、成本和失败归因保持一致。

### 5.2 安全与隐私

- 建立匿名、Gateway Key、不同 Project、Admin 各角色与敏感操作的允许/拒绝矩阵，包括 step-up/MFA、会话过期、撤销、降权。
- 检查 SSRF、DNS rebinding、重定向、代理、IPv4/IPv6、本机与云元数据地址；以本地可控目标验证，避免触达真实内网服务。
- 检查配置导入、路径/文件名、上传、归档恢复、日志注入、HTML/Markdown 渲染及浏览器跨站请求边界。
- 检查主密钥/KMS/备份密钥的用途分离、轮换中断、错误密钥、认证标签损坏与权限；证据中不得包含凭据或真实客户正文。
- 检查 Token Guard 和流式脱敏跨 chunk、UTF-8、多字节边界、超长输入、异常上游格式与策略删除/禁用时的行为。
- 检查审计完整性失败是否按契约拒绝操作，以及匿名洪泛能否耗尽资源导致服务不可用。

### 5.3 API、Provider 与兼容性

- 从实际路由注册生成端点清单，与 manifest、README、SDK 用例逐项对照；记录未服务和实验性能力。
- 检查 OpenAI/Anthropic 请求校验、错误 envelope、SSE 终止、工具调用、usage、签名 Thinking、流取消和未知字段策略。
- 覆盖每个已启用 Profile 的模型/部署标识、版本、认证、可支持操作及限制，禁止以一个 Profile 的通过代表整个 Provider。
- 枚举使用上游列表；catalog 只补能力。先检查已有真实响应证据，再评估 decoder；没有样本则列证据缺口。
- 检查超时、鉴权失败、配额、地域不可用不会错误永久标记为 unsupported；证据来源、时间与失效规则应可解释。
- 本地 SDK 对照验证传输与序列化；真实 Provider 兼容性另列，不以本地 mock 结果替代。

### 5.4 数据可靠性、升级与灾备

- 对预留、WAL 追加、同步、结算、派生更新和对象登记之间的中断点建立表格；逐项验证重启后结果。
- 检查 Ledger 缺失、截断、认证失败、checkpoint 不可信、重放取消、磁盘满、只读目录、写入失败。
- 用隔离快照验证旧版本升级、新版本启动失败后的处置和恢复；明确不支持的降级，不能把“能启动”当成数据兼容。
- 验证数据库、Ledger、Audit、Usage、对象为同一快照；备份 key 和 master key 缺失/错误时应明确失败。
- 分别测量恢复时间（RTO）和可丢失数据窗口（RPO）；对照事先声明的持久化契约，无目标则先建立基线。

### 5.5 前端、交互与可访问性

至少走完以下真实浏览器旅程：初始化/登录 → Provider 创建与刷新 → Deployment 能力确认 → Project 策略与 Gateway Key → 调用 → Usage/失败诊断 → 禁用/撤销后再次调用。

同时覆盖 MFA、权限降级、密钥轮换、备份指引、异步结果取消/删除，以及空列表、慢网络、错误与过期会话。

- 检查缓存失效、重复提交、后台轮询、切换项目后的旧数据、表单服务端错误与危险操作确认。
- 检查前端显示的价格、单位、时区、项目归属、能力状态和后端事实一致。
- 检查键盘可达、焦点返回、标签、对比度、缩放和窄屏布局，以及 i18n 缺失。
- 页面级测试证明行为契约，真实浏览器证明完整旅程；静态截图不能证明 API、权限或提交成功。

### 5.6 性能、观测与交付

- 区分纯路由、持久化写入、并发流式和异步队列负载；记录吞吐、p50/p95/p99、错误率、分配、RSS、goroutine、FD、磁盘与队列长度。
- 先固定硬件、系统、工具链、配置、数据规模、预热和负载；同机重复比较，报告方差和原始数据。默认以可控上游测网关开销。
- 长稳实验建议先运行 30 分钟冒烟，再按资源安排 2–4 小时；不以短实验宣称长期稳定。资源回收和公平性须有时序证据。
- 对日志 → 指标 → 告警 → dead-man → runbook 做一次故障演练；检查标签基数、敏感信息、失败归因和无流量时行为。
- 检查依赖锁定、漏洞与许可证、CI 权限、Actions 固定版本、SBOM、签名验证、构建版本注入、容器用户与持久卷布局。
- 核对单实例部署约束、升级/回滚指引和内嵌前端生成链路；本轮不重新设计 HA，也不自动发布产物。

## 6. 验证矩阵与测试执行规则

每条高风险链路至少覆盖成功、拒绝、边界、超时/取消、并发、重启恢复中适用的场景；不适用必须说明原因。

| 场景组 | 必测组合 | 判定依据 |
| --- | --- | --- |
| 路由与策略 | 禁用 Key/Project、未知能力、错误 Profile、fallback 无可用目标 | 无违规出站，错误稳定，状态无脏写 |
| 执行与结算 | 发送前失败、发送后未知、流中断、重复完成、进程终止 | attempt、Ledger 与预算符合 INV-03/06 |
| 授权与留存 | 跨项目 ID、同项目不同 Key、降权、过期、取消与完成竞争 | 已声明授权边界成立，无超期可读或重复副作用 |
| 数据与恢复 | 缺段、截断、篡改、错误 key、磁盘失败、双进程 | 按契约拒绝或恢复，派生物不污染 |
| 控制台 | 创建→调用→诊断→撤销；网络失败与重新登录 | UI 与服务端状态一致，失败可恢复 |

### 6.1 命令策略

执行者先发现实际测试名和依赖条件，以下为计划命令，不表示已经运行：

```bash
# 全面评审集成基线：S0 或 S3 选一个阶段执行一次并共享证据。

```

前端全面交接时在 `web/` 执行一次 `npm run typecheck`、`npm test`、`npm run build`；仓库根目录核对 `git diff --exit-code -- internal/webui/dist`。评审已有提交时重建应无漂移；后续修复前端时，生成 bundle 与源码进入同一提交，先核对差异再暂存，暂存后重建验证漂移。不手工合并生成产物。

- 迭代中先运行受影响测试，再按需要扩大；CSS/文案只做对应视觉检查，设计系统/样式使用 `src/design-system.test.ts`。
- 不默认执行 `make check`：它包含全仓 race。当前策略要求按并发影响范围选择 race；既有 CI 全仓 race 的结果单独记录。
- 后续 push 前执行适用全量门禁一次；同一代码树已有有效结果可复用，后续纯 Markdown 修改不触发重跑。
- fuzz 使用 CI 已存在的目标，先核实名字，再单目标限定时长运行；保存随机种子和最小复现输入。覆盖率用于定位未守护分支，不设任意百分比门槛。

- 每条证据绑定 SHA、工作区差异、工具链、配置摘要、命令、退出码、耗时及原始日志。缓存成功、历史成功和静态阅读不能替代本轮运行结果。

## 7. 发现记录、定级与对抗验证

### 7.1 发现模板

每条 finding 使用以下字段，不完整的进入候选队列：

```text
ID / 标题 / 所属模块 / 负责人
基线 SHA / 文件:行号 / 调用入口
类型：确认 BUG / 契约争议 / 测试缺口 / 架构建议
前提：默认或特殊配置、权限、数据与并发条件
复现：最小步骤、输入、命令与日志位置
预期：对应契约或不变量
实际：可观测结果与影响范围
已有防御：检查过的拦截点、为何无效或有效
严重度 / 置信度 / 独立复核者 / 裁决
最小修复方向 / 回归验证 / 剩余风险
```

### 7.2 严重度

| 级别 | 判定标准 | 处置 |
| --- | --- | --- |
| P0 | 可达的严重越权/凭据泄露、不可恢复的数据或账务破坏、广泛不可用且无有效缓解 | 阻断发布，优先修复并独立复验 |
| P1 | 关键流程错误、重要隔离失效、可显著放大的账务/资源问题、恢复失败 | 原则上阻断发布；例外须由发布责任人书面接受风险和缓解 |
| P2 | 受限条件下的功能缺陷、可恢复一致性偏差、明显性能/运维问题 | 指定责任人与目标迭代 |
| P3 | 低影响体验、可维护性和非阻断文档问题 | 排期改善，不混入高危 BUG 统计 |

严重度与置信度分别记录。未复现的严重猜测标记“候选 P0/P1，待验证”，既不冒充确认漏洞，也不因缺环境直接关闭。

### 7.3 裁决流程

1. 按根因去重，保留所有触发路径与独立来源。
2. 每条候选 P0/P1、账务/授权发现以及存在契约争议的发现，交给非原作者证伪。
3. 证伪者从外部入口追踪实际配置、认证、路由、校验和存储路径，尝试找出有效拦截措施。
4. 裁决为 `CONFIRMED`、`REFUTED`、`PARTIAL` 或 `UNVERIFIED`；部分成立必须重新描述影响并重新定级。
5. 报告保留被推翻结论及原因，避免下一轮重复误报；关闭必须引用新证据，不能只凭“已修改”。
