## REL-01: sequence identity can be reused after an accepted notification

**Trigger and trace.** `internal/deadman/engine.go:77-100` starts `deliveryLoop` before the initial `Tick`. At `:125-143`, Tick increments the sequence/enqueues its heartbeat under `mu`, releases that lock and wakes delivery, then waits for probes and anchor pulls. It does not persist the enqueue here. `drainOne` at `:319-331` takes the queued head, marks it in flight, releases `mu`, and sends it. The first delivery-path save is after the HTTP request and audit append, at `:351-363`. Tick separately saves after its probes/transitions at `:199`. A process crash after receiver acceptance but before either path successfully persists the new sequence leaves the previous durable sequence. `loadState` (`internal/deadman/store.go:10-49`) restores that previous sequence; `enqueue` (`engine.go:247-281`) derives the next event ID from it again, now potentially with a different observation timestamp.

**Important qualification.** A slow probe alone does not keep the gap open until Tick finishes: a successful delivery can itself persist the new sequence while the probe is still blocked. The defect requires a crash in the send/acknowledgement/audit/persistence interval before either save completes, or persistence failure that leaves old disk state. Ordinary successful delivery closes the gap. REL-01 is valid when expressed this way; claiming that the whole probe duration necessarily remains vulnerable after a completed delivery would be too broad.

**Existing defenses and impact.** `tickMu` serializes ticks; `mu` protects shared state; in-flight heartbeat protection prevents coalescing away the head being sent. Delivery enforces FIFO, bounded batches, retry/backoff, and retention after audit failure. `saveState` uses a private temporary file, file sync, rename and directory sync (`store.go:52-92`). Those defenses protect completed saves and delivery ordering, but cannot make an as-yet-unsaved sequence durable. The receiver contract (`deploy/observability/external-probe/RECEIVER-CONTRACT.md:7-17`) requires monotonic sequences and idempotent duplicate acknowledgement. Consequently a reused ID can cause a fresh heartbeat to be discarded as a duplicate/replay, delaying fresh liveness evidence and possibly causing a false timeout. Replay handling protects against false freshness. Subsequent genuinely newer sequences normally recover; permanent service loss is not demonstrated.

**Original fixture adjudication.** Read `/private/tmp/halro-reliability-review/review_test.go` and its overlay mapping. Blocking the checker correctly exposes the unlocked pre-save interval, and direct `drainOne` invokes the actual send/save implementation. However, it substitutes the worker schedule, reads the disk at transport entry rather than physically killing a process after durable receiver acknowledgement, and starts a Tick goroutine without joining it before cleanup. Its restart is a `loadState` + `enqueue` model, not a second `New`/`Run` process. These are evidence limitations, not reasons to refute the underlying ordering.

**Independent validation.** A new socket-free overlay invokes real `Engine.Run`, including its delivery worker and wake channel, with a checker blocked until cancellation. A fake HTTP transport records the current disk state and models successful receipt with HTTP 204; a restart model loads that disk state and enqueues a heartbeat observed one second later. Cases start with real saved sequences 0 and 41. Both show that the outbound sequence exceeds disk sequence and the restart reuses its ID for a different observation. Run and probes are joined before test cleanup. Race detection passed. This validates initial-run and nonzero-durable-sequence boundaries; it does not claim a real receiver durability test, process kill, physical power loss, or a later tick in the same uninterrupted Run.

**Proposal, not an additional finding.** Persist sequence allocation and the queued event before exposing it to delivery, while retaining heartbeat independence from slow probes. A remediation must cover persistence errors and preserve receiver idempotency; merely holding a memory mutex does not address crash durability.

## Usage summary: drained increment is invisible until persistence or return

**Trigger and trace.** Background maintenance calls `saveUsageCheckpoint` (`internal/app/runtime.go:944-952`). That method catches the collector up, calls `TakeCheckpoint` at `:1014`, then performs `PutUsageCheckpoint` at `:1033`, returning the increment on failure and committing on success (`:1029-1044`). `TakeCheckpoint` drains `rollupDelta` under the aggregate mutex at `internal/usage/checkpoint.go:194`, unlocks at `:195`, and encodes outside the lock. `takeRollupDelta` explicitly replaces the live delta with an empty map (`internal/usage/rollup.go:191-198`). The checkpoint-local snapshot is not consulted by summary reads.

The reachable Admin summary handler calls `syncUsageAdmin` (`internal/app/admin_usage_summary.go:112-115`), which only calls collector `CatchUp` (`internal/app/admin_usage.go:721-727`). Catch-up cannot reapply already-consumed Ledger records to recreate a drained increment, and does not lock the whole checkpoint/store/read protocol. `collectSummaryRows` reads the stored rollup first at `admin_usage_summary.go:289`, then the current pending map at `:292`; `PendingRollup` (`internal/usage/rollup.go:242-250`) reads only the replacement map. Thus a request between drain and bbolt commit sees neither copy of finalized events in that checkpoint. The window begins before encoding completes, not merely at the bbolt call.

**Existing defenses and scope.** `internal/store/bolt/store_usage.go:50-94` validates and writes the head, segments and rollup in one transaction; `UsageRollupRange` at `:341-371` uses a consistent bbolt read transaction. Aggregate locking protects each individual operation. Failure paths return the increment (`runtime.go:1062-1066`; `usage/rollup.go:201-223`), and successful persistence makes it visible in stored rows. These protect durable consistency but do not give summary a single coherent view across disk and memory. An overlapping summary can undercount completed requests, cost and related rollup fields, then recover. The stored+pending reads can also straddle the drain/commit boundary even if the store read began before draining. No evidence here supports permanent loss, wrong settlement, or a P1 classification.

**Parent fixture adjudication and independent rerun.** Read the parent's `/private/tmp/halro-review-260905/summary-review_test.go`, overlay and log. The existing `summaryRuntime(t,1)` initializes isolated storage, bills one request via the repository test helper, opens the runtime and logs in an Admin (`internal/app/admin_usage_summary_test.go:69-90`; `internal/app/usage_rollup_test.go:57`). `getSummary` exercises the authenticated HTTP handler and checks status 200. The fixture catches up, takes a checkpoint, reads summary, returns the snapshot and reads again. This deliberately pauses at an actual production boundary; it does not run the maintenance goroutine or inject a failure inside bbolt. Independent execution reproduced requests `1 → 0 → 1` and cost in micro-USD `90 → 0 → 90`. Request counts are asserted by the test; costs are logged and were independently checked in the output. Source inspection confirms there is no surrounding synchronization that makes this paused boundary unreachable in maintenance.

**Proposal, not an implemented repair.** Give summary a coherent view of persisted, in-flight and pending increments, with a generation/transaction protocol or shared synchronization that also prevents double counting. Simply adding the in-flight increment without coordinating the stored read can introduce a different inconsistency.
