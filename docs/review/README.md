# 多角色评审方案

本目录存放对 Heimdall 的周期性多角色评审报告（按日期命名，如 `260805.md`）。本文件定义**评审框架**：有哪些角色、每个角色查什么、一次评审该选哪些角色。

## 设计原则

1. **角色独立**：每个角色独立通读代码、独立产出结论，不共享中间判断。交叉证实的问题（多个角色独立发现同一缺陷）置信度最高——这是多角色相对单次评审的核心价值。
2. **证据驱动**：每条发现必须带 `文件:行号`，区分【肯定/建议/问题/疑似BUG】。
3. **参照系**：以 Redis 设计哲学为对照（简单性优先、单二进制自包含、最少依赖、数据结构即核心、拒绝功能蔓延、可读性即文档、务实性能取舍、最少惊讶、开箱即用）。
4. **分层选择**：不是每次都跑全部角色。按"本次改动性质 + 距上次全面评审的时间"选择角色子集（见下方选择指南）。

## 角色清单

角色分三档：**核心档**（每次全面评审必跑）、**专项档**（按项目性质补充）、**按需档**（特定触发条件才跑）。

### 核心档（6 个，已在 260805 首次执行）

| 角色 | 核心问题 | 主要范围 |
|---|---|---|
| 架构设计 | 模块边界是否清晰、有无过度抽象/死代码/依赖蔓延 | `internal/` 包划分、`go.mod`、`docs/adr` |
| 交互设计 | 关键流程能否顺畅走完、危险操作是否防误触 | `web/src` 页面与交互流 |
| 视觉设计 | 设计系统一致性、可访问性、产品气质 | `web/src` 样式与 design-system |
| 核心逻辑 | 业务不变量正确性、并发、错误/中止路径 | `internal/` 业务包 + `*_test.go` |
| 可用性 | 开箱即用、错误信息可行动、文档即手册 | README、Makefile、`cmd/`、`docs/` |
| BUG 排查 | 有代码证据的具体缺陷（并发/泄漏/边界/加密） | 全仓，高危区优先 |

### 专项档（按项目性质补充；本项目为安全网关，强烈建议纳入）

| 角色 | 核心问题 | 为何对本项目重要 |
|---|---|---|
| **安全威胁建模** | 信任边界、认证授权矩阵、密钥链、SSRF/注入、审计完整性 | 项目自称 security-first；BUG 排查是"找缺陷"视角，威胁建模是"攻击者"视角，能挖出前者挖不到的攻击链（如本轮 XFF 绕过） |
| **测试盲区** | 关键不变量有无测试守护、哪些路径裸奔 | 已知高危 BUG（熔断器误复位）正是测试盲区导致缺陷存活；产出"盲区地图"指导补测试 |
| **性能与容量** | 单机吞吐上限、瓶颈、长跑内存增长 | 网关类产品核心指标；逻辑评审已暗示 fsync 串行化瓶颈与只增不减的 map。**建议有压测环境时做**（纯读代码产出有限） |

### 按需档（触发条件满足才跑）

| 角色 | 触发条件 |
|---|---|
| API 兼容性契约 | 改动了 OpenAI/Anthropic 兼容层，或要发版承诺兼容性——用真实 SDK 跑对照 |
| 供应链与发布工程 | 改动了 CI/构建/依赖——查签名、SBOM、可复现构建、版本注入 |
| 数据迁移与升级 | 改动了 bbolt schema / pricing / ledger 格式——查升级平滑度与回滚 |
| 可观测性 | 改动了 metrics/alert/runbook——查告警可操作性与接入成本 |

**已评估无需单设角色**：产品/需求（PRD 与 ADR 已完整）、可访问性（并入视觉）、i18n（有 CI 门禁 `i18n.test.tsx` 守护）。

## 选择指南

| 场景 | 建议角色组合 |
|---|---|
| **季度全面评审** | 核心 6 + 安全 + 测试盲区（本项目基线，共 8） |
| 大型功能合并前 | 架构 + 核心逻辑 + 安全 + 测试盲区 + BUG |
| 前端重构后 | 交互 + 视觉 + 测试盲区（前端部分） |
| 发版前 | 可用性 + API 兼容性 + 供应链 + 数据迁移 |
| 快速健康检查 | BUG + 核心逻辑 |

## 执行方式

- 每个角色 = 一个独立评审 Agent，并行启动，互不知情。
- 汇总时**主动标注交叉证实**：多个角色独立指向同一问题的，单列并提升优先级。
- 报告结构：评分总览表 → 各角色分章（肯定在前、问题在后）→ 统一 BUG 清单 → 按 P0/P1/P2 分级的修复清单 → 交叉验证说明。
- 修复清单按"严重度 × 修复成本"排序，优先推"高杠杆低成本"项。

[progress.md](260805/progress.md) 是整改的活的对照表——哪些做了、哪些没做、以及实现过程中对原结论的修正。评审报告本身按日期归档、不再改动，进度另立一处，两者分工明确。

## 历史评审

- [260805.md](260805/260805.md) — 首次全面评审，8 个评审角色（核心 6 + 安全威胁建模 + 测试盲区）+ 6 个对抗验证角色。安全由两个互不知情的角色独立完成，6 条最严重 finding 再各经一个对抗角色证伪。综合评分区间 6.5~7.5。**对抗验证是本轮关键一环**：6 条 P0 无一原样照收——Redaction/TokenGuard 悬空引用 fail-open（原头号安全 P0）被 REFUTED（攻击链被 409 + 两层 fail-closed 拦截），熔断器 `Done(nil)` CONFIRMED 但收窄至 half-open 窗口，其余 4 条 PARTIAL。净化后最该先修的是"未认证审计洪泛→fail-closed 反噬"攻击链（唯一未被削弱的匿名可达安全问题）。

### 方法沉淀：评审后应加对抗验证

多个"发现型"角色并行产出后，**对最严重的若干条各派一个独立"证伪型"角色**，默认 finding 为错、要求在代码里复现完整路径或找出拦截防御，裁决 CONFIRMED/REFUTED/PARTIAL。这一步的价值已被验证：发现型评审擅长指出"代码分支有问题"，但不擅长回答"这条路径在完整系统里真能走到吗"；交叉证实提高的是"代码可疑"的置信度，不等于"漏洞可利用"。季度全面评审建议固定包含这一环。
