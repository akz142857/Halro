## 1. 为什么要做这一轮

v0.8.5 之后的变化不是一条直线，而是"加上去、评审、再拿掉、再换方向"：

1. 9 月 20–27 日加入了路由准入、调用方幂等、配置 v2、订阅接入、metadata journal 与 HA（52 个提交），260927 评审了这一段，原始裁决 No-Go，随后 R-001–R-014 在仓库范围内关闭；
2. 9 月 27 日–10 月 1 日继续加 HA（#385、#386）和整改提交 `c8b97b1b`；
3. 10 月 15 日 #404 把 HA 与 metadata journal 整体移到 `ha` 分支（−57,120 行），其中 `c8b97b1b` 被**部分**回退；
4. 10 月 15–17 日内存有界重设计 P0–P3 与热状态上限（#405–#408、#421–#424），直接改写账务权威（Ledger）、用量历史和治理状态的内存与启动路径；
5. 依赖、工具链与 CI 维护（#410、#411、#415、#417、#396、#425）。

每个 PR 都单独评审过，但没有任何一次评审看过**最终代码相对 v0.8.5 的整体**。具体风险：

- 260927 的结论是对着含 HA 的代码做的；回退之后，哪些整改还在、哪些随 HA 一起没了、哪些被回退改回了旧行为，没有人逐条核对过；
- P1–P3 改写的文件（usage、ledger、budget、gateway、app）与 260927 评审过的功能（幂等、路由挂起、Advisor、指标）大量重叠，后者的结论可能已经失效；
- 发布准备时只做了"接缝抽查"，并已发现 CHANGELOG 漏掉 P2/P3、`doctor` 在首次启动前误报两个问题——说明逐 PR 评审确实漏东西。

## 2. 本轮要回答的问题

1. **最终 `main` 相对 v0.8.5 到底交付了什么**：逐功能列清单，标出哪些已实现、哪些只是门禁/文档、哪些被回退后净为零；
2. **260927 的结论今天是否仍然成立**：R-001–R-014 逐条复核，F01–F15 逐项复核；
3. **内存有界重设计是否正确**：账务权威、失败关闭、可重建、确定性重放、内存与磁盘真正有界；
4. **回退是否干净**：无 HA 残留（代码、配置键、指标、告警、文档、CLI），也没有误删非 HA 的修复；
5. **升级是否安全**：从真实 v0.8.5 数据目录升级、回滚围栏、备份/恢复、崩溃恢复；
6. **产品各面是否描述同一件事**：CHANGELOG、文档、配置参考、指标/告警/runbook、控制台、兼容性清单与实际行为一致；
7. **能否发布 v0.9.0**：给出 GO/NO-GO 与阻断项清单。

## 5. 评审方法

### 5.1 三遍读法

1. **分段读**（第 3 节表格）：对每个合并 `M`，读 `git diff M^1 M` 和它的 PR 描述、评审评论、机器人评审结论。记录"PR 声称做了什么 / 实际做了什么 / 测试证明了什么"。
2. **净 diff 读**：对 `git diff v0.8.5..main` 按包读，顺序按风险：`ledger` → `budget` → `usage` → `archive` → `governance` → `app`（启动、恢复、备份） → `gateway`/`gatewayapi` → `store/bolt` → `config` → `cmd/halro` → `routegate` → `provider` → `web/src`。
3. **交叉点读**：按第 6 节矩阵，沿调用链读，不以 diff 边界截断（变化触及旧代码的权威边界时，追到 v0.8.5 以前的代码）。

### 5.2 角色

角色定义以 [`../README.md`](../README.md) 为准。本轮选：

| 角色 | 负责 | 主要段 |
| --- | --- | --- |
| 核心逻辑 | 账务不变量、并发、错误/中止路径 | D、A 复核 |
| BUG 排查 | 有代码证据的具体缺陷 | 全部，净 diff |
| 安全威胁建模 | 新文件/新端点/新监听的信任边界，HMAC 与密钥派生 | D（M01、M02、M04、M07）、A（F03、F04、F05） |
| 测试盲区 | 每条不变量有无测试守护、反向验证是否真的失败 | D |
| 性能与容量 | 内存/磁盘/启动时间是否真正有界，新锁 | D（M02–M05） |
| 可用性（升级与运维） | 升级路径、错误信息、文档、runbook、CHANGELOG | C、D、E |
| 交互设计 | 控制台变化（F08、M01 的默认范围） | A、D |

不跑视觉设计和架构设计全量角色；架构问题在核心逻辑和回退完整性评审中顺带记录。

### 5.3 发现的记录规则

沿用 260927：每条发现一个文件 `findings/V-NNN-pX-短名.md`，带 `文件:行号`、复现或证据、影响、建议；分类为【问题/疑似BUG/建议/肯定】。严重 finding（P0/P1）在定稿前做一次**对抗性复核**：另一角色独立尝试推翻它，结论写入 `adversarial-verdicts.md`。

严重度：

| 级别 | 含义 | 对发布的影响 |
| --- | --- | --- |
| P0 | 账务错误、数据丢失/损坏、认证绕过、密钥泄露、升级损坏数据 | 阻断，必须修 |
| P1 | 失败开放、可被外部触发的资源无界增长、恢复失败、错误的回滚/升级行为 | 阻断，必须修或由 owner 书面接受 |
| P2 | 错误信息误导、文档/指标与行为不一致、测试盲区 | 修复或登记为 issue 并在发布评估中列出 |
| P3 | 可读性、命名、重复代码 | 登记 |

| E01 | 从真实 v0.8.5 数据升级 | 已发布 v0.8.5 二进制写入**有规模的**数据（≥10 万请求、含 Work Unit/Run/Outcome、路由挂起、幂等记录），再用候选版本升级、启动、跑请求、全部 verify | macOS + Linux 容器 |
