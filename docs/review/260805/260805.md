# Halro 多角色评审报告（2026-08-05）

> 评审方式：**八个**独立评审角色（架构设计、交互设计、视觉设计、核心逻辑、可用性、BUG 排查、安全威胁建模、测试盲区）并行评审整个仓库，各自基于代码证据独立给出结论，最后交叉汇总。安全威胁建模由**两个**互不知情的角色独立完成（本报告将其结论合并去重），以最大化交叉验证。
> 参照系：Redis 设计哲学——简单性优先、单二进制自包含、最少外部依赖、数据结构即核心、拒绝功能蔓延、可读性即文档、务实的性能取舍、最少惊讶、开箱即用。
> 评审基线：`main` @ `126fb32`。
> 评审框架见 [README.md](../README.md)。

## 评分总览

| 维度 | 评分 | 一句话结论 |
|---|---|---|
| 架构设计 | 7.5 / 10 | 骨骼像 Redis（WAL 账本 + 单进程边界 + 零抽象存储层），肌肉在向企业级 Java 漂移（app 上帝包、死代码预埋） |
| 交互设计 | 7.5 / 10 | 单次操作的严谨度一流，但六步配置链缺贯穿性引导，模态框会静默丢弃表单内容 |
| 视觉设计 | 7.5 / 10 | 颜色系统是"可执行契约"，但间距/字号 token 形同虚设，中文排版是二等公民 |
| 核心逻辑 | 7.5 / 10 | 计账层显著强于调用层；happy path 想清楚了，abort path 各写各的 |
| 可用性 | 6.5 / 10 | 运维证据链远强于开发者体验；一流的校验文案没有送到调用方手里 |
| 安全威胁建模 | 7.4 / 10 | "security-first" 大部分兑现（会话/密码学/SSRF/前端达商业水准），但防御在"边界与降级路径"有系统性缺口 |
| 测试盲区 | 6.5 / 10 | 上限很高（万次崩溃注入、千并发不超卖、property fuzz），下限很低（中止路径 4.0，正是已知 BUG 的成因） |
| BUG 排查 | — | 1 高危 + 6 中危 + 4 低危/疑似（第七章）；安全评审另列 3 条 P0 攻击链/fail-open |

**跨维度交叉证实的缺陷（多角色独立指向同一问题，置信度最高）**：

1. **熔断器 `Done(nil)` 语义混用**——核心逻辑、BUG 排查、测试盲区**三个**角色独立发现，均判为最高严重度。测试盲区进一步证明其根因是"7 个中止路径 0 个测试"。
2. **safelog 脱敏对 Group/LogValuer/非-error Any 失效**——BUG 排查、两份安全威胁建模、测试盲区**四个**角色独立命中。
3. **SSE 裸 `\r` 事件边界**——核心逻辑（解码侧）、BUG 排查（编码侧）、两份安全评审共同指向。
4. **`recordsByEventID`/`eventDigests` 无界内存增长**、**数据面无认证前限流**、**变更先落库审计后写**——逻辑与安全评审交叉证实。

**安全评审独有的 P0（BUG 排查视角未覆盖）**：Redaction/TokenGuard 悬空引用 fail-open、审计 HMAC 密钥与被审计者同域、Developer Workbench 打通控制面→数据面。

> **重要：以上及其他 6 条最严重发现已经过对抗验证（第十一章），无一条原样照收。** 裁决：熔断器 `Done(nil)` **CONFIRMED**（限 half-open 窗口，原"永不跳闸"表述夸大已修正）；审计密钥同域 **PARTIAL**（File 模式成立、KMS 模式证伪）；Developer Workbench **PARTIAL**（网络隔离绕过成立、源 IP 伪造默认配置下证伪）；safelog 脱敏 **PARTIAL**（实现有洞但生产无触发点，属"定时炸弹"）；startAttempt 资源泄漏 **PARTIAL**（缺清理属实但路径不可达）；**Redaction/TokenGuard 悬空引用 fail-open 被 REFUTED**（攻击链在重新启用项目时被 409 拦截 + 两层 fail-closed 纵深防御）——**这条原本是头号安全 P0，验证证明不可利用。** 详见第十一章与各条【验证】行。

## 一、总评：与 Redis 哲学的对照

Halro 的核心架构决策明显是"想清楚了才写的"，且多数决策与 Redis 哲学同构：

| Redis 哲学 | Halro 的落地 | 判定 |
|---|---|---|
| 单二进制自包含 | 一个 Go 进程 + bbolt + flock 独占锁 + go:embed 前端，无外部数据库/缓存 | ✅ 做到了 |
| 数据结构即核心 | Ledger WAL 是唯一记账权威，一切派生态（checkpoint、聚合、Parquet）可丢弃可重建（ADR 0002） | ✅ 最强的一处 |
| 务实性能取舍 | WAL 组提交（批量编码 + 单次 fsync），教科书式 | ✅ |
| 拒绝功能蔓延 | ADR 0010 用实测数据拒绝了插件系统/双 artifact 四条歧路 | ✅ 范本级 |
| 简单并发模型 | 预算用"项目一把锁 + 按序列号单点应用"，有千并发不超卖测试守护 | ✅ |
| 开箱即用 | `halro start` 零配置自举、回环安全默认 | ⚠️ 差半步（`make start` 强依赖 npm；生成的 config.yaml 零注释） |
| 错误信息可行动 | 校验层文案一流，但 HTTP 层坍缩成 `invalid request body` | ❌ 内部有、外部无 |
| 可读性即文档 | AST 边界测试是"可执行架构规则"；但 "phase2" 里程碑代号侵入 24 个文件的类型名 | ⚠️ |
| YAGNI | `internal/authority` 是零引用的分布式预埋死代码 | ❌ 明确违规 |

**一句话总结**：底层工程质量（计账、加密、可观测性、设计系统的自动化断言）高于同类开源项目的平均水准；失分集中在三类系统性问题——① 错误/中止路径没有被当成一等公民（熔断器误复位、资源泄漏、错误信息坍缩），② 已有的最佳实践没有下沉为共享能力（前端模式各写各的、CSS 基类缺失），③ 对"未来"的过度投资（authority 死代码、phase2 命名、形同虚设的 token）。

## 二、架构设计（7.5 / 10）

### 值得肯定

1. **【肯定】单进程一致性边界 + OS 独占锁，真正的"Redis 式"自包含**
   `docs/adr/0001-single-process-architecture.md`、`internal/store/lock/lock_unix.go:34`
   ADR 0001 把"一个 Go 进程"定为 v1 一致性边界，用 `syscall.Flock(LOCK_EX|LOCK_NB)` 对数据目录加独占锁，启动即失败的硬契约（`internal/app/bootstrap.go:57`、`runtime.go:106` 先取锁再开库）。不是"暂时没做分布式"的托辞，而是把单机约束写成可执行契约。

2. **【肯定】Ledger WAL 唯一记账权威 + 组提交，派生态明确可丢弃**
   `internal/ledger/log.go:323`（collectBatch）、`:352`（writeBatch 单次 Sync 覆盖整批）、`internal/ledger/event.go:318`
   追加日志 + 内存状态机重放几乎是 Redis AOF + 内存数据结构的同构映射。ADR 0002 铁律："删除任何派生状态都不得改变重放出的账本余额"。**整个项目最强的架构决策。**

3. **【肯定】存储层拒绝 Repository 抽象，直接依赖具体类型**
   `internal/store/bolt/store.go`、`internal/app/runtime.go:49`
   全仓没有"为了将来换数据库"的 `Store interface`。既然 ADR 0001 决定永不换 bbolt，就不为假想的可替换性付抽象税。

4. **【肯定】零配置启动 + 安全默认**
   `cmd/halro/main.go:120-149`、`internal/config/default.go:16`
   配置不存在时自动写入回环安全默认值；公网明文监听需显式 `--allow-insecure-public-listen`。等价于 `redis-server` 无参启动 + `protected-mode yes`。

5. **【肯定】ADR 0010 是证据驱动拒绝复杂性的范本**；**架构规则写成可执行测试**（`internal/semantic/boundary_test.go:16` 用 AST 强制分层）。

### 问题与建议

1. **【问题】`internal/app` 是上帝包**
   `internal/app/runtime.go:45-103`。13,758 行、42 个文件，其中 37 个 `admin_*.go` 占 6,684 行；`Runtime` 结构体 58 个字段、6 把互不相干的 Admin 级互斥锁。组装根与 Admin 业务完全混居。
   **建议**：拆出 `internal/adminapi`（HTTP handler + Admin 会话/限流状态），`app` 只保留 `Open/Run/Close` 与装配。

2. **【问题】`internal/authority` 是零引用的死代码——为未发生的分布式预埋抽象**
   `internal/authority/authority.go:108`。全仓无任何 importer；155 行定义了 fencing token 语义，`StandaloneEpoch` 恒为 1。antirez 直到 3.0 才写 Cluster，2.x 里绝不预埋 fencing token 类型。
   **建议**：删除代码，保留 ADR 0004 的文字契约与 `docs/architecture/distributed-state-ownership.md` 的状态归属矩阵（矩阵本身写得很好）。

3. **【问题】"phase2" 里程碑代号泄漏进 24 个源文件的类型命名**
   `Phase2Service`、`StatelessPhase2Adapter`、`BedrockPhase2Adapter`……对读者零信息量，ADR 0009 里它们其实是"Files / Batches / Async Invocations 资源"。
   **建议**：按领域重命名（`resources` / `asyncops` / `batchfiles`）。

4. **【建议】`store.go` 5,094 行单文件**（30 个 bucket、149 个方法），应按数据域拆分——同目录已有 `pricing_migration.go` 等拆分先例。

5. **【建议】`gatewayapi` 的 4 个接口（约 30 个方法）只有 `*gateway.Service` 一个实现**，是不必要的抽象层；与 store 层"直接用具体类型"的做法双重标准。

6. **【建议】Parquet 导出为"可丢弃派生态"引入 6 个间接依赖，包括地理几何库 `twpayne/go-geom`**
   `internal/usage/parquet.go`（986 行）。全项目投入产出比最差的一处依赖。建议降级为可选导出或改为无依赖的 NDJSON。

7. **【建议】`jsonschema-go` 位于主 require 段但生产代码零引用**（仅 `deploy/observability/schema_test.go` 使用），污染 SBOM 范围。

8. **【建议】`gateway.Service` 2,194 行承担 8 项职责**（路由/预算租约/重试/熔断/并发配额/TokenGuard/双向脱敏/定价结算），五条协议路径各自重复了同一套编排。建议提取统一的 attempt 执行管线。

9. **【观察】AWS SDK 12 个模块进主二进制**——ADR 0010 已量化论证并设回归门禁，属知情妥协，不扣分；未来 GCP/Azure 需求出现时应坚守"一个云 = 一次新 ADR"。

## 三、交互设计（7.5 / 10）

### 值得肯定

1. **【肯定】Gateway Key 一次性展示的防丢失设计非常完整**
   `web/src/pages/ProjectsPage.tsx:438-531`。幂等键用 ref 固化在对话框生命周期内（超时重试不会静默多发活密钥）；防长按 Enter 连发；密钥展示态 `closeDisabled={!acknowledged}`；复制失败有兜底提示；必须勾选"已保存"才能完成。MFA 恢复码（`SettingsPage.tsx:150-157`）更进一步用 `beforeunload` 拦截关标签页。

2. **【肯定】不可变价格版本走两步确认 + 重新认证 + 结果不明确时的安全重试**
   `web/src/pages/DeploymentsPage.tsx:305-422`。`ambiguousResult`（网络错误/5xx）时隐藏"返回修改"、只留"按原内容重试"，避免改内容后用同一幂等键重试造成语义冲突。

3. **【肯定】异步测试反馈是全站亮点**：`InlineTestControl` 统一五态机（idle/running/success/failure/**stale**），`stale` 态在配置变更后诚实标注"旧结论不再可信"；Webhook 测试把端点响应体打印在行内（很多聊天平台返回 200 却在 body 里拒绝）。

4. **【肯定】双语完整性有 CI 门禁**：`i18n.test.tsx` 强制 zh-CN/en-US key 完全对等；格式化全走 `Intl`；切换语言不刷新页面。

5. **【肯定】"最少惊讶"在细节层被反复兑现**：Esc 永远是取消；确认框默认焦点在"取消"上；启用/禁用按钮用 sizer 保证两态等宽、列不跳动；`LoadMore` 既是真实按钮又挂 IntersectionObserver。

### 问题与建议

1. **【问题】六步配置链没有任何首次使用向导，Setup 完成后直接掉进空 Dashboard**
   `web/src/App.tsx:96`、`web/src/pages/DashboardPage.tsx`。全新实例的 Dashboard 全是 0 和"无数据"，没有一处提示下一步该去建凭据；Credential 还藏在 Providers 页的第二个 tab 里，侧边栏看不到。
   **建议**：Dashboard 增加"首次配置"空态 checklist（六步各显示完成数 + 直达按钮），以 `DeveloperPage` 的"发一次真实请求"为动线终点——所需的 `EmptyState`、`dependency-notice`、`notice-link` 三个模式都已存在，只欠串联。

2. **【问题】非受控模态框 Esc/点背景会静默丢弃已填内容**
   `web/src/components.tsx:190,206`。`DeploymentForm` 等长表单填一半误触即无声消失、无撤销；全站只有 `AlertForm` 做了脏检查（还用的是 `window.confirm`）。
   **建议**：把脏检查上提到 `Modal`（`dirty?: boolean`），用自研 `dangerous` Modal 替代浏览器原生 confirm。

3. **【问题】禁用按钮不说明原因，且文案已写好却没接上**
   `web/src/pages/DeploymentsPage.tsx:214,222`。部署被启用路由引用时"禁用/删除"被 disabled 但无任何提示；locale 里 `deployments.routeBlocked`（"请先停用引用该部署的模型路由"）**在整个代码库中零引用**——是遗漏而非设计。

4. **【建议】删除类确认强度对不可逆程度不敏感**：删凭据时已算出 `useCount`（几个 Provider 在用）却不展示影响面；删项目不提示其下有几把活跃 Key。建议给 `ConfirmButton` 加 `impact` 插槽，影响面非零时要求输入资源名。

5. **【建议】创建成功后缺"继续下一步"接力**：所有创建成功都是"模态消失 + 列表刷新"，刚建完 Deployment 的用户不知道它默认停用、需先测试再启用。建议成功态改为"继续创建下一层实体 / 立即测试"。

6. **【建议】校验时机不统一**：`PriceVersionForm` 默认值 `"0"` 触发"打开瞬间即显示红色错误"（`DeploymentsPage.tsx:322,399`）；全站三种校验流派并存（zod 提交时 / 手写常驻 / 单条 problem）。建议统一为"blur 或提交后才显示"。

7. **【建议】主按钮禁用时不说明缺什么**——而 `DeveloperPage` 的 `missingRequirements` 列表（`role="status"` 实时列出缺项）已是最优解，应抽成共享组件。

8. **【问题】登录后控制台内没有语言切换入口**：`LanguageSelect` 只在 Login/Setup 出现，进控制台后藏在 Settings 三层之下；登录页的语言选择不落存储、刷新即丢。

9. **【建议】CRUD 成功缺全局反馈通道**：Settings 页有成功回执，六步链上的创建/更新一律只有"模态消失"，屏幕阅读器用户完全感知不到成功。建议补轻量 toast/live-region。

## 四、视觉设计（7.5 / 10）

### 值得肯定

1. **【肯定】三层 token 架构落地且有测试强制执行**
   `web/src/design-system/tokens.css`、`design-system.test.ts`。原语（`--p-*`）→ 语义（`--color-*`）→ 遗留别名的单向依赖清晰；CI 递归扫描业务文件，出现色值字面量或直接消费 `--p-*` 即红。不是"文档级设计系统"，是"可执行契约"。

2. **【肯定】明暗双主题不是机械反转，带对比度断言**：Light 单独选 paper 系画布、把 lime 主色换成深橄榄保证白底对比度；测试对 8 前景 × 2 背景做 4.5:1 断言；有 `forced-colors` 与 `prefers-reduced-motion` 兜底。

3. **【肯定】图标一律有文字等价物，颜色从不单独承载状态**（`StatusDot` 用 `aria-hidden` + `.sr-only`，11 个页面无破例）。

4. **【肯定】一次性明文密钥有专属危险态视觉**（`.secret-value`：危险色 + 虚线边框 + `user-select: all`，刻意不与"保存"共用主色）——把视觉语言当安全提示用。

5. **【肯定】列表行抗抖动细节**（状态文案 sizer、`overflow-anchor: none`、webhook 回执限定在所属行的 `grid-column: 1 / -1`）。

### 问题与建议

1. **【问题】spacing/radius/z-index/motion 四组 token 定义了但业务 CSS 几乎零消费**
   `--space-1..16` 在 `styles.css` 中出现 **0 次**，裸 px 出现 1522 次；gap 值 21 种、padding 组合 60+ 种、圆角 7 种。"颜色有系统、尺寸全靠手感"。
   **建议**：给 `design-system.test.ts` 加第二条规则——裸值计数设基线只允许下降；先收敛 gap（4/8/12/16/24）和 radius（3/6/10）。

2. **【问题】字号 18 种裸值，8px/9px 大量用于中文标签**
   `styles.css:157,586,626` 等 39 处 `font: 8px/9px`，承载"搜索/状态"等中文标签——1x 屏上基本是墨团。**建议**：最小字号提到 12px；同功能的 `.deployment-toolbar` 已用 `var(--font-size-xs)`，直接对齐。

3. **【问题】字体栈没有 CJK 族，却默认中文界面**
   `tokens.css:60-61`。Windows 上中文掉到宋体，mono 栈的中文回退基线/字重完全不匹配；Inter 声明了但从未打包。**建议**：补 `"PingFang SC", "Microsoft YaHei", "Noto Sans CJK SC"`；单二进制产品不引 webfont，就把 Inter 从 token 里删掉，诚实声明系统字体栈。

### 问题与疑似 BUG

1. **【疑似BUG·高】熔断器 `Done(nil)` 是"完全成功"语义而非"中性"**（与 BUG 排查交叉证实，详见第七章 #1）。

2. **【疑似BUG】客户端取消/断开被计为上游可用性故障**
   `service.go:1669-1683` + `provider/openai/adapter.go:423-426`。客户端断开 ⇒ 读上游 body 报错 ⇒ 包成 `ErrorMalformed` ⇒ 计入熔断失败。一次客户端侧批量断连（前端发布、网关重启）会把健康 provider 的熔断器打开，自伤式雪崩。**建议**在分类前先判 `context.Canceled` 归为中性。

3. **【疑似BUG】传输层错误 `Retryable:true` + `Ambiguous:true` 并存，实际永不重试、永不故障转移**
   `retryable()`（`service.go:1656-1667`）先短路 `Ambiguous` ⇒ `Retryable` 成死代码。连接被拒/DNS 失败/TLS 握手失败——**最需要转移的"provider 整体不可达"场景反而不转移**；且 `settlementForResult` 对 Ambiguous 按估算 token 落账，**一次"连接被拒绝"会向项目收一整笔估算成本**，而请求根本没到上游。
   **建议**：把"请求是否已发出"与"响应是否已开始"拆成两个维度——连接建立失败应 `Ambiguous:false, Retryable:true`（可转移、不计费）。

4. **【问题】`startAttempt` 之后的防御性错误分支缺清理**
   `service.go:736-739,1408-1411,1563-1566,999-1002,1074-1077`。`Generation()`/`NativeMessages()` 解析失败时直接 return，缺 defer 兜底，未释放预算预留/并发槽/breaker lease/request finalize。
   **【验证：PARTIAL——缺陷属实、后果证伪】**（第十一章）：这 5 处确系"缺 defer 清理"的防御性分支，铁证是 ChatStream 相邻的 `streamRedactor` 失败分支（`:1396`）做了完整清理、12 行后的 `Generation` 分支却什么都没做。**但"活跃累积泄漏"被证伪**：Chat/ChatStream/Embeddings 三处的接口断言与 `ResolveOperation` 等价，是**不可达的死代码**；两处 native messages 分支被现有 adapter 绕过（anthropic 直接实现、bridge 失败发生在调用时→走 `finish`）；且"breaker 永久 open"对健康 target 不成立（健康态 `Acquire` 根本不 `halfOpen++`）。属"潜在清理缺失"而非"正在累积的泄漏"。
   **建议**：仍应修（把 return 改为统一 `abort()` 或前移 primitive 解析），因为它是 defer 缺失的隐患模式，未来新增 adapter 可能让某条分支变可达——但优先级从 P0 降为 P2。

5. **【问题】`applyErr` 毒化后仍继续向 WAL 追加永远不会被应用的事件**
   `manager.go:802-826`——先 `Append`（落盘）再检查 `applyErr`；毒化后每个请求仍写入无效事件，**重启重放会在毒事件上再次失败、进程起不来**，WAL 还堆着无效尾巴。**建议**：Append 前先读 `applyErr` 短路，apply 失败时同步 `MarkUnavailable`。

6. **【问题】时钟注入只做到 budget 层**：`ServiceOptions` 无 `Now` 字段（`service.go:588` 硬编码 `time.Now`），而 `s.now()` 决定鉴权时间戳、价格选取、限流桶、TokenGuard 窗口——外部包测试无法固定网关时钟，下一次"今天过、明天挂"会出现在另一个包。`tokenguard/manager.go:408,486,515` 的 checkpoint 路径同样无法注入。

7. **【问题】Phase 2 资源幂等的 `reserved` 状态无恢复路径**：进程在"写 reserved → 调上游"之间崩溃，幂等键锁死 7~30 天（查重分支对非 completed 一律 409）。另外 `internal/idempotency` 的 Reserve/Transition 状态机是**死代码**——两套幂等实现并存，应删一套或明确标注。

8. **【问题】流式中断按"满额 max_tokens"估算计费可能显著超收**
   `streamSettlement`（`service.go:2068-2102`）：吐了 20 个 token 就断开的流，未指定 `max_tokens` 时会按项目上限（可能几万 token）计费。网关明知自己 emit 过多少 chunk。**建议**：累计已投递输出 token，用 `min(已投递估算, max_tokens)` 作上界。

9. **【问题】预算超限会在每个候选 Deployment 上重复完整定价流程**：`ErrExceeded` 不视为 fatal，日预算耗尽的项目每个请求都在全部候选上依次执行"锁定定价→落盘 pin→校验失败→删 pin"。预算是请求级不变量，应首次超限即短路。打满预算的租户上这是放大数倍的磁盘写入。

10. **【建议】熔断失败计数无时间窗口**（跨数天的零星失败会在无关时刻跳闸）；**项目锁+定价锁横跨 fsync**（单项目吞吐上限 ≈ 1/(4×fsync)，`MarkStarted`/`Finalize` 不参与余额判定、可移出锁外合批）；**SSE 解码不支持裸 `\r` 行终止符**；**限流桶在 limit 热更新时重置为满**（清掉 TPM 欠账）；**`eventDigests` 等 map 只增不减**（内存随请求总量线性增长）。

### #1 详情（两个独立评审角色交叉证实）

`Done(nil)` 的实现是"完全成功"语义（`failures=0`、`openUntil` 清零、`halfOpen` 清零），而 gateway 有 7 处在**请求根本没到达上游**的本地拒绝路径（并发上限、计价错误、TokenGuard 拒绝、预算超额、pin 提交失败、MarkStarted 失败、脱敏策略错误）上调用它。

> **【验证：PARTIAL——(a) CONFIRMED，(b) 原表述夸大】**（第十一章）

1. **半开探针被本地原因中止即误闭合熔断器：CONFIRMED（限 half-open 窗口）**。可复现序列（`FailureThreshold=2`）：两次真实 5xx 跳闸 → 到达 `openUntil` 后一个请求获授 half-open 探针（`halfOpen=1`）→ 该探针在到达上游前命中并发上限 → `Done(nil)` 全量清零 → 熔断器被从未到达上游的探针闭合。**边界修正**：完全 open 期间 `Acquire` 直接返回 `ErrOpen` 短路，本地拒绝走不到——缺陷**只在 half-open 窗口**成立。
2. **混合流量下熔断器"永不跳闸"：原表述夸大**。正确说法是：非可用性结果（本地拒绝、4xx、200）会清零 `failures`，这是连续失败计数器的固有语义；但 `FailureThreshold` 次**连续**可用性失败仍会正常跳闸。只有在"上游 5xx 与非失败结果持续交替"这种较刻意的形态下才长期压制跳闸，**不是"永不"**。

`manager_test.go:32-35` 的断言恰好把"`Done(nil)` 后熔断器闭合"当成**预期正确行为**——等于固化了 (a) 所指的缺陷，且无任何用例覆盖"探针被本地中止"。

**修复**：拆成三态——`Success` / `Failure` / `Abandon`（仅释放半开名额、不动计数），7 处本地拒绝改调 `Abandon`。修复时应连带处理逻辑评审发现的两个同族问题：客户端取消不计入失败（第五章 #2）、失败计数加时间窗口（第五章 #10）。

|---|---|---|
| TB-1 公网 → Gateway | Bearer `gw_`、JSON body(≤4MiB) | 零信任：密钥须 SHA-256 命中快照 |
| TB-2 管理员 → Admin | `__Host-` cookie + CSRF + Origin | 高信任，但**无 RBAC，通过即全权限** |
| TB-3 网关 → 上游 Provider | 管理员配置的 `base_url`（HTTPS 强制、DNS pin、私网拒绝） | 半信任 |
| TB-4 进程 → 磁盘 | master.key(0600)、bbolt、audit、ledger | **完全信任：磁盘写权限 = 完全失陷** |
| TB-5 网关 → KMS | KeyARN 固定、EncryptionContext 绑定 | 强绑定 |

**结构性正面结论（两份一致，值得固化为不变量）**：数据面（TB-1）**无 SSRF 面**——请求体里的 `model` 只是查表键，用户可控字段无法构造出站 URL；租户隔离**无 IDOR**——所有 `ProviderResource` 查询强制携带 `project.ID` 作查询键；`safetransport` 的 dial 时地址校验消除了 DNS rebinding TOCTOU；备份与 master.key 强制分离（备份+备份密钥 ≠ 凭据泄露）；审计用 write-ahead intent 实现崩溃安全的抗抵赖。

### 认证与授权（评级）

会话管理与密码学实现是全项目最强的部分（均 9.0）：Session token 存 SHA-256 而非明文、双超时 + `SessionGeneration` 全局失效、登录/改密/MFA 完成必换会话（无会话固定）、`__Host-` + Secure + HttpOnly + SameSite=Strict、无状态 HMAC CSRF + Origin 双检、TOTP 步进防重放、`DummyVerify` 抗用户枚举、HKDF per-credential 派生、全程常数时间比对、KMS EncryptionContext 绑定、**无一处自造密码学**。前端安全近乎满分（9.5）：全仓 0 处 `dangerouslySetInnerHTML`、CSRF token 与一次性密钥只在 React 内存（localStorage/cookie 全禁且有测试断言）、严格 CSP 无 `unsafe-inline`。

### P0 级安全问题（三条 fail-open / 信任模型缺陷）

> ⚠️ 这三条均已经过对抗验证（第十一章）。裁决摘要：S-P0-1 **REFUTED**（分支存在但攻击链不可达）、S-P0-2 **PARTIAL**（File 模式成立、KMS 模式证伪）、S-P0-3 **PARTIAL**（网络隔离绕过成立、源 IP 伪造在默认配置下证伪）。以下保留原始断言，修正见每条末尾的【验证】行与第十一章。

**S-P0-1 · Redaction/TokenGuard 悬空引用 fail-open**（仅第二份命中，原判最严重）
`internal/redaction/engine.go:428`、`internal/tokenguard/manager.go:294-298`。策略 ID 非空但查不到时，引擎 `return value, nil` / `Decision{Allowed:true}`——跳过自定义规则。安全性依赖控制面的引用完整性检查，据称有绕过序列：`禁用项目 P → 删除 P 引用的策略 → 重新启用 P`。
**【验证：REFUTED】** fail-open 分支真实存在，但攻击链在第③步被 `admin_projects.go:386` 的 `validateProjectReferences` 以 409 拦截（重新启用时校验引用的策略仍存在）；另有两层纵深防御——运行时鉴权对禁用项目 fail-closed（`auth/snapshot.go:91`，流量到不了引擎）、启动期一致性扫描发现悬空引用即拒绝启动（`redaction.go:28`）。且命中放行分支时 7 类硬编码密钥的强制基线仍生效，**非"零脱敏"**。**降级为加固建议**：去掉删除守卫 `admin_redaction.go:269`/`admin_token_guard.go:297` 的 `Enabled` 条件，消除存储中残留悬空引用这个弱面（不构成可利用漏洞）。

**S-P0-2 · 审计 HMAC 密钥与被审计者同域**（两份一致）
audit HMAC key = `HKDF(master.key)`。持有 master.key + data_dir 的主体既是被审计者，又能派生审计密钥 → 重建任意事件序列 → 重算全链 → 重写 checkpoint。`reconcileAuditCheckpoint` 比较的两个对象都在 TB-4 内、都可写。
**【验证：PARTIAL】** **File 模式 CONFIRMED**：`vault/audit.go:10` 确认纯 master.key 派生，两个比对对象都在 data 目录内，且全库无任何外部锚点（deadman 只外发心跳、不含 audit LastHash）——无痕重写成立。**KMS/key_slots 模式 REFUTED**：磁盘无 master.key 明文（config 禁止），仅持 data 目录、无 KMS 凭据者无法派生 audit key，且 KMS 使用留痕 CloudTrail。**修复**：推荐 KMS 模式；File 模式补外部锚点（`Summary{Records,LastHash}` 周期性推到 syslog/S3 Object Lock），把 File 模式的"重写全链"变可检测。

**S-P0-3 · Developer Workbench 默认启用，打通控制面 → 数据面**（仅第二份命中）
`internal/app/admin_developer.go:70` 把 admin 监听器上的请求注入 gateway 路由树。据称绕过只作用于 gateway_listen 的网络控制，且转发 `X-Forwarded-For` 可伪造数据面源 IP。
**【验证：PARTIAL】** **(a) 绕过网络隔离成立但须重述**：默认确实 enabled（`config/default.go:41`），确实绕过防火墙/WAF/mTLS/IP 白名单等网络层控制——但**不绕过认证**，调用方仍须是持会话+CSRF+MFA 的合法管理员且持有效 API key（`runtime.go:955` 挂 `requireAdminMutation`），属"认证管理员的横向能力"而非匿名绕过。**(b) 源 IP 伪造默认配置下 REFUTED**：`admin_developer.go:51` 保留真实 `RemoteAddr` 未改写，默认 `trust_proxy_headers=false` 使 gateway 忽略 XFF（`handler.go:692`）；伪造仅在"手动开启 trust_proxy_headers 且把 admin 网段列入 trusted_proxy_cidrs"的非默认双重误配下可达。admin 侧审计根本不记 source IP，不可污染。**修复**：默认关闭 Developer Workbench 或文档明示它打破网络隔离假设（降为加固，非 P0）。

### 高危攻击链（最危险的一条，两份殊途同归）

**未认证 DoS → fail-closed 反噬 → 静默植入后门**：攻击者无需凭据，用无 Origin 头狂刷 `POST /admin/api/v1/session/login`——审计写入发生在限流**之前**（`admin_session.go:41`），每次触发 `fsync` + `recordsByEventID` 永久增长 → 磁盘写满/OOM。因审计是 fail-closed，磁盘满后所有管理操作返回 503。此时（本就持有或已窃取会话的）攻击者创建后门 gateway key：`PutGatewayKey` 成功且已载入内存快照 → **密钥立即生效**，但 `auditAdminMutation` 失败返回 503 却**不回滚**（`admin_projects.go:229`）——变更无审计记录。**这条链把项目引以为傲的 "fail-closed 审计" 从安全属性反转成了攻击杠杆。**

### 中低危与已缓解

- **SSRF 残余缺口**（两份一致）：`validateAddress` 已拦截 169.254.169.254（IMDS）、RFC1918、link-local，质量很高；但放行 CGNAT `100.64.0.0/10`——第二份指出这直达**阿里云元数据 `100.100.100.200`**；另放行 `192.0.0.0/24`、`198.18/15`、`240.0.0/4`、NAT64。修复：加显式 deny 前缀表。
- **数据面无认证前限流**（两份一致）：认证在完整 JSON 解析之后才发生，gateway router 只有 `recoverPanics`，无全局连接/速率闸；`http.Server` 未设 `WriteTimeout`。伪造 Bearer + 4MiB 深嵌套 JSON 并发即可 CPU/内存放大 DoS。
- **ledger 只有 CRC32 无密码学完整性**（仅第一份命中）：与 audit 的 HMAC+hash 链严重不对称；磁盘写权限即可伪造 `cost_micros_usd` 绕过预算。修复：ledger 帧升级为 HMAC。
- **MFA 注册竞速**（仅第二份命中）：`MFAPolicy=required` 但管理员未注册 MFA 时，仅凭密码拿到会话的攻击者可抢注自己的 TOTP。
- **`safelog` 白名单式脱敏是 fail-open 设计**（两份一致，与 BUG #3、测试盲区同源）：未覆盖 `hms_`/`hmt_`/`setup_` 前缀与 Group/LogValuer/Any 形状。
- **已缓解，明确肯定**：RE2 正则无 ReDoS、embed.FS 无路径穿越、上游请求头零透传、审计 HMAC+hash 链+checkpoint 检测尾部截断、备份 Zip-Slip 防护、Admin JSON `DisallowUnknownFields`+拒绝尾随值、配置层强制非 loopback 必须 TLS。

### 安全成熟度评分：**7.4 / 10**

会话/密码学/SSRF/前端/KMS 达到甚至超过商业安全产品水准（作者显然带着威胁模型在写代码）。短板呈现清晰模式：**防御在"设计层"很完整，在"边界与降级路径"上有系统性缺口**——脱敏只覆盖 happy-path 数据形态、fail-closed 承诺没有配套的可用性保护、认证边界画在解析之后、审计用 HMAC 而同为状态权威的 ledger 只用 CRC32。**最高杠杆的三项修复**（合计不到 50 行）：safelog 补 `Resolve()`+Group 递归+Any 兜底、登录限流提到 Origin 检查之前 + 失败审计聚合采样、gateway 加认证前 O(1) 密钥预检中间件。

## 十一、对抗验证（P0 findings 复核）

对 6 条最严重的 findings 各派一个独立对抗验证角色，任务是**证伪**——默认 finding 是错的，只有在代码里逐步复现出完整路径、且找不到任何拦截时才判 CONFIRMED；找到拦截防御则 REFUTED；部分成立则 PARTIAL 并精确划定边界。这一步把"并行独立评审的推断"收敛为"经过对抗核验的结论"。

**结果：6 条无一条原样照收。** 1 条被完全证伪，5 条被收窄或纠正——其中包括原本的头号安全 P0。

| # | 原 finding | 裁决 | 复核结论 |
|---|---|---|---|
| 1 | 熔断器 `Done(nil)` 复位保护 | **PARTIAL** | (a) 半开探针被本地中止即误闭合 **CONFIRMED**（限 half-open 窗口，完全 open 期 `Acquire` 短路走不到）；(b) "混合流量永不跳闸" **夸大**——连续 5xx 仍跳闸，只有失败与非失败持续交替才压制。现有测试 `manager_test.go:32` 反把缺陷当预期行为。 |
| 2 | Redaction/TokenGuard 悬空引用 fail-open | **REFUTED** | fail-open 分支真实存在，但攻击链在"重新启用项目"时被 `admin_projects.go:386` 的 409 拦截；另有鉴权 fail-closed（`auth/snapshot.go:91`）+ 启动期一致性扫描（`redaction.go:28`）两层纵深。命中放行时硬编码密钥基线仍生效，非"零脱敏"。**原头号安全 P0 不可利用。** |
| 3 | 审计密钥与被审计者同域 | **PARTIAL** | **File 模式 CONFIRMED**（纯 master.key 派生、两比对对象都在 data 目录、全库无外部锚点）；**KMS 模式 REFUTED**（磁盘无明文、无 KMS 凭据无法派生、CloudTrail 留痕）。 |

### 对这次评审的启示

1. **对抗验证的价值被这一轮直接证明**：并行评审最吓人的那条 P0（Redaction fail-open）经证伪其实打不穿。如果跳过这一步，报告会把一个不可利用的问题当成头号安全事故推给开发团队——这正是"发现型"评审的系统性风险：它擅长指出"这里的代码分支有问题"，但不擅长回答"这条路径在完整系统里真的能被走到吗"。
2. **交叉证实 ≠ 正确**：safelog 是四角色交叉命中的，置信度按理最高，但对抗验证仍指出它"有洞无触发点"。交叉证实提高的是"这段代码确实可疑"的置信度，不等于"这是一个正在造成危害的漏洞"——后者需要可达性与后果的独立核验。
3. **净化后的优先级更可信**：真正未被任何验证削弱、且匿名可达的安全问题，其实是那条"未认证审计洪泛 → fail-closed 反噬"攻击链（P0 第 3 项）——它不依赖任何前置权限，也没有被证伪。经过这轮净化，它从"并列多条 P0 之一"上升为"最该先修的一条"。

## 附：评审方法说明

八个评审角色 + 六个对抗验证角色各自独立通读代码（合计约 800 次工具调用），不共享中间结论；安全威胁建模由两个互不知情的角色独立完成，6 条最严重 finding 再各经一个对抗角色证伪。交叉汇总时发现的一致性信号（多角色独立指向同一问题，是多角色评审最有价值的产出）：交叉汇总时发现的一致性信号（多角色独立指向同一问题，是多角色评审最有价值的产出）：

- **熔断器 `Done(nil)`**：核心逻辑、BUG 排查、测试盲区**三角色**独立发现，判定一致 → 最高置信度。测试盲区补上了根因（中止路径零测试）。
- **safelog 脱敏失效**：BUG 排查、两份安全威胁建模、测试盲区**四角色**独立命中。
- **SSE 裸 `\r`**：核心逻辑（解码侧）、BUG 排查（编码侧）、两份安全评审共同指向同一规范缺口的两面。
- **数据面无认证前限流 / `recordsByEventID` 无界增长 / 变更先落库审计后写**：逻辑与安全评审交叉证实。
- **"最佳实践未下沉" / "abort path 各写各的"**：交互、视觉、逻辑、测试盲区从四个方向指向同一工程习惯——成功主干扎实、中止/清理/降级路径薄弱。
- **"内部质量高于外部呈现"**：可用性（校验文案没送到调用方）、视觉（token 只管住颜色）、安全（脱敏只覆盖 happy-path 形状）三向印证。
