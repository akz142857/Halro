> 本文件是**方案**。执行后的报告落在 `release-1.0.0-report.md`，整改台账落在 `progress.md`，继承核对台账落在 `carry-forward.md`（见第 8 节）。
> 评审框架（角色定义、选择指南、对抗验证方法论）见 [`docs/review/README.md`](../../README.md)，本文不重复定义，只做"这一轮该怎么跑"。

## 1. 本轮的性质

产出必须是**一个放行判断**：v1.0.0 能不能发；不能发的话差什么、每一项由谁在什么条件下关闭。问题清单是达成这个判断的手段，不是终点。`v1.0.0-rc.2` 标签在本轮里是**发布流水线的验证载体**（G4），不是评审对象本身。

这决定四件事，贯穿全文：

1. **每条发现除 P0/P1/P2 外，必须额外标注"是否阻塞发布"。** 严重但可用运维手段绕过的，和不严重但发出去就收不回的（存储格式、公开 API 契约、发布说明措辞），在放行评审里的次序与周期评审不同。
2. **证据链本身是被审对象。** `docs/verification/` 七份、`docs/milestones/implementation-status.md`、release workflow 的门禁、runbook——不是背景材料。上线前最典型的失败模式是"每份文档都说自己通过了，但没人对着真东西跑过一遍"。
3. **实跑不可替代。** 备份恢复、runbook 演练、容量实测、发布流水线端到端四项列为**硬性判据**（G4~G6、G9）。这四项在 260805、260807 两轮里一直缺席，260809 计划要做但那一轮没跑成。读代码得出的结论在这四项里不算证据。
4. **必须产出"已知限制"清单**并进入发布说明。单写者、单数据目录、无 HA（[HA 提案](../../../todo/halro-ha-architecture.zh-CN.md) 已定 1.1.0）、Gemini/Bedrock Beta 能力上限——这些不是缺陷，但不写进发布说明，第一个把它跑成两副本的运维就是我们的责任。

### 2.2 本区间的新增面

按需要独立评审对象的粒度归并：

1. **拓扑提交协议**（`18f3939` + `a96cf4b` + `c051edc`）——store commit 成为唯一提交点，审计记录与 mutation 同事务落盘，激活失败让运行时进入 stale 并**拒绝数据面流量**。这是本区间**最关键的新机制**，它改的是"管理面变更何时对数据面生效"这条语义，且新引入了一个可以让网关整体拒流的状态。
2. **能力探测与调用接口识别**（`7d1a48b`、`4af0228`、`aa21324`、`14e4413`、`acb136c`）——调用接口改为探测识别而非询问；能力探测新增 Admin 端点面与出网面；探测的计费调用记的是 `ProviderCalls` 计数，不进 Ledger。
3. **幂等键成为创建操作的必填项**（`c051edc`）——Provider / Deployment / Route / Project 的记录 ID 由 `Idempotency-Key` 派生，重试撞 409。这是**对外 API 语义的收紧**，1.0.0 发出去就固定了。
4. **私网端点开关真正生效**（`95b5d47`）——`allow_private_provider_endpoints` 之前形同虚设，现在会生效。开关一旦生效，出网面就真的变了。
5. **前端类型尺度整改**（`de53ee0`、`f058d2f`、`dbe9318`）——260810 视觉评审 P1 的整改，含 12px 下限。
6. **签名模型目录与调用目标解析**（`5041976`、`b206285`）——新的外部信任输入。

### 2.3 260811 API 全链路评审的七条 finding 已宣告全部关闭

### 2.5 发布流水线自身仍未验证

`v1.0.0-rc.1` 标签存在，但从未产出 Release。已核实的机制事实：`.github/workflows/release.yml` 的 `publish` job 带 `environment: v1-release`（`release.yml:264`），并在发布前强制校验 `secrets.M11_RELEASE_EVIDENCE_JSON`（`release.yml:277-284`）。**未验证**的是三者中哪一个导致 job 未完成：Environment 未配置或未审批、secret 未设置、job 根本没被触发。

这是 B3 的第一号问题。在它有结论之前，任何"我们准备好发版了"都是空的。本轮用 rc.2 实证关闭它（G4）。

### 4.3 模型合规与拒答处置（本轮以 Fable 5 执行，这一节是执行要求）

本轮预期由 Fable 5 承担全部或大部分角色。有三条与之相关的事实，直接决定提示词怎么写：

**一、Fable 5 的安全分类器覆盖网络安全类内容。** 官方定位是它在找 bug 上的能力提升**不包括以安全为焦点的分析**。对自有代码库做防御性加固属于良性场景，但仍可能被误判。

**二、被拒时返回 HTTP 200 + `stop_reason: "refusal"`，不是报错。** 也就是说一个安全角色可能"顺利完成"却交回空结论，而汇总时看起来只是这个角色没发现问题。**这是本轮最危险的失败模式**：一条被误当作 REFUTED 的真问题会带着上线。

**三、Fable 5 要求 30 天数据保留；零数据保留（ZDR）组织下每个请求返回 400，与内容无关。** 开工前先用一个角色试跑验证可用性，再铺开。

据此，`role-prompts.md` 的通用前置块对所有角色施加以下约束。它们同时是合规要求和质量要求——把评审锚在"我们的控制点在哪、是否 fail-closed"上，本来就比锚在"怎么打进去"上更有产出：

- **声明立场**：这是对自有代码库的授权防御性评审，目的是加固本系统。这是准确的上下文，不是规避话术。
- **要什么**：信任边界、控制点清单、每个控制点在异常路径上是 fail-closed 还是 fail-open、缺陷的可达性论证（哪些前置条件必须成立）、修复方向。
- **不要什么**：可直接运行的攻击脚本或武器化 PoC；绕过检测/日志/审计的手法；针对第三方或线上系统的操作；任何真实凭据、密钥、生产数据的粘贴。复现路径以"代码路径 + 触发前置条件"描述，证据用 `file:line`。
- **自检与留痕**：每个角色在结论末尾列出它实际读过的文件与运行过的命令。**空引用即视为疑似拒答或截断**，不得计入"查过没发现"。
- **处置**：确认拒答的角色，先按上述边界重写提示词跑第二次；仍拒答则改派另一模型（Opus 5 系）跑同一角色。角色本来互不知情、独立产出，代价是一个角色重跑，不是整轮作废。**报告必须标注每个角色实际跑在哪个模型上**。
- **提示词风格**：给 Fable 5 的提示词写成"目标 + 不允许空白的下限"，而不是枚举式清单——过于规定性的提示词对它反而降低产出质量。`role-prompts.md` 已按此写法给出。

## 5. 必须有结论、不允许空白的清单

角色多的时候，最想看的东西反而可能没人碰。以下每一条在报告中必须有明确的正面或负面结论，**"未涉及"不是可接受的状态**：

| # | 事项 | 归属 | 为什么在这张表上 |
|---|---|---|---|

## 6. 对抗验证

发现型角色产出后，对最严重的 5~7 条各派一个独立"证伪型"角色，**默认 finding 为错**，要求在代码里复现完整路径或找出已有拦截防御，裁决 CONFIRMED / REFUTED / PARTIAL。

两轮历史数据支持这个投入：260805 六条最严重发现无一原样成立（头号安全 P0 被完全 REFUTED）；260807 五条中四条 CONFIRMED、一条 PARTIAL（紧急程度高估约两档）。**在放行评审里这一步比以往更重要**——误判为 P0 会无谓推迟发布，误判为已缓解会带着上线。

预期的对抗对象集中在第 5 节的 1、2、3 三项，以及 A5 报出的最严重 BUG。

**证伪型角色同样适用 §4.3 的合规与拒答约束，且这里最不能出错**：一个被拒答的证伪角色返回空结论，而空结论在裁决表里长得像 REFUTED。因此证伪角色的结论必须包含它读过的文件与走过的代码路径；不含这些的裁决一律作废重跑。

## 8. 执行方式与产出物

执行顺序：

```
第 0 步 继承核对（§3，单角色，先于一切）
   ↓
A/B/C/D 四档 15 个角色并行，互不知情
   ↓

   ↓

   ↓
汇总：八维度打分 → G1~G9 逐条判定 → Go / 有条件 Go / No-Go
```

执行要求：

- 15 个发现型角色**并行启动、互不知情**，独立通读、独立产出，不共享中间判断。安全（A2/A3）沿用双角色互证。
- 每条发现必须带 `file:line`，区分【肯定 / 建议 / 问题 / 疑似BUG】，并**额外标注是否阻塞发布**。
- **每个角色的产出必须标注它实际跑在哪个模型上**，并附它读过的文件与运行过的命令（§4.3 的拒答自检）。
- C1、C3、B1 与 G3~G6、G9 涉及**实跑**：产出必须包含实际命令与输出，读代码得出的结论在这些项里不算证据。
- 汇总时主动标注：(a) 跨角色交叉证实的问题；(b) 与历史结论矛盾、或表明某项"已完成"需要撤销的发现。
- 若结论为 No-Go 或有条件 Go，产出一份**最短关闭路径**：按"阻塞项 × 关闭成本"排序，指出先做哪三件事能把状态翻成 Go。
