## 1. 结论（≤200 字）

本区间的新门禁在**单元与注册表层**守护得相当好：漂移扣留、越界能力拒绝、签名目录验签、迁移拒绝、ADR 0018 并发额度，都有以缺陷行为命名的负面用例，且 CI 对全树跑 `-race`。盲区高度集中在**一处**：拓扑提交协议新引入的 stale 状态。它是本区间唯一能让整个数据面拒流的状态，却只有一条**直接注入 `markStale` 标志**的测试，没有任何测试从真实调用点触发它。正因为没人从调用点走过一遍，两处 fail-open 缺陷至今不可见，我已用只读探针实证复现：**任一子系统激活成功会清掉另一子系统造成的 stale**，且**恢复循环会在 5 秒内清掉 redaction / Token Guard 的 stale 而不重跑那两条激活**——策略仍是旧的，运行时却自称 current 且 ready。这不是"缺一条测试"，是缺测试导致的实质 fail-open。

## 2. 本角色评分

**6.5 / 10**。

**为什么不是 7**：7 分档是"机制建得对、门没上锁——存在 fail-open 缺口或缺回归守护"。这里超出了那一档：缺口不是推断出来的，是**两次实证复现**的 fail-closed 反转（A4-01、A4-02），且落在本区间最关键的新机制上；同时本轮唯一一处对外收紧的语义（Idempotency-Key 必填）在 5 个 create 端点里有 3 个**一条负面断言都没有**（A4-05）。

**为什么不是 6**：6 分档要求"P1 数量可观"或"同一种错误在多处重复"。这里 P1 只有两条，且是同一处机制的两个面；本区间其余新增面（能力目录、签名快照、探测、迁移、withholding）的负面测试质量明显高于历史水平——`TestAnEntryExceedingItsProfileIsRefusedRatherThanTrimmed`、`TestManagerRejectsRollbackAndSequenceReuse` 这一类测试名本身就是不变量，且 CI 的 `-race` 是全树无条件的，不是可选门禁。

要到 8 分还差什么，见 §7 的补测试清单（10 项，其中 3 项是 8 分的硬前提：A4-01/02 的修复 + 从调用点出发的 stale 负面测试 + 三个 create 端点的必填/重放断言）。

## 3. 肯定项（值得在后续改动中保护）

1. **`-race` 是全树、无条件的门禁**，不是"改并发时才跑"：`.github/workflows/ci.yml:55` 是 `go test -race ./...`。`AGENTS.md:24` 的分层策略只约束本地迭代，不削弱 CI。因此"新不变量有没有 race 断言"的问题，等价于"有没有并发地跑过它"，而不是"有没有开 race"。
2. **ADR 0018 的额度不变量有真正并发的负面用例**：`internal/budget/admission_test.go:26`（64 goroutine 抢同一预算，断言 durable 余额不超预算、`pendingAdmitted` 归零无泄漏）、`:98`（append 失败必须把已准入额度还回去）、`:169`（结算在途时保守方向可接受）、`internal/budget/manager_test.go:276`（千次并发预约不超卖）。这是本仓库并发测试的正确样板。
3. **越界能力"拒绝而非钳制"在三层各有负面测试**：目录层 `internal/modelcatalog/catalog_test.go:595`、`:343`、`:277`；部署解析层 `internal/app/admin_deployment_resolution_test.go:141-145`（`operator_declared` 也不能顶穿 profile ceiling）、`:197-207`；调用目标层 `internal/domain/invocation_target_test.go:68`。三层各自独立断言，不靠彼此。
4. **`activateTopology()` 不接受 context 形参**（`internal/app/providers.go:82-86` 的注释点明"call sites are not offered the choice"）——把 F-01 那一整类错误变成编译期不可能。比任何测试都强，值得保护。
5. **扣留测试断言的是"候选为空"而不是"请求later失败"**：`internal/app/capability_withholding_test.go:185-190` 的注释明说"Withheld means withheld"。这是正确的断言层级。
6. **签名目录的负面用例是对抗性的**，不是happy path 的镜像：`internal/modelcatalog/snapshot_dynamic_test.go:95`（版本/过期/pin/未知能力）、`:159`（私钥字节冒充分离签名）、`:175`（快照有效期必须落在签名根有效期内）、`:243`；`internal/modelcatalog/manager_test.go:180`（LKG 丢失后的序列重放）、`:223`、`:255`、`:283`（压缩与解码上限）、`:345`（拒绝重定向）。
7. **探测取消路径是真并发测试**：`internal/app/admin_model_capability_detections_test.go:437` 用后台 worker + Admin DELETE 竞争，断言"迟到的 supported 结果不得存活"。
8. **迁移的拒绝方向有测试且断言"拒绝时未改动文件"**：`internal/store/bolt/store_test.go:735-762`（更高 schema 被拒且未 mutation）、`:563-600`（迁移失败整体回滚）、`:601-640`（被拒的迁移没有改变文件大小）。

### A4-01 · 任一子系统激活成功会清掉另一子系统造成的 stale

- **级别**：P1
- **类型**：【疑似BUG】（由测试盲区导致，不是纯测试缺口）
- **是否阻塞 v1.0.0 发布**：**是**
- **证据**：
  - `internal/app/activation_state.go:52-58` — `markCurrent()` 无条件清空 `staleSince` 与 `reason`，tracker 是**进程级单例**，没有按子系统分维度（`:31-36` 只有一个 `staleSince/reason/generation`）。
  - 四个独立的 `markCurrent()` 调用点：`internal/app/providers.go:94`（拓扑）、`internal/app/admin_projects.go:487`（认证快照）、`internal/app/admin_redaction.go:327`（脱敏策略）、`internal/app/admin_token_guard.go:345`（Token Guard 策略）。
  - 四个 `markStale()` 调用点同理：`providers.go:91`、`admin_projects.go:484`、`admin_redaction.go:324`、`admin_token_guard.go:342`（外加恢复循环内的 `activation_state.go:125`）。
  - **实证**（只读探针，见 §8 PROBE1）：注入 `markStale("redaction policies: injected failure")` 后执行一次**成功的、完全无关的** `activateTopology()`，`status()` 变为 `stale=false reason="" generation=1`；数据面从 503 恢复为 401（即已放行到鉴权层），`/health/ready` 返回 200。
- **触发前置条件**：(a) redaction 或 Token Guard 策略的激活失败一次（`ListRedactionPolicies` 读失败、`ReplacePolicies` 校验失败、或 30s `activationTimeout` 到期）；(b) 之后任意一次 Provider / Deployment / Route / Credential / Price / Project / Gateway Key 的成功变更，或恢复循环跑一轮。
- **后果**：脱敏（数据泄漏控制）或 Token Guard（准入控制）仍在按**旧策略集**工作——`redactor.ReplacePolicies` 与 `tokenGuard.ReplacePolicies` 在全仓各只有一个调用点（`admin_redaction.go:320`、`admin_token_guard.go:338`），除这两条激活路径外没有任何东西会重新装载它们；启动期装载在 `internal/app/redaction.go:15`、`internal/app/tokenguard.go:13`。于是运行时对外自称 current 且 ready，实际上在用被管理员刚刚撤销的策略处理流量。这是 CLAUDE.md 列为最高严重度的 fail-open 方向。
- **为什么现有测试看不见**：唯一的 stale 测试 `TestStaleActivationRefusesDataPlaneTraffic`（`internal/app/commit_protocol_test.go:56`）在 `:64` 直接调 `markStale`、在 `:87` 直接调 `markCurrent`，中间不跨越任何子系统。测试把 tracker 当成一个布尔开关来验，而缺陷恰恰在"这个开关被谁清"。
- **修复方向**：让 stale 按原因分维度（每个激活域一个 flag，`Stale = 任一域为真`），`markCurrent(domain)` 只清自己那一维；或最小改动——`markCurrent` 只在 `reason` 属于本域时清除。同时补一条从调用点出发的负面测试（见 §7 T-1）。

### A4-02 · 恢复循环清掉了它并不修复的 stale

- **级别**：P1
- **类型**：【疑似BUG】
- **是否阻塞 v1.0.0 发布**：**是**（与 A4-01 同一处修复即可一并关闭）
- **证据**：
  - `internal/app/activation_state.go:107-131` — `runActivationRecovery` 每 5 秒（`:28` `activationRetryInterval`）只重跑 `activateTopology()`（`:119`）与 `reloadAdminAuth()`（`:124`）。它**从不**调用 `activateRedactionPolicies()` 或 `activateTokenGuardPolicies()`。
  - `activateTopology()` 成功即 `markCurrent()`（`providers.go:94`），于是 stale 被清除。
  - **实证**（§8 PROBE2）：注入 `markStale("token guard policies: injected failure")` 后启动恢复循环，**5.5 秒**内 `status()` 变为 `{Stale:false Reason:"" Generation:1}`，而 Token Guard 的策略集从未被重新装载。
- **触发前置条件**：redaction 或 Token Guard 激活失败一次即可，**不需要任何后续管理员操作**——恢复循环自己就会在一个 tick 内把它清掉。这比 A4-01 更容易命中：A4-01 需要一次无关变更，A4-02 是自动发生的。
- **后果**：同 A4-01，且"自愈"的宣称（`activation_state.go:18-22` 注释："this is an outage that heals itself once the underlying cause does"）对这两个域是**假的**——它治好的是症状（拒流量），不是病因（旧策略）。真正的恢复只有两条路：进程重启（`redaction.go:15` / `tokenguard.go:13` 重新装载），或管理员再保存一次该类策略。文档与 runbook 里都没有这条恢复说明。
- **为什么现有测试看不见**：`runActivationRecovery` 在全仓**零测试覆盖**（`grep -rn "runActivationRecovery" internal/` 仅得实现与启动处）。它是一个每 5 秒跑一次的后台循环，没有任何用例观察过它清了什么、没清什么。
- **修复方向**：恢复循环重跑**全部**激活域（拓扑、认证、redaction、Token Guard），或按 A4-01 的分维度方案让它只清自己修好的那一维。补测试见 §7 T-2。

## 6. carry-forward 三处边角的逐条结论

### 边角 ① · F-05 只测了"禁用 binding"，"整体移除"变体无独立测试

**结论：行为正确，缺口纯属测试层面，P3，不阻塞。**

- 守卫按"启用集合缺席"判定：`internal/app/admin_providers.go:1164-1169` 从入参 instance 的 `EffectiveProfileBindings()` 构建 `enabled` 集合，`:1181` 只问 `!enabled[bindingID]`。移除与禁用因此走**同一分支**，与 `:1146` 注释"switching off — or simply omitting"一致。
- **实证**（§8 PROBE3，只读探针）：把被引用的 chat binding 从 `bindings` 列表里**整体移除**后 PUT，返回 `409 binding_referenced_by_deployment`，错误文案与禁用变体完全一致，且 `stored.Revision` 保持 2 未动、bindings 仍为 2 条——refusal 未落盘。
- 残余风险：一个退化情形值得知道——若请求把 `bindings` 传成**空列表**，`domain.ProviderInstance.EffectiveProfileBindings()`（`internal/domain/models.go:291-302`）会从 Provider 顶层字段**合成**一条 legacy binding，其 ID 由 `DefaultProviderProfileBindingID(p.ID, p.ProfileID)` 派生。此时 `enabled` 集合的内容不再来自请求体。这条路径同样无测试。
- 补测试：§7 T-11（低优先级，两条断言）。

### 边角 ② · F-01 只覆盖 Key/Project/Route，Provider/Deployment 断连变体无用例

**结论：机制层面已被更强的守护覆盖，测试缺口可接受，P3，不阻塞。**

- F-01 的缺陷类别是"激活跑在 Admin 请求的 context 上，客户端断连即中止"。该类别现在是**编译期不可能**：`activateTopology()` 不接受 context 形参（`internal/app/providers.go:82-86`，注释明说不给调用方这个选择），context 由 `activationContext()` 从 `r.backgroundCtx` 派生（`:72-80`）。Provider 与 Deployment 的变更走的正是 `activateTopologyAfterCommit()`（`admin_providers.go:131,203,284,332,654,717,769`；`admin_deployments.go:176,348,405`）——与已有用例覆盖的 Route 是**同一个函数**。
- 因此 Provider/Deployment 变体不可能在 Route 变体通过时失败。补一条只增加执行时间，不增加信息量。
- **但**：`activationTestRuntime` 的三条用例（`activation_context_test.go:47,73,97`）确实只驱动 Key/Project/Route。若将来 Provider/Deployment 改走别的激活函数，无测试报警。这属于 A4-10 同类的"纪律无守护"，优先级同为 P3。
- 补测试：§7 T-12（可选）。

### 边角 ③ · 子项 2 的两个方向性决定没有从调用点出发的负面测试

**结论：这是三处边角里唯一的实质问题，且比 carry-forward 估计的严重——它不是覆盖缺口，它掩盖了两处 fail-open 缺陷。升级为 P1，阻塞。**

- carry-forward 的描述准确：`admin_redaction.go:324` 与 `admin_token_guard.go:342` 的"激活失败 → markStale"、`admin_alerts.go:355-362` 的"告警投递失败**不**标 stale"（注释给出了理由：告警是出站通知，不决定请求是否被授权/脱敏/准入，为它拒绝全部流量是更大的事故——这个方向性判断我认为**正确**），三者都没有从调用点出发的负面测试。
- 本次从调用点方向核对后发现：**"markStale 之后会怎样"这一半根本不成立**。
  - A4-01：任一其他子系统的成功激活会清掉它（PROBE1 实证）。
  - A4-02：恢复循环 5 秒内自动清掉它，且不重跑 redaction/Token Guard 激活（PROBE2 实证）。
  - 而 `redactor.ReplacePolicies` / `tokenGuard.ReplacePolicies` 在全仓各只有一个调用点（`admin_redaction.go:320`、`admin_token_guard.go:338`），所以策略确实仍是旧的。
- 告警侧"不标 stale"的决定不受影响（它本来就不进 stale），但同样零测试：没有用例断言"告警端点激活失败**不得**让数据面拒流"。这条负面测试有价值——它锁住的是一个刻意的**非**行为，最容易在后续重构中被"顺手补齐"成 fail-closed 而造成大范围拒流。
- 补测试：§7 T-1、T-2、T-3。
