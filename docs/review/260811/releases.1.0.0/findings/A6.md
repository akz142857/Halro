# A6 · 架构设计与工程规范（v1.0.0 放行评审）

评审区间：33bc13b → 2cd24a7（HEAD 已核实为 2cd24a76a569fe53f878c1ab1be31441f4c008e0）。本角色不受 diff 限制，判断整体形状。

## 1. 结论（≤200 字）

本区间的新增子系统**延续了既有分层，没有绕过**：modelcatalog 独立成包且只依赖 domain+safetransport，能力探测的 Provider I/O 全部经 provider.Adapter 接口执行，全仓无反向导入。pre-1.0.0 纪律总体被执行——旧构造被删除而非并存。但 internal/app 作为组合根在吸收正确性关键机制（提交协议、激活状态、漂移复核），拆分前提在以每轮约 2.5 倍的耦合增速衰减；一处对外契约文档与新语义直接矛盾。无阻塞发布项。

## 2. 本角色评分：7.5 / 10

锚点对照（scoring-rubric.md §3）：不是 7——本区间机制的门是上了锁的（漂移扣留有具名测试、指标标签有钳制函数、i18n 有精确对等测试、路由删除有回归守护），不属于"机制建得对但门没上锁"。不是 8——8 档要求"文档与代码一致"，而 `docs/contracts/idempotency-contract.md` 与本区间唯一一处对外语义收紧直接矛盾（A6-07），metrics-reference 存在遗留缺口（A6-09）。7.5 表示：结构纪律达到 8 档，契约文档一致性停在 7 档。

## 3. 肯定项（值得在后续改动中保护）

1. **modelcatalog 的分层是教科书式的**。包内仅导入 `internal/domain` 与 `internal/safetransport`（`internal/modelcatalog/manager.go:19`）；远端目录抓取强制 HTTPS + host 白名单（`internal/modelcatalog/manager.go:143-151`），下载有 1 MiB 上界（`internal/modelcatalog/manager.go:28`、`readBounded` at `manager.go:351`）；消费方只有 internal/app。新的外部信任输入没有获得任何越过 safetransport 的特权。
2. **能力探测没有绕过 provider 层**。探测计划与执行走 `provider.CapabilityDetector` / `provider.Adapter` 接口（`internal/app/admin_model_capability_detections.go:226-227`、`:296-310` 的 unwrap 链），app 只做编排；本区间非测试 Go 代码中未新增任何 `http.Get/http.Client/net.Dial` 直连（对区间 diff 的扫描为空）。
3. **pre-1.0.0 删除纪律被执行而且有守护**。旧的 `/providers/{id}/models` 路由被替代后是 404 而不是并存，且有具名测试钉住（`internal/app/admin_invocation_targets_test.go` 中 `TestAdminUsesInvocationTargetRouteAndRemovesLegacyModelsRoute`，对旧路由断言 `http.StatusNotFound`）；无人读取的 deployment scheduling 字段被直接删除（提交 3580a89）；错误的探测结果用 reset 迁移丢弃重建而不是双读兼容（`internal/store/bolt/store.go:609`、`:630`），迁移编号/名称契约未被破坏。
4. **Prometheus 标签纪律**。capability 指标每个标签都经有界钳制函数收敛到枚举（`internal/app/capability_metrics.go:113-123`、`:137-173`），越界值坍缩为 `"unknown"`；模型/部署/凭据 ID 明确排除在标签外（`capability_metrics.go:18-21` 的注释即契约）。
5. **数据面拒流中间件的位序有书面理由**：`refuseWhileSnapshotsStale` 放在限流与鉴权之前，因为拒流的理由正是鉴权快照不可信（`internal/app/activation_state.go:77-84`）。这一行注释是防止后人"顺手调整中间件顺序"的关键。
6. **全仓层次无违规**：internal/ 下除 app 外无包导入 app；provider/gateway/gatewayapi/semantic 无一导入 store（全仓 grep 为空）。

**结论（不是重复上一轮的判断）：** "1.0.0 前不拆"仍然正确——这一点没有争议价值，拆的收益仍是零功能零安全，而风险窗口正卡在发布前。但 260807 关闭 P2-19 时的两个支撑事实**已经不再成立**：(a) "五把锁零外部引用、状态可整体搬走"——`adminTopologyMu` 现在被数据面拒流的恢复循环（`activation_state.go:118`）和 Provider registry 重建（`providers.go`）持有，拆分要么把提交协议一起搬走、要么让锁跨包，两条路都不再是"纯文本替换"；(b) "跨界符号约 11 个、可枚举"——现在约 27 个，且新增的都不是工具函数而是提交协议与能力体系的核心动词（`activateTopologyAfterCommit` 被 3 个 admin 文件调用、`activationContext` 被 4 个、`checkpointAudit` 被 4 个）。**拆分成本在以每个间隔约 2.5 倍耦合增速上升，"以后拆也不贵"这个隐含前提已经失效。** 因此本轮的结论不是"拆/不拆"，而是：1.0.0 后第一个间隔必须做一次书面二选一（宣布 app 为永久归宿，或立即拆），并即刻停止引用 08-07 的边界表——它已过期。另一个应当明说的事实：本区间**有能力把新子系统放进独立包时确实放了**（modelcatalog 3,392 行独立成包），落进 app 的 4,300 行（capability_* + admin_model_* + activation_state 等 18 个文件）是编排与提交协议——前者归 app 是对的，后者意味着 app 从"组合根"变成了一条最高严重度不变量（mutation 原子性 + stale 拒流）的**属主**，它的正确性守护只有 app 包内测试（`commit_protocol_test.go`、`activation_context_test.go`）。这是接受得了的状态，但要知道自己接受了什么。
