# A3 · 安全评审 · 授权与状态完整性

角色视角：已通过认证的管理员、或已落盘的状态，能否被用来把系统带到一个不该到达的
配置上。产出为控制点与失效方式，不含攻击脚本。

运行模型：**Fable 5（claude-fable-5）**。未遇到任何拒答、`stop_reason: refusal` 或空响应。

---

## 1. 结论（≤200字）

能力体系的核心闸门是**健壮且 fail-closed 的**：profile ceiling 在 `reviewCapabilities`
里被**无条件、最先**检查（源类型的豁免只作用于"目录 vs 声明"这一层，绝不作用于
ceiling）；目录侧任何来源都被 `Clamp` 到 profile 天花板；主 mutation 的审计意图与
store 提交同事务落盘。三条下限里 #1（两个安全阀能否组合越过 ceiling）与 #2（快照经
备份/热加载/重启被降级）**均判为否**——服务用的能力集在每次加载都被重新钳到当前
binding ceiling，漂移 fail-closed，setOffered 只"提供"不"启用"。

但发现一处真实缺口：**binding/provider 的能力天花板本身，对非 strict（chat 家族）
的 Beta profile（Gemini、Bedrock Converse、Mantle）是管理员可写的**，`isStrictOperationProfile`
把它们排除在天花板校验之外——这直接违反 CLAUDE.md "不得放宽 Gemini/Bedrock Beta
能力上限"的钉死约束，是本视角下"管理员把系统带到不该到达配置"的具体路径。另外能力
声明类审计记录是尽力投递、非事务的（下限 #3）。

## 2. 本角色评分：**7 / 10**

机制建得对、主链 fail-closed，但"门差一道锁"：pinned Beta ceiling 对 chat 家族
profile 由管理员可越过（A3-01），二级审计记录不具崩溃安全性（A3-02）。符合 rubric §3
的 7 分档（"机制建得对，但门没上锁——存在 fail-open 缺口或证据只到作者自述级"）。要到
8 分：A3-01 关闭 + A3-02 纳入事务或补回归守护。

## 3. 肯定项（值得保护）

- **P-1 profile ceiling 先于一切、无条件检查**：`internal/app/capability_drift.go:97-104`
  在任何目录/声明比较之前，先判断 `snapshot.Capabilities` 与 `deployment.Capabilities`
  是否都 ⊆ `binding.Capabilities`，否则 `Drifted` 且 `NoLongerSupported` 报告越界项。
  源类型（operator_declared / verified_probe）的豁免只出现在其后的目录比较分支
  （`:152`、`:129`），**永远无法回到 ceiling 之上**。
- **P-2 放行是白名单而非 `!= drifted`**：`capability_drift.go:235-242` `capabilityReviewAdmitsTraffic`
  显式列举可服务状态，新增状态默认不可路由——避免"编译器沉默被当成判断"。
- **P-3 目录侧任何来源都被钳到天花板**：`internal/modelcatalog/catalog.go:380`（`Merge`
  末尾 `Clamp(..., key.Ceiling())`）、`:291`（`Entry.Validate` 拒绝超天花板条目）。
  `Union` 明确注释"绝不授予能力"，且无任何决定服务的路径调用它（`catalog.go:449-461`）。
- **P-4 主 mutation 与审计意图同事务**：`internal/app/admin_audit_intent.go:14-31` 说明
  store commit 是唯一提交点，intent 在 mutation 前构造、随同一 bbolt 事务落盘
  （`admin_deployments.go:163-168` `newAdminAuditIntent` → `PutDeployment(dep, exp, intent)`），
  崩溃后由 `drainAdminAuditIntents`（`admin_audit_intent.go:115-126`）在启动时补投。
  actor 取自服务端认证的 session 而非请求体（`admin_audit_intent.go:34-36`）。
- **P-5 审计链 HMAC + 截断锚点**：`internal/audit/log.go` 为 HMAC 哈希链，`scan`
  逐帧校验序号连续（`:313`）、前向哈希（`:316`）、HMAC（`:333`）；`audit_anchor_verify.go:179`
  的 `AnchorVerdictTruncated` 给出尾部截断的可检测裁决。无任何 Admin 端点可改写/截断
  审计日志。
- **P-6 stale 拒流 fail-closed 且自愈**：`internal/app/activation_state.go` 的
  `refuseWhileSnapshotsStale`（`:84`）置于鉴权与限流之前（"授权快照不可信就不该先从它
  判断"），`runActivationRecovery`（`:107`）每 5s 自动追平，**无需人工**恢复，撤销类
  变更（吊销 key/删除 project）在 stale 期间宁可拒也不 fail-open。

## 4. 发现清单

### A3-01 · 非 strict Beta profile 的能力天花板对管理员可写，越过钉死上限

- **级别**：P2
- **类型**：问题
- **是否阻塞 v1.0.0 发布**：需裁决（触及 CLAUDE.md 钉死不变量，但需管理员且爆炸半径限
  于其自建的 Beta Provider）
- **证据**：
  - `internal/app/admin_providers.go:916-919` provider 级能力天花板校验、`:939-941`
    binding 级天花板校验，**两处都以 `isStrictOperationProfile(...)` 为前置条件**。
  - `internal/app/admin_providers.go:975-982` `isStrictOperationProfile` 仅覆盖
    `ProfileOpenAIMediaResources / BedrockInvokeTitanEmbedV2 / BedrockInvokeTitanImageV2 /
    BedrockAgentRerankCohere35 / BedrockAsyncNovaReel`——**不含** `ProfileGeminiText`
    （`internal/domain/provider_profile.go:32`）、`ProfileBedrockConverseText`（`:33`）、
    三个 Mantle profile。
  - `internal/domain/models.go:269-289` `ProviderProfileBinding.Validate` 不含任何
    `⊆ DefaultProviderCapabilitiesForProfile` 的校验；`internal/domain/provider_profile.go`
    的 `ValidateProviderProfile` 只校验 surface/scheme/profile 组合，不校验能力。
  - profile 钉死默认：Gemini `{Chat,Streaming,Embeddings,DeveloperRole}`、Bedrock Converse
    `{Chat,Streaming,StreamUsage}`（`internal/domain/models.go:500-505`），注释明确"Beta
    profile intentionally declares only ..."。
- **触发前置条件**：管理员通过 `POST/PUT /providers` 对 Gemini 或 Bedrock-Converse
  Provider 传入 `capabilities`（或 `bindings[].capabilities`）含 `tools/vision/reasoning/
  json_mode` 等超出钉死默认的项。天花板校验被 `isStrictOperationProfile==false` 跳过，
  `instance.Capabilities`/`binding.Capabilities` 原样落盘。随后一个 `mode=operator_declared`
  的 Deployment 因 `resolveDeploymentTargetWithCatalog:1079-1085` 只对 `binding.Capabilities`
  做 subset 判断，即可声明并服务这些能力——服务集越过了被钉死、需契约复核才能放宽的
  Beta ceiling。
- **与下限 #1 的关系**：这是下限 #1 追问的"放宽到 Provider ceiling 之上"的**唯一可达
  路径**，但达成它的原语是"被放宽的 binding"，而非两个能力安全阀本身（后者始终被
  binding ceiling 无条件封住，见 §5 下限#1）。代码把 `binding.Capabilities` 当作
  "provider ceiling"，而该 ceiling 对 chat 家族 Beta profile 本身高于钉死的 profile 默认。
- **现有控制点为何没拦住**：`isStrictOperationProfile` 是唯一的天花板执行点，它按
  "单操作 profile"划定范围，恰好把需要保护上限的多能力 Beta profile 排除在外。下游
  provider adapter 以同一 `binding.Capabilities` 构造（`internal/app/providers.go:580`），
  无二次兜底。
- **修复方向**：天花板校验对**所有** profile 生效（去掉 `isStrictOperationProfile`
  前置，或将非 strict 也纳入 `⊆ DefaultProviderCapabilitiesForProfile`）；对确需超默认
  的场景走显式契约复核旗标，而非默认放行。补一条负面测试：Gemini/Bedrock-Converse
  Provider 声明 tools 必须被拒。

### A3-02 · 能力声明类审计记录非事务、崩溃可丢，与实际 mutation 不一致

- **级别**：P3（窗口窄、主 mutation 仍被记录；但直接命中下限 #3）
- **类型**：疑似BUG
- **是否阻塞 v1.0.0 发布**：否
- **证据**：
  - 主 mutation 走事务意图：`admin_deployments.go:168` `PutDeployment(dep,0,intent)` →
    `:177` `completeAdminMutation`（投递 `deployment.create`）。
  - 但能力声明记录走**另一条、非事务**路径：`admin_deployments.go:178-182`
    `auditCapabilitySnapshot` → `admin_deployments.go:191-203` 调
    `appendAdminAuditWithMetadata`（写 `capability.snapshot.created` 与
    `operator_capabilities_declared`）。
  - `appendAdminAuditWithMetadata`（`internal/app/admin_session.go:488-512`）是**直接批量
    追加**到审计日志，不经过 `AdminAuditIntent`、不随 store 事务落盘，也不被
    `drainAdminAuditIntents` 覆盖。
- **触发前置条件**：进程在 `PutDeployment` + `deliverAdminAuditIntent` 已完成、但
  `auditCapabilitySnapshot` 的批量追加尚未 fsync 之间崩溃。重启后 drain 只补主
  `deployment.create` 意图，**不补**能力声明记录。
- **后果**：一个携带 operator_declared 能力（可越目录、按 A3-01 亦可越钉死上限）的
  Deployment 持久存在，却**没有** §8.3 要求的"声明者 + 声明内容 + 目录状态"三合一
  可信记录。审计链在崩溃窗口下与实际 mutation 不一致。
- **现有控制点为何没拦住**：事务意图协议只覆盖一条主记录；二级"能力评审事件"被设计
  成独立事件（`admin_deployments.go:188-190` 注释），但独立的代价是脱离了事务/drain
  的崩溃安全保障。
- **修复方向**：把 `operator_capabilities_declared` / `capability.snapshot.*` 也表达为
  `AdminAuditIntent`（携 metadata），与主 mutation 同事务落盘、同 drain 补投；或在
  drain 里按 Deployment 现状重建缺失的声明记录。

### A3-03 · stale 进出无可信/持久留痕

- **级别**：P3
- **类型**：建议
- **是否阻塞 v1.0.0 发布**：否
- **证据**：`internal/app/activation_state.go:41-58` `markStale`/`markCurrent` 纯内存
  （`activationTracker`）；进出仅经 `r.logger`（`providers.go:90-91`、`activation_state.go:128`）
  记录，**不进** HMAC 审计链，`internal/app/metrics.go`/`capability_metrics.go` 也无专门的
  stale 计量序列。
- **触发前置条件**：任一 mutation 提交后 `activateTopology` 失败即进入 stale（数据面
  全面拒流）；恢复后 `markCurrent` 清除。整段"拒流事故"只在进程日志里留痕。
- **后果 / 下限 #3 的这一半**：管理员**不能**定向、无痕地切换 stale——它由激活成败派生，
  非直接可控（这是好的）；但一段 stale 事故没有防篡改或持久的证明，事后审计只能依赖
  易失的进程日志。
- **修复方向**：stale 进/出各写一条审计事件（actor=system），并暴露 `halro_activation_stale`
  gauge 供告警（与 C2 的指标契约对齐）。

## 5. 三条下限逐条应答

**下限 #1 —— 两个安全阀（`mode=operator_declared` 可超目录声明；目录条目出现在既有
声明之下算复核而非漂移）能否组合成"把能力放宽到 Provider ceiling 之上"？**

**结论：单靠这两个安全阀——否（fail-closed）；但 ceiling 本身对 Beta chat profile
可被管理员越过——见 A3-01。**

- 两个阀都被 **binding/profile ceiling 无条件封住**，封锁点独立于源类型：
  - 创建路径：`admin_deployments.go:550-552`（`deploymentFromInput` 统一 subset 检查）
    与 `:1079-1085`（operator_declared 分支仍 `ProviderCapabilitiesSubset(*retained,
    resolution.binding.Capabilities)`）。
  - 评审/加载路径：`capability_drift.go:97-104` **最先**检查 ceiling，`operator_declared`
    / `verified_probe` 的豁免只在其后的目录比较分支（`:152`）生效。
  - 目录侧：`catalog.go:380`/`:291` 保证目录条目 ≤ `Key.Ceiling()`（= 钉死 profile
    默认），故"复核"分支 `setOffered` 提供的能力也 ≤ 天花板。
  - `setOffered`（`capability_drift.go:209-217`）只写 `AvailableForReview`（建议性），
    **绝不启用**；采纳需一次推进 revision 的管理员 PUT，重新过创建路径的 subset 检查。
- 因此两阀组合**无法**把服务用的 `deployment.Capabilities` 抬到 `binding.Capabilities`
  之上。测试佐证：`internal/app/admin_deployment_resolution_test.go:144,205`
  "a declaration widened the profile ceiling" 断言声明不能越 ceiling。
- **真实缺口在 ceiling 的定义**：对非 strict Beta profile，`binding.Capabilities` 本身
  由管理员写入且不被钳到钉死 profile 默认（A3-01）。相对被契约钉死的上限，能力确实能被
  越过——但原语是"放宽的 binding"，不是两个能力阀。

**下限 #2 —— 能力快照经 Backup/Restore、热加载、进程重启后，是否可能被降级或替换成
更宽松的版本？**

**结论：否（fail-closed）。未找到降级/替换即扩权的路径。**

- **服务用能力集 = `deployment.Capabilities`，非 snapshot**；每次加载
  `reviewCapabilities` 都独立地把 `deployment.Capabilities` 与 `snapshot.Capabilities`
  同时 subset-检查到**当前** `binding.Capabilities`（`capability_drift.go:97-98`）。快照
  即便被替换得更宽松，也不改变服务集，且若快照/服务集超当前 binding → `Drifted` →
  `capabilityReviewAdmitsTraffic` 拒流（`:235-242`）。
- **重启**：builtin 目录编译进二进制、`sync.OnceValues` 固定（`admin_deployments.go:1130-1136`
  注释），进程内不漂移；若换更窄的新二进制，`reviewReasonProfileNarrowed` 直接 fail-closed。
- **热加载（签名目录）**：只换目录、不换 Deployment 快照。目录变宽 → `CatalogAdvanced`
  → 仅 `setOffered` 提供、不启用；目录变窄且快照源为 `builtin`/`signed_catalog` →
  `reviewReasonCatalogNarrowed` → `Drifted` fail-closed（`capability_drift.go:139-157`）。
- **Backup/Restore**：`internal/backup/archive.go` 是整目录加密归档（backup key + 每文件
  SHA256 + master key 指纹绑定，`manifest`），Deployment 记录随 bbolt 原样回灌、不经
  `domain.Validate` 重校验；但**服务时**仍被 binding ceiling 兜住（同上），越界即 Drifted。
- **唯一残留风险**：一份旧备份里若含被放宽的 Beta binding（A3-01 的产物），restore 会
  把那个"软 ceiling"一并带回——根因仍是 A3-01，非 restore 特有的降级通道。

**下限 #3 —— 审计链与 stale 状态标记的可信度：能否在不留痕下让运行时进出 stale，或让
审计记录与实际 mutation 不一致？**

**结论：进出 stale——管理员不能定向无痕切换（good），但 stale 事故无防篡改留痕
（A3-03）；审计与 mutation 一致性——主 mutation 事务安全（good），但能力声明类记录
非事务、崩溃可丢，构成不一致（A3-02）。**

- 审计链本体防篡改：HMAC 哈希链 + 序号/前向哈希校验 + 截断锚点裁决（P-5）。无 Admin
  端点可改写/截断日志。
- 主 mutation 与其审计意图同事务落盘、崩溃后 drain 补投（P-4）——这一条**成立且强**。
- 但 §8.3 的能力声明记录走非事务批量追加（A3-02），崩溃窗口下 mutation 在、声明记录不在。
- stale 由激活成败派生、内存态、仅日志留痕（A3-03），非管理员可定向操纵，但缺持久/
  防篡改证明。
