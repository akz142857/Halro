## 4. 发现清单

### B3-01 · rc.1 publish 未产出 Release 的根因：环境无审批人 + secret 未设置；job 确实被触发过

- **级别**：P0
- **类型**：【问题】
- **是否阻塞 v1.0.0 发布**：**是**
- **证据**：

三个候选（Environment 未配置/未审批、secret 未设置、job 未触发）中，**"job 未触发"被证伪**，另外两个成立。

`v1-release` 的 deployment 记录幸存（deployment 记录不随 run 删除而消失），它给出了逐秒的时间线：

```
$ gh api repos/akz142857/Halro/deployments
  id 5785970777 | environment v1-release | ref v1.0.0-rc.1
  sha ad815d628057ddd3a87d4c3e24715d0fd34a3a82
  created_at 2026-08-06T23:35:08Z | performed_via_github_app: github-actions

$ gh api repos/akz142857/Halro/deployments/5785970777/statuses
  2026-08-06T23:35:12Z  in_progress  → run 31131173718 / job 92721604435
  2026-08-06T23:35:19Z  failure      → run 31131173718 / job 92721604435
  2026-08-07T04:02:18Z  inactive
```

读法：
1. **job 被触发了。** 存在 run `31131173718`，它与同一次 tag push 触发的 ci run `31131173946` 是同一批（run id 相邻，`ad815d6` 的 check suite 建于 `2026-08-06T23:28:38Z`）。`release.yml` 在 tag 提交处存在（`git ls-tree ad815d6 .github/workflows/`）且 YAML 合法（python `yaml.safe_load` 解出 `on: {workflow_dispatch, push: {tags: [v*]}}`）。
2. **publish 没有等待审批。** deployment 从 `in_progress` 直接到 `failure`，**中间没有 `waiting`/`queued` 状态，全程 7 秒**。如果 `v1-release` 配置了 required reviewers，job 会先停在待审批状态。它没有停。
3. **7 秒等于失败在第一行断言。** `release.yml:277-284` 的第一条是 `test -n "${M11_RELEASE_EVIDENCE_JSON}"`；一个只做 checkout + download-artifact + cosign-installer 再失败的 job 不会是 7 秒——7 秒是环境准入后立刻断言失败的量级。

**今天的状态（比 rc.1 当时更差）**：
```
$ gh api repos/akz142857/Halro/environments --jq '.total_count'   → 0
$ gh api repos/akz142857/Halro/actions/secrets --jq '.total_count' → 0
$ gh api repos/akz142857/Halro/actions/variables --jq '.total_count' → 0
```
`v1-release` Environment **现在根本不存在**（rc.1 之后被删除），repo 级 secret 与 variable 都是空的。

- **触发前置条件**：打任何 `v*` tag。`git diff ad815d6..HEAD -- .github/workflows/release.yml` 显示 publish 门禁逻辑自 rc.1 起**未变**（53 增 40 删，全部是 Heimdall→Halro 改名、`upload-artifact@v4→v7`、新增 `MODEL_CATALOG_TRUST_ROOTS`）。
- **修复方向**：见 §5.1 的阻塞项清单。核心是先建 Environment 并配 required reviewers，再准备 evidence bundle。

### B3-03 · 构建不可复现，且它与 M11 证据门禁互相锁死

- **级别**：P0
- **类型**：【问题】
- **是否阻塞 v1.0.0 发布**：**是**
- **证据**：

**(a) 二进制不可复现。** `release.yml:153` 把构建时刻的墙钟塞进 ldflags：
```
-X github.com/akz142857/Halro/internal/buildinfo.Date=$(date -u +%Y-%m-%dT%H:%M:%SZ)
```
实跑三次构建（GOOS=linux GOARCH=amd64 CGO_ENABLED=0，`-trimpath`）：

| 构建 | 差异 | SHA-256 |
|---|---|---|
| A | 基准 | `efa347f5523abb27bab560cd76825b949930602c473c90987f0adb85f5a8d3e8` |
| B | 与 A 完全相同的 ldflags | `efa347f5...` **与 A 逐字节相同** |
| C | 只把 `Date` 从 `...T00:00:00Z` 改成 `...T00:00:01Z` | `1b7a3da699e45144642e6284900dd46094b920e7c85c4af54cd86993e33596ed` **不同** |

即：Go 构建本身是确定性的（A==B），**唯一的不确定输入就是那个 `date -u`**。而 `binaries` 是 4 路 matrix，每条腿在各自 runner 上独立调用 `date -u`，所以四个平台档各带一个不同的时间戳；`container` job（`release.yml:186` 附近）第三次独立调用 `date -u` 作为 `RELEASE_DATE` build-arg，于是容器里的二进制与同 commit 的 linux/amd64 档也不相同。

**(b) tar.gz 不可复现。** `release.yml:165-167` 用 `tar -C release -czf ...`，没有 `gzip -n`、没有 `--sort=name --mtime`。实跑（同一份输入目录、文件 mtime 不变，间隔 2 秒打两次包）：
```
t1.tar.gz  f8aeb66890005ae47c53ae109dbcc213627f21cf9439f5367072e9999b3b4d0d
t2.tar.gz  e3bf312dea61c28faae440fde66284e687552acb365d6789a648785453ebca29
→ DIFFERS
gzip 头前 10 字节：1f8b 0800 b5fd 7a6a 0003
                  1f8b 0800 b8fd 7a6a 0003
                            ^^^^^^^^^ 偏移 4-7 是 gzip MTIME，差 3（=sleep 2 + 用时）
```
差异**只在 gzip 头的 MTIME 字段**。注：该实跑在 darwin/bsdtar 上做，runner 是 ubuntu/GNU tar；GNU gzip 从流压缩时同样写入当前时间到该字段，结论可移植。同一 workflow 在 `docker save ... | gzip -n` 处**用了** `-n`，说明作者知道这个坑，只是没覆盖到 tar 这一处。

**(c) 这与 M11 证据门禁互相锁死——这才是真正的阻塞点。**
`tools/m11/release-evidence/verify.py:309-318` 的 `verify_artifact_files` 会**重新计算** `--artifacts-dir` 下每个 artifact 的 SHA-256，并要求它等于 bundle 里写的 `sha256`：
```python
digest = hashlib.sha256(path.read_bytes()).hexdigest()
require(digest == artifact.get("sha256"), f"release artifact digest does not match bundle: {name}")
```
`verify.py:284-287` 还要求每个 artifact 带 `sigstore_verified: true` 与 `sigstore_bundle`。

于是：evidence bundle 里的摘要**只对产出它的那一次 run 有效**。因为构建不可复现，一旦重新打 tag 或整体重跑 workflow，四个平台档的摘要全变，之前人工准备好的 bundle **必然失败**。这把发布流程锁成了一条很窄的路：

> tag → run 跑完 → publish 因缺 secret 失败 → 人工下载该 run 的 `release-assets` → 算摘要、验签、写 bundle → 设 secret → **只能"重跑失败的 job"**（`gh run rerun --failed`，复用同一 run 的 artifact）

这条路能走通，但它**没有被写进任何文档**，而且脆弱：artifact 默认 90 天过期，过期后该 run 再也无法补发；`docs/runbooks/m11-production-operations.md:67` 描述的是"reviewer 下载 → 设 secret → **批准环境**"，隐含 publish 会停在审批处等人——而 B3-01 证明它不会停。

- **触发前置条件**：任何一次希望产出 Release 的 tag。
- **修复方向**：`Date` 改用 tag 的 committer date（`git log -1 --format=%cI`）或 `SOURCE_DATE_EPOCH`，四条 matrix 腿与 container 共用同一个值；`tar` 加 `--sort=name --owner=0 --group=0 --numeric-owner --mtime="@${SOURCE_DATE_EPOCH}"` 并 `gzip -n`。修完之后 bundle 就能脱离单次 run，第三方也能从 tag 重建并比对 `checksums.txt`。

### B3-04 · 外部使用者无法独立完成 cosign 验签：验签参数从未文档化

- **级别**：P1
- **类型**：【问题】
- **是否阻塞 v1.0.0 发布**：**是**（G4 的直接内容）
- **证据**：

文档一共三处让使用者验签，**三处都只说"要验"，没有一处给命令**：
- `docs/milestones/release-notes-v1.0.0.md:129` — "Verify `checksums.txt`, the SPDX SBOM, and Sigstore bundles."
- `docs/guides/operator-guide.md:427` — "Read release notes and verify the binary checksum and Sigstore bundle."
- `docs/guides/releasing.md:45` — 面向发布者，不是面向使用者。

而 Sigstore 无密钥验签**必须**提供签名者身份。实跑（cosign v2.6.5，`go install github.com/sigstore/cosign/v2/cmd/cosign@latest`）：
```
$ cosign verify-blob --bundle blob.txt.sigstore.json blob.txt
Error: --certificate-identity or --certificate-identity-regexp is required for verification in keyless mode

$ cosign verify-blob \
    --certificate-identity "https://github.com/akz142857/Halro/.github/workflows/release.yml@refs/tags/v1.0.0-rc.2" \
    --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
    --bundle blob.txt.sigstore.json blob.txt
Error: bundle does not contain cert for verification, please provide public key
```
第二条走过了参数校验、停在"我这份 bundle 是假的"上——说明这两个参数正是缺的那一环。这两个值只出现在 `release.yml:299-306`（publish job 内部自验），**没有任何面向使用者的文档写出它们**。

结论：**一个外部使用者拿着 Release 页面和现有文档，跑不出一条能通过的 `cosign verify-blob`。** 他必须去读 workflow 源码反推 identity 字符串。

- **触发前置条件**：任何外部使用者尝试验签。
- **修复方向**：在 release notes 与 README 里给出可直接复制的完整命令块（含 `--certificate-identity`、`--certificate-oidc-issuer`，以及 `sha256sum --check checksums.txt` 与"先验 checksums.txt 的签名，再用它验其余文件"的正确顺序）。

### B3-05 · 文档描述的"四方审批环境门禁"在真实仓库中不存在

- **级别**：P1
- **类型**：【问题】
- **是否阻塞 v1.0.0 发布**：**是**
- **证据**：

`docs/guides/releasing.md:22-24`：
> "Configure the GitHub `v1-release` environment with required reviewers. Its approval is the explicit boundary where reviewers verify the exact-commit GA Provider matrix, 24-hour soak artifacts, RC checklist, and release description."

`docs/runbooks/m11-production-operations.md:67`：
> "四方 reviewer 必须先下载 `provenance` job 的 `release-assets`，完成 SBOM、checksum、Sigstore 与 bundle 审核，再把脱敏 JSON 设置为 `v1-release` Environment 的 `M11_RELEASE_EVIDENCE_JSON` secret **并批准环境**。"

实际：`gh api repos/akz142857/Halro/environments` → `total_count: 0`。环境不存在，更没有 required reviewers。B3-01 的 deployment 时间线证明 rc.1 时它也没有审批人（`in_progress` → `failure`，无 `waiting`）。

**后果链**：GitHub 在 job 首次引用一个不存在的 environment 时会**自动创建它，且不带任何保护规则**。所以：
- 如果有人把 `M11_RELEASE_EVIDENCE_JSON` 设成 **repo 级 secret**（repo secret 对带 environment 的 job 同样可见），publish 会**在零人工审批的情况下直接创建正式 Release**。
- 文档承诺的"四方签署 + 环境审批"两道人工闸门里，**只有 evidence bundle 的内容校验这一道真实存在**（由 `verify.py` 强制），"审批"这一道是空的。

这不是理论推演：evidence bundle 的四方签署是 `verify.py:290-307` 校验的**数据字段**，而不是 GitHub 的审批动作。谁掌握了 secret 的写入权限，谁就能同时提供"四方签署"和"审批"。

- **触发前置条件**：任何拥有 repo secret 写权限的人设置该 secret 并打 tag。
- **修复方向**：创建 `v1-release` Environment，配置 required reviewers（且 reviewer 不应与设置 secret 的人是同一人），并把 secret 设为 **environment secret** 而非 repo secret。修完后用 `gh api .../environments` 的 `protection_rules` 作为放行证据。

### 5.3 下限三 · 版本号注入与可复现构建

**版本号注入：正面结论，可用。**
`internal/buildinfo/buildinfo.go:3-7` 定义 `Version`/`Commit`/`Date` 三个变量，`release.yml:151-153` 与 `Dockerfile:16-21` 用同一组 `-X` 覆盖，两条路径不会漂移。实跑确认注入生效（B3-肯定-4）。`RELEASE_VERSION: ${{ github.ref_name }}` 对 tag push 求值为 tag 名；`RELEASE_COMMIT: ${{ github.sha }}` 对 annotated tag 由 GitHub 解引用到目标 commit，与 publish job 里 `git rev-list -n 1 "${GITHUB_REF_NAME}"`（`release.yml:285`）一致。**无发现。**

**可复现构建：负面结论，不可复现。** 完整证据见 **B3-03**。三点摘要：
1. Go 编译本身**是**确定性的：相同 ldflags 两次构建字节相同（`efa347f5...` == `efa347f5...`）。
2. `release.yml:153` 的 `Date=$(date -u ...)` 是唯一的不确定输入：只改这一个字段一秒，产物摘要即变（`efa347f5...` ≠ `1b7a3da6...`）。4 路 matrix + container 共 5 次独立取时，5 个不同时间戳。
3. `release.yml:165-167` 的 `tar -czf` 缺 `gzip -n`，gzip 头 MTIME 字段每次不同（实测 `b5fd7a6a` vs `b8fd7a6a`，其余字节相同）。同一 workflow 在 `docker save | gzip -n` 处用了 `-n`，说明是遗漏而非取舍。

**这条下限的真正代价不在"第三方复算不了摘要"，而在它与 M11 证据门禁锁死**（B3-03(c)）：`verify.py:309-318` 要求 bundle 里的摘要与磁盘上的 artifact 逐字节相等，而摘要每次 run 都变，于是 evidence bundle 只对单次 run 有效，发布流程被压成一条没有文档、且受 artifact 90 天保留期限制的窄路。修可复现构建同时解开这两个结。

补充说明一处我自己的环境噪声，以免被误读为发现：我在 scratchpad 里构建时 `go version -m` 显示 `vcs.modified=true` 与 `+dirty`，那是因为我的工作树里有一个未跟踪的评审目录（`docs/review/260811/releases.1.0.0/`，我开工前就存在）。CI 的干净 checkout 不会有这个标记。**不是发现。**
