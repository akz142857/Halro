## 5. 发现清单

### B1-01 · 已发布的容器 / K8s / systemd 部署布局全部无法启动

- **级别 P0** ｜ 类型【问题】｜ **阻塞 v1.0.0 发布：是**

**机制。** Halro 在 `data_dir` 的**父目录**里创建发布锁：

```go
// internal/store/lock/lock_unix.go:64
return filepath.Join(filepath.Dir(dataDir), fmt.Sprintf(".halro-publication-%x.lock", digest[:8]))
```

因此 `data_dir` 的父目录必须可写。仓库自己知道这条约束并写进了
`docs/guides/backup-restore.md:168-197`：

> Mount a persistent **parent** directory and configure `storage.data_dir` as a child of it
> ... **Do not set the volume mount point itself as `storage.data_dir`.** ... The parent must be writable

**但四个已发布工件全部违反它：**

| 工件 | 证据 | 后果 |
|---|---|---|
| Operator Guide | `docs/guides/operator-guide.md:493` `-v halro-data:/var/lib/halro`；`:497` "Container configuration must use `/var/lib/halro` for `storage.data_dir`" | 父目录 `/var/lib` 在镜像层里属 root，uid 65532 不可写 |
| Dockerfile | `Dockerfile:23,27,29,31` 只创建/chown/`VOLUME` 了 `/var/lib/halro` | 镜像开箱只支持这个坏布局 |
| systemd | `deploy/systemd/halro-aws-kms.service:26-27` `ProtectSystem=strict` + `ReadWritePaths=/var/lib/halro` | `/var/lib` 只读 → 同样失败 |
| Kubernetes | `deploy/kubernetes/halro-aws-kms.yaml:49,65` `readOnlyRootFilesystem: true` + PVC 挂在 `/var/lib/halro`；该文件不含 ConfigMap，操作者按 operator-guide:497 填 data_dir | 同样失败 |

**实证 1 — 照 operator-guide.md:490-494 原样跑容器：**

```
$ docker build -t halro-b1:test .          # 成功
$ docker run --rm --user 65532:65532 \
    -v ".../ctr-config.yaml:/etc/halro/config.yaml:ro" \
    -v ".../ctr-master.key:/run/secrets/halro-master.key:ro" \
    -v halro-data-b1:/var/lib/halro \
    halro-b1:test
{"level":"INFO","msg":"runtime host hardening applied",...}
halro: open publication lock: open /var/lib/.halro-publication-fdff7c09c3790d29.lock: permission denied
```

**实证 2 — 同一镜像、同一配置，只把 `data_dir` 改成挂载点的子目录：**

```
$ # data_dir: /var/lib/halro/data
$ docker run --rm --user 65532:65532 ... halro-b1:test init --config /etc/halro/config.yaml
Halro initialized
```

**实证 3 — 把 systemd/k8s 的形状（父目录只读）在宿主上复现，与容器无关：**

```
$ chmod 555 <parent>            # 模拟 ProtectSystem=strict / readOnlyRootFilesystem
$ # data_dir = <parent>/halro
$ ./bin/halro init --config <cfg>
halro: open publication lock: open <parent>/.halro-publication-f89033536f6291a1.lock: permission denied
$ # data_dir = <parent>/halro/data（父目录仍只读，但 halro/ 可写）
$ ./bin/halro init --config <cfg>
Halro initialized
```

**触发前置条件。** 照 `docs/guides/operator-guide.md:487-497` 的任一条部署路径操作。
无需任何异常输入，是 100% 必现的首次启动失败。

**为什么没被发现。** CI 的 `container` job（`.github/workflows/ci.yml:141-155`）只做
`halro version` 和 `docker image inspect` 两件事，**从不挂卷启动容器**。发布流水线
（`release.yml:192-220`）把这个镜像打成 `halro-container.tar.gz` 签名发布——即"发布的是一个
从未被启动过的镜像"。

**修复方向。** 四处统一到 backup-restore.md 已经写对的布局：镜像里创建并 chown
`/var/lib/halro-volume`（`VOLUME` 与 `WORKDIR` 同步），`data_dir` 用
`/var/lib/halro-volume/data`；systemd 的 `ReadWritePaths` 与 k8s 的 `mountPath` 跟着改。
**同时必须加 CI 守护**——只改文档和 Dockerfile 而不加"挂卷启动"步骤，这个缺陷会以完全相同
的方式回来。

> 注：本轮任务书提到的上一次尝试推测（"卷挂载到 `/var/lib/halro` 与数据目录自身冲突"）
> **结论成立、机制判断错误**。冲突不在挂载点本身，而在 `filepath.Dir(dataDir)` 的发布锁；
> 且上次的补丁只改了 Dockerfile 与 operator-guide，**漏掉了 systemd unit 与 k8s manifest
> 这两处同源缺陷**，也没有加守护。

### B1-02 · 容器路径没有任何初始化步骤，两种失败都不可行动

- **级别 P1** ｜ 类型【问题】｜ **阻塞 v1.0.0 发布：是**（与 B1-01 同一条路径）

`Dockerfile:37` 的 `CMD` 是 `serve`，而 `serve` 不会初始化存储。
`docs/guides/operator-guide.md:487-503` 整节没有 `halro init` 这一步。空卷首启：

```
$ docker run ... halro-b1:test          # data_dir 已是子目录，卷为空
halro: load vault key check: record not found
```

操作者按指引挂了只读的 `master.key` 后想手动 init：

```
$ docker run ... halro-b1:test init --config /etc/halro/config.yaml
halro: master key already exists
```

两条消息都只说"是什么"，不说"下一步做什么"。第二条尤其误导：master.key 确实存在，
但数据目录是空的——`docs/guides/user-guide.md:87-90` 描述的正是这个"部分状态"场景
（"Halro refuses to repair it automatically and asks for the matching files to be restored
by hand"），而二进制吐出的那句话里没有这个信息。

**触发前置条件。** 首次在容器里部署，且按 operator-guide 把 master.key 以 `:ro` 挂进来。

**修复方向。** operator-guide 的容器小节补一条 init 步骤（含 master.key 该放在可写位置还是
先在宿主生成）；`master key already exists` 补一句状态判断（"数据目录为空但 Master Key 已存在"
是与"两者都在"不同的情况）。

### B1-03 · 容器把端口发布出去也连不上，而 `docker ps` 报 healthy

- **级别 P1** ｜ 类型【问题】｜ **阻塞 v1.0.0 发布：需裁决**

`docs/guides/operator-guide.md:494` 的 `-p 8080:8080 -p 8081:8081` 与 `:497` 要求的配置互相
抵触：Halro 在非 TLS 下拒绝绑定非回环地址，所以容器内只能监听 `127.0.0.1`，而 `docker -p`
连的是容器 IP，不是回环。

```
$ docker run -d --name halro-b1p ... -p 18888:8080 -p 18889:8081 halro-b1:test
$ docker logs halro-b1p | grep -c "listener started"
3
$ curl -m 5 -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18888/health/ready
000        # curl exit=56 connection reset by peer
$ curl -m 5 -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18889/admin
000        # curl exit=56
$ docker run --rm --network container:halro-b1p curlimages/curl -s -o /dev/null \
    -w '%{http_code}\n' http://127.0.0.1:8080/health/ready
200        # 容器内回环正常
$ docker ps --filter name=halro-b1p --format '{{.Status}}'
Up About a minute (healthy)
```

**HEALTHCHECK 走的也是容器内回环（`Dockerfile:33-35`），所以一个对外完全不可达的容器会被
编排系统判定为健康。** 在 k8s 上这意味着 readiness 通过、Service 把流量导过来、然后全部超时。

**触发前置条件。** 按 operator-guide 的 `docker run` 发布端口，且未启用 TLS。

**修复方向。** 容器小节明确二选一：要么在容器内启 TLS 并给出证书挂载方式，要么写明
`-allow-insecure-public-listen` + `0.0.0.0` 的适用边界（仅 Gateway、且必须有外层网络控制）。
现在的写法是第三种：既发布端口又要求回环，两边都不成立。

### B1-04 · `halro doctor` 把"父目录不可写"报成"数据目录正被占用"

- **级别 P1** ｜ 类型【疑似BUG】｜ **阻塞 v1.0.0 发布：否**

新操作者遇到 B1-01 后最可能做的事就是跑 doctor。它给出的诊断把人引向一个不存在的进程：

```
$ chmod 555 <parent>    # 父目录不可写；没有任何其他进程持有这个目录
$ ./bin/halro doctor --config <cfg>
{"healthy":false,...,"checks":[...,{"name":"data_lock","status":"fail",
 "detail":"data directory is in use or cannot be locked"}]}
halro: doctor requires exclusive offline access
```

对照组（同一二进制、布局正确的空闲目录）：

```
$ docker run --rm ... halro-b1:test doctor --config /etc/halro/config.yaml
healthy = True
  data_lock = pass - exclusive offline snapshot acquired
  ... 共 22 项检查全 pass
```

`docs/guides/operator-guide.md:456-458` 的 Troubleshooting 第一条写的是"另一个 Halro 或离线
命令持有它。找到持有者；不要删锁文件绕过"——**照这条做的人会去找一个根本不存在的持有者**，
而真正的原因（`filepath.Dir(dataDir)` 不可写，`internal/store/lock/lock_unix.go:64`）不会被
想到。

**触发前置条件。** `data_dir` 的父目录不可写（即 B1-01 的每一种部署形态）。

**修复方向。** `data_lock` 检查区分 `EACCES`（父目录不可写 → detail 指向父目录路径与所需权限）
与 `EWOULDBLOCK`（真的被占用）。这两种是不同的运维动作，不该共用一句话。

### B1-05 · `init` 因为不会绑定的监听地址而拒绝执行，且没有对应的放行开关

- **级别 P2** ｜ 类型【问题】｜ **阻塞 v1.0.0 发布：否**

```
$ docker run ... halro-b1:test init --config /etc/halro/config.yaml
halro: server.gateway_listen must bind loopback unless TLS is enabled
```

`init` 不打开任何监听端口，却对监听地址做校验并中止。而 `-allow-insecure-public-listen` 只有
`start` 和 `serve` 有（`./bin/halro init --help` 只列出 `-config`），所以配置里一旦写了
`0.0.0.0`（容器场景的自然选择），`init` 就没有任何办法通过——只能先写回环、init 完再改回去。

消息本身是可行动的（说清了"要么回环、要么开 TLS"），扣分在**不该在这个命令里拦**。

**修复方向。** `init` 只校验它真正要用的东西（storage、master_key custody）；监听地址的校验
留给会绑定它的 `start`/`serve`。

### B1-08 · 首启 checklist 在一个能正常出 200 的实例上报"0/4 完成、未发布模型、未授予访问"

- **级别 P1** ｜ 类型【疑似BUG】｜ **阻塞 v1.0.0 发布：需裁决**

这是下限第一条的正面答案，详见 §6.1。同一实例上的两次观测：

```
$ curl -s -b c3.txt http://127.0.0.1:8081/admin/api/v1/onboarding/readiness
state: configuring  completed: 0 / 4
   connect_provider = current / provider_test_required
   publish_model    = blocked / provider_blocking_model
   grant_access     = blocked / model_blocking_access
   verify_request   = blocked / request_ready

$ curl -s http://127.0.0.1:8080/v1/chat/completions -H "Authorization: Bearer gw_..." \
    -H "Content-Type: application/json" \
    -d '{"model":"chat","max_completion_tokens":64,"messages":[{"role":"user","content":"hi"}]}'
HTTP/1.1 200 OK
{"id":"chatcmpl-b1mock","object":"chat.completion",...,"model":"chat",...}
```

根因：`internal/app/admin_onboarding.go` 的三个就绪判定**只认探针证据**——
`provider.LastTestStatus == DeploymentTestHealthy && LastTestRevision == Revision`
（`:202-208`）、Deployment 同款（`:254-256`）、Route 同款（`:282-284`）。而
`halro bootstrap`（`docs/guides/user-guide.md:169-186`，本仓推荐的最快路径）建链时不跑任何探针，
所以三个目标全部落空。

两个独立的问题叠在一起：

1. **证据模型太窄。** `:132-139` 的注释已经论证过"下游探针可以顶替 Provider 测试"，但没有把
   **真实成功流量**纳入证据——而它比探针强。
2. **文案是错的，不只是保守。** goal 2/3 报的是 `provider_blocking_model` 与
   `model_blocking_access`（`:290,352`），字面意思是"模型没发布""访问没授予"。实际两者都存在
   且可用。唯一真实的那句是 goal 1 的 `provider_test_required`。

成功一次请求后（`metrics.RequestsSuccess > 0`，`:375`）状态跳到 `first_value_reached`，
但 goal 1~3 **仍然停在 current/blocked**，于是同一份 JSON 同时说"第一个请求已成功"和
"你还没连上 Provider"：

```
state: first_value_reached  completed: 1 / 4
   connect_provider = current / provider_test_required
   publish_model    = blocked / provider_blocking_model
   grant_access     = blocked / model_blocking_access
   verify_request   = complete / request_succeeded
```

（该状态跨重启保持，我 `docker restart` 后复查一致。）

**缓解**：控制台在 `first_value_reached` 后整块隐藏 checklist
（`web/src/pages/DashboardPage.tsx:74`、`web/src/pages/FirstRunChecklist.tsx:48`），所以
"自相矛盾"这一半用户看不到。**没被缓解的是第一半**：bootstrap 之后、首个请求之前，控制台
会把 checklist 显示出来，对一个已经能用的系统说"0/4，模型未发布"。

**触发前置条件。** 用 `halro bootstrap`（或任何未跑连接测试的方式）建链后打开控制台首页。

**修复方向。** 把"该 Route 上出现过成功请求"作为 publish/access 两个目标的充分证据；
在没有任何证据时，goal 2/3 的 detail_code 区分"对象不存在"与"对象存在但未验证"，
不要用"blocking"措辞描述一个已经存在的对象。

### B1-09 · 连接失败的请求按 `max_completion_tokens` 全额结算

- **级别 P2** ｜ 类型【疑似BUG】｜ **阻塞 v1.0.0 发布：需裁决** ｜ **移交 A1 / A5 复核**

停掉上游后发一个请求，Gateway 返回 502，`error_class = connect`——即 TCP 连接就没建立，
不存在"上游是否已经计费"的歧义。但账目按预留的最大输出全额落账：

```
失败请求 req_aq3eg...：outcome=provider_error, error_class=connect,
  input_tokens=2, output_tokens=64(prepared), cost_micros_usd=130
成功请求 req_05f4m...：outcome=success,
  input_tokens=11, output_tokens=8,  cost_micros_usd=27
```

定价 1.0/2.0 USD per M（in/out）。失败那条 = 2 + 64×2 = 130 micros，正是
`max_completion_tokens: 64` 的满额。也就是说**上游宕机期间，调用方为每一次从未发出的请求
支付满额输出费**，并同步消耗 Project 日预算。

我无法在本角色内判断这是 `gateway-correctness.md` 里"ambiguous outcome 保守结算"的有意设计
外溢，还是 release 路径漏了 `connect` 这一类**明确未发出**的失败。从可用性看后果是清楚的：
上游一断，预算被以最快速度烧掉，而 429/402 会紧接着到来。

**修复方向（待 A1 裁决）。** `error_class == connect`（以及任何"确定没有字节发出"的类）应释放
预留而非结算。若这是有意设计，必须写进 `docs/contracts/gateway-correctness.md` 与发布说明。

## 6. 下限项逐条应答

### 6.1 下限 1：首次运行 checklist 显示的就绪状态与真实就绪状态是否一致

**结论：不一致（负面）。** 见 B1-08，两个方向都不一致：

- **假阴性（会被用户看到）**：`halro bootstrap` 建成的完整可用链，checklist 报
  `state: configuring`、`completed_goals: 0/4`、`publish_model: blocked/provider_blocking_model`、
  `grant_access: blocked/model_blocking_access`。同一实例同一时刻发请求得到 HTTP 200。
- **自相矛盾（被 UI 隐藏）**：成功请求之后 `state` 变成 `first_value_reached`、goal 4 complete，
  但 goal 1~3 仍为 current/blocked，一份 JSON 里同时断言"第一个请求已成功"和"尚未连接 Provider"。

一致的部分：全新实例（无任何对象）上报 `credential_missing` / `provider_blocking_model` /
`model_blocking_access`，与事实相符；`action_href` 指向的页面是对的。
`/health/ready` 报 `{"accounting":"healthy","status":"ready"}` 也是准确的——它描述的是进程与
记账子系统，不是业务就绪，没有过度承诺。

### 6.2 下限 2：走不通时的错误信息是否可行动

**结论：分化明显——配置类可行动，部署与诊断类不可行动。**

| 场景 | 消息 | 可行动？ |
|---|---|---|
| 非回环 listener | `server.gateway_listen must bind loopback unless TLS is enabled` | **是**，两条出路都说了 |
| 数据目录被占用 | `data directory is already locked by another process` | **是**，且 operator-guide:456 有对应条目 |
| 上游调用失败 | 响应体 `provider_error` + `X-Request-Id`，Admin 里可查到 `error_class: connect` | **基本是**，但需要先知道去 Admin 查；服务端日志里**一行都没有**，无控制台访问的人查不到 |
| 端口占用 | `bind: address already in use` | **半**，没说改哪个键（B1-07） |
| 未知命令 | `unknown command "--help"` | **否**，不回落到 usage（B1-06） |
| 容器空卷 | `load vault key check: record not found` | **否**，不提示需要先 init（B1-02） |
| master.key 存在但数据为空 | `master key already exists` | **否**，与 user-guide:87-90 描述的场景对不上（B1-02） |
| 父目录不可写 | `open publication lock: ... permission denied` | **否**，只给了路径，不说明这是 `data_dir` 的父目录（B1-01） |
| 同上，跑 doctor | `data directory is in use or cannot be locked` | **否，且主动误导**——把人送去找不存在的持有者（B1-04） |

最后两条决定了这一项的判定：一个新操作者按官方文档部署容器，会先撞上一条只给路径的
permission denied，再被 doctor 引到错误方向。**这条下限判为负面。**

### 6.3 下限 3：README 与快速开始文档与二进制实际行为是否一致
