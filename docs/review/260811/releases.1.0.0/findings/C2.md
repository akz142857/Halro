## 1. 结论

既有的可观测性基座质量高：指标契约、标签基数纪律、rule tests、CI 门禁、Watchdog + deadman
双信号都建得讲究。问题全部集中在一处——**本区间的新增面没有接进告警链**。整个 46 个提交里，
`deploy/observability/` 只动了 `smoke.sh` 一个文件（就是 PR #146 那次修复），
`alert-rules.yml`、`recording-rules.yml`、`rule-tests.yml`、`alertmanager.yml`、
`operations-runbook.md` 一行未改。10 个新指标进了 metrics-reference.md，对应 0 条告警、
0 条 rule test、0 条 runbook 处置。最严重的一条是本区间最关键的新机制：**拓扑激活失败让运行时
进入 stale 并拒绝全部数据面流量，而这个状态在 Prometheus 侧没有任何指标、没有任何告警，
表现形式是"流量归零 + 错误率 0"——恰好是所有现有告警都看不见的形状。**

## 3. 肯定项（值得在后续改动中保护）

1. **PR #146 的修复方式本身是范本**：`deploy/observability/smoke.sh:363-371` 不只把 60 改成 150，
   而是把推导写进注释（"Watchdog route sets group_interval: 1m … the wait is either 0s or exactly
   60s and never in between"），并在 `smoke.sh:286-298` 加了超时后的双端诊断输出——
   让"预算不够"和"投递真的坏了"在日志里可区分。这正是防止它再次被当成噪声长期忽略的做法。
2. **标签基数纪律是编译期闭合的，不是靠约定**：`internal/app/capability_metrics.go:18-21` 的注释
   写明禁用哪些标识符，`capability_metrics.go:137-173` 的 `boundedResolution*` 族把每个枚举外的值
   收敛成 `"unknown"`；`internal/domain/model_capability_detection.go:246` 在**写入期**用
   `slices.Contains(capabilityNames, capability)` 白名单校验，所以
   `halro_model_capability_probe_total` 的 `capability` 标签基数由 `ProviderCapabilities`
   的 17 个字段名（`internal/domain/models.go:354-373`）固定，上界约 7×17×7 ≈ 833 series，有界。
3. **"读失败时省略整族而不是报 0"**：`internal/app/metrics.go:624-640` 配合
   `docs/contracts/metrics-reference.md:166-175`，并把"告警必须用 `absent()` 而不是把缺失当作
   没有漂移"写进契约。这个方向是对的（可惜没有对应告警，见 C2-04）。
4. **`internal/app/metrics_contract_test.go:78-89` 存在一条真门禁**：任何导出的 `halro_*` 族
   若不在 metrics-reference.md 中就让测试失败。它的存在使 10 个新指标全部进了文档，
   这不是靠人工自觉。（它的盲区见 C2-03，但门禁本身是资产。）
5. **KMS runbook 是 runbook 的正确形态**：`docs/runbooks/m11-production-operations.md:49-55`
   给 6 条 KMS 告警逐条写了处置动作（"禁止自动改用 Recovery"、"立即 fail closed，
   禁止手工替换 descriptor"）。这与通用 runbook 的泛化流程形成对照，是应该被复制的样板。
6. **deadman 的心跳合并保护了 receiver 语义**：`internal/deadman/engine.go:256-267` 在入队新心跳时
   剔除队列中的旧心跳，但显式保留 `e.inflight` 那一条，避免"重放的旧心跳延长 receiver deadline"
   这个 deadman 最典型的自欺路径；`RECEIVER-CONTRACT.md:8-10,28-30` 在接收端也重复了这条约束。
7. **Watchdog 的 `send_resolved: false` 有正确的理由并写下来了**：
   `deploy/observability/alertmanager/alertmanager.yml:33-36`——Prometheus 消失必须产生沉默，
   而不是一条合成的 resolved 签到。

### C2-01 · stale 状态（运行时拒绝全部数据面流量）在监控侧完全不可见

- **级别**：P1
- **类型**：【问题】
- **是否阻塞 v1.0.0 发布**：需裁决（倾向阻塞——修复成本约 20 行，收益是本区间最关键新机制的唯一可观测信号）
- **证据**：
  - 拒流量点：`internal/app/activation_state.go:84-99`。它直接 `writeJSON(..., 503, ...)` 返回，
    **不递增任何计数器**。
  - 挂载位置：`internal/app/runtime.go:1249` 与 `internal/app/runtime.go:1272`，
    在 `LimitOpenAI` / `GuardOpenAI`（及 Anthropic 对应中间件）**之前**。因此被拒的请求
    从不进入 gateway handler，`halro_requests_total` 不增加。
  - 无指标：`docs/contracts/metrics-reference.md:49-135` 的 101 个导出族中没有任何
    activation / stale 项；对 `internal/app/metrics.go` 全文检索 `stale|activation` 只命中
    两处注释（`metrics.go:77`、`metrics.go:165`），无 `metricHeader` 输出。
  - 无告警：`deploy/observability/prometheus/alert-rules.yml` 全文 24 条规则，无一条涉及 activation。
  - Prometheus 看不到 readiness：`deploy/observability/prometheus/prometheus.yml:20-53`
    三个 job 只抓 `/metrics`，没有 blackbox exporter，没有对 `/health/ready` 的探测。
  - `up{job="halro"}` 不受影响：`/metrics` 由独立的 `metricsRouter`
    （`internal/app/runtime.go:1428-1440`）提供，它**没有** `refuseWhileSnapshotsStale`。
    所以 `HalroTargetDown`（`alert-rules.yml:5-11`）在全量拒流期间保持沉默。
  - 错误率告警也不会触发：`HalroHighErrorRate`（`alert-rules.yml:68-74`）依赖
    `halro:requests_errors:ratio5m`（`recording-rules.yml:9-15`，分子分母都来自
    `halro_requests_total`），且额外要求
    `increase(halro_requests_total[10m]) >= 20`。拒流期间该计数器完全不动 → 分子 0、分母 0
    → 比值 0，且门槛条件为假。**错误率显示为 0.00，请求数显示为 0。**
  - 规则集中没有任何"流量归零"告警：`alert-rules.yml` 全文只有一处 `absent()`
    （`alert-rules.yml:6`，作用于 `up`），没有对 `halro_requests_total` 的 `absent()`
    或 `rate() == 0` 断言。
- **触发前置条件**：任一激活域（routing registry / auth snapshot / redaction / token guard）
  在一次已提交的 Admin mutation 之后激活失败即置位——
  `internal/app/providers.go:91`、`internal/app/admin_projects.go:484`、
  `internal/app/admin_redaction.go:324`、`internal/app/admin_token_guard.go:342`。
  恢复循环每 5s 重试（`activation_state.go:28,107-131`），所以多数瞬时故障会自愈；
  **需要告警的恰恰是那些不自愈的**（例如 store 持续读失败）。
- **实际后果**：一个运维在出厂告警栈（`compose.example.yaml` 只含 prometheus + alertmanager）
  下，看到的全部现象是"请求曲线掉到 0，错误率 0，target up，无任何告警"。
  这与"今天没人调用"在监控上完全同形。
- **唯一的旁路信号**（都不在 Core 出厂形态里）：
  - deadman 探 `/health/ready`（`deploy/observability/external-probe/config.example.yaml:32`），
    `failures_to_down: 3` × `interval: 30s` ≈ 90s 后发 `state_transition down`。但 deadman 是
    独立部署、Phase D 准入项，`deploy/observability/README.md:109` 明确说不能与 Core 同机作为
    生产证据——即出厂不带。
  - k8s readinessProbe（`deploy/kubernetes/halro-aws-kms.yaml:41-44`，
    `periodSeconds: 5` × `failureThreshold: 12` = 60s）会把唯一副本摘出 Service endpoints。
    这反而**降低**可诊断性：客户端从"503 带 `configuration_stale` 说明"变成"无 endpoint"。
  - 两条旁路都没有被任何文档与 stale 关联起来。
- **修复方向**：在 `internal/app/metrics.go` 导出
  `halro_activation_stale`（gauge 0/1）与 `halro_activation_stale_since_seconds`（gauge，
  0 表示不 stale），从 `r.activation.status()` 读取——它已经是 render-time 可读的状态，
  与 `halro_deployment_capability_status` 同一模式。配一条
  `halro_activation_stale == 1 for: 1m` 的 critical 告警（1m 允许恢复循环的 12 次重试先跑完），
  runbook 条目写清"为什么拒、影响什么、怎么恢复"。
  另建议补一条 `halro_activation_refused_total` 计数器，使"拒了多少"可量化。
  > 与 D1 的交叉：D1 报告后端已在 `/admin/api/v1/system/status` 暴露 `activation` 字段
  > （`runtime.go:1490-1497` 同一来源）而前端未消费。从 C2 视角看，前端不消费只是"人看不到"，
  > **监控侧完全没有这个信号才是更重的一半**——因为控制台需要有人正在看，告警不需要。
  > 两者应一起关闭。

### C2-06 · smoke.sh 的 150s 预算与 `group_interval: 1m` 之间没有守护，PR #146 属"已修但无守护"

- **级别**：P2

- **是否阻塞 v1.0.0 发布**：否
- **证据**：
  - 修复本体确认存在且推导正确：`deploy/observability/smoke.sh:363-371`
    （提交 `1092737 fix(observability): let the Watchdog smoke wait outlive one delivery retry`），
    `wait_event firing '*' 150`，而 `alertmanager.yml:11-15` 的 Watchdog 路由
    `group_wait: 0s / group_interval: 1m / repeat_interval: 1m`。
    150 次 × (python3 启动 + `sleep 1`) ≈ 150~165s 墙钟，覆盖第 0/60/120 秒三次派发，余量 ≥ 1 次。
  - 但耦合关系无任何断言。`validate.sh` 里唯一钉住 Alertmanager 时间参数的一行是：
    `grep -Eq 'repeat_interval: 1m' "$observability/alertmanager/alertmanager.yml"`
    ——钉的是 **`repeat_interval`**，而预算依赖的是 **`group_interval`**。钉错了旋钮。
  - 因此：把 `group_interval` 从 `1m` 改成 `3m`（一个看起来无害的降噪调整），

  - 这条同时进 A4 的"已修但无守护"清单。
- **触发前置条件**：任何人调整 Watchdog 路由的 `group_interval`（含为降噪而调大）。
- **修复方向**：在 smoke.sh 里从 `alertmanager.yml` 解析 `group_interval` 并断言
  `budget >= 2 * group_interval_seconds + 30`，或至少在 `validate.sh` 里把
  `grep -Eq 'group_interval: 1m'` 也钉上并注释说明它被 smoke.sh 的预算依赖。
  前者更好——它把"预算按最坏投递路径设"变成一条会自动跟随配置的不变量，而不是一个注释里的常数。

### C2-07 · 优雅关闭预算 30s 硬编码，而同一份配置允许的最长请求是 2m（同类"按名义耗时设预算"）

- **级别**：P2
- **类型**：【问题】
- **是否阻塞 v1.0.0 发布**：否
- **证据**：
  - 关闭预算：`internal/app/runtime.go:1068`
    `shutdownCtx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 30*time.Second)`，
    并且所有监听器**共享**这一个 ctx 顺序 `Shutdown`（`runtime.go:1069-1074`），
    即 30s 是总预算不是每个。异常路径同值（`runtime.go:1056`）。该值不可配置。
  - 同一份默认配置允许的最长请求：`internal/config/default.yaml:99`
    `route_total_timeout: 2m0s`，`default.yaml:102` `stream_idle_timeout: 1m0s`。
    `configs/config.example.yaml:221` 同为 `120s`。
  - k8s 侧的宿主预算是够的：`deploy/kubernetes/halro-aws-kms.yaml:26`
    `terminationGracePeriodSeconds: 60` > 30s + `Close()`。**问题不在宿主，在进程内部**：
    30s 预算是按"典型请求几秒钟"这个名义值设的，而配置允许的最坏在途请求是它的 4 倍。
  - 可观测性侧的缺口：被关闭截断的在途 attempt 没有专门的指标或状态标签。
    `alert-rules.yml` 中没有任何针对重启期截断的规则。运维在一次重启后看到的是
    `halro_requests_total{status="error"}` 抬升，无法与上游故障区分。
- **触发前置条件**：在有长请求（流式生成、Bedrock async、大 batch）在途时收到 SIGTERM。
  单写者 + `Recreate` 策略下每次升级都是这个场景。
- **实际后果**：被截断的 attempt 属于"provider 结果不明"，按仓库不变量应保守记账
  （不静默退款）。这不是记账错误，但它是一类**在监控上不可归因**的错误来源。
- **修复方向**：把关闭预算做成配置项并给出默认值 ≥ `route_total_timeout`（或显式记录
  "关闭时最多等 30s，超出的在途请求会被截断"作为已知限制并写进发布说明）；
  另加一个 `halro_shutdown_truncated_attempts_total` 让重启噪声可被减掉。
  这一条与 A1/C3 的判断可能重叠，此处只从"预算按名义值设 + 无信号"的角度记录。

### C2-08 · deadman 单个 target 的 `timeout` 被 readiness 与 freshness 两次请求共享

- **级别**：P3
- **类型**：【问题】
- **是否阻塞 v1.0.0 发布**：否
- **证据**：
  - `internal/deadman/http.go:96-98`：`checkContext, cancel := context.WithTimeout(ctx, cfg.Timeout.Value())`
    一次创建，随后既覆盖 `:101` 的 readiness 请求，也覆盖 `:110` 的
    `checkFreshness(checkContext, ...)`。两次 HTTP 往返共用一个 5s 预算
    （`deploy/observability/external-probe/config.example.yaml:8` `timeout: 5s`）。
  - freshness 那次请求打的是 Prometheus `/api/v1/query`，表达式为
    `time()-scalar(max(timestamp(up{job="halro"} == 1)))`（`config.example.yaml:53`），
    它的耗时随 TSDB 规模与负载变化，与 `/-/ready` 不同量级。
  - 配置的 schema 与文档都把 `timeout` 描述为单次探测超时，没有说它是两次之和。
- **触发前置条件**：Prometheus 在压力下 `/-/ready` 慢 + query 慢，两者之和超过 5s。
  连续 3 个 tick（`failures_to_down: 3` × `interval: 30s` = 90s）即发出 `state_transition down`——
  即一次**假阳性**的"Prometheus 挂了"。
- **说明**：假阳性方向对 deadman 是安全的（fail-closed），所以级别是 P3 而不是更高。
  但它会消耗运维对该通道的信任，而这正是本轮要求检查的"按名义耗时设预算"的同一形状。
- **修复方向**：给 freshness 单独一个 context（同为 `cfg.Timeout`），或引入
  `freshness.timeout` 并让 schema 明说。另建议把 `interval: 30s` 与
  `failures_to_down × interval = 90s` 同 `heartbeat_ttl: 90s` 的关系写进注释——
  目前这两个 90s 相等是巧合还是设计，配置文件里看不出来。

### C2-09 · ops webhook 自身故障没有独立探测路径；报告"投递坏了"的告警走的正是坏掉的那条路

- **级别**：P3

  或在 Phase D 准入清单里把"ops 投递路径的心跳"列为一条独立要求。
  前者是 4 行配置，且不引入新组件。

### 附加下限 · deadman 作为独立故障域的假设，在当前部署形态下是否仍成立

**部分成立。**

- **成立的部分**：仓库把独立性当作部署要求而不是代码属性，并且说清了这一点——
  `external-probe.example.yaml:1` 开篇即 "Run this stack only on an independently operated
  host/failure domain"；`README.md:109-113` 与 `operations-runbook.md:88-90` 都禁止与 Core 同机
  作为生产证据，并要求通知身份与最终 Contact Point 不得复用 Alertmanager 的；
  `RECEIVER-CONTRACT.md:39-41` 明说 "This repository contract is not that evidence"。
  代码侧的独立性也做到了：`halro-deadman` 是独立二进制（`cmd/halro-deadman`），
  独立 state/audit 文件、独立 TLS 材料、独立 systemd 硬化单元
  （`external-probe/halro-deadman.service`），出网无代理、禁重定向（`http.go:38-45`）。
- **不成立/未证实的部分**：
  1. Core 出厂形态（`compose.example.yaml`）**只含 prometheus + alertmanager**，
     且 `validate.sh` 强制断言服务集恰为这两个。deadman 是可选附加物。
     所以"独立故障域"在默认安装下**不存在**——它不是被削弱，是没有被部署。
     这直接影响 C2-01：stale 的唯一外部信号恰恰依赖这个默认不存在的组件。
  2. deadman 探的是三个 `/-/ready` 与一个抓取新鲜度查询，**不覆盖 ops 通知投递路径**
     （C2-09）。所以它是"Core 活着吗"的独立见证，不是"告警送得出去吗"的独立见证。
  3. FIFO 严格顺序（`engine.go:317-318`，`RECEIVER-CONTRACT.md:12-14`）意味着队首事件
     若被接收端**永久**拒绝（如 4xx），其后的心跳被无限期阻塞，receiver 会因 TTL 超时报"down"。
     方向是 fail-closed 所以安全，但故障表征会是"Halro 挂了"而非"某类事件被拒"。
     `event.schema.json` 与 schema 双向测试（`deploy/observability/schema_test.go`）
     降低了这个风险，未单列为发现。
  4. CI 只证明镜像可构建、配置可校验、状态机与重试正确
     （`ci.yml:180-194`、`schema_test.go`、`deadman_image_test.go`），
     `README.md:128-131` 自己也承认这些不证明故障域独立性。
- **结论**：假设在**文档与代码层面成立且被诚实标注**，在**默认部署形态下不成立**，
