# A5 · BUG 排查

> 角色：A5（BUG 排查）。全仓，重点在区间 diff（基线 33bc13b → HEAD 2cd24a7）。

## 1. 结论（< 200 字）

本区间新增的三大子系统（拓扑提交协议、能力探测、签名模型目录）在错误路径与
并发路径上写得相当克制：可能计费的 provider 调用用 reserved→running→unknown 三态
durable 记账、崩溃后不重放；`publicCapabilityDetection` 逐字段剥离密钥/内部字段；
provider 变更在提交前就用同一 policy 校验 credential audience，堵住了"改坏 BaseURL
让整张注册表致命 refuse → 全数据面 stale"这条自伤路径；签名目录验签、序列回滚、
canonical 重算、过期都 fail-closed。**未发现可复现的 P0/P1 缺陷。** 唯一有代码证据
的具体缺陷是一处 bbolt `ForEach` 中途 mutation（与本仓其余所有同类代码的写法相悖），
但我用 2000 条记录做的复现未能触发丢数据，故降级为 P3。另有两条 P3 观察。

## 2. 本角色评分：7.5 / 10

理由：新代码的错误路径与并发不变量普遍建得对、且有 durable 记账兜底（锚点 §3 的
7～8 档之间）。扣分点：(a) 存在一处与全仓安全写法不一致的 bbolt 迭代中 mutation，
虽未复现出丢数据但违反了 bbolt 明文契约，属"门没完全上锁"；(b) cancel 路径的乐观
并发在高频探测写入下会频繁 409，是可用性摩擦。没有 CONFIRMED 缺陷、也没有系统性
错误簇，故高于 7；但既然有一处契约违背 + 无针对性守护，不到 8。

## 3. 肯定项（值得在后续改动中保护）

- **P-1 提交前 audience 校验堵死 stale 自伤**：`admin_providers.go:862-876` 在
  `providerFromInput` 里用 `providerEndpointPolicy(r.config)` 重算 audience 并要求
  `credential.Audience == audience` 才允许提交。这正好使 `providers.go:389-391` 的
  致命 `refuse`（audience mismatch → 整张注册表构建失败 → markStale → 全数据面拒流）
  在正常 provider 更新下**不可达**。而 audience 字符串只由 scheme://host:semantic 组成、
  与 `AllowPrivate` 无关（`transport.go:119-129`），所以收紧私网开关也不会把已有
  provider 推进 audience-mismatch。这条 fail-closed 没有过度到自伤，值得保留。

- **P-2 可能计费调用的 durable 三态记账**：`admin_model_capability_detections.go:434-451`、
  `spendDetectionProbe`(:615-667) 在 provider 调用**前**把 reserved 再 running 落盘，
  崩溃后 `InterruptModelCapabilityDetections`(:162) 把 reserved/running 一律置 unknown、
  从不自动重放。`domain/model_capability_detection.go:73-88` 明确写死这个边界。符合
  "含糊的 Provider 结果保守记账、绝不静默退款"的仓库不变量。

- **P-3 探测记录出参剥离密钥/内部字段**：`admin_model_capability_detections.go:814-827`
  的 `publicCapabilityDetection` 删除 `target_fingerprint / credential_revision /
  credential_key_version / created_by / idempotency_key_hash / request_hash /
  provider_call_records / expiry_recorded_at`。审计元数据里模型名以 sha256 记
  (`detectionAuditMetadata`:810 `model_sha256`)。无秘密外泄。

- **P-4 目录观察者异步 reconcile 避免递归拓扑锁**：`admin_model_catalog.go:43-57`
  的注释与实现说明过期可能在 Admin mutation 已持有 `adminTopologyMu` 时被 `Current()`
  发现，故失败/过期路径把 reconcile 丢到后台 goroutine，观察者绝不递归取拓扑锁。
  这是本轮少见的把并发再入想清楚的地方。

- **P-5 safetransport 先校验全部解析地址再拨号其一**：`transport.go:141-159` 对
  `LookupNetIP` 返回的每个地址都 `validateAddress`，再只拨已校验过的 `addresses[0]`，
  同一次调用内无 TOCTOU。6to4/Teredo/NAT64 与云元数据地址显式拒绝(:168-208)。

## 4. 发现清单

### A5-01 · bbolt `ForEach` 迭代过程中对同一 bucket 做 `Put`（与全仓写法相悖）

- 级别：**P3**
- 类型：【疑似BUG】
- 是否阻塞 v1.0.0 发布：**否**
- 证据：`internal/store/bolt/model_capability_detection.go:169-197`。
  `InterruptModelCapabilityDetections` 在 `bucket.ForEach(...)` 回调**内部**执行
  `bucket.Put(key, encoded)`（:194）。bbolt 的游标契约明确：
  `go.etcd.io/bbolt@v1.5.0/cursor.go:19-21` — "Changing data while traversing with a
  cursor may cause it to be invalidated and return unexpected keys and/or values. You
  must reposition your cursor after mutating data." 而 `bucket.go` 的 `ForEach` 正是
  用 `c := b.Cursor(); for k,v := c.First(); ...; c.Next()` 实现。
- 交叉对照：本仓其余**所有**需要"边遍历边改"的地方都刻意用"先收集、后写入"规避此坑，
  例如 `store_pricing.go:927-975`（`quarantineIncoherentPricingHighWatersTx`，先填
  `updates` map 再在 ForEach 外 Put）、`store.go:1237-1258`（`rewriteBucket`）、
  `store_pricing.go:993-1005`（`RecoverDeploymentPricePins`，先攒 `deletes/updates`）。
  唯独这条 startup 恢复路径没有遵循，是明显的一致性缺口。
- 触发前置条件：崩溃时**有多条**能力探测处于 `queued/running` 且分布跨越多个 bbolt
  leaf page；恢复时把每条的值增大（追加 unknown 状态与时间戳）触发页分裂，可能使
  游标跳过/重复访问后续记录。后果是部分探测未被标记 interrupted（其 reserved/running
  的可能计费调用停留在非终态），或 `ForEach` 迭代异常。
- **诚实说明（负面复现）**：我在 scratchpad 用 bbolt v1.5.0 建 2000 条小值记录、
  在 `ForEach` 内把每条改成 400 字节大值（跨多 leaf page + 值增长），`visited=2000
  updated=2000 dropped=0` —— **未复现出丢数据**。故不主张"确有数据丢失"，仅主张
  "违反了明文契约且与全仓安全写法不一致，是应当消除的定时炸弹"，据此定 P3。
- 现有守护：`model_capability_detection_test.go:112` 的
  `TestCapabilityDetectionRecoveryInterruptsWithoutReplayingCalls` 只造**一条**记录，
  永远不会触发多页游标失效，看不见这个缺口。
- 修复方向：改为本仓既有的"先在 ForEach 里 collect key+encoded、循环外统一 Put"模式，
  与 `quarantineIncoherentPricingHighWatersTx` 对齐；并补一条含 ≥ 数百条在途探测的
  恢复用例作回归守护。

### A5-02 · 取消探测的乐观并发在高频探测写入下会频繁 409

- 级别：**P3**
- 类型：【建议】
- 是否阻塞 v1.0.0 发布：**否**
- 证据：`admin_model_capability_detections.go:873-909`。`cancelAdminModelCapabilityDetection`
  用 `requireRevision`(ETag) 强制 `d.Revision != expected → 409 capability_detection_changed`
  (:883-886)。而 `runCapabilityDetection` 每次 provider 调用会把 revision 至少推进两次
  （reserved 落盘 :438、running 落盘 :448、结果落盘 :485），一次多探测的运行期内 revision
  高频推进。
- 触发前置条件：控制台持有的 ETag 来自上一次轮询，取消请求发出时探测正好又写了一次
  → 版本失配 → 409，需重新拉取再取消。运行中的探测几乎总处于"正在写"的状态，使
  cancel 大概率首发 409。
- 影响：纯可用性摩擦（正确性无损：取消最终会成功，`CancelRequestedAt` 也会被后续
  probe 循环在 :417/:478 检查到）。与 D1 的"stale/409 提示是否可理解"相关。
- 修复方向：cancel 作为幂等意图，可不要求精确 revision 匹配（只要目标存在且非终态即
  受理），或在 409 响应里回带最新 revision 让前端自动重试。

### A5-03 · Gemini `DescribeInvocationTarget` 的解码结构体缺 JSON tag，靠大小写不敏感匹配

- 级别：**P3**
- 类型：【建议】
- 是否阻塞 v1.0.0 发布：**否**
- 证据：`internal/provider/gemini/adapter.go` 的 `DescribeInvocationTarget` 内
  `var item struct { Name, DisplayName string; InputTokenLimit int64; OutputTokenLimit
  int64; SupportedGenerationMethods []string }` 无任何 `json:"..."` tag，而 Gemini 返回
  camelCase 键（`name/displayName/inputTokenLimit/...`）。当前能工作只因 encoding/json
  的字段名大小写不敏感回退。
- 影响：功能正确，但脆弱——同文件的 `ListInvocationTargets` 用的是带 tag 的匿名结构体，
  两处风格不一致；未来若有人给字段改名/加下划线会静默丢字段。非缺陷，属规范面。
- 修复方向：与 `ListInvocationTargets` 对齐，给 `Describe` 的结构体补齐 json tag。

## 5. 下限项应答

本角色（A5）无"不允许空白"的枚举下限，只有产出约束：**要有代码证据的具体缺陷，
不接受"可能有问题"式结论、不把设计取舍写成缺陷**。逐条应答：

- **不接受泛化竞态表述** → 我逐一走过并发点并给出裁决而非泛论：
  admin mutation 与 `runActivationRecovery` 均在 `adminTopologyMu` 下串行
  (`admin_providers.go:101/183/219`、`activation_state.go:118-120`)，无锁反转；
  catalog `Refresh` 的 `stateMu→statusMu` 锁序与 `reject/expireIfNeeded` 一致
  (`manager.go:275/494/523`)，观察者失败路径异步化避免递归拓扑锁
  (`admin_model_catalog.go:43-57`)——**这些都不是缺陷**，明确记为正面。
- **不把设计取舍写成缺陷** → "stale 拒全数据面流量"是刻意的 fail-closed（A1 归口），
  我只核查它是否被普通 mutation 意外触发成自伤，结论是**被提交前校验堵死**（见 P-1），
  故不作为缺陷上报。
- **资源泄漏/边界/加解密随机源** → 抽查：`newProviderBindingAdapter` 错误路径关闭
  authorizer 与 idle conns(`providers.go:641-647`)；`writeAtomic` temp 文件 defer
  Remove + fsync 目录(`manager.go:580-610`)；签名验签用 `ed25519.Verify` + 长度校验
  (`snapshot.go:168-179`)、canonical 重算防篡改；未见泄漏或弱随机源。均无缺陷。
