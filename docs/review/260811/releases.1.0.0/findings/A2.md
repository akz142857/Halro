# A2 · 安全评审 · 信任边界与凭据链

区间：基线 33bc13b → HEAD 2cd24a7。本角色只给控制点清单与其失效方式，不含攻击脚本。

## 1. 结论（≤200 字）

本区间新增的三条面——能力探测 Admin 端点、私网端点开关生效、签名模型目录——总体延续了既有信任边界纪律：新写端点走 `requireAdminMutation`（会话+同源+CSRF+管理员角色），签名目录全路径 fail-closed（无签名/无可信根/过期/回滚一律拒绝并回落到 bundled），私网开关生效后出网面只多了 RFC1918/CGN，云元数据、环回、保留段仍被无条件拦截。未发现 P0/P1。存在两处一致性缺口：能力探测发起（花费凭据的计费调用）和 invocation-target 的 GET 侧信道（`refresh=true` 与 describe 解析路径）在花费凭据这件事上，其防护层级低于既有 `test`/删除类端点——前者靠 SameSite=Strict 单层兜底、无 CSRF/同源/step-up，后者的 describe 路径连角色门都没有。均为 P2，不阻塞发布。

## 2. 本角色评分：7.5 / 10

签名目录与 safetransport 修复的质量高（验签、来源约束、回滚保护、fail-closed 都成立且有负面测试）。扣分点在能力探测这条新出网面上"花费凭据"的一致性没有对齐既有端点的纵深防御——不是漏洞，是控制点分层的不齐，1.0.0 固定下来后再收紧要多一个兼容维度。

## 3. 肯定项（值得在后续改动中保护）

- **私网开关的单点收敛。** `providerEndpointPolicy(cfg)` 成为唯一派生点，ValidateURL 与 AudienceWithPolicy 由同一个 policy 派生，杜绝了"一个调用给了 policy、另一个静默套最严"的 bug 复发形态。`internal/app/providers.go:37-42`；六个调用点均改用它（`admin_providers.go:787,861,1053`、`bootstrap.go:56`、`admin_onboarding.go:75`、`doctor.go:318`）。
- **出网约束在运行时 dial 时再次强制，而非只在录入时校验。** `pinnedDialContext` 对解析出的每个地址重跑 `validateAddress`，只 dial 本次校验过的地址，杜绝 DNS-rebind。`internal/safetransport/transport.go:131-160`。
- **元数据/环回/保留段与 AllowPrivate 解耦。** 即使 `allow_private_provider_endpoints=true`，`alibabaMetadata`、`googleGCEMetadata`(169.254.169.254)、环回、link-local、`deniedPrefixes`（含 6to4/Teredo/NAT64）仍被无条件拒绝；只有 RFC1918 与 CGN 段跟随开关。`internal/safetransport/transport.go:168-216`。
- **签名目录全链 fail-closed。** 空可信根 → `ProductionTrustRoots()` 返回 nil → `verifySignatures` 无匹配根 → 返回 "signature is not trusted"（`snapshot.go:260-286`）；验签失败/过期/回滚/超限时 `reject`/`markDegraded` 一律把 `active` 置回 `Builtin()`（`manager.go:522-551`），不服务未验证内容。
- **签名装配拒绝把私钥当签名塞进信封。** `AssembleSignedSnapshot` 先本地验签再包装，且强制载荷为 canonical、拒绝 trailing JSON。`snapshot.go:147-180,150-160`。
- **敏感值不入审计。** provider 排除审计只记 reason class，注释明确底层错误携带 hostname/key 故不落盘（`capability_audit.go` 的 `auditProviderExclusions`）；探测审计对 provider model 做 `model_sha256` 哈希（`admin_model_capability_detections.go:809`）；`publicCapabilityDetection` 剥离 `target_fingerprint/credential_revision/credential_key_version/created_by/idempotency_key_hash/request_hash`（`:814-827`）。

## 4. 发现清单

### A2-01 · invocation-target 的 GET 侧信道能在无 CSRF/同源/step-up 下花费 Provider 凭据

- 级别：**P2**　类型：【问题】　阻塞 v1.0.0：否
- 证据：
  - `internal/app/admin_invocation_targets.go:98-101` — `listAdminInvocationTargets` 注册为 `requireAdmin`（GET，见 `runtime.go:1357`），`refresh=true` 时会 bypass 缓存、用运营者凭据打上游 List 调用。代码识别到"arrives as a GET"，于是手动补了 `requireAdministratorRole`，但**没有补 same-origin/CSRF**。
  - `internal/app/admin_invocation_targets.go:196` — `resolveAdminInvocationTarget`（GET，`runtime.go:1358`）在 `!matched` 路径调用 `describeInvocationTarget`，后者向上游发 `DescribeInvocationTarget`（`:231-257`）。此路径**既无 refresh 门、也无角色门、也无 CSRF/same-origin**，read_only 管理员即可触发上游调用。
- 对照既有控制点：花费凭据/有上游副作用的既有端点走的是 `requireAdminMutation`（`test`=`runtime.go:1361`，经 `requireAdminSelfMutation` 强制 same-origin+CSRF+角色，`admin_session.go:335-345`），删除类还叠 `requireDestructiveStepUp`。新 GET 侧信道只有 `requireAdmin`（`admin_session.go:253-265`，不含 CSRF/same-origin/角色）。
- 触发前置条件：一个已认证的 Admin 会话；对 resolve 路径连 read_only 角色都够。跨站发起被 `SameSite=Strict` 会话 cookie（`admin_session.go:361`）挡住——这是唯一的兜底层，而其余花费凭据的端点是 SameSite + 同源头 + CSRF token 三层。
- 后果：不是越权，是纵深防御缺一层——被盗会话或站内 XSS 情形下，计费上游调用比删除操作更容易被驱动；且 read_only 角色的语义（"不触碰系统数据"）在 resolve.describe 上被穿透，它能让系统花钱/打上游。
- 修复方向：把 resolve 的 describe 解析路径纳入 `requireAdministratorRole`（与 list 的 refresh 门对齐）；对两条花费凭据的 GET 侧信道，要么改成显式 POST 走 `requireAdminMutation`，要么在 GET 上补 `adminSameOrigin` 校验，使兜底不止 SameSite 一层。

### A2-02 · 能力探测发起花费凭据但不要求 step-up（与既有 test 端点一致、与"计费不可逆"不一致）

- 级别：**P2**　类型：【建议】　阻塞 v1.0.0：否
- 证据：`internal/app/admin_model_capability_detections.go:48` `createAdminModelCapabilityDetection` 注册为 `requireAdminMutation`（`runtime.go:1362`），会启动最多 `MaxProviderCalls` 次可计费上游探测（`:434-462`）。它有 CSRF+同源+角色+Idempotency-Key+速率限制（`:49-53,202-209`），但**无 step-up**。
- 对照：`testAdminProvider`（`admin_providers.go:339`）同为花费凭据、同为 `requireAdminMutation`、同样无 step-up。所以新端点与既有 test 端点**一致**；step-up 在本仓库被保留给**删除/销毁类**（`requireDestructiveStepUp` 仅出现在 delete credential/provider/route/deployment、alerts、redaction）。
- 判断：这是设计取舍而非缺陷——本角色不将其记为 BUG。列出是因为 §5 表 5 与 260807 遗留都触及"计费 Provider 调用的门控"：一个被盗会话可在不重新认证的情况下驱动一串计费探测。若要收紧，应与 test 端点一并纳入 step-up，避免再造不一致。
- 修复方向（可选，非阻塞）：把"发起会花费 Provider 凭据的操作"（detection 发起 + provider test）统一到一个 step-up 层，而不是逐个端点决定。

### A2-03 · 签名模型目录：来源约束依赖编译期常量，运行时无二次校验（信息项）

- 级别：**P3**　类型：【肯定/建议】　阻塞 v1.0.0：否
- 证据：`internal/modelcatalog/manager.go:141-156` — 生产路径下 URL、host 允许清单（`raw.githubusercontent.com`）、SafeTransport policy 全部编译进二进制，`HTTPClient/Endpoint` 仅测试注入。可信根经 `-ldflags` 注入 `ReleaseTrustRoots`（`release.yml:153`），source/dev 构建为空 → 任何签名目录验签失败 → 回落 bundled（fail-closed）。
- 判断：来源约束成立且 fail-closed。唯一需运维知情的后果：**release 构建若启用 catalog 但未注入 trust roots，会静默无法更新**（可用性，非安全）。已由 `ModelCatalog.Enabled` 默认 false（`config/default.go:125`）缓解——默认不出网。
- 修复方向：无需改代码。建议在发布说明/B3 环节确认 release job 校验 `MODEL_CATALOG_TRUST_ROOTS` 非空（当前 `release.yml:153` 只是注入，未见非空断言）。

## 5. 下限项逐条应答

### 下限 1 — 能力探测新增 Admin 端点面的鉴权/CSRF/revision/step-up 与既有端点是否一致

**基本一致，两处分层缺口（A2-01/A2-02），无越权。** 逐条：

| 新端点 | 中间件 | 鉴权 | CSRF+同源 | 角色门 | revision/幂等 | step-up |
|---|---|---|---|---|---|---|
| `POST /model-catalog/refresh` | `requireAdminMutation` | ✓ | ✓ | ✓ | n/a（无载荷） | 无（与既有 create 一致） |
| `GET /model-catalog` | `requireAdmin` | ✓ | 读，n/a | 读，n/a | ETag n/a | n/a |
| `GET /providers/{id}/invocation-targets` | `requireAdmin` | ✓ | **refresh 花费但只补角色门、无 CSRF/同源**（A2-01） | refresh 时手动补 | n/a | 无 |
| `GET /providers/{id}/invocation-targets/*`（resolve） | `requireAdmin` | ✓ | **describe 花费但无任何补充门**（A2-01） | 无 | n/a | 无 |
| `POST /providers/{id}/model-capability-detections` | `requireAdminMutation` | ✓ | ✓ | ✓ | Idempotency-Key 必填+速率限制 | 无（与 test 一致，A2-02） |
| `GET /model-capability-detections/{id}` | `requireAdmin` | ✓ | 读，n/a | 读，n/a | ETag ✓ | n/a |
| `DELETE /model-capability-detections/{id}`（cancel） | `requireAdminMutation` | ✓ | ✓ | ✓ | **requireRevision ✓**（`:874`） | 无（cancel 非破坏，一致） |

证据：`runtime.go:1353-1364`；`admin_session.go:314-322,335-345`（Mutation 强制同源+CSRF+角色）；`admin_model_capability_detections.go:874`（cancel 的 revision 门）。会话认证、角色随请求实时读取（`admin_session.go:280-291`）、cookie `Secure+HttpOnly+SameSite=Strict`（`:361`）均与既有端点同源同码。GET 的 CSRF 缺口由 SameSite=Strict 兜底但只有单层——记为 A2-01。

### 下限 2 — 私网开关生效后的出网面变化与 safetransport 约束完整性

**开关生效使出网面新增 RFC1918 + CGN(100.64/10) 两类目标，其余约束在所有 Provider/Credential 路径上仍完整。**

- 开关生效前后的实际差量（`internal/safetransport/transport.go:190-216`）：`AllowPrivate` 只放行 `address.IsPrivate()`（RFC1918）与 `carrierGradeNAT`。**不受开关影响、始终拒绝**的有：unspecified、loopback、multicast、link-local(含 169.254.169.254)、`alibabaMetadata`(100.100.100.200)、`deniedPrefixes`（0.0.0.0/8、192.0.0.0/24、198.18.0.0/15、240.0.0.0/4、NAT64、6to4、Teredo）、非 global-unicast。→ 云元数据 SSRF 与环回未被开关打开。
- 六个 Provider/Credential 录入路径与出网路径均经统一 policy：录入 `admin_providers.go:787,861,1053`、`bootstrap.go:56`、`admin_onboarding.go:75`、`doctor.go:318`、注册表加载 `providers.go:373-375`；运行时出网客户端 `newProviderBindingAdapter`（`providers.go:572-576`）把同一 policy 传给 `safetransport.NewClient`，`pinnedDialContext` 在 dial 时对每个解析地址复跑 `validateAddress(…, policy.AllowPrivate)`（`transport.go:153-159`）。→ HTTPS 强制（`RequireHTTPS:true`，`providers.go:39`）、host 允许清单（per-provider `instance.AllowedHosts`，`providers.go:374` + 校验与 dial 两处 `hostAllowed`，`transport.go:107,138`）、DNS/IP 校验、pinned dial、无重定向（`CheckRedirect` 返回 `ErrUseLastResponse`，`transport.go:80-82`）、无环境代理（`Proxy:nil`，`transport.go:67`）全部保留。
- 一致性：webhook 侧走独立 `webhookPolicy`（`alerts.go:23-26`，`AllowPrivateWebhooks`），与 provider 侧互不影响；两个开关现在都真实生效（此前只有 webhook 生效）。
- F-06 的连带：开关收紧时旧 provider 端点变非法，现改为 `excludeProvider`（withheld，非致命，`providers.go:376-388`），而凭据解密失败/audience 不符仍致命（`:389-391,405-411`）。这条 fail-closed 边界正确：配置类失败降级、密码学/完整性类失败拒绝启动。

### 下限 3 — 签名模型目录的验签、来源约束、失败处置是否 fail-closed

**三者均 fail-closed，无绕过路径。**

- 验签：`DecodeAndVerifySignedSnapshot`（`snapshot.go:190-223`）在 `MergeSnapshots` 之前依次强制：schema 范围、dictionary 版本、sequence>0、generated/expires 区间、未来时间、过期、entry 数上限、canonical revision 匹配、pinned revision 匹配（`validateRemoteSnapshot:225-258`），再 `verifySignatures`（`:260-286`）。后者要求 ≥1 签名、算法=ed25519、KeyID 命中可信根、根有效期与快照时间窗双向包含、`ed25519.Verify` 通过。空可信根集合直接导致无命中 → 返回错误。**无签名或验签失败绝不产生 Catalog。**
- 来源约束：远端仅 `raw.githubusercontent.com`、HTTPS、编译期 host 允许清单、`MaxConnsPerHost:1`，测试注入之外不可改（`manager.go:141-156`）。下载有大小/解压比/entry 上限（`download:334-390`）防 zip-bomb。
- 失败处置：`Refresh` 任一步失败调 `reject`（`manager.go:522-543`）→ 有 LKG 时 `active=Builtin()` 且 state=degraded，无 LKG 时 unavailable；`loadLastKnownGood` 验签失败/过期 `markDegraded` 且过期 LKG **不** store 进 active（`:440-450`，active 保持 NewManager 里的 `Builtin()`）；`expireIfNeeded` 到期把 active 换回 `Builtin()`（`:490-514`）；sequence 回滚/复用（`:251-256`）、checkpoint 不可用（`:248-249`）、CAS 期间 checkpoint 变化（`:277-285`）均 reject。→ 任何异常都退回 bundled 已审目录，绝不服务未验证/被回滚的远端内容。
- 二次确认：`AssembleSignedSnapshot`（签名装配，`:147-180`）与运行时读取共用同一 canonical+验签逻辑，且拒绝把 64 字节私钥当签名塞入。
