# B4 · 数据迁移与升级

评审区间:基线 `33bc13b` → HEAD `2cd24a7`。模型:Fable 5(claude-fable-5)。全部跨版本结论来自实跑(基线二进制、rc.1 二进制、HEAD 二进制三方对照,隔离实例建在会话 scratchpad 下),未实跑处逐条注明。

## 1. 结论

迁移机制本身是这个仓库里做得最扎实的部分之一:全链单事务、降级 fail-closed、拒绝信息(schema 20)可行动、restore 保留回滚目录。问题全部集中在公告层:本区间 22.5k 行改动没有产生一行 CHANGELOG;而 1.0.0 唯一的既有标签 rc.1 到 HEAD 之间,升级路径实际上不存在(配置被拒、备份验签失败、master key 认证失败),失败方式有两处呈现为误导性错误,而这一切在 CHANGELOG 与发布说明中均无一字。机制可发,公告不可发。

## 2. 本角色评分:5.5 / 10

锚点(scoring-rubric.md §3):5~6 档 ——"无 CONFIRMED P0,但 P1 集中在同一子系统;已知问题有运维绕过手段,但绕过手段本身没有写进文档"。两条 P1 都在公告子系统;rc.1 用户的绕过手段(重建实例)存在但没写进任何文档。不到 7(P1 并非各自孤立且无书面绕过),不到 6(其中一处失败方式把版本不兼容呈现为密钥/篡改问题,超出"缺文档"的范畴)。给 5.5 而非 5:破坏面经实证收窄——区间内迁移全部就地升级,真正丢数据的场景仅限未发布的中间构建。

## 3. 肯定项(值得在后续改动中保护)

- **迁移链在一个 bbolt 写事务内跑完**(`internal/store/bolt/store.go:1131-1209`,`s.db.Update` 包住整个 for 循环):任何迁移中途崩溃,schema 版本、迁移历史、数据变更一起回滚。24~27 因此天然具备崩溃原子性,不需要每条单独的 kill-point 测试。
- **降级双向 fail-closed 且不静默**:迁移路径拒绝更新的 schema(`store.go:1142-1146`,"newer than this build supports");只读诊断路径精确匹配(`store.go:840-843`)。实证:v27 目录上跑基线二进制 doctor,metadata 检查 fail,信息为 `metadata schema version 27 does not match required version 23`。
- **schema 20 的拒绝信息是本仓库可行动错误的范本**(`store.go:378` 起,migration 20;实跑输出见附录 §C.4):命名了受影响的部署数量,给出两条出路(`make reset CONFIRM=RESET` 重建,或留在旧构建)。CHANGELOG 的 Operator impact 段(`CHANGELOG.md:97-104`)与实测行为完全一致。
- **restore 原子切换并保留回滚目录**(实证输出含 `previous_data_dir=.halro-pre-restore-*`;`docs/guides/backup-restore.md:164-165` 明确"不要就地降级,恢复升级前的归档")。
- **迁移名与步骤名被测试冻结**(`internal/store/bolt/migration_names_test.go:15-38`):防止重命名让实例与自己的迁移历史失配。
- **restore 会迁移 bbolt 这件事文档里写了**(`docs/guides/backup-restore.md:258`,"opens/migrates bbolt")——虽然 CLI 输出没说(见 F-3)。

### F-2 【问题·P1】rc.1 → 1.0.0 实际上不存在升级路径,且三处断裂无一公告、两处失败方式误导

- **是否阻塞 v1.0.0 发布:需裁决**——若发布说明明确写入"rc.1 从未发布、其数据目录与备份与 1.0.0 不互通、必须重建实例",可以带着这个事实发;不写不能发。
- **证据与实测**(全部实跑,rc.1 二进制从 `v1.0.0-rc.1` 标签构建,当时项目名为 heimdall):
  1. **配置被拒**:HEAD 二进制拒绝 rc.1 生成的配置文件,三个已删除字段(`adjustment_soft/hard/daily_hard_limit_micros_usd`,删除于 `8868e85`,基线前)逐行报错。信息可定位,但 CHANGELOG 无条目。
  2. **备份跨不过去**:rc.1 创建的 `.hmbk`(manifest schema 19、format 2)在 HEAD 上 `backup verify`/`restore` 均失败,错误为 **`backup authentication failed`**。根因:`0814cac`(Rename Heimdall to Halro,2026-08-08,基线前)把备份加密域串从 `heimdall:backup:v1\x00` 改为 `halro:backup:v1\x00`(rc.1 树与 HEAD 的 `internal/backup/crypto.go:206` 对照)。同一把 32 字节备份密钥,错误却呈现为密钥错误或归档被篡改。
  3. **数据目录跨不过去**:含部署的 rc.1 目录在 HEAD 启动被 migration 20 拒绝(信息可行动,见肯定项);**空的** rc.1 目录被拒于 `master key does not authenticate the metadata store` —— 根因同为 rename:vault 审计域从 `heimdall:metadata` 变为 `halro:metadata`(HEAD `internal/app/init.go:131`,HKDF 串见 `internal/vault/vault.go:146`)。master key 本身完全正确,错误却指向密钥。
  4. **公告缺席**:CHANGELOG 与 `docs/milestones/release-notes-v1.0.0.md` 均无 rename 及其密码学后果的任何记录(`grep -i "rename\|heimdall"` 双双为空)。发布说明的升级流程(release-notes-v1.0.0.md:138-141)与 CHANGELOG rc.1 段的自述("记录早期操作者需要采取的差异",`CHANGELOG.md:149-152`)都在暗示一条并不存在的升级连续性。

- **修复方向**:发布说明加"从 rc.1 升级"一节,直说无路径、需重建;可选:给 backup verify 的认证失败与 vault 认证失败补一句"若归档/目录产自 2026-08-08 rename 之前的构建,属版本不兼容"。

### F-3 【问题·P2】老备份在新二进制上恢复:成功,但迁移发生在 restore 内部且全程无提示

### F-4 【问题·P2】新备份在旧二进制上的拒绝信息不可行动:版本不兼容与八种损坏折叠成同一句话

- **是否阻塞 v1.0.0 发布:否**
- **证据**:实跑:v27 备份在基线二进制上 verify/restore 均失败,唯一输出 `backup manifest is invalid`。代码上 `manifest.Metadata.SchemaVersion > boltstore.CurrentSchemaVersion()`(`internal/backup/archive.go:274`)与 foundManifest 缺失、加密标志、水位不一致等约八个不相关条件共用一条错误(`archive.go:271-279`)。fail-closed 成立,归因不成立:操作者无法区分"备份坏了"与"二进制旧了",而后者的正确动作(换新二进制)恰好是前者的错误动作。metadata store 同类拒绝已经做对了(`store.go:1143-1146` 报出两个版本号),备份路径应当对齐。
- **触发前置条件**:灾难恢复时抓到的二进制比备份旧——恰是最紧张的场景。
- **修复方向**:把 schema 越界从 `archive.go:271-279` 的合并条件中拆出,报 `backup metadata schema %d is newer than this build supports (%d)`。

## 5. 下限项逐条应答

**下限 1 —— reset 迁移的数据后果是否已写进变更说明与发布说明;运行它的实例会看到什么。**
负面,但需先修正前提:reset 迁移是**两条**(25、26),不是三条(F-5)。后果**完全未公告**:CHANGELOG 在整个区间零提交(F-1),发布说明亦无。运行它的实例**什么都看不到**——实跑 v23→v27 就地升级,9 行启动日志无一字涉及迁移或重置(附录 §C.3)。缓解事实:对一切已发布/基线实例,重置是空操作;真实丢数据面限于未发布中间构建(F-5,该场景本身无法实跑,原因见该条)。

**下限 2 —— "需要重新初始化数据目录"的公告是否覆盖本区间全部破坏性变更。**
分两半。区间内(33bc13b→HEAD):**正面**——24~27 全部就地升级,实跑证实无新增再初始化要求(带拓扑的 v23 目录升级后 doctor 全 pass、路由完整),既有的 schema 20/21/22 公告(`CHANGELOG.md:97-104`、`128-135`、`137-145`)与实测行为逐条一致,schema 20 的拒绝信息与公告承诺相符;区间也未动 ledger/usage/audit/backup 任何格式(`git diff 33bc13b..2cd24a7 --name-only` 于四目录计 0 文件)。升级路径整体:**负面**——真正的公告黑洞在 rc.1 边界(F-2):rename 造成的备份/vault 密码学断裂与配置字段删除,使"需要重建实例"这个事实上存在的要求没有出现在任何公告里,而它才是 1.0.0 唯一有既有标签的升级入口。

**下限 3 —— 跨版本 backup/restore 的失败方式,实测而非推断。**
已实测四个方向(命令与输出见附录 §C):
1. **基线 v23 备份 → HEAD 二进制:成功**(非拒绝、非部分成功)。verify 通过,restore 成功并在内部静默迁移至 v27(F-3),启动后 readiness 200、Gateway Key 可用、拓扑完整。
2. **HEAD v27 备份 → 基线二进制:干净拒绝,归因误导**。verify/restore 均以 `backup manifest is invalid` 拒绝(F-4),fail-closed 成立,不指明版本原因。
3. **rc.1 v19 备份 → HEAD 二进制:误导性失败**。`backup authentication failed`——既非成功也非版本拒绝,呈现为密钥/篡改问题,实为 rename 换掉加密域串(F-2.2)。
4. **HEAD v27 目录 → 基线二进制(就地降级)**:干净拒绝且信息准确(`metadata schema version 27 does not match required version 23`)。
结论:同代(rename 之后)的跨 schema 恢复是"成功+静默迁移";跨 rename 边界的恢复是"误导性失败"。部分成功(还原一半)在任何方向都未出现。
