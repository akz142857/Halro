# C3 · 性能与容量（实跑，承担 G9）

模型：claude-fable-5（Fable 5）。未遇到拒答或空响应。

## 1. 结论（≤200 字）

单机容量的治理瓶颈是 **darwin 上的 F_FULLFSYNC**，与文档一致。实测：账目生命周期在 64 并发下达
1223 lifecycles/s，随并发（非项目数）线性扩展，验证 ADR 0018 的形状；管理写路径受 bbolt `db.Update`
不合并的每次全量 fsync 限制，本机约 100 tx/s，端到端管理变更约 31~42 mut/s。**拓扑提交协议把管理写路径
吞吐实测降低 25.3%**（41.7→31.1 mut/s，+33.9% 延迟，p=0.008），因每次变更多一次 db.Update（删除
intent）。**argon2 内存放大已实测复现且未修**：每个并发登录尝试占 64.2 MiB，无信号量，16 并发即
1.06 GiB、64 并发达 4.13 GiB，且 Go scavenger 数分钟内不归还。长跑（2588 次变更）内存与 goroutine
无泄漏。**测试环境是 macOS/darwin，不是 Linux/NVMe**，绝对数字偏悲观 1~2 个数量级，见 §2。G9 已取得实测数据。

## 2. 测试环境（偏差必须如实写明）

| 项 | 值 |
|---|---|
| 机器 | Apple M4 Pro, darwin/arm64, 14 逻辑核, 64 GiB RAM |
| OS | macOS 26.6 (Darwin 25.6.0) |
| Go | go1.26.5 darwin/arm64 |
| 文件系统 | APFS，`os.File.Sync` 发 `F_FULLFSYNC`（真磁盘屏障） |
| 被测提交 | HEAD = `2cd24a7`；对照 = `18f3939^` = `3c78646` |
| 隔离 | scratchpad git worktree 副本 + 独立 init 实例，端口 28080/28081/29090 |

**偏差与影响（这是本报告最重要的免责声明）**：

- 本机每次 fsync 走 `F_FULLFSYNC`，是真正的物理磁盘屏障，通常比 Linux NVMe 上的 `fdatasync` 贵
  **1~2 个数量级**。因此所有"每秒事务/变更/生命周期"的绝对值是 **单机地板**，Linux NVMe 生产机会显著更高。
- **可迁移的是形状，不是数字**：扁平 vs 随并发扩展、线性内存放大、协议前后的相对差，这些跨主机成立；
  绝对吞吐不成立。文档 `standalone-capacity-baseline.md:41-43` 已明确这一点，本报告与之一致。
- 内存放大（argon2）与是否 darwin 无关——那是算法参数 × 并发度，Linux 上放大系数完全相同。
- 仍未在 Linux NVMe + 生产构建标志 + 关闭 race 的条件下复现（`standalone-capacity-baseline.md:99-100`
  的"仍开"项在本轮依然仍开）。

## 4. 肯定项（值得在后续改动中保护）

- **账目吞吐由并发而非项目数治理**（ADR 0018 的核心承诺）：`internal/budget` `BenchmarkRequestLifecycle`
  实测 projects=1/8/64 在 workers=64 下分别为 1223/1220/1157 lifecycles/s，三行同噪声内一致，单项目不再被
  per-project 锁封顶。这是正确且应保护的设计，见 `docs/verification/standalone-capacity-baseline.md:62-73`。
- **管理写路径长跑无泄漏**：2588 次真实 HTTP PUT 变更后 RSS 仅 +1.4 MiB 并在 ~900 次后持平，
  `go_goroutines` 稳定在 18。审计 intent 采用"投递后删除"而非"打标保留"，避免最频繁写路径上的无界增长
  （`internal/store/bolt/store_admin_audit.go:92-104`；设计理由见提交 18f3939）。
- **intent 与 mutation 同事务**：`putAdminAuditIntentTx` 在同一 `bbolt.Tx` 内写入
  （`internal/store/bolt/store_projects.go:22-27`），因此协议本身没有为"记账"额外增加一次 fsync，额外成本
  只来自事后的 delete（见 §5.3）——这是一个克制的实现。

## 5. 三条下限逐条应答（全部有实测数字）

### 下限 1 — 结论必须来自实测数字，给出环境、方法与原始数字 ✅ 正面

环境见 §2。方法：committed benchmark（`internal/ledger`、`internal/budget`、`internal/store/bolt`）
+ 端到端 HTTP 写路径 benchmark（scratchpad-only 的 `_test.go`，两个 worktree 各跑一份）+ 真实二进制
起实例后的并发/长跑观测。原始数字：

**账目生命周期（`BenchmarkRequestLifecycle`，workers × projects）**：

| projects\workers | 1 | 8 | 64 |
|---|---:|---:|---:|
| 1 | 44.7 | 163.3 | **1223** |
| 8 | 47.1 | 166.4 | 1220 |
| 64 | 39.7 | 143.9 | 1157 |

（lifecycles/s；每 lifecycle = 5 个 Ledger 事件。64 并发 = 6117 events/s。）

**原始 WAL 追加（`BenchmarkConcurrentAppend`）**：appenders=1/8/64/256 → 214/895/7271/12870 events/s，
观测 batch 大小 1.0/4.05/32.4/63.8——group-commit 随并发合并，符合设计。

**bbolt 元数据写（`BenchmarkMetadataWriteTransaction`）**：`db.Update` 在 workers=1/8/64 恒为
101.7/100.0/106.3 tx/s（**扁平**，不合并）；`db.Batch` 为 91/453/4317 tx/s（合并生效）。
**管理变更走的是 `db.Update`**，故其吞吐被单次全量 fsync 钉死在 ~100 tx/s。

**端到端管理写路径**（真实 admin router：revision 校验→store commit→activation→audit）：HEAD 中位
31.1 mut/s（区间 27~34）。这个数比裸 100 tx/s 低，因为每次变更含多次 db.Update（mutation-tx + audit
checkpoint + delete-intent）。

结论：单机（darwin 地板）容量画像清晰，G9 有实测支撑。**Linux NVMe 上账目与写路径吞吐会显著高于以上
数字；以上是地板不是天花板。**

### 下限 2 — 长跑内存增长 + argon2 并发内存放大 ✅ 正面（含一条未修风险）

**长跑（真实实例，2588 次 HTTP 变更 / 120s）**：RSS 4,236,224 → 4,237,680 KiB（+1,456 KiB 全程），
~900 次后完全持平；`go_goroutines`=18 稳定；`halro_metadata_batch_calls_total`=0（印证管理路径不合并）。
**无内存泄漏、无 goroutine 泄漏。**

**argon2 并发内存放大（260807 遗留项，实测复现）**：`internal/adminauth/password.go:16` 设
`argonMemoryKiB = 64*1024`（64 MiB/次），`VerifyPassword`（:74）与 `DummyVerify`（:96）均无并发限制。
登录处理器 `loginAdmin`（`internal/app/admin_session.go:48`）在每请求路径上同步调用它，登录失败的未知用户
也走 `DummyVerify`（:78、:85）。实测（对同一实例并发发起登录，采样进程 RSS 峰值）：

| 并发登录数 | RSS 峰值 | 相对基线增量 | 每连接 |
|---:|---:|---:|---:|
| 0（基线） | 30 MiB | — | — |
| 16 | 1057 MiB | 1027 MiB | 64.2 MiB |
| 32 | 2084 MiB | 2054 MiB | 64.2 MiB |
| 64 | 4136 MiB | — | 64.2 MiB |

**每并发登录精确占 64.2 MiB，完全线性，无上界。** 且 RSS 是高水位：64 并发一次冲高到 4.13 GiB 后，
后续 4 分钟（含整个 2588 次长跑）Go scavenger 都未把它还给 OS。

后果与控制点分析（本区间未新增控制点，此风险是 260807 遗留）：
- 现有唯一控制点是 `login_rpm`（默认 5，`internal/config/default.go:46`）的**每源每分钟**限流
  （`allowAdminRate`，`admin_session.go:404-426`）。但它是 per-source：其一，单源在一分钟内被允许的
  ~5 个请求若并发到达，即 5×64=320 MiB；其二，限流按源分桶，maxTrackedAdminSources=4096，源可变则
  乘数 = 源数 × rpm，仍无全局并发上限。真正兜底的是"进程总内存×fsync"而非任何 argon2 专用信号量。
- 260807 记录此前仅靠 k8s `1Gi` limit 兜底；**裸机与 Docker 默认无该 limit**。实测 16 并发即越过 1 GiB，
  说明该兜底的裕度极小。默认 Admin 监听为 loopback（`default.yaml:18`），把利用面收窄到"可达 Admin 监听"
  的部署（非 loopback 部署、或本机恶意进程）。
- **是否阻塞 v1.0.0：需裁决。** 它不是 G9 意义上的"容量不足"，但在无 cgroup limit 的裸机/Docker 上，
  一次并发登录风暴可把进程推向 OOM，属容量域可用性风险，与 A2/A3/A5 的安全视角有交集。修复方向：给
  argon2 验证加一个小容量全局信号量（如 = GlobalConcurrency 或 CPU 数量级），排队而非并行分配 64 MiB 块。

### 下限 3 — 拓扑提交协议对写路径吞吐的影响必须被测到 ✅ 正面

方法：同一段 scratchpad-only HTTP 写路径 benchmark（PUT 项目，走完整 admin router），分别在
HEAD（`2cd24a7`，含协议）与 `18f3939^`（`3c78646`，协议前）两个 worktree 各跑 5×100 op，benchstat 比较。
这是"两侧都构建、同输入同 harness"的反向验证，非从 diff 推断。

benchstat 结果：

```
                                   sec/op                         mutations/s
C3AdminProjectUpdateWritePath   23.99m → 32.12m  +33.90%      41.69 → 31.13  -25.33%   (p=0.008 n=5)
```

**拓扑提交协议使管理写路径吞吐下降 25.3%（延迟 +33.9%），统计显著。** 归因：协议把审计记录并入 mutation
事务本身不加 fsync（§4），真正的成本来自事后 `deliverAdminAuditIntent`
（`internal/app/admin_audit_intent.go:87-107`）里的 `DeleteAdminAuditIntent`
（`store_admin_audit.go:97-104`）——那是每次变更**额外一次 `db.Update`**，在 darwin 上即额外一次
F_FULLFSYNC（~10 ms），足以解释 8 ms/op 的差。

裁决：**不阻塞 v1.0.0。** 管理变更是人工、低频操作，31 mut/s 的单机地板远高于任何真实管理负载；且在
Linux NVMe 上这一 fsync 的绝对成本降 1~2 个数量级，25% 的相对差会相应缩小。这是一个应被记录的正确性
换吞吐的取舍，不是容量瓶颈。数据面（Gateway 请求）不经此路径，不受影响。

## 6. 发现清单

### C3-01 argon2 登录验证无并发信号量，内存放大线性无上界
- 级别：**P1** ｜ 类型：【疑似BUG / 问题】｜ 是否阻塞：**需裁决**
- 证据：`internal/adminauth/password.go:16`（64 MiB/次）、`:74` `VerifyPassword`、`:94-100` `DummyVerify`；
  调用点 `internal/app/admin_session.go:78,85,90`（每请求同步，未知用户也触发）；唯一限流
  `admin_session.go:404-426` 为 per-source-per-minute，非全局并发上限。
- 触发前置条件：Admin 监听可达（非 loopback 部署，或本机进程），并发发起登录/无效登录请求；无 cgroup
  内存 limit（裸机/Docker 默认）。实测 16 并发 = 1.06 GiB，64 并发 = 4.13 GiB，且高水位不归还。
- 修复方向：argon2 验证前置一个小容量全局信号量（排队而非并行分配），或把 per-source 限流补一个进程级
  in-flight-hash 上界。

### C3-02 拓扑提交协议使管理写路径吞吐降 25.3%（darwin 实测）
- 级别：**P3** ｜ 类型：【建议 / 肯定】｜ 是否阻塞：**否**
- 证据：benchstat 41.69→31.13 mut/s（p=0.008）；额外 fsync 来自
  `internal/app/admin_audit_intent.go:106` → `internal/store/bolt/store_admin_audit.go:97-104` 的
  `DeleteAdminAuditIntent`（独立 `db.Update`）。
- 触发前置条件：darwin/F_FULLFSYNC 主机上的高频连续管理变更；Linux NVMe 上相对差缩小。
- 修复方向：无需阻塞。若日后管理写吞吐成为约束，可把 delete-intent 折叠进下一次 mutation 事务或批量
  drain，消掉每变更的额外屏障。仅作记录。

### C3-03 管理元数据写走 db.Update 不合并，单机地板 ~100 tx/s
- 级别：**P3** ｜ 类型：【肯定 / 疑问】｜ 是否阻塞：**否**
- 证据：`BenchmarkMetadataWriteTransaction` update 行 workers=1/8/64 恒为 101.7/100.0/106.3 tx/s；
  `halro_metadata_batch_calls_total`=0 印证生产路径未用 Batch。
- 说明：这是设计选择（管理变更需强持久且低频），非缺陷。记录以便设定重启/运维 SLO 时不误以为可随并发扩展。
