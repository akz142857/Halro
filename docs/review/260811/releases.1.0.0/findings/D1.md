## 1. 结论（不超过 200 字）

Credential → Provider → Deployment → Route → Project → Gateway Key 这条路径本身的表单结构清晰，能力探测
（capability detection）的分状态提示是本区间设计得最讲究的一块，且有测试守护。但三条下限里有两条给出明确的负面
结论：创建表单撞上 409 幂等重放时，五个受影响资源（Provider/Deployment/Route/Project/Gateway Key）没有一个
把它与普通的"数据被别人改了"区分开，且服务端可读的英文提示会未经翻译直接出现在 zh-CN 界面；stale（运行时拒绝
数据面流量）这个本区间最关键的新状态，在控制台里完全不可见——类型定义里都没有这个字段。第三条（能力探测流程）
基本合格，只有一处成本披露不完整。

## 2. 本角色评分：6.0 / 10

理由（对照 scoring-rubric.md §3 锚点）：无 CONFIRMED P0，落在"5~6"到"7"之间。不给 7 分，因为两条命中下限的
负面发现都属于"有绕过手段但完全没有写进产品里"——即锚点 5~6 档的定义句本身；不给 5 分或更低，因为这两条都不是
主干走不通（管理员仍能创建 Provider/Deployment/Route/Project/Key，只是撞上 409 时会被误导），且能力探测这条本
区间投入最大的新交互面做得扎实、有回归测试守护，把分数往上拉。三条证据基础：D1-01（409 重放）、D1-02（stale
不可见）为负面主证据；D1-03 与"肯定项"第 1、2 条为正面主证据。

## 3. 肯定项

1. **能力探测把"探测不到"和"模型拒绝"分开说，并且分状态给出明确下一步。** `queued/running` 显示进度与取消成本
   提示；`ambiguous` 给出候选接口选择器；`completed` 且无可用能力时区分"需要去 Provider 修凭据"和"探测结论就
   是不支持"两种情况；`failed/canceled/interrupted` 逐个候选接口列出"问了什么、答了什么、这个接口本来能验证什么"，
   并提供"改用人工声明"的退路。`web/src/pages/DeploymentsPage.tsx:1291-1351`，尤其 1323-1329 行的设计注释直接
   点出"a failure is not the model is broken"这个易错点。这是本区间对"不懂内部模型的管理员能否看懂系统在做什么"
   这条下限回答得最好的一处。
2. **保存被拦截时命名每一个具体原因，而不是一个灰掉的按钮。** `web/src/pages/DeploymentsPage.tsx:1057-1075`
   （`saveBlockers` 数组）+ `1470-1473` 的渲染——把 "缺名字/缺模型/缺接口结论/缺检测/缺运营点/限额不合法" 五六种
   互斥情况显式列出，配合 `deployments.saveBlockers.*` 的 i18n 文案（`en-US.ts`/`zh-CN.ts` 对应键齐全）。
3. **能力探测的核心分支有测试守护。** `web/src/pages/DeploymentsPage.test.tsx` 中对 `ambiguous`
   （约 303-360 行）与 `failed`（约 457-471 行附近）状态的断言存在，说明这块不是"写了但没人验过"。
4. **技术细节默认折叠。** `profile_id`、`binding_id`、`access_surface` 等内部数据模型概念统一放在
   `<details>{t("deployments.technicalDetails")}</details>` 里（`DeploymentsPage.tsx:355-364`），不在默认视图
   打扰不熟悉 Provider Profile 的管理员，这个模式在 `providers`/`routes` 表单里也保持了一致。

## 4. 发现清单

### D1-01：409 幂等重放在五个创建入口里都和普通冲突长得一样，且服务端英文原文会直接出现在 zh-CN 界面

- **级别**：P1
- **类型**：【问题】
- **是否阻塞 v1.0.0 发布**：是
- **证据**：
  - 后端对 Provider/Deployment/Route/Project 的重放统一走
    `internal/app/admin_create_idempotency.go:59-74`（`writeAdminCreateReplay`），返回
    `code: "<resource>_idempotency_replay"`（例如 `provider_idempotency_replay`），message 是英文句子
    `"this request already created " + resource + " " + existingID`。调用点：
    `internal/app/admin_providers.go:197`（provider）、`:648`（route）、
    `internal/app/admin_deployments.go:170`（deployment）、`internal/app/admin_projects.go:88`（project）。
  - Gateway Key 走独立但同构的路径：`internal/app/admin_projects.go:255-266`，`code:
    "gateway_key_idempotency_replay"`，同样是英文句子；第 257 行注释明确写着正确的恢复方式——
    "the operator has to revoke and reissue to obtain a plaintext"——但这句话只存在于 Go 源码注释里，从未进入
    任何响应字段或前端文案。
  - 前端集中错误翻译表 `web/src/i18n/errors.ts:6-25`（`codeMessages`）没有为上述任何一个
    `*_idempotency_replay` code 建条目，于是全部落到第 31 行的通用分支：
    `error.status === 409 → t("errors.conflict")`，文案是"数据已被其他操作修改，请刷新后重试"
    （`zh-CN.ts:54`）——这句话对"重放"场景是误导性的：什么都没被别人改，是这次请求自己在重复第一次已经成功的创建，
    "刷新重试"不会解决问题（同一个 idempotency key 还在，还会撞同一个 409）。
  - `errorDetail()`（`web/src/i18n/errors.ts:39-57`）对 409 会把 `error.message` 原样吐出（第 53-56 行），
    这正是英文原句泄漏进 zh-CN 界面的路径。同一个文件里第 41-49 行的注释和 `localizedWorkflowCodes`
    列表证明团队清楚这个反模式并为其他几个 code（如 `ambiguous_capability_binding`、
    `deployment_price_unavailable`）主动屏蔽了它，唯独没有把新增的这五个 code 加进去。
  - 五个创建表单全部只用通用 `<ErrorState error={mutation.error} />`，没有任何一处特判这五个 code：
    `web/src/pages/ProvidersPage.tsx:595`、`web/src/pages/RoutesPage.tsx:297`、
    `web/src/pages/ProjectsPage.tsx:511`（project）与 `:618`（key）、`web/src/pages/DeploymentsPage.tsx:1458-1460`
    （后者甚至已经为另一个 code `resolution_changed` 做了特判，对比之下更能看出这五个 code 是被漏掉而非"设计上
    选择不特判"）。
  - 无回归测试：`grep -rn "idempotency_replay" web/src` 无命中（见附录命令）。
- **触发前置条件**：管理员在同一个已打开的表单里提交创建，且首次请求已在服务端成功落盘但响应未送达浏览器
  （超时、标签页挂起后恢复、网络抖动等），随后表单内重试——四个资源表单和 Gateway Key 表单都刻意让
  `idempotencyKey` 是"每次打开表单固定一个"的 `useRef`（见各文件里重复出现的同一段注释，如
  `DeploymentsPage.tsx:899-901`、`ProvidersPage.tsx:478-480`、`RoutesPage.tsx:248-250`、
  `ProjectsPage.tsx:423-425`、`:536-537`），这是协议要求的正确行为，但也正是它让"重试撞 409"成为设计内会发生
  的路径，而不是极端情况。
- **修复方向**：
  1. 给这五个 code 各自一条 `errors.ts` 条目和对应的 zh-CN/en 文案，讲清楚"这不是冲突，是你已经成功创建过了"；
  2. 利用响应里的 `id` 字段（后端已经返回了）让 UI 提供"去看那条记录"的操作，而不是丢弃它；
  3. Gateway Key 场景需要单独一句更强的提示——明文已经不可能再取回，必须撤销重开，直接复用
     `admin_projects.go:257` 注释里已经想清楚的措辞。

### D1-02：stale（运行时因激活失败拒绝数据面流量）在控制台里完全不可见

- **级别**：P1
- **类型**：【问题】
- **是否阻塞 v1.0.0 发布**：是
- **证据**：
  - 后端的 `activationStatus`（`Stale`/`StaleSince`/`Reason`/`Generation`）定义在
    `internal/app/activation_state.go:60-74`，并通过 `adminSystemStatus`
    （`internal/app/admin_usage.go:407`，字段名 `activation`）暴露在 `/admin/api/v1/system/status`；
    第 91-98 行的注释说明这不是随便一个字段——它对应的是数据面 503（`configuration_stale`）这个后果。
  - 前端 `SystemStatus` 类型定义（`web/src/types.ts:821-832`）没有声明 `activation` 字段；
    `web/src/pages/SettingsPage.tsx:128-161` 的 `DiagnosticsPane` 逐项渲染了
    `build`/`draining`/`accounting_status`/`write_path`/`audit`，唯独没有 `activation`。
  - 对整个 `web/src` 做 `grep -rn "activation" --include tests 排除` 零命中（见附录命令），确认不是分散在别处
    渲染，而是彻底缺失：没有诊断面板条目，没有全局横幅（`Layout.tsx`/`App.tsx` 本身也没有任何"系统降级"横幅
    机制可以复用——连既有的 `draining` 都只藏在 Settings→Diagnostics 里，不是全局提示，这点本身也值得记一笔，
    但不在本轮新增范围内）。
  - `docs/runbooks/` 与 `cmd/` 下没有任何面向 stale 状态的操作指引（`grep -rln "activation\b" cmd/
    docs/runbooks/` 只命中一处与本机制无关的 `model-catalog-publishing.md`）。
  - 自愈机制存在（`internal/app/activation_state.go:28,101-131`，5 秒重试），但重试也可能持续失败（例如
    `runActivationRecovery` 第 124-127 行：auth 快照重载失败会继续保持 stale），这种情况下运行时可以在没有任何
    控制台信号的前提下长时间拒绝真实客户端流量。
- **触发前置条件**：任意一次导致 topology 激活失败的管理面变更（`store commit` 成功但快照未能跟上，例如受权限、
  I/O、shutdown 压力影响）；触发后不需要管理员做任何事就会进入这个状态，只是完全看不见。
- **修复方向**：把 `activation` 加进 `SystemStatus` 类型和 `DiagnosticsPane`，stale 为真时至少给出
  "自 {{staleSince}} 起、原因 {{reason}}、系统正在自动重试、数据面请求正被拒绝"这类文案；如果时间允许，比照
  `draining` 的位置做一个页面顶部的横幅——考虑到 stale 拒绝的是外部客户端流量而不是管理员自己的操作，管理员单靠
  在 Settings 里点开 Diagnostics 才能看到本身也偏被动，值得在汇总阶段与 C2（告警）的结论对照，看是否需要一条
  独立于 Prometheus 的、控制台内的提示路径。

### D1-03：能力探测的成本提示没有说明这些调用不进 Ledger/预算

- **级别**：P2
- **类型**：【建议】
- **是否阻塞 v1.0.0 发布**：否（this 本身是 A1 判定范围的延伸，D1 只判断文案是否会造成误解）
- **证据**：`web/src/i18n/locales/en-US.ts:679`（`detectionCostBoundary`: "Up to {{count}} low-cost checks"）、
  `:684`（`detectionCancelCost`: "...may still incur cost."）——两处都告诉管理员这些探测调用"有成本"，但没有一处
  说明这些调用只计入 `ProviderCalls` 计数（`internal/app/admin_model_capability_detections.go:427-435,623-624`），
  不进 Ledger、不计入项目预算或 Usage 页面。一个第一次用这套系统的管理员，读到"may incur cost"最自然的理解是
  "会出现在我的用量/账单里"，实际不会。
- **触发前置条件**：无——这是文案覆盖不全，不是功能缺陷，任何一次能力探测都会遇到这句不完整的提示。
- **修复方向**：在 `detectionCostBoundary` 或紧邻处加一句"这些调用不计入项目预算与用量统计"，与 A1 对该缺口
  的结论呼应。

## 5. 下限项逐条应答

1. **能力探测与调用接口识别：管理员是否知道系统在做什么、探测失败时下一步是什么。**
   **正面结论，附一处待改进。** 状态机的每一步都有对应文案和下一步操作（见"肯定项"1、2，以及测试覆盖"肯定项"3），
   失败/歧义/不可用三种终态都不会把管理员留在死路上。唯一的缺口是成本提示没说清"不进账"这件事（D1-03，非阻塞）。

2. **创建表单撞上 409 幂等重放时，界面是否说清了发生什么、以及该怎么继续。**
   **负面结论。** 五个受影响的创建入口（Provider/Deployment/Route/Project/Gateway Key）全部退化成通用"数据被
   别人改了，刷新重试"提示，且服务端携带的、本可读的英文说明会未经翻译直接展示在 zh-CN 界面（D1-01）。这是本轮
   唯一一处对外收紧语义的改动（`c051edc`）配套的前端工作还没做完的地方。

3. **stale 状态在控制台里是否被说清：为什么拒、影响什么、怎么恢复。**
   **负面结论，且是三条里最明确的一条。** 不是"说得不够清楚"，是完全没有出现——前端类型定义都没有这个字段
   （D1-02）。管理员没有任何控制台内的方式知道网关正在拒绝真实客户端流量、已经拒绝了多久、为什么、以及是否需要
   人工干预。
