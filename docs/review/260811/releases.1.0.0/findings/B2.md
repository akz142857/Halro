## 1. 结论（≤200 字）

## 2. 评分

**7.0 / 10**。锚点（scoring-rubric.md §3）：7 = "机制建得对，但门没上锁……或证据只到作者自述级别；文档与代码不一致"。本视角无 P0/P1：数据面契约本区间零改动且有自动化 ratchet（golden 清单测试 + SDK 矩阵 job + 负面用例），唯一收紧语义的改动有回归测试并同步改了唯一已知调用方（控制台）。不到 8 的原因是 8 档要求"文档与代码一致"：三处对外可观察行为（Admin 创建必填幂等键、503 stale 拒流、unknown-field 拒收）在英文契约面上缺席或自相矛盾（B2-01/02/03），其中一处（idempotency-contract.md）现在是主动误导。不给 6.5：P2 全部是文档补写级别，每条关闭成本以行计，没有需要改行为的缺口。

## 3. 肯定项

- **manifest golden ratchet 设计正确**：`docs/compatibility/endpoint-manifests.json` 由 `BuiltinEndpointManifests()` 生成并被 `internal/compatibility/manifest_test.go:12-42` 钉死；`Validate()` 强制 compatible 状态必须携带已验证 SDK matrix 与 deviations（`internal/compatibility/manifest.go:62-67`），experimental 端点被测试禁止宣称 SDK 兼容（`manifest_test.go:44-60`）。声明升格必须过测试，这是防"兼容性通胀"的自动闸门，后续改动应保护。
- **409 replay 不回放的语义选择**：重试撞 409 报 `<resource>_idempotency_replay` 并点名既有 ID，而不是把旧记录当作本次创建的结果回放——因为同 key 不同 body 时回放是撒谎（`internal/app/admin_create_idempotency.go:58-74`）。派生 ID 把 resource 与 actor 编进摘要，跨端点、跨管理员不会互撞（`admin_create_idempotency.go:47-56`）。
- **未实现端点回 JSON 信封而非裸文本**，SDK 的错误类型解析得动，`/v1/models` 还有针对性提示（`internal/gatewayapi/handler.go:900-927`）。实测真实 handler 的 400 也带 `param` 定位（见 §6 命令）。
- **创建幂等有负面测试**：缺 key 400、重试 409 点名 ID、换 key 可再建，三态齐全（`internal/app/commit_protocol_test.go:100-158`；gateway key 路径另有 `internal/app/admin_projects_test.go:82,112-113`）。

### B2-02 · 503 `configuration_stale` 是数据面新增的可观察响应，无英文契约记载；Anthropic 路由上用错信封、无 Retry-After

- 级别：P2 类型：【问题】
- 是否阻塞 v1.0.0 发布：否（建议随 B2-01 一并补文档；信封修正可后置）
- 证据：`internal/app/activation_state.go:84-99`（对所有 `/v1/*` 返回 503 + OpenAI 形 `{"error":{...}}` 信封）；同一中间件挂在 Anthropic 组 `internal/app/runtime.go:1272-1277`，即 `/v1/messages` 的 503 不是 Anthropic 的 `{"type":"error","error":{...}}` 形（对照正常错误路径 `internal/gatewayapi/handler.go:387` 是 Anthropic 形）。文档面：`configuration_stale` 只出现在 `docs/architecture/provider-to-project-api-call-chain.zh-CN.md:126`（中文）；`docs/contracts/gateway-correctness.md`、`openai-compatibility.md`、endpoint manifests、发布说明均无（grep 实证）。响应无 `Retry-After`，而同门禁的 429 有（`tests/compatibility` 的 error matrix 验证过 429）。

### B2-03 · chat/embeddings 的 manifest 漏报 "unknown fields rejected"，实测所有未列字段（含 OpenAI 官方常用参数）一律 400

- 级别：P2 类型：【问题】
- 是否阻塞 v1.0.0 发布：否（golden 文件加一行 deviation 即平）
- 证据：实跑真实 facade（`tests/compatibility/server` 挂的是真 `gatewayapi` handler + 真解码器）：`frequency_penalty`、`presence_penalty`、`logit_bias`、`logprobs`、`store`、`metadata`、`service_tier` 全部 400 `json: unknown field ...`（命令与输出见 §6）。根因 `internal/openaiapi/types.go:139`（`DisallowUnknownFields`）。而 `docs/compatibility/endpoint-manifests.json` 中 `openai.chat-completions.v1` 与 `openai.embeddings.v1` 的 deviations 只说 "provider-specific unsupported fields are rejected before provider I/O"——读起来是"选中的 Provider 表达不了才拒"，不是"OpenAI 官方字段没列进 request_fields 也拒"。对照组证明这是漏报而非风格：`openai.responses.stateless.v1` 明确写了 "unknown fields ... are rejected" 且有 `rejected_request_fields` 清单，`anthropic.messages.2023-06-01` 的 rejected 列表里有 "unknown fields"（均已实测吻合：`top_k` 200、`not_a_field` 400、`store=true` 400）。散文契约 `docs/contracts/openai-compatibility.md:19` 写了拒收，故降为 P2 而非 P1——但 manifest 自称 machine-readable 契约，四个 compatible 端点两个写了两个没写，外部使用者拿 manifest 做 diff 会得出错误结论。
- 触发前置条件：调用方从 OpenAI 直连迁到 Halro，请求带任一未列参数（`frequency_penalty` 是真实世界高频参数）。
- 修复方向：两份 manifest 的 deviations 加 "unknown fields are rejected"（或补 `rejected_request_fields`），`HALRO_UPDATE_GOLDEN=1` 重生成。

### B2-04 · official SDK black-box contracts 步骤：覆盖的是"协议层线型"，不是网关行为——应如实定位，不应当作端到端兼容证据

- 级别：P2 类型：【建议】
- 是否阻塞 v1.0.0 发布：否
- 证据与边界：
  - **覆盖了什么**：六个官方 SDK（openai/anthropic × python/node/go，`.github/workflows/release.yml:38-81`、`tests/compatibility/{python/test_sdk.py,node/test-sdk.mjs,go/sdk_test.go}`）打真实 `gatewayapi` facade（`tests/compatibility/server/main.go:224-236` 用 `gatewayapi.NewWithOptions`），断言非流式/流式全链路、工具调用参数分块拼接、usage-only chunk、Responses 事件序列、错误状态矩阵 401/403/429/502、`x-api-key`+`anthropic-version`、客户端断流后服务端资源释放（`test_sdk.py:100-117`）。对"SDK 能不能解析 Halro 的线型"这个问题，覆盖是实打实的。
  - **漏了什么**：backend 是桩（`server/main.go:26-30` 直接实现 service 接口），故 SDK 矩阵完全没有穿过：语义翻译、路由、Provider profile 能力过滤（manifest 里每个 `profile_coverage.unsupported_request_fields` 声明都不在 SDK 测试路径上，只有单测 `internal/compatibility/provider_fields_test.go` 守护）、redaction、budget/limiter、真实鉴权。真实二进制多挂的中间件（`internal/app/runtime.go:1249-1252` 的 `refuseWhileSnapshotsStale`/`LimitOpenAI`/`GuardOpenAI`）compat server 一个都没挂，503 stale 信封、per-source 限流响应对 SDK 是否可解析无验证。NotFound/MethodNotAllowed JSON 信封没挂进 compat server（实测其 `/v1/models` 回 chi 裸文本 404，与真实二进制 `runtime.go:1290` 行为不同），manifest 声明的流内 `error` 事件、429 的 `Retry-After` 头、`Halro-Route-Mode` native 直通模式均无 SDK 级断言。
- 修复方向：不必把桩换成全栈（那是集成测试的职责边界），但 ① compat server 应挂 NotFound/MethodNotAllowed 与（可注入的）stale 中间件，把三种信封纳入 SDK 断言；② 在 workflow step 或 manifest README 写明该 gate 的证明边界，防止它在放行论证里被引用成端到端证据。
