# A1 · 核心逻辑与记账不变量（v1.0.0 放行评审）

- 评审区间：33bc13b → 2cd24a7（实际 HEAD 与 review-plan.md §2 一致）
- 执行模型：Fable 5（claude-fable-5）
- 日期：2026-08-11

## 1. 结论

记账链（ADR 0018）独立走查后成立：额度在任一瞬间被记在 `pendingAdmitted` 或 `state.Balance` 之一、绝不两处皆无，失败路径与终态均 fail-closed，并有真负面测试且 `-race` 实跑全绿。拓扑提交协议的"store commit 是唯一提交点"在崩溃点与并发下成立，审计意图同事务落盘、重投递幂等。但 stale 机制有一个真实缺口：四个激活域共享一个 stale 标志，任一域激活成功会无条件清除其他域的失败，恢复循环还会在 ≤5s 内"治愈"它并不修复的 redaction/token guard 快照——这恰好是该机制要关死的 fail-open 方向（A1-01，P1）。能力探测计费调用不进 Ledger 是有界、可见、且记账语义上正确的边界，不阻塞发布，但须写入已知限制。

## 2. 本角色评分

**6.5 / 10**（锚点见 scoring-rubric.md §3）

为什么不是 6：无 P0；记账主链（本仓库最高优先级不变量）经独立走查与 `-race` 实跑证实未被新代码破坏，且 ADR 0018 的关键性质有真正的负面测试（`TestFailedAppendReleasesAdmittedSpend` 注入 durability 故障）守护，不止于作者自述。

为什么不是 7：7 分档要求"P1 各自孤立且都有书面绕过或计划"。A1-01 无书面绕过，且它正处在拓扑提交协议自我宣称要保护的方向上（收回类变更不得在快照落后时继续生效）——"机制建得对，但门没上锁"的典型形态，还叠加了一个会主动摘锁的恢复循环。

## 3. 肯定项（值得在后续改动中保护）

1. **准入协议的两处计账不变量实现正确**：`internal/budget/manager.go:283-309`（锁内读 balance + pending、先加后放锁）、`manager.go:483-487`（`defer releaseAdmitted` 覆盖成功与失败两条路径、在 `appendApplyRecord`（即 Apply）返回之后才执行）。加入 pending 先于放锁，移出 pending 后于 Apply，两个方向的重叠只存在保守侧。
2. **终态 fail-closed**：`manager.go:755-761`（apply 已终态则拒绝再写，避免 WAL 里堆积永不可 apply 的记录）、`manager.go:782-790`（Apply 失败置终态并 `MarkUnavailable`，不给"账本健康但状态机死了"留出两个答案）。
3. **审计意图与 mutation 同一 bbolt 事务**：`internal/store/bolt/store_providers.go:170,223,269,331`、`store_projects.go:26,83`；启动 drain 失败即拒绝启动（`internal/app/runtime.go:668-680`），使"发生了但没记录"不可达而非仅罕见。
4. **重投递幂等**：审计日志按 EventID 去重且负载不一致即报错（`internal/audit/log.go:217-222`）；意图积压有 4096 上限、满了拒绝新 mutation 而非静默堆积（`internal/store/bolt/store_admin_audit.go:21,40-45`）。
5. **stale 拒流的位置正确**：挂在 limiter 与 auth guard 之前、两个协议门面都有（`internal/app/runtime.go:1249,1272`），readiness 同步报 not_ready（`runtime.go:1493-1495`）。
6. **加载器的"容忍 vs 致命"二分有清楚的准绳**：篡改/vault 信任失败拒绝整个加载（`internal/app/providers.go:348-353,405-411`），操作者可修复的配置态只摘除受影响对象（`providers.go:375-388,434-528`）——"一条坏记录不得让二进制打不开自己写过的数据目录"。
7. **探测调用的耗费纪律**：每次可能计费的调用先 durable 预约 reserved→running 再出网，崩溃收口为 UNKNOWN、绝不重放（`internal/app/admin_model_capability_detections.go:442-451`、`admin_model_capability_detections.go:611-637`）；上限硬编码 12（`internal/domain/model_capability_detection.go:16-21`），probe 本身 2048B 入 / 16 token 出（`internal/provider/capability_detection.go:58-59`）。
8. **幂等创建答 409 而非重放响应**（`internal/app/admin_create_idempotency.go:58-75`）：不冒充"本次请求创建了它"，语义诚实。
9. **State.Apply 的因果与守恒校验**：started/settled 必须先有 reservation、结算不得换 project/period/价格快照、reserved 不得透支（`internal/ledger/event.go:337-375`）。

## 4. 发现清单

### A1-01 单一 stale 标志跨四个激活域共享，任一域成功会清除其他域的失败；恢复循环会在 ≤5s 内清掉它并不修复的域

- 级别：**P1**
- 类型：疑似BUG
- 是否阻塞 v1.0.0 发布：**需裁决**（本角色意见：阻塞——它使 a96cf4b 的核心保证在收回类变更上失效，修复面小）
- 证据：
  - `internal/app/activation_state.go:52-58` — `markCurrent()` 无条件清空 `staleSince` 与 `reason`，不区分是哪一个域失败的。
  - 四个互相独立的激活域都写同一个 tracker：路由注册表 `internal/app/providers.go:86-96`；auth 快照 `internal/app/admin_projects.go:478-488`；redaction `internal/app/admin_redaction.go:315-328`；token guard `internal/app/admin_token_guard.go:333-346`。
  - 恢复循环只重建 topology + auth：`internal/app/activation_state.go:115-127`。`activateTopology()` 成功即 `markCurrent()`（`providers.go:94`），此时 redaction/token guard 快照未被触碰。
- 触发前置条件（两条独立路径）：
  - **路径 A（确定性，无需并发）**：一次 redaction 或 token guard 策略激活失败（如 `ListRedactionPolicies`/`ListTokenGuardPolicies` 的瞬态 store 读失败）→ 运行时 stale、数据面拒流。≤5s 后恢复循环 tick：`activateTopology()` 重建的是路由注册表（没坏，必然成功）→ `markCurrent()` 清除 stale → 数据面恢复放行，但 redactor / token guard 仍运行旧策略集，直到下一次同类策略 mutation。状态端点报 current，操作者无从得知刚提交的更严策略不在生效。
  - **路径 B（跨域竞争）**：Gateway Key 吊销提交后 auth 快照激活失败 → stale("auth snapshot")。在恢复循环下一个 tick 之前，另一个（或同一个）管理员完成任意一次拓扑/策略 mutation 且其激活成功 → `markCurrent()` 清除 stale。被吊销的 key 继续通过认证，恢复循环因标志已清而不再修复 auth 快照，直到下一次 project/key mutation。
- 未拦住它的控制点：`markCurrent` 不知道自己在为哪个域作答；恢复循环的修复范围（topology+auth）与 stale 的标记来源（四个域）不对齐；`commit_protocol_test.go` 四个测试均未覆盖跨域清除（`internal/app/commit_protocol_test.go:17-186`，只测单域的 header、拒流、幂等与意图落盘）。
- 修复方向：把 stale 从单标志改为按域的原因集合（map[domain]reason），`markCurrent(domain)` 只清自己的域、任一域非空即拒流；或让恢复循环与每条成功路径都重建全部四个快照后才允许清标志。并补一条负面测试：域 X 激活失败后，域 Y 的成功 mutation 不得使数据面恢复放行。

### A1-02 审计意图投递失败后没有进程内重试，只有下一次进程重启的 drain；注释宣称的"after a delivery failure"重试并不存在

- 级别:**P2**
- 类型：问题
- 是否阻塞 v1.0.0 发布：否（记录已 durable，积压对 status/doctor 可见，4096 上限 fail-closed）
- 证据：
  - `internal/app/admin_audit_intent.go:113-115` 注释："It runs at startup … and after a delivery failure"。实际调用点仅启动一处：`internal/app/runtime.go:672`。恢复循环（`activation_state.go:107-131`）不 drain 意图；投递失败只记日志（`admin_audit_intent.go:78-81`）。
  - 投递用的是 Admin 客户端的 `request.Context()`（`admin_audit_intent.go:78`）：客户端在 commit 后断连即投递失败。对比：激活已被 354428c 移到 runtime 自己的 context（`providers.go:72-80`），投递没有同步跟进。
- 后果：一条投递失败的记录会滞留在意图桶里直到下一次重启——可能是数周；期间后续 mutation 的记录正常进入审计日志，重启 drain 时旧意图才补入，审计链的追加顺序与发生顺序脱节（drain 内部按 OccurredAt 排序只能保证补入批次自身有序，`store_admin_audit.go:83-88`）。长期不重启 + 持续失败会走到 4096 上限拒绝一切 admin mutation（`store_admin_audit.go:43-45`）——fail-closed 方向正确，但操作者被拒的时点远晚于故障发生。
- 修复方向：投递改用 runtime context（与激活同理）；恢复循环或独立 ticker 在积压 > 0 时调用 `drainAdminAuditIntents`；注释与实现二者改其一以对齐。

### A1-03 ADR 0018 的"结算在途保守性"测试名不副实，且保守性主张存在一个未声明的例外（结算成本 > 预约额）

- 级别：P3
- 类型：问题
- 是否阻塞 v1.0.0 发布：否
- 证据：
  - `internal/budget/admission_test.go:169-218`：`TestAdmissionIsConservativeWhileASettlementIsInFlight` 实际是串行序列——`Settle` 完全 apply 之后才做第二次准入，从未构造"appended 未 applied"的在途窗口。它测的是"结算后余额计入预算"，不是名字与 ADR §Required verification 所声称的性质。
  - `internal/adr/`（`docs/adr/0018-…md:280-283`）自述该测试覆盖"deliberately stale in the conservative direction"。保守方向只在结算额 C ≤ 预约额 R 时成立：`internal/ledger/event.go:367-375`（结算把 Reserved−R、Committed+C），若实际 provider token 超出 prepared 估计使 C > R，则结算 append 与 apply 之间的窗口里准入读到的是偏低的总额。旧实现（锁跨 append）不存在这个窗口。
- 影响评估：窗口为毫秒级、超额上界为在途结算的 Σ(C−R)，且"请求在途即可能超预算"本就是预约制固有属性（预算只在准入时刻检查）——不构成回归级缺陷，但 ADR 的保守性论证与守护测试都比自述的弱一档。
- 修复方向：用 `ledger.Options.WrapDurability` 或 apply 阻塞钩子构造真正的在途窗口重写该测试；ADR "Consequences" 补一句 C>R 例外的量级说明。

### A1-04 记账观察者在 applyMu 持有期间被调用，观察者 panic 会永久挂死全部记账而非 fail-closed

- 级别：P3
- 类型：建议
- 是否阻塞 v1.0.0 发布：否
- 证据：`internal/budget/manager.go:773-799` — `applyMu.Lock()`（773）后调用 `state.Apply`，随后在仍持锁状态下逐个调用 observers（792-797），Unlock 在 799。当前唯一 observer 是 `usageCollector.Observe`（`internal/app/runtime.go:345`）。observer panic 会越过 799 的 Unlock 向上传播，被 HTTP 层 `recoverPanics` 吞掉后 applyMu 永久持有——此后每条记账 append 无限阻塞（挂起而非拒绝），网关既不服务也不报 unavailable。
- 触发前置条件：observer 实现自身出 bug 而 panic（当前为进程内代码，概率低，但该路径是全部记账的单点）。
- 修复方向：observer 调用移出 applyMu（快照 record 后在锁外调用，顺序性由调用方已有的 sequence 保证），或至少用 defer 保证 Unlock 与 panic 时置 applyErr 终态。

## 5. 下限项逐条应答

### 5.1 拓扑提交协议在崩溃点与并发下是否成立；stale 拒流会不会成为可被触发的自伤路径

**崩溃点：成立。** 逐窗口走查：(a) commit 前崩溃——mutation 与意图同事务，两者都不存在，一致；(b) commit 后、审计 append 前崩溃——意图已 durable（`store_providers.go:170` 等），启动 drain 在监听前补投递且失败即拒绝启动（`runtime.go:668-680`）；(c) 审计 append durable 后、意图删除前崩溃——重投递被 EventID 去重挡下、负载不一致则报错（`audit/log.go:217-222`），at-least-once 收敛为 exactly-once；(d) commit 后、激活前崩溃——重启从 store 全量重建快照，天然追上。响应丢失的情形由幂等键闭环：重试撞 409 并报出既有 ID（`admin_create_idempotency.go:65-75`），操作者能确认变更已生效。

**并发：成立，但有 A1-01 的例外。** 单一提交点由 `adminTopologyMu`（及 route/project 双锁的固定顺序，`admin_providers.go:670-676`）序列化；意图 EventID 冲突在事务内拒绝（`store_admin_audit.go:40-42`）；激活在 runtime context 上执行、客户端断连不能决定生效与否（`providers.go:60-80`）。**负面结论**："激活失败让运行时进入 stale 并拒流直到快照追上"这半句在跨域场景不成立——任一域的激活成功会清掉其他域的 stale，恢复循环还会确定性地清掉 redaction/token guard 域的失败而不修复其快照（A1-01, P1）。

**stale 自伤路径：面窄、可自愈，评估为可接受的设计代价。** 触发它需要"一次管理面 mutation + 一次内部激活失败"同时成立：数据面流量、外部输入、Gateway Key 持有者都无法触发它；管理员也无法用合法配置故意触发——会致激活确定性失败的配置态已被加载器改为摘除而非失败（`providers.go:375-382,516-528`；e1d94be、c051edc 的两处收口），拒绝整个加载的只剩 vault/篡改类（`providers.go:405-411`），那种状态下拒流是正确答案。恢复无需人工：5s 循环自动重试（`activation_state.go:28,107-131`），瞬态故障（store 读失败、30s 激活超时）自愈；需要人的只有持久性根因（master key 损坏、持久 I/O 故障），而那些场景中"继续用已知落后的授权快照服务"才是更坏的选项。粒度上一次价格激活失败也会拒掉全部数据面流量——粗，但方向保守，接受。

### 5.2 ADR 0018 的额度不变量是否成立（独立判断，非照着复核）

**成立。** 不照 ADR 的论证、按代码时序独立走查 `internal/budget/manager.go`：

1. **"两处之一、绝不两处皆无"**：`admit` 在 per-project 锁内完成 balance+pending+本次预约的检查并把额度计入 `pending`（`manager.go:283-309`），放锁在计入之后；`releaseAdmitted` 由 `reserveAttemptDetailed` 的 defer 执行（`manager.go:486`），时点必然晚于 `appendApplyRecord` 返回，而后者返回前 `state.Apply` 已把预约计入 balance（`manager.go:782-800`）。所以从准入到 durable+applied，额度连续地记在 pending；从 Apply 起记在 balance；重叠只在两处皆有的保守方向。失败路径（append 或 apply 失败）走同一个 defer 回滚 pending——此时预约未 apply、不在 balance，回滚正确。
2. **危险的中间态被终态兜住**：append 已 durable 但 apply 失败时，pending 被释放而 balance 永不包含该预约——孤立看是漏记，但 `applyErr` 终态 + `MarkUnavailable`（`manager.go:783-790`）使这之后不再有任何准入能成功（`manager.go:760-761` 在写之前拒绝），重启时 replay 撞上同一条 apply 失败即拒绝启动。漏记的窗口里没有任何决策会消费它，fail-closed 成立。
3. **共享 map 的数据竞争已按 ADR 自述修复**：pending 挂在 per-project 的 `projectAdmission` 上（`manager.go:229-234`），锁与数据同域。
4. **实跑证据**：`go test -race ./internal/budget/ -count=1` 通过（含 64 worker 的 `TestConcurrentAdmissionNeverExceedsTheDailyBudget` 与注入 durability 故障的 `TestFailedAppendReleasesAdmittedSpend`，`admission_test.go:26-143`）。
5. **两处保留意见**（不推翻不变量）：结算在途的保守性主张在 C>R 时有微小例外、且名义上覆盖它的测试实为串行（A1-03）；observers 在 applyMu 内被调用（A1-04）。

无锁的四个事件（accepted/started/settled/finalized）依赖调用方逐步 await 维持因果，`State.Apply` 对乱序 fail-closed（`ledger/event.go:337-353`）——违约的结果是拒绝而非错账，可接受。

### 5.3 能力探测计费调用不进 Ledger 的后果，及是否阻塞 1.0.0

**后果**：这是第一批绕开网关记账纪律的计费 Provider 调用，产生一个"运营者上游真实账单 > Halro 账本合计"的永久缺口。但缺口三重有界：调用数 ≤12/检测（`domain/model_capability_detection.go:21`，config 默认 10、校验上限钳到 12，`config.go:752`），单调用 ≤2048B 入 / 16 token 出（`capability_detection.go:59`），创建有 RPM 限制与 single-flight。且它并非不可见：逐调用 durable 记录在检测记录里（含 reserved/running/completed/unknown 状态机，崩溃不重放）、审计记录带 `provider_calls`（`admin_model_capability_detections.go:811`）、Prometheus 有 `halro_model_capability_detection_provider_calls_total`（`metrics-reference.md:124`）。

**为什么不该进 Ledger**：Ledger 的权威范围是"项目的数据面代账"——五事件生命周期、预算预约、按 Gateway Key/Project 归因。探测是管理面自发流量，没有 project、没有 key、没有价格快照归属；把它记进某个项目的预算是错账而非补账。真正的替代方案（运营者级 spend 账目维度）是 1.0.0 之后的独立设计。此外该缺口在性质上并非首创——`testAdminProvider`/主动健康探测的 `Prober.Probe`（`admin_providers.go:339-424`、`health.go:63`）早已是不入账的上游调用，本区间只是加大了量并第一次给了它调用级台账。

**结论：不阻塞 1.0.0。** 附两个条件：(1) 发布说明的已知限制必须写明"能力探测/连接测试/健康探测产生的上游费用不计入 Halro 账本与预算"（归 B4/汇总收口）；(2) 不得以本结论为先例让未来任何**数据面**调用绕过 Ledger——本结论的全部依据是"管理面、有界、有台账"三条同时成立。
