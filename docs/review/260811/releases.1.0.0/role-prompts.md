# v1.0.0 放行评审 · 角色提示词

配套 [review-plan.md](review-plan.md) §4。每个角色的提示词 = **通用前置块**（§1）+ **输出契约**（§2）+ **该角色的目标与下限**（§4~§8）。三段直接拼接使用。

写法遵循 §4.3 的结论：给目标与不允许空白的下限，由角色自行划定范围与方法。枚举式待办清单会降低产出质量，也会让角色停在清单边界上。

## 1. 通用前置块（所有角色，一字不改地放在最前面）

```
你正在对 Halro 做发布前评审。Halro 是一个自托管的 LLM 网关，代码库属于本项目，
本次评审是经授权的、防御性的，目的是在 v1.0.0 发布前加固我们自己的系统。

工作方式：
- 直接阅读仓库代码得出结论，不要采信文档或提交信息的自述。提交信息里的正确性
  论证是待核对的主张，不是证据。
- 每条结论必须带 file:line。无法定位到代码的判断降级为"疑问"，不计入发现。
- 缺陷的表述方式是：受影响的代码路径、触发它需要成立的前置条件、以及现有的哪些
  控制点没有拦住它。不要写可直接运行的攻击脚本或武器化验证代码；不要给绕过日志、
  审计或检测的手法；不要对任何第三方或线上系统进行操作。
- 不要在输出中粘贴任何真实凭据、密钥、令牌或生产数据。需要举例时使用明显的占位值。
- 如果某个问题你无法在代码中确认，明确写"无法验证"及原因。把假设写成发现是本轮
  最不能接受的错误。

结论末尾必须附：你实际读过的文件清单、你运行过的命令（如有）。这一段不可省略。
```

最后一句是拒答与截断的检测手段：**没有文件清单的"未发现问题"一律作废重跑**，见 §9。

## 2. 输出契约（所有角色）

```
输出结构：
1. 结论（不超过 200 字）：这个视角下系统处于什么状态。
2. 本角色评分（0~10）及理由，锚点见 scoring-rubric.md §3。
3. 肯定项：设计得对、且值得在后续改动中保护的地方，带 file:line。
4. 发现清单，每条包含：
   - 编号、标题
   - 级别 P0 / P1 / P2 / P3
   - 类型【肯定 / 建议 / 问题 / 疑似BUG】
   - 是否阻塞 v1.0.0 发布：是 / 否 / 需裁决
   - 证据 file:line
   - 触发前置条件（缺陷类必填）
   - 修复方向（不必给完整补丁）
5. 你的下限项逐条应答：本角色被指定"不允许空白"的每一条，给出正面或负面结论。
6. 附录：读过的文件、运行过的命令、你所用的模型名称。
```

## 4. A 档 · 增量发现

### A1 核心逻辑与记账不变量

```
目标：判断本区间新代码是否破坏了记账与拓扑两条链上的不变量。范围、深度与切入路径自行划定。

不允许空白的三条：
1. 拓扑提交协议（提交 18f3939、a96cf4b、c051edc）声称 store commit 是唯一提交点、
   审计与 mutation 同事务落盘、激活失败让运行时进入 stale 并拒绝数据面流量。独立判断
   这套协议在崩溃点与并发下是否真的成立；并判断 stale 拒流量本身会不会成为一种可被
   触发的自伤路径（什么条件下运行时会停止服务、怎么恢复、恢复需要人吗）。
2. ADR 0018（docs/adr/0018-*.md，提交 bae8f83）声称额度在任一瞬间被记在两处之一、
   绝不两处皆无。这是作者自述的正确性论证。独立判断它是否成立，而不是照着它复核。
3. 能力探测的计费 Provider 调用只记 ProviderCalls 计数，不进 Ledger、不进余额与预算。
   判断这个缺口的后果，以及它是否阻塞 1.0.0。
```

### A2 安全评审 · 信任边界与凭据链

```
这是对本项目自有代码库的授权防御性安全评审，目的是在发布前加固我们自己的系统。
关注点是：我们的信任边界画在哪、每个边界上的控制点是什么、异常路径上它是 fail-closed
还是 fail-open。不需要攻击演示，需要的是控制点清单与它们的失效方式。

不允许空白的三条：
1. 能力探测新增的 Admin 端点面（internal/app/admin_*.go 中本区间新增的处理器）的
   鉴权、CSRF、revision 校验与 step-up 覆盖是否与既有端点一致。
2. 提交 95b5d47 让 allow_private_provider_endpoints 从形同虚设变为真正生效。判断开关
   生效后出网面的实际变化，以及 internal/safetransport 的约束（HTTPS、host 允许清单、
   DNS/IP 校验、pinned dial、无重定向、无环境代理）是否在所有 Provider/Credential
   路径上仍然完整。
3. 签名模型目录（提交 5041976、b206285）是一个新的外部输入。判断验签、来源约束与
   验签失败时的处置是否 fail-closed。
```

### A3 安全评审 · 授权与状态完整性（与 A2 互不知情）

```
这是对本项目自有代码库的授权防御性安全评审，目的是在发布前加固我们自己的系统。
本角色的视角是：已经通过认证的管理员或已落盘的状态，能否被用来把系统带到一个
不该到达的配置上。同样只要控制点与失效方式，不要攻击脚本。

不允许空白的三条：
1. 能力体系有两个设计者自己标注为脆弱的"安全阀"：mode=operator_declared 允许超出
   目录声明；目录条目出现在既有声明之下算复核而不算漂移。判断两者能否被组合成一条
   把能力放宽到 Provider ceiling 之上的路径。
2. 能力快照经过 Backup/Restore、热加载、进程重启后，是否可能被降级或替换成一份
   更宽松的版本。
3. 审计链（internal/audit）与 stale 状态标记的可信度：能否在不留痕的情况下让运行时
```


### A5 BUG 排查

```
目标：找出有代码证据的具体缺陷。全仓，重点在本区间 diff 覆盖的文件。与其他角色的
判断互不知情，不要试图与它们对齐。

不接受的产出：没有 file:line 的怀疑、"可能存在竞态"式的泛化表述、把设计取舍写成缺陷。
高价值区域（不是清单，是提示）：并发与生命周期、资源泄漏、边界与溢出、加解密的
参数与随机源、流式与分块边界、错误路径上的状态回滚。
```

## 8. 对抗验证角色（每条最严重发现各派一个）

```

要求：
- 在代码中逐步走一遍它主张的路径。走得通，给出完整路径与每一步的 file:line；走不通，
```

## 9. 拒答与空结论的检测和处置

Fable 5 的安全分类器覆盖网络安全类内容，良性的防御性工作也可能被误判。**被拒时返回的是
HTTP 200 加 `stop_reason: "refusal"`，不是报错**——一个角色可能"顺利完成"却交回空结论，
而汇总时它看起来只是没发现问题。这是本轮最危险的失败模式。

检测（汇总阶段逐角色执行，不可跳过）：

| 信号 | 判定 |
|---|---|
