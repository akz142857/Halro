# v1.0.0 放行评审 · 评分体系

配套 [review-plan.md](review-plan.md) §7.3。本文件定义**怎么打分才能被复核**：维度、锚点、权重、封顶规则、以及分数与放行判定的映射。

评分不是这轮的目的，放行判定才是。分数的作用是让"差在哪里"可比较、可跟踪——所以每个分数都必须能被另一个人拿着同样的证据重新算出来。

## 1. 通用规则

1. **每个分数至少 3 条证据**，形式为 `file:line` 或实跑命令与输出。没有证据的分数不成立，记为"未评估"，而不是给一个中间值。
2. **未评估 ≠ 及格。** 某维度证据不足时写 `N/A（原因）`，并在放行判定中按"该维度未通过"处理，不参与加权平均。
3. **打分与发现分离。** 先有带 `file:line` 的发现，再有分数；不允许先定分数再找理由。
4. **每维必答"要到 8 分还差什么"**，列成可执行条目（谁做、做什么、怎么验证），不接受"继续加强"式表述。
5. 分数取整到 0.5。区间中位不是默认值——如果给 6.5，要说明它为什么不是 6 也不是 7。

## 2. 八个维度

前六个是本轮点名要评的（安全、系统设计、规范、逻辑、性能、可用性），后两个是放行判定必需的补充——1.0.0 能不能发，取决于它出事后能不能救、以及能不能被可信地交付出去。

| # | 维度 | 含义 | 主要证据来源 |
|---|---|---|---|
| D1 | **安全性** | 信任边界、认证授权矩阵、凭据链、出网面、审计完整性、秘密不外泄 | A2、A3 + 对抗验证 |
| D2 | **系统设计** | 模块边界、分层是否被绕过、抽象是否有对应负担、pre-1.0.0 纪律（错误构造不与替代并存） | A6、A1 |
| D3 | **工程规范** | gofmt、错误包装不泄露敏感值、指标基数、i18n 齐全、提交与文档规范、契约文件与代码一致 | A6、B2、C2 |
| D4 | **逻辑正确性** | 业务不变量在新代码下是否成立：记账权威、拓扑提交协议、fail-closed、重放确定性、并发与中止路径 | A1、A4、A5 + 对抗验证 |
| D5 | **性能与容量** | 单机吞吐上限与瓶颈归因、长跑内存增长、写路径新增成本 | C3（实测，不接受代码推断） |
| D6 | **可用性** | 开箱到第一个请求成功、错误信息可行动、控制台流程能被不懂内部模型的管理员走完、视觉一致性 | B1、D1、D2 |
| D7 | **可运维性** | 事故中能否自救：runbook 可照做、备份恢复可走通、告警可操作、崩溃恢复矩阵成立 | C1、C2 |
| D8 | **可交付性** | 发布流水线端到端、artifact 可被外部独立验签、证据链文档与真实状态一致、迁移与破坏性变更已如实公告 | B3、B4 |

## 3. 0~10 锚点

同一套锚点适用于全部八个维度。锚点描述的是**状态**，不是程度副词——判定时找到最贴合的那一档，不在两档之间凑数。

| 分数 | 状态 |
|---|---|
| **0~2** | 该维度存在已确认的、无绕过手段的阻塞缺陷；或该维度根本没有被建设（无控制点、无证据、无文档） |
| **3~4** | 主干可用，但存在 CONFIRMED 的 P0，或存在一类系统性缺口（同一种错误在多处重复出现）。发出去会造成实际损害 |
| **5~6** | 无 CONFIRMED P0，但 P1 数量可观或集中在同一子系统；已知问题有运维绕过手段，但绕过手段本身没有写进文档 |
| **7** | 无 P0，P1 各自孤立且都有书面绕过或计划；机制建得对，但**门没上锁**——存在 fail-open 缺口、缺回归守护、或证据只到"作者自述"级别 |
| **8** | 无 P0 无 P1；关键路径有负面测试或门禁守护；异常路径 fail-closed 已被验证而非推断；文档与代码一致 |
| **9** | 达到 8 分，且该维度的判断建立在**实跑证据**上（不是读代码），且历史同类问题有防复发机制 |
| **10** | 达到 9 分，且该维度的守护是**自动化且强制**的（CI 门禁、启动期校验、格式版本拒绝），人为疏忽无法绕过 |

7 分那一档是本项目的历史高发区，值得单独说明：260807 的综合结论就是"新建的防线本身建得讲究，但门没上锁"。判定时如果发现某维度"设计对、实现在、就是缺一道锁或缺一条守护"，它是 7 分，不是 8 分。

## 4. 权重与总分

```
总分 = 0.20·D1 + 0.20·D4 + 0.12·D2 + 0.12·D7 + 0.12·D8 + 0.10·D6 + 0.08·D5 + 0.06·D3
```

| 维度 | 权重 | 理由 |
|---|---:|---|
| D1 安全性 | 0.20 | 项目自我定位是 security-first 的网关，凭据托管是它存在的理由 |
| D4 逻辑正确性 | 0.20 | 记账错误不可事后修复——钱已经花了，账错了就永远错了 |
| D2 系统设计 | 0.12 | 决定 1.0.0 之后改动的成本，而 1.0.0 之后每个改动都多一个兼容性维度 |
| D7 可运维性 | 0.12 | 单写者、无 HA 的架构把恢复责任全部压在运维手上 |
| D8 可交付性 | 0.12 | rc.1 的 publish 从未跑通；发不出去的版本，其他维度得几分都不重要 |
| D6 可用性 | 0.10 | 自托管网关的第一印象决定它会不会被用起来 |
| D5 性能与容量 | 0.08 | 重要但可通过书面容量上限管理，且本轮首次具备实测条件 |
| D3 工程规范 | 0.06 | 影响长期成本，短期不阻塞放行 |

权重之和为 1.00。**权重不因某维度得分低而临时调整**——那等于把结论倒着写。

## 5. 封顶规则（否决项优先于加权平均）

加权平均容易让一个阻塞项被七个好维度稀释掉。因此：

| 触发条件 | 后果 |
|---|---|
| 任一维度存在 **CONFIRMED 的 P0** | 该维度得分封顶 **4**，总分封顶 **5.0** |
| 任一**硬性判据 G1~G9** 未通过 | 总分封顶 **6.5**，且不得出具 Go |
| 某维度记为 **N/A（未评估）** | 总分按剩余权重归一化计算，并在结论中显式列出未评估维度；**D1、D4 未评估直接判 No-Go** |
| 某角色结论被判定为**疑似拒答或空结论**且未重跑 | 其覆盖的维度记为 N/A，适用上一行 |

封顶生效时，报告要同时给出**封顶前的加权分**与**封顶后的最终分**，并说明是哪一条触发的。两个数字的差距本身就是信息：差距大说明系统整体健康、只卡在少数几点上；差距小说明问题是弥散的。

## 6. 分数与放行判定的映射

分数不能单独决定放行——它是判定的输入之一，硬性判据才是闸门。

| 最终总分 | G1~G9 状态 | 判定 |
|---|---|---|
| ≥ 8.0 | 全部通过 | **Go** |
| ≥ 8.0 | 有未通过项 | **有条件 Go**，附条件清单与关闭负责人 |
| 6.5 ~ 8.0 | 全部通过 | **有条件 Go**，P1 逐条给出运维绕过方案并写入发布说明 |
| 6.5 ~ 8.0 | 有未通过项 | **No-Go** |
| < 6.5 | 任意 | **No-Go**，附最短关闭路径（先做哪三件事能翻成 Go） |

历史参照：260805 综合评分区间 6.5~7.5；260810 视觉单项 7.2。**如果本轮总分与两轮前基本持平，那本身是一条需要解释的发现**——中间隔着 22.5k 行新代码和多轮整改，分数不动意味着新增面把整改的收益吃掉了。
