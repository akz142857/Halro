## 2. 阻断级：升级路径上的备份陷阱

**唯一一条我认为应当在发布前处置的。** 实测复现，见 `runtime-evidence.md` R2-a。

用 HEAD 二进制对一份 v0.4.0 数据目录执行 `halro backup create`：

```
schema BEFORE: 32
$ halro-head backup create --config … --output … --key-file …
halro: usage checkpoint payload does not match its watermark
schema AFTER:  33
```

重跑仍失败。而此时：

```
$ halro-v040 backup create … → metadata schema version 33 is newer than this build supports (32)
$ halro-v040 start …         → 同上
```

**该目录已经没有任何一个二进制能给它做备份。** 唯一出路是先用 HEAD `start` 一次让派生物
重建（已验证之后备份立刻成功）。

根因 `internal/app/backup.go:600-603`：

```go
checkpointAggregate, restoreErr := usage.RestoreCheckpoint(checkpointPayload)
if restoreErr != nil || checkpointAggregate.Snapshot().Watermark != checkpoint {
    return backup.Manifest{}, errors.New("usage checkpoint payload does not match its watermark")
}
```

`restoreErr != nil`（**陈旧但合法的 v7**）与"payload 与水位不符"（**损坏**）被合成同一条错误。
**启动路径对同一份磁盘状态判"重建"，备份路径判"致命"**——两条路径给出相反结论，
且报错文本把陈旧说成了损坏（违反 B2 的"陈旧状态应被拒而非误读"的精神：这里是被误读成了损坏）。

同源的第二个陷阱：**`halro ledger verify` 会静默把目录从 32 单向迁到 33**（实测）。
一个名字纯只读的命令，运维拿它做升级前体检，副作用是让旧二进制再也打不开这个目录。

**建议处置（二选一，都在发布前）**：

1. 让 `backupCreate` 区分两种情形——陈旧版本的 checkpoint 与"缺失"同等对待
   （走 `checkpoint = ledger.Watermark{}` 那条既有分支），只把真正的水位不符判为致命；或
2. 至少改错误文本并在发布说明里写死操作顺序："**先用旧二进制备份，再换二进制**；
   换过二进制之后，第一个动作必须是 `start`，不能是 `backup create` 或 `ledger verify`。"

第 1 条更符合 pre-1.0.0 的"就地修复"，且与 `runtime.go:834` 已有的判断保持一致。

## 3. 高：契约与实现直接矛盾（B4）

**V1，已实测复现。** `/v1/messages` portable 路径上，**凡携带 `output_config.effort`
且落到 `minimax.chat.v1` 的请求，100% 在预算预留之后失败**，且不触发 fallback、
400 不指名字段。而 `internal/compatibility/manifest.go:353` 把
"output_config.effort reaches MiniMax's thinking switch" 声明为**受支持的 transform**。

两层原因叠加，两层都比原报告更绝对：

- `internal/compatibility/anthropic/mapping.go:31` **无条件**赋值，而
  `anthropicapi.MessageRequest.MaxTokens` 是非指针 `int64`——**连没写 `max_tokens` 的请求
  也拿到指向 0 的非空指针**。
- Anthropic 的合法 effort 阶梯 `low/medium/high/xhigh/max` 里**没有 `none`**，
  所以任何合法 effort 都让 `thinkingOn` 为真。

**影响面比 MiniMax 大**：`output_config.effort: "max"` 是 Anthropic 合法值但不在
`openaiapi.ReasoningEffortLevels` 里，实测对
`openai.chat-embeddings.v1`、`azure-openai.chat-embeddings.v1`、
`openai-compatible.chat-embeddings.v1`、`minimax.chat.v1`、`bedrock.mantle.chat.v1`
**五个 profile** 的字段规则全部返回 `[]`，然后在 `provider/primitive.go:163` 死在预留之后。
**只有 `deepseek.chat.v1` 声明了 `[reasoning_effort]`。**

**为什么会漏（直接证据）**：DeepSeek 有 `deepseek_test.go:125`
`TestDeepSeekRendersEveryRequestItsDeclarationAdmits` 把"渲染器拒绝的必须已声明"双向锁死；
**`minimax_test.go` 没有任何等价测试**。而 `manifest_derivable_coverage_test.go` 只锁
manifest ↔ 字段规则的一致性，**两边同时沉默时它是满意的**。

**修复不是补一行**：只加镜像规则会让 `minimax.chat.v1` 被每一个带 effort 的 portable
Messages 请求排除，与 `manifest.go:353` 的声明彻底对立。要么承认那条转换不成立，
要么处理 `mapping.go:31` 的 `ptr(0)`——是设计决定。

## 5. 中：其余成立的发现

按主题归并，去掉被对抗验证推翻的部分。

### 5.1 汇总端点（V3 已复现 + A2/A5）

- **两段读竞态（CONFIRMED，已复现）**：`collectSummaryRows` 先读 bbolt 快照、再读内存增量，
  中间无共同锁；checkpoint 落在窗口内则整批增量两头落空。实测窗口 = 整个 View 事务时长：
  30 天视图 4.3 ms（命中率 ~7e-5），400 天满键 **2.2 s（~3.6%/次刷新）**。
  `watermark_sequence` 那半条成立（响应宣称覆盖到它没计入的 sequence，违反 B8）。
  **自愈，磁盘没丢账。** 修法是让两次读描述同一 WAL 前缀（store 已在同一事务写了
  `keyUsageRollupState`，可用作重试判据），不是换顺序。
- **默认月窗口一年里有 34 天只给 11 个月**（CONFIRMED，穷举验证）：`AddDate(0,-11,0)` 在
  `end` 落于 1/3/5/8/10 月的 29–31 号时被 Go 规范化。分布是 7/6/7/7/7（2025 只有 6 个，
  闰日吸收一个），`end=2026-01-31 → start=2025-03-03` 精确命中。
  **违反 PRD 自己写的"最近 12 个月"**，而两个现有测试都看不见它。
- **首个桶标签写整月而只含部分数据**，`totals` 因此偏低；界面与 i18n 无"残缺周期"标注。
  （图是折线图、x 轴用真实 `bucket.start`，所以有未加说明的视觉信号——原报告说"直接画柱、
  完全没用 Start/End"是错的。）
- **遍历量与超时**：`UsageRollupRange` 对范围内每一行无条件反序列化再过滤；
  **它和 `collectSummaryRows` 都不接 context，bbolt View 不可取消，admin `http.Server`
  没有 `WriteTimeout`，全仓无 `TimeoutHandler`**。实测 365 天满键 = 367,190 行 /
  2.01 s 读事务 / 565 MB churn。十年才到 3652 天，所以不是"现在就能打爆"，
  但**一年满负荷的 2 秒读事务**是应该写进发布记录的数字。
- **折叠与过滤的两个可辨识性缺口**：某维度当天超过 200 个值时，按值过滤被折叠掉的那些
  返回 HTTP 200 + 全零，与"没有流量"不可区分（分组视图有 `groups_truncated`，过滤视图没有
  对应物）；真实值恰好叫 `__other__` 时与溢出桶混同。总账不丢，是归属不可辨。
- `summarize` / `renderGroups` 五处 `_ = Add(...)` 丢弃溢出错误，会渲染"半合并"的行并返回
  200。现实不可达（需 ~9.2e18 量级），但方向与 B2 相反。

## 6. 判过但没问题的（写下来，是为了让读者知道它被判过）

- **B8 的核心不变式成立**，两条独立证据：实机上 dump 全部 33 行 rollup，与
  `usage rebuild-summary` 全量重建后逐字节相等；A1 的代码级实验（batch = 0/7/41/199/1000，
  237 个键越过 200 上限，`reflect.DeepEqual`）四种分批与一次性重建完全相等。
  等价性的论证也给出来了：checkpoint 批次按序列号连续切分 WAL，`admitted` 由已落盘行播种，
  批内按 `FirstSequence` 排序准入，于是"某键之前已准入多少个"两条路径相同。
- **同事务性成立**：`PutUsageCheckpoint` 是单个 `db.Update`；`ResetUsageDerivatives` 在一个
  事务里清三样；启动时用**相等**而非顺序比较两个水位，不等即整体重建；重建失败**拒绝启动**
  而非降级服务。
- **`ResetUsageDerivatives` 的覆盖面是对的**，遗漏的三样都不该被清也不会重复计数：
  Parquet 按 `LastSequence` 去重、ledger chain checkpoint 是 WAL 自身的信任锚、
  TokenGuard 不是 WAL 派生物。
- **出网面**：允许清单由连接自己的 endpoint 主机名服务端推导，调用方给不了；
  MiniMax 没有 `validateEndpoint` 与多数派同形（只有 Bedrock Mantle 特殊），
  且 SafeTransport 兜得比预想更全——拨号时必然解析并逐地址校验再只拨已校验的那一个（无 TOCTOU），
  `169.254.169.254` 与 `100.100.100.200` 单独点名且不受 `AllowPrivate` 影响。
  **operator 能指向任意公网 HTTPS 主机（与 openai_compatible 同权），指不到回环/元数据地址。**
- **凭据不外泄**：MiniMax 的 `ProviderCode` 是自造的 `"minimax_"+code`，
  上游 `status_msg` **被完全丢弃**；明文加载后立即 `clear`；AAD 绑定 type+audience，
  密钥无法被当作别的 provider 的凭据复用。
- **上游自执行工具关得住**（两条线都 fail-closed）；**`anthropic-beta` 到不了 MiniMax**
  （三层拦截）；**`[DONE]` 哨兵豁免不能被别的 provider 触发**，且截断不会被当成完整结算。
- **汇总端点无跨 Project 越权**：角色模型只有全局的 administrator / read_only，
  read_only 的唯一含义是"只能 GET"，不存在按 Project 划分的作用域。
- **前端不变式**：`web/src` 内除注释外无 `localStorage`/`sessionStorage`/`document.cookie`，
  CSRF 令牌只是模块级变量；canary 扫描是对 `internal/webui/dist` **全目录内容**的扫描，
  按产物而非文件清单，新代码自动覆盖。
- **i18n 门禁是真遍历**（`flattenKeys` 递归展开全部键做 zh/en 全等），另有未引用键、
  中文标点、术语一致性、纯文本四道；三块新文案中英齐全。
- **`adapterBuilders` 是这次合并唯一真正加固的注册点**，且是**双向**穷举（缺行报错、
  孤儿行也报错），**不跳过 withheld**——这是 switch 结构做不到的。
- **`profileAllowsPrimitiveDerived` 的语义变更方向是收紧的**，旧的宽松分支不可达
  （上一条 if 已拒空 primitive），无调用方依赖它。
- **全量门禁**：`make check` exit 0（含 `go test -race ./...`）；
  `make frontend` 后 `internal/webui/dist` 无漂移。
- **抽样基准无回归**：HEAD 与 v0.4.0 背靠背，路由解析中位数 +0.9%（噪声内）、
  分配逐字节相同；WAL replay HEAD 略快。

## 7. 发布记录（`docs/verification/assessments/v0.5.0.md`）必须写进去的

1. **Re-init required：no**（实测：v0.4.0 写出的真实数据目录被 HEAD 干净迁移到 33，
   派生物按 fail-closed 全量重建，账目从 WAL 重建后与升级前逐字节一致）。
2. **升级操作顺序是有约束的，必须写死**：
   - 备份要用**旧二进制**、且在**换二进制之前**做；
   - 换过二进制之后，对数据目录的第一个动作**必须是 `start`**——
     `backup create` 与 `ledger verify` 都会先把目录单向迁移到 33，而 `backup create` 随后失败。
3. **升级窗口的一次性代价**：首次启动要付一次全量 WAL 重放（checkpoint 被版本拒），
   耗时与内存随 WAL 长度线性增长。**这个量级本轮没有在长 WAL 上测过**，
   发布前应在一个接近生产规模的 WAL 上测一次并把数字写进记录。
4. **降级不可逆**：HEAD 跑过一次之后，v0.4.0 的 `start`/`bootstrap`/`ledger verify`/
   `backup create`/`restore` 全部硬失败（fail-closed，报文明确）。
5. MiniMax 是 Beta；**Responses profile 与大陆主机 `api.minimaxi.com` 记为"未实测"**，
   且 `provider-real-matrix.md` 自陈那两轮"carried no `-commit` binding and produced no
   archived evidence file"——结论只存在于叙述里，没有可复核的证据文件。
6. **`performance-baseline.md` 已过时**（两个版本上同时复核），要么重测要么注明其 commit。
7. 已知缺口清单：新 Admin 端点族无契约守卫；`profileOperationTable` 绑定值无守卫且文档
   为它指的守卫是假的；模型目录与 `providers.types.*` i18n 无守卫。

## 8. 结论

**范围内没有发现威胁记账正确性的缺陷**——B1/B7/B8/B9 四条经实机与代码级双重验证成立，
`make check` 全绿，基准无回归，原地升级实测通过。

**建议 NO-GO 直到第 2 节的备份陷阱被处置**（改 `backup.go` 的判定，或在发布说明里写死
操作顺序）。理由不是它会损坏数据——不会——而是它让运维在**升级这一刻**失去备份能力，
而备份恰恰是升级流程里唯一的退路；且报错文本把"陈旧"说成"损坏"，会把一次正常升级
读成一次数据损坏事故。

第 3、4 节两条（B4 的契约矛盾、B12 的假守卫）**不阻断发布**，但都应在 v0.5.0 之后
立即处置：前者是已发布契约在说假话，后者是"下一个平台会踩"的确定性缺口。
