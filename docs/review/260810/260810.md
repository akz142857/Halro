# Halro Admin Console 全局视觉评审（2026-08-10）

> 范围：仅评审视觉表现，不建议调整信息架构、业务流程或页面结构。重点检查字体、字号、字重、颜色、视觉层级、密度、表格/卡片/表单和弹窗的一致性。
>
> 方法：在当前本地实例中实测登录页、11 个主导航页面、设置页 6 个分区、创建与危险确认弹窗，并检查桌面与 390px 移动端代表状态；同时交叉审阅 `web/src/styles.css`、Design System tokens、Light/Dark theme 与相关组件源码。
>
> 主题覆盖：已登录页面实测 Light；未登录页面实测 Dark；Dark 的已登录页面以相同语义 token、源码和现有对比度门禁交叉确认。首次初始化页因实例已完成初始化，采用与登录页共用的认证视觉层和源码检查。

## 结论

**整体视觉完成度：7.2 / 10。**

Halro 已经形成明确且一致的视觉语言：绿黑品牌色、纸张感浅色主题、紧凑的运维控制台气质、统一的卡片/表格/表单/弹窗边界，以及完整的 Light/Dark 语义颜色体系。主要问题不是页面各自“长得不一样”，而是同一个系统性缺口反复出现：**文字层级过多、10–11px 小字大量存在、页面标题与正文的尺度跨度过大**。这使内容越复杂的页面越显得细碎、发灰和疲劳。

不需要重做页面结构。通过收敛字号、字重、文字颜色和少量 CSS 视觉细节，可以显著提升整体品质。

### 优先级总览

| 优先级 | 结论 | 影响范围 |
|---|---|---|
| P1 | 设计系统写明中文字号下限为 12px，但业务 CSS 中仍有 116 处 10px、11px、`.625rem` 或 `.6875rem` 的声明 | 全局；Operations、Developer、Settings Config、Redaction 最明显 |
| P1 | 页面标题最高到 54px，而常用正文/说明多为 10–14px，视觉倍率过大 | 所有主页面、登录页 |
| P1 | 高密度页面把“次要”和“更次要”都压进 10–11px + muted 色，层级没有变清楚，只是更难读 | 审计时间线、系统配置、开发者工作台、表格详情 |
| P2 | Light 主操作色偏深橄榄绿，满足对比度但品牌活力弱；按钮、焦点环和 eyebrow 的亮度感不完全一致 | 全局 Light |
| P2 | 中等宽度登录页隐藏品牌故事后留下大面积空白，登录表单仍贴左 | 登录/初始化 |

| P3 | 字号、间距和圆角仍大量直接写值；现有 ratchet 只约束 spacing/radius，不约束字体尺度 | 设计系统维护性 |

## 一、全局字体与字号

### 1. 设计规范与实际实现冲突（P1）

`web/src/design-system/tokens.css` 明确写明“12px is the floor”，并把 `--font-size-xs` 定为 12px；但 `web/src/styles.css` 中仍有：

- 48 个 `10px` 字号声明；
- 52 个 `11px` 字号声明；
- 8 个 `.625rem`（10px）声明；
- 8 个 `.6875rem`（11px）声明；
- 合计 116 个低于规范下限的声明命中。

这不是少量技术信息的例外，而是分布在导航、按钮、帮助文案、状态、表格详情、审计时间、系统配置和弹窗中。中文在 1x 屏幕或低 DPI 远程桌面上会明显损失笔画分离度。

建议统一为以下字阶，不改变任何结构：

| 用途 | 当前常见值 | 建议值 |
|---|---:|---:|
| 页面标题 H1 | 48–54px | 桌面 40–44px；移动 32–34px |
| 面板标题 H2 | 20–25px | 20–22px |
| 小节标题 H3/H4 | 13–18px | 16–18px / 13–14px |
| 正文与表单值 | 13–16px | 14–15px |
| 标签、表头、按钮 | 10–13px | 12–13px |
| 辅助说明、时间、状态 | 10–12px | 最小 12px |
| 代码、ID、技术值 | 10–12px | 12–13px，行高至少 1.5 |

优先把所有 10px/11px 替换为 `--font-size-xs`，再按阅读重要性提升到 `--font-size-sm`。不要新增新的 11.5px 或 `.72rem` 档位。

### 2. 字阶过多（P1）

总览页实测同时出现 10、11、12、13、14、16、18、22、30、54px 共 10 个字号层级。字号多并没有带来更清晰的层级，反而让相邻文字看起来像不同模块各自定过一次样式。

建议把常规页面收敛到 6 个可见层级：12 / 13 / 15 / 18 / 22 / 42px。数字指标可保留 28–30px 作为第七个专用层级。

### 3. 字重（P2）

系统中同时出现 token 化的 400/500/600/800，以及手写的 650、700、900。650 在当前系统字体下能正常渲染，但并非所有 Windows/CJK 字体都有该真实字重，最终可能映射到 600 或 700，导致平台差异。

建议：

- 正文 400；
- 标签、按钮、导航 600；
- 标题 600 或 700；
- 品牌标识可保留 800/900；
- 移除业务样式中的 650，统一映射到 `--font-weight-semibold`。

### 4. 等宽字体使用（P2）

等宽字体适用于 ID、金额、时间、代码和可复制值；目前也用于大量普通状态、标签和说明。中文等宽回退的字面宽度与拉丁字符不同，会让短说明显得更碎。

建议保留等宽字体于：ID、URL、模型名、金额、指标值、时间戳、代码、审计事件类型。导航说明、空状态、按钮、字段帮助和普通状态改用 sans。

## 二、颜色与主题

### 正面结论

- Light/Dark 使用同一套语义 token，token key 完全对齐。
- 主要文字、次要文字、第三层文字和关键边界均有自动对比度门禁，当前达到 WCAG AA。
- Success/Warning/Danger/Info 不再只依赖颜色，通常同时配有文字、边框或图标。
- Light 使用非纯白 canvas，Dark 使用绿黑而非纯黑，品牌辨识度明确。

### 需要调整

1. **Light 主操作色偏沉（P2）**

   当前主按钮为深橄榄绿配白字，可读性合格，但视觉上比状态绿和品牌 lime 更“脏”。建议在保持 4.5:1 对比度的前提下，把 Light 的 primary surface 向稍明亮、稍饱和的绿移动；深色值继续用于文字链接或 hover，不要让 CTA、focus ring、eyebrow 分别像三套绿色。

2. **小字号与 muted 叠加（P1）**

   `--color-text-secondary` / `tertiary` 本身对比度合格，但当 10px 字体、细字重、等宽字体和较大字距同时出现时，实际感知会显著变弱。颜色无需先变深；应先把字号提升到 12px、字重提升到 500，再判断是否需要调色。

3. **大面积浅色页面层级偏平（P3）**

   Light 下 canvas、surface 与 subtle 的差异较轻，主要依靠 1px border 分区。总览页和系统配置长页面中，卡片层级会逐渐融成同一张白纸。建议只对 raised/overlay 增强轻微阴影或边界强度，不增加新色块，也不改变结构。

## 三、逐页面评审

### 登录页 / 首次初始化

优点：品牌色、聚焦态、字段尺寸和 CTA 对比清晰；Dark 默认符合安全产品气质。

问题：

- 中等桌面宽度下品牌故事区域被隐藏，表单仍固定在左侧，右侧留下大面积无意义空白。
- 登录页 H1 与 13px 说明的比例偏大。
- 底部安全说明使用 12px 等宽，视觉上接近“免责声明”，可读性弱。

建议：不改 DOM；在故事区隐藏的 breakpoint 下，仅通过 CSS 把 `.login-panel` 水平居中并设置合理最大宽度；H1 降到 40–46px；安全说明保持 12px 但改 sans 或减少字距。

### 运行总览

优点：指标、趋势、治理、归因、异常和内部状态的模块边界一致；数字扫描效率高。

问题：

- H1 54px 过度占据第一视觉层，下面大量 10–12px 信息显得更小。
- 六项指标的辅助说明为 10px；治理条、Top 5、异常和内部状态又使用不同的 10/11/12px 组合。
- 宽屏信息密度很高，但没有真正的“安静层”；所有卡片都有等量细线和小字。

建议：H1 降到 42px；指标辅助文字、breakdown row、empty state 全部提升到 12px；表头和标签统一 12px；仅关键指标值使用 mono。

### 凭据与服务商

优点：资源卡片的身份、类型、端点、凭据、能力和状态分组清晰；操作层级明确。

问题：技术详情、端点、状态说明、凭据辅助信息多处为 10/11px；卡片主内容为 12–13px，尺度差距过小，容易“全都像辅助信息”。

建议：资源名称 15px/600；主要事实 13px；标签与状态 12px；技术详情 12px/mono。操作按钮不低于 12px。

### 模型部署

优点：当前页面是字号使用较一致的页面之一，13px 内容占比高；价格与能力的状态表达清楚。

问题：卡片中的 micro label 仍为 10px；创建弹窗中 section heading、字段 label、说明的尺度接近，阅读时需要逐行确认。

建议：保留现有布局；micro label 提升到 12px；弹窗 section heading 用 16px/600，字段 label 12–13px/600，帮助文字 12px/400。

### 模型路由

优点：单表格结构直接，状态和操作没有过度装饰。

问题：公共模型、Deployment、Provider、上游模型、策略和优先级在同一行中视觉权重接近；长 ID 抢占注意力。

建议：公共模型 13–14px/600；长 ID 12px/mono/tertiary；其余表格值 13px；表头统一 12px/600，减少 letter-spacing。

### 安全策略

优点：Token Guard 与 Redaction 使用统一页面入口，状态和动作颜色明确。

问题：Redaction 编辑器是全系统小字号最集中的区域之一，规则说明、顺序提示、tag、错误数、scope、footer 提示多为 10–11px；复杂内容因此显得拥挤而非专业。

建议：所有规则元信息和 footer 提示提升到 12px；规则标题 13–14px/600；错误计数保留 danger 色但不缩小；仅正则、ID 与替换表达式使用 mono。

### 项目与密钥

优点：项目与 Gateway Key 的从属关系可见，危险操作样式一致。

问题：日期、有效期、ID、模型选择说明、启用说明和 footer 提示多为 10px；展开项目后同时出现卡片标题和详情 H2，字号层次略显跳跃。

建议：日期/有效期/ID 统一 12px；项目名 15px/600；详情标题保持 18–20px；不改变展开结构。

### 开发者工作台

这是本轮视觉整改优先级最高的页面之一。

问题：实测有 20 类可见元素使用 10px，代码编辑器/响应体为 11px；请求、代码、响应三大区域内部又混用 10/11/12/13px。长时间阅读代码和 JSON 时疲劳明显。

建议：

- 代码编辑器、代码示例、响应体统一 13px/1.65；
- tab、状态、footnote 最小 12px；
- 字段正文 13–14px；
- `REQUEST ID` 等短标签可用 12px mono + 大写，不再用 10px；
- 保留三段式现有结构。

### 用量与调用

优点：筛选器、记录数、表格和证据层级完整。

问题：请求 ID、尝试数、token 来源、计价证据和时间等最需要核对的证据恰好使用 10/11px；表格值的主次对比主要靠变小，而不是字重和颜色。

建议：表格值 13px；证据/时间/ID 12px mono；主要状态 12px/600；次级说明使用 tertiary，但不要再缩小。

### 告警与审计

这是最需要优先整改的页面。

实测当前数据下，页面有 204 个可见节点继承 10px、100 个节点继承 11px。根因是审计时间线每条记录都重复使用 10px 时间/结果和 11px 描述，记录越多，小字节点越多。

建议：

- `.timeline small`：10px → 12px；
- `.timeline p`：11px → 12–13px；
- event type / sequence 保留 mono 12px；
- actor → target 作为正文使用 sans 13px；
- webhook reply/secret 辅助信息提升到 12px。

无需改变时间线结构，这一组字号调整就能显著改善整页观感。

### 根密钥状态

优点：视觉最克制的页面之一；H1 已单独限制为 48px，核心状态、事实和说明区分清楚。

问题：slot identity、recovery note 仍为 10px；与安全关键内容的重要性不匹配。

建议：全部提升到 12px；状态主标题保持 25px；无需其他结构或颜色调整。

### 设置与状态

优点：左侧分区导航一致，General、Security、Accounts、Instance、Diagnostics 的卡片系统稳定。

问题集中在 System Config：90 项配置的 key、说明和值分别为 10/10/11px，长时间排障难以阅读；配置标题 13px 与值 11px 的差距也不足。

建议：

- config title 13–14px/600；
- key 12px mono；
- description 12–13px sans；
- value 13px mono/600；
- `dt/dd` 全局默认不要再设为 11/10px，改为局部组件控制。

### 空状态、加载态、错误态、404

共享组件在边框、状态色和操作按钮上保持一致。主要问题仍是 `.loading`、`.dashboard-empty` 等使用 10px。统一提升到 12px 即可，不需要重做组件。

## 四、弹窗与浮层

### 正面结论

- 普通弹窗与危险确认统一使用同一个 `Modal`；标题、关闭、scrim、focus trap 和危险色语义一致。
- Provider、Deployment 等长表单有 sticky header/footer，桌面和移动端都不会丢失主要操作。
- 移动端弹窗全屏化正确，字段会变为单列，没有水平溢出。
- 危险确认把后果、重新验证和最终动作放在同一视觉容器中，层级正确。

### 问题与建议

1. 弹窗标题固定 22px，而大量说明/帮助文字为 10–11px，尺度断层过大。标题可保留 20–22px，但正文必须提升到至少 12px。
2. 长弹窗 section header 建议统一 16px/600；不要让 H3、H4、label 都落在 12–13px。
3. 关闭按钮 `×` 在移动端视觉尺寸偏小。保持按钮触控面积不变，字符本身提升到 20px，并使用 secondary text 色。
4. 能力 tag 很多时，10px 会让内容像密集脚注。tag 统一 12px，padding 可保持不变。
5. Discard prompt 与危险确认的按钮顺序和颜色一致，当前无需调整结构。

## 五、移动端视觉

代表页面在 390px 下没有水平页面溢出，指标会降为两列，弹窗会全屏，基础响应式行为正确。

需要修复：

- 顶部横向导航显示明显的原生灰色滚动条，且位于导航下方，像加载条或布局错误。建议隐藏 scrollbar 轨道，同时在右侧增加轻微渐隐提示可横向滚动；不改变导航结构。
- 移动端 H1 仍约 34px，表现可以；正文最小字号问题依然存在，应与桌面同批处理。
- 弹窗底部操作区视觉正确，但辅助说明过小；提升字号后需复核一屏高度，不必改变字段顺序。

## 六、建议的整改批次（均不改结构）

### Batch 1：建立真正的字号下限（P1）

1. 将全部 10px/11px/`.625rem`/`.6875rem` 提升到至少 12px。
2. 优先处理 `.timeline*`、`.config-entry*`、`.developer-*`、`.redaction-*`、`dt/dd`、`.field small`、`.eyebrow`、`.logout-button`。
3. 增加 Design System 测试：业务 CSS 不得出现低于 12px 的绝对字号；若确需例外，必须使用显式 allowlist。

### Batch 2：收敛标题与正文尺度（P1）

1. 全局 H1 desktop 上限从 54px 降到 42–44px。
2. 页面说明保持 14–15px；面板标题保持 20–22px。
3. 统一 label/table header/button 到 12–13px，正文到 14–15px。

### Batch 3：字重与字体族清理（P2）

1. 650 → 600 token；减少 700/900 在业务组件中的使用。
2. 普通说明从 mono 改回 sans；mono 只保留给技术值。
3. 减少小字上的大写和过宽 letter-spacing。

### Batch 4：主题与细节 QA（P2）

1. 调整 Light primary green，使 CTA 与品牌 lime 更一致，同时维持 AA。
2. 在 Light/Dark 中逐项复核 hover、focus、disabled、loading、selected、error。
3. 隐藏移动导航原生 scrollbar；修复中等宽度登录表单的视觉居中。

## 七、验收标准

- 业务 CSS 中不存在低于 12px 的可见文本字号。
- 任一主页面常规可见字号不超过 7 档。
- 页面标题、面板标题、正文、标签、辅助信息的层级在所有页面一致。
- Operations、Developer、Settings Config 在 100% 缩放和 1x DPI 下连续阅读无小字负担。
- Light/Dark 的正文、状态、边界继续通过现有 AA 门禁。
- 390px 下无页面级横向溢出，顶部导航不显示原生滚动条。
- 普通、危险、长表单、丢弃修改四类弹窗在桌面和移动端都完成视觉复核。

## 最终判断

当前版本的视觉基础已经足够稳定，不需要重新设计页面结构。建议在发布前至少完成 Batch 1 和 Batch 2：它们是全局一致性与基本可读性问题，不是审美偏好。Batch 3 和 Batch 4 可以在同一轮 CSS-only 整改中完成，并按仓库约定使用聚焦视觉检查；只有涉及组件行为或语义标记时再运行相关测试。
