## 跨角色交叉证实的缺陷（置信度最高）

按独立命中的角色数排序。这是多角色评审相对单次评审的核心价值所在。

**1. `reconcileLedgerChainCheckpoint` 的 `!ok` 早退是 fail-open（两份核心逻辑独立命中，给出两条不同攻击路径）**
`internal/app/runtime.go:1020-1024`：`ChainHead()` 返回 `ok=false` 时直接 `return nil`，**根本不加载 checkpoint**。而 `ok=false` 只表示"本次扫描没见到 epoch-4 帧"，无法区分"全新实例"与"WAL 被做过手脚"。
- 第一份的路径：把 epoch-4 帧**降级**成 epoch-3（丢掉 64 字节 `previousHash||MAC`、版本字节改 3、重算无密钥的 CRC32），全程不需要任何秘密。
- 第二份的路径更简单：**直接删掉整个 WAL 文件**，网关以零余额零历史正常启动。
- 两份都指出同一个放大器：`PutLedgerChainCheckpoint` 全仓非测试调用点只有 `runtime.go:1034` 一处，**只在启动时推进**。一个数月不重启的实例，运行期间产生的全部帧都不在 checkpoint 保护内。对照审计侧每次 append 后都 `checkpointAudit`。
- 第二份补了一刀：`reconcileAuditCheckpoint`（`runtime.go:995-1009`）**无条件加载 checkpoint**、空日志对上非零 checkpoint 会失败——ledger 侧没有对齐同一套写法。且全仓 `_test.go` 对 `reconcileLedgerChainCheckpoint` 的引用为零，门禁旗舰功能零测试。

**2. `vault_material.go:62-66` 信封缺失时静默回落到重新派生密钥（测试盲区 + 两份安全 + 一份核心逻辑）**
`ErrNotFound` 时不 fail-closed，而是回落到 `vault.DeriveLedgerHMACKey(masterKey)`。若信封因任何原因缺失（从旧备份恢复、轮换写入失败、被删），派生出的是**不同的 key**，全部历史帧变 `ErrTampered`——正是 ADR 0016 明确要防的那个 failure mode，被一个未测的 fallback 分支引了回来。且"信封曾经存在过然后消失"与"从未存在"两种状态在这里不可区分。

**3. 审计外部证人可端到端静默失效（核心逻辑 ×2 + 安全 B + 测试盲区）**
发射端与拉取端**全是 fail-open 且只有 `logger.Warn`**：`audit_anchor.go:52/60` 失败即 Warn+return；`deadman/anchor.go:76/84` 拉取失败 Warn+continue；`engine.go:142` 的 `pullAnchors` **返回值被直接丢弃**，不影响状态机、不触发 transition、不影响心跳；`runtime.go:115` 的 `anchorAuthFailed` 计数器**从未渲染进 `/metrics`**。凭据过期、端点不可达、deadman 根本没跑——以上任一情况下两侧都持续报绿，ADR 0015 的整套非否认性可以死掉几个月无人知晓。
叠加两个次级缺口：`LastAnchorSequence` 单调推进且持久化，锚点文件被删则该区间**永不重拉**；数据目录回滚后本地锚点序号重置，新锚点全部 `<= since` 被静默丢弃——**恰是最需要外部证人的时刻证人静默罢工**。

**4. `VerifyAuditAnchors` 不检查锚点序号连续性（核心逻辑 ×2 + 安全 B + 测试盲区）**
`audit_anchor_verify.go:113-126` 只对给定 anchors 逐条判 agree/disagree/truncated，不检查 `Sequence` 是否连续、不检查最新 anchor 是否覆盖当前链长。保留环仅 1000 条、每 10 秒发射一次即约 2.8 小时覆盖，拉取侧停机更久就产生空洞而永不被报出。安全 B 补充了更根本的一层：**证人记录本身不可验证**——`deadman/anchor.go:37-57` 写的是明文 JSON-lines、无签名无 hash 链，而同一代码库的 `metricsauth` 凭据审计是带链的。攻击者截断本地 audit 后再从证人文件删掉对应行，剩余每行都 agree。

**5. `sourcelimit` 溢出预算的不对称性，IPv6 下成本极低（三份安全 + BUG 排查）**
`limiter.go:83-91` 以完整 `netip.Addr` 为键、无前缀聚合。持一个 IPv6 /64 的攻击者可零成本使用 16384 个**真实可路由**地址，既拿到 `16384 × limit` 的有效额度，又把跟踪表占满；此后所有**新出现的合法客户端**（含持有效 `gw_` key 的付费租户）挤进单个共享溢出预算。限流器本身内存有界（这一点做对了），但它把"分布式地址洪水"转换成了对已认证客户的全局拒绝服务，且跑在认证之前无法给合法 key 开绿灯。修法：键归一化为 IPv4 完整地址 / IPv6 的 `/64` 前缀。

**6. 口令校验绕过 step-up 节流，read_only 可触发（两份安全独立命中）**
`admin_stepup.go:49-53` 的注释自述："It is the only entry point; the primitive underneath is unbounded and silent." 但有 5 处直接调 `adminauth.VerifyPassword` 绕过它：`admin_session.go:196`（改密码）、`admin_mfa.go:105/443/510/562`（MFA 增删/重生恢复码/停用）。这些挂在 `requireAdminSelfMutation` 层，**本轮新引入的 `read_only` 角色也能调**（设计意图是账号自服务不受角色限制）。Argon2id 参数 64 MiB × 3 iter × p=2，admin 监听器无并发上限（对比 metrics 有 `MaxConcurrentScrapes`），且失败**无审计**。安全 B 点出了为什么这是本轮新问题：上一轮所有持会话者都是管理员，"已认证 ≠ 可信"这件事本轮才第一次成立。

## 一、核心逻辑（6.0~6.5 / 10）

两份独立报告。共识部分：epoch-4 帧格式的实现与 ADR 0016 严格一致、密钥轮换"重封不换钥"因而不破坏历史帧可验证性、备份/恢复的链头对账用的是自己重新扫描的结果而非 manifest 的一面之词、cost adjustments 退役在记账语义上干净。

### 值得肯定

1. **epoch-4 帧布局的取舍是对的**（`log.go:583-612`、`:684-698`）。CRC 字段保持原有含义与字节范围不变，MAC 在 CRC 填好之后再算因而同时认证了 CRC；`nextHash = SHA256(MAC)` 而非哈希整帧，延链时不需要重读 payload。`scan` 里 CRC 先于 MAC 校验，把"撕裂尾帧"和"被篡改的历史帧"在最便宜的那一层就分开了。
2. **HMAC 密钥的"派生仅用于 bootstrap"是正确答案**（`vault/ledger.go:10-17`）。真正的密钥存在 Vault 信封里，Master Key 轮换只重加密信封、不改 HMAC 密钥本身。两条轮换路径（file 模式 `key_rotation.go:199/246/489`、KMS 模式 `kms_key_lifecycle.go:795/877/977/1036`）都有"轮换后 ledger key 字节不变"的显式断言。
3. **并发 Append / 崩溃重放 / 撕裂尾帧三种情况的链状态机正确**。所有帧编码在 `writeBatch` 内、`l.mu` 持有下串行完成；`chainHash/chainSequence/chainOffset` 只在 fsync 成功后整体推进；写或 sync 失败时链状态一律不前进并 `MarkUnavailable`。缺密钥时直接拒写（`log.go:502-505`）而非降级成 epoch 3。
4. **兼容闸门用"下限"而非"相等"**（`runtime.go:228-243`），注释诚实记录了 epoch 3 曾漏升闸门的历史 bug 并说明 migration 17 为什么直接跳到 4——不重复"精确相等导致漏保护"这个坑本身。
5. **cost adjustments 退役的记账语义是 fail-closed 的**：`checkpointVersion` 4→5（`usage/aggregate.go:16`），旧 usage checkpoint 一律拒绝并从 ledger 全量重建，不存在口径静默跳变。顺带修掉一个错标的 gauge（`heimdall_pricing_recovery_pending_intents` 原本声称统计两类 intent 却只读 adjustment bucket）。
6. **NDJSON 可选化实现与 ADR 0017 逐条对应**：`writeNDJSONAtomic` 与 `writeParquetAtomic` 的 temp/fsync/rename/dir-fsync 序列逐行同构；Format 按 manifest 条目记录、空值回读为 parquet；Verify 按条目自身 format 分发。**评审计划里"关闭导出后重放路径是否完整"这个问题的前提不成立**——0017 没有引入"关闭"这一档，`config.go:595` 只允许 `parquet|ndjson`。

### 问题与疑似 BUG

1. **【疑似BUG·高】epoch 降级绕过 ADR 0016 全部保证** — 见交叉证实 #1。第一份报告称已写 PoC 实测：全量降级后用正确密钥重开成功、`VerifyChain` 返回 `err=nil, chainVerified=false`、`VerifyLedger` 不报错；后缀降级（保留前 2 帧 epoch-4、第 3 帧起降级并伪造金额）同样全部放行。**已派对抗验证，见第十章。**
2. **【疑似BUG·高】删光 WAL 即可绕过同一门禁** — 见交叉证实 #1 第二条路径。**已派对抗验证，见第十章。**
3. **【疑似BUG·中高】派生读模型的取消/失败会单向毒化记账权威**（第二份独有）
   `ledger/log.go:360-364` 的 `Replay` 对**任何** visit 错误调用 `status.RequireRecovery()`；`status.go:36-53` 是单向棘轮，只有生产代码从未调用的 `MarkHealthyAfterVerifiedRecovery` 能复位；`usage/collector.go:80-84` 的 `CatchUp` visit 第一行就返回 `ctx.Err()`；`admin_usage.go:354-360` 每次 Dashboard/Usage 请求都以 `request.Context()` 调 `CatchUp`。
   断言的后果：管理员打开 Dashboard 后关页签，恰逢重放较长 WAL 后缀，则记账状态永久变为 `AccountingRecoveryRequired`，所有 `Append` 拒绝、`/health/ready` 503，全网关停摆直至重启——而 WAL 本身完好无损。派生态的失败不应处决记账权威。此缺陷基线已存在，但本轮重写 `Replay` 未借机修正，且 Usage 页重做扩大了暴露面。**已派对抗验证，见第十章。**
4. **【问题·中】`RestoreCheckpoint` 不恢复 `eventIDs` 去重集**（第二份独有）
   `usage/aggregate.go:136-146` 的 checkpoint 结构不含 eventIDs，恢复后 `a.eventIDs` 为空。而 `ledger.State` 明确容忍"同一确定性恢复事件被崩溃重复落盘"（`event.go:286-299`），即同一 EventID 可有两个物理帧。若 usage checkpoint 恰落在两份副本之间，重启后第二份会被**二次计入** attempts/费用。不影响余额（ledger.State 正确），但破坏了"派生链与 ledger 重放一致"。
5. **【问题】三态判定在报告层丢失关键区分**：`ChainReport` 把"epoch 1-3 历史遗留帧"和"有 epoch-4 帧但被降级/无密钥"都归入 `ChecksumOnly`，运维无法从 `heimdall ledger verify` 输出区分"升级前的老库"与"刚被降级改写过"。
6. **【问题】`heimdall doctor` 完全不做链校验，与代码注释自相矛盾**：`log.go:199-203` 明写 `VerifyChain` 是"for offline tooling — the verify CLI/doctor path"，但 `doctor.go:149` 走的是 `InspectReplay`，不传密钥不做 MAC 校验，然后在 `:161` 打出 `pass`。doctor 在 `:127` 已经解锁了 master key，完全有能力校验。**doctor 报 pass 的库可能整个是伪造的。**
7. **【问题】两条离线路径带写副作用地绕过闸门**：`app/usage.go:78`（`heimdall usage export/prune`）与 `app/backup.go:493` 都用 `ledger.Open()` 无密钥打开**活的** WAL，而 `OpenWithOptions` 在 partial 时会 `Truncate + Sync`。备份路径尚可自辩（快照副本会带密钥重开并与 manifest 比对），但 usage CLI 纯粹读派生态，没有理由持写句柄并截断权威账本。
8. **【建议】ledger/audit HMAC key 自身没有轮换路径**：两条轮换路径都只重封。KMS 侧对疑似泄露明确拒绝 rewrap 并要求 DEK 轮换，但 DEK 轮换恰恰保持 HMAC key 原封不动。链密钥一旦泄露，无法在保持历史帧可验证的前提下更换。建议立项记录。
9. **【建议】退役后的恒等字段应写明**：`SettledAttempt.BaseCostMicrosUSD/NetCostMicrosUSD` 恒等、`AttemptEvent` 的三个 cost 字段恒同、`Bucket.OriginalCostMicrosUSD` 恒等 `CostMicrosUSD`，前端仍消费 `final_cost_micros_usd`。作为 API 兼容别名可接受，但没有任何注释说明"自 8868e85 起恒等"，下一个读者会以为净额口径仍存在。

## 二、架构设计（8.0 / 10，上轮 7.5）

### 值得肯定

1. **依赖纪律是本轮最亮的一条线**。22870 行新增、5 个新子系统，`go.mod` **直接依赖净增为零**（唯一变化是 `jsonschema-go` 版本 bump 与 `golang.org/x/sys` 从 indirect 提为 direct）。二进制 37,004,322 → 37,597,122 字节，**+593 KB / +1.6%**。`internal/timezone/database.go`（272 行）自己读 tzdata 算 SHA-256 而不引入任何时区库；`internal/sourcelimit/limiter.go` 117 行纯 stdlib。
2. **Ledger HMAC 密钥管理完全复用 audit 的两层信封**，`vault/ledger.go:17` 与 `vault/audit.go:10` 逐行同构，注释明写 "mirroring DeriveAuditHMACKey exactly except for its domain separation strings"。
3. **ADR 0015/0016 是真决策记录**。三条硬证据：0016 头部 `Amended 2026-08-06` 承认 `feat/timezone-governance` 同日抢走了 epoch 3、整份 ADR 从 epoch 3 改写为 epoch 4；0015:232-235 明写"哪些比设想做得窄"（sink B/C 只是配置占位）；0016 的 Rejected alternatives 里那句 "A log whose history was rewritten to prove it was never rewritten is not evidence." 可以直接进教科书。
4. **"架构规则写成可执行测试"的纪律扩展了形态**。本轮没有新增 AST 测试，但增了三张**路由枚举网**：`admin_users_test.go:256`（`chi.Walk` 扫全部 48 条写路由，read_only 必须 403 且 `code == "read_only_role"`）、`admin_stepup_test.go:65`（破坏性删除端点的 step-up 覆盖扫描，带 `swept >= 9` 防漏扫）。枚举而非手写清单，意味着下一个新写接口默认在覆盖范围内。
5. **RBAC 明确拒绝了权限矩阵**。`domain/admin.go:9-21` 只有两档，注释开门见山："Admin roles are deliberately just two"。企业级产品到这一步几乎必然长出 role-permission-resource 三张表，这里没有。
6. **cost adjustments 的退役执行得干净**，净删 2139 行，bbolt bucket 与 migration v13 刻意保留（append-only 约定）。**退役比新增更能证明架构纪律。**

### 问题

1. **【问题】`internal/app` 上一轮"不拆"的决定，这一轮已经不成立了**

   | 指标 | 126fb32 | HEAD | 变化 |
   |---|---|---|---|
   | 非测试文件数 | 42 | 49 | +16.7% |
   | 非测试行数 | 13758 | 15155 | +10.2% |
   | Runtime 字段数 | 57 | 64 | +7 |
   | Runtime 内互斥锁 | 10 | 11 | +1 |

   关键数字不是这些，而是：**`internal/` 非测试代码本轮共增 2804 行，其中 1397 行（49.8%）落在 `internal/app` 一个包里**。上一轮"不拆"的论证有个隐含前提——app 是稳态的。本轮数据推翻了这个前提：新子系统的默认落点就是 app（7 个新文件）。
   **判断：不拆的结论仍可维持，但必须配一道闸门，否则它就是在为默认漂移背书。** 建议加一条与 `semantic/boundary_test.go` 同形态的可执行规则——不限制导入，而是**限制 Runtime 字段数与 mutex 数**（快照测试，超出即需显式改快照 + 评审）。这是这个仓库自己已证明有效的手法，成本一个文件，不承担重构风险。目前 app 是全仓唯一**没有任何可执行架构约束**的包，而它恰恰最需要。

## 三、安全威胁建模（7.5~8.0 / 10）

> 本章合并三份互不知情的安全报告。三者对 RBAC 实现质量、step-up 语义、锚点凭据域的判断高度一致；差异处已标注。

### 结构性正面结论（应固化为不变量）

1. **角色不进会话，每请求从 store 回读**（`adminauth/session.go:78-83` 里 `AdminSession` 根本没有 role 字段；`admin_session.go:270-283` 每次请求 `GetAdminUser` 现取）。降权立即生效，不存在"会话里冻结的角色"可被篡改——**这是同类实现最常错的地方**。
2. **自提权无路径**。`AdminUser.Role` 的全部写入口都经核对：`createAdminUser`（仅 administrator 可达）、`changeAdminPassword`（原样带回 `user.Role`）、`updateAdminPreferences`（从 store 读全量对象、只改 Locale/Appearance）、MFA 旋转。**没有任何"改角色"端点**，read_only 无法自升。不存在 mass-assignment。
3. **默认拒绝式中间件 + 路由树全量扫描测试**。`requireAdminMutation` 包裹在 self 层之外，新增写端点自动挂上角色门；`admin_users_test.go:250-289` 用 `chi.Walk` 遍历**真实路由树**逐条断言 403。两份安全报告都手工核对了 `runtime.go:1112-1232` 的全部 Post/Put/Delete/Patch，**未发现漏挂中间件的 mutation**。
4. **step-up 根本没有"step-up 凭证"，因此不存在窗口/绑定/重放问题**。每次请求现场读 body 逐次校验，不换发任何短时提权 token。评审计划问的"能否重放到另一个端点"——**不能，因为没有可重放的物件**。
5. **TOTP 单次消费是事务性的**。`AcceptAdminMFATimeStep` 在 bbolt `Update` 事务内检查并单调推进 `LastAcceptedTimeStep`，两个并发请求带同一 code 只有一个能提交。
6. **历史账号 backfill 成 administrator 是正确的，不是缺陷**（这条明确反驳了评审计划里的假设）。迁移前的事实状态是所有账号都拥有全权限，backfill 成 administrator 是忠实记录既有权限、不产生新增授权；backfill 成 read_only 反而会把运维者静默锁在门外。且只回填 `Role == ""` 这一种精确形状，其他未知值原样保留继续 fail validation。
7. **锚点端点鉴权实现层面是隔离的**：独立 authorizer 实例、独立凭据文件、`anchorAuthorizer == nil` 时返回 false（fail-closed）、路由只在 `Enabled && Sink == dead_man_pull` 时注册、**无视 `Metrics.RequireAuth` 开关永远要求凭据**、metrics 那条特有的"零配置派生 token"回落没有被复用。锚点内容只含链摘要与实例标识，无事件载荷。
8. **`safelog` 是本轮质量最高的改动之一**：`Value.Resolve()` 处理 `LogValuer`、`KindGroup` 递归、`[]byte` 按字符串渲染、`fmt.Stringer` 兜底、新增 `hm[st]_` 自签令牌模式，`Handle` 同时对 message 做 `Redact`。
9. **XFF 修复是实打实的**：`handler.go:707-737` 合并**所有** `X-Forwarded-For` 行再从右往左取第一个不可信地址，且仅当直连对端本身在 `trustedProxies` 内才读。无法解析的地址返回零值而**不是放行**。上一轮"只读第一行"的问题确实修好了。

### P1 级问题

**S-P1-1 · 口令校验绕过 step-up 节流，read_only 可触发** — 见交叉证实 #6。**已派对抗验证，见第十章。**

**S-P1-2 · step-up 的判据画错了线：只保护"删除"，不保护"铸造凭据"和"关闭安全控制"**（两份安全独立命中，已核实）
step-up 的自述威胁模型是"a stolen session alone should not be able to do it"，但被保护的 9 个端点全是 DELETE，而对攻击者价值更高的操作一个都没有：

| 操作 | step-up | 攻击者收益 |
|---|---|---|
| 铸造网关密钥（明文一次性返回，`admin_projects.go:200-247`） | **无** | 拿到 `gw_` 明文，**admin 会话被吊销后依然可用** |
| 替换上游 Provider 凭据（`PUT /credentials/{id}`） | **无** | 把流量导向攻击者控制的 key/端点 |
| 改写/清空脱敏策略 | **无** | 关闭 redaction，后续全部 prompt 明文过境 |
| 解除 Token Guard 封锁 | **无** | 直接撤销一个已生效的安全控制 |
| 删除路由/策略/项目 | 有 | 只是可见的破坏 |

会话窃取者拿不到 DELETE，但拿得到一枚长期 `gw_` 密钥——**收益严格大于删除**。讽刺的是 `createAdminUser` 已经内联了 step-up，理由正是"铸造带系统访问权的新凭据"，同一条理由对网关密钥完全适用却没执行。判据应从"是不是 DELETE"改成"是不是发凭据 / 削弱安全控制 / 不可逆"。

**S-P1-3 · MFA 验证无账号级限速且失败零审计**（一份安全命中，已核实）
`completeMFA`（`admin_mfa.go:268-303`）唯一节流是按**源地址**的 `allowAdminLogin`。账号侧只有"每个 challenge 5 次尝试"，而 challenge 可无限申请且**不绑定源地址、不绑定 UA**。攻击者用 1 次登录换 1 个 challenge，从 N 个源地址各花掉尝试次数，账号维度没有天花板——猜测速率随源地址数线性增长。
对照：step-up 路径有 per-username 失败预算，登录密码失败有 `auditAdminLogin(..., "failure", ...)`。而 MFA 验证失败**既没有账号级预算，也没有任何审计事件**（`admin_mfa.go:299-303` 只写 401）。**登录密码猜测留痕，第二因子猜测零留痕。**

**S-P1-4 · 锚定链路端到端可静默失效** — 见交叉证实 #3。

**S-P1-5 · 证人记录本身不可验证** — 见交叉证实 #4。

### P2 级问题

- **"独立凭据域"是注释里的承诺，代码与配套工具都不支持，且随附客户端直接违反它**。`config.go:466-484` 的校验**不检查** `audit.anchor.credential_file != metrics.credential_file`；CLI 只有 `heimdall metrics rotate|revoke|status`，**没有任何子命令能生成或轮换锚点凭据**；最直接的证据是随附的 dead-man 客户端就是这么设计的——`deadman/config.go:50-55` 明说 AnchorURL "shares BearerTokenFile"，`anchor.go:109` 与 `http.go:106,124` 把**同一个 token 分别发给 `/metrics` 和 `/audit/anchors`**。所以对"拿到 metrics token 能不能读锚点"这个问题：**在推荐部署形态下能**。危害有限（锚点无敏感内容、只读），但"外部见证"的凭据独立性名存实亡。
- **锚点端点不强制 TLS**：`config.go:466-479` 启用 `dead_man_pull` 只校验 `metrics.enabled` 与 `credential_file`，不要求 `metrics.tls.enabled`。给一个专门用来做非否认性的通道配明文传输，是自相矛盾的。
- **新 pre-auth 限速器对存量配置默认关闭**：`config.Decode` 不与 `Default()` 合并，`requests_per_minute` 缺省 0 即禁用。代码注释承认这是刻意的向后兼容选择。攻击者视角：本次引入的这道 pre-auth 防线对所有存量部署默认是关的。**安全控制的默认值应该是开。**
- **`allowAdminRate` 的 map 清理在单窗口内无效，且每请求 O(n)**：`admin_session.go:410-438` 在 `len(windows) > 4096` 时遍历删除更旧条目，但同一分钟内的洪水里没有任何条目更旧，于是每个请求都做全量 O(n) 扫描且删不掉任何东西，总成本二次方且 map 无上限增长。**同一个仓库在 `sourcelimit` 里已经把有界策略写对了一次。**
- **ledger 链与它保护的对象同信任根**：持 `master.key` 者可同时改数据、改 MAC、改 checkpoint。这不是实现 bug 而是**边界声明缺失**——ADR 0016:38-44 其实正面写明了这个边界（"不防在 `mode: file` 下持有 master.key 的人"），这一点值得肯定；问题是**这条边界没有传导到 `docs/architecture/threat-model.md`**，而 ADR 是决策记录、威胁模型才是运维者会读的那份。
- **Developer Workbench 逐字转发调用方的 `X-Forwarded-For`**（`admin_developer.go:64-68`）：当 `trust_proxy_headers=true` 且管理员地址落在 `trusted_proxy_cidrs` 内（管理面与数据面共用 ingress 的常见部署），`gatewayapi.sourceIP` 就会采信完全由调用方构造的链。后果不是提权（调用方已是 administrator），而是**证据与策略的可信度**：绕过项目 `AllowedCIDRs`、污染 Token Guard 的 `SourceHash`（可把封锁扣到任意伪造源上，或轮换伪造源规避自身封锁）、使用量归属可伪造。数据面正常路径靠"最右侧非可信地址"防住了客户端伪造，workbench 这条捷径把它绕开了。

### 建议

- 删除用户不吊销其会话（`admin_users.go:151` 只调 `DeleteAdminUser`，对比改密码时会调 `DeleteAdminSessionsForUser`）。结果确实 fail-closed（`GetAdminUser` 返回 `ErrNotFound` → 503），但依赖的是错误路径而非显式吊销，且 503 与真实 bolt 故障不可区分。
- 无角色变更端点，降权必须删号重建（连带丢失 MFA 注册），会诱导运维长期保留过多 administrator，或直接改 bolt 绕过。
- `requireAdminSetupMutation`（`admin_session.go:296`）已定义但全路由无引用，是死代码。死的授权中间件将来容易被误用/误信。
- `safelog` 敏感键名表缺 `totp`、`code`、`hmac`、`recovery`、`challenge`。
- `admin_errors.go:43` 的默认分支 `adminBadRequest(writer, err.Error())` 原样回显内部错误；`gatewayapi/handler.go:944` 的 `decodeProblem` 注释断言"text is built from constants and indices, so passing it through leaks nothing"，当前成立，但**把"不泄露"交给了调用方自律**。建议把断言变成机制（白名单化错误构造）。
- `audit/log.go:35,108` 的 `maxTrackedEventIDs = 4096` 把去重从"全历史"改为"尾部窗口"。内存修复正确，但去重语义被削弱且这个前提没有被断言或测试固定。
- `admin.mfa_policy` 默认 `optional`，在默认部署里 step-up 退化为"再输一次密码"。对会话窃取者仍有效（主要目标），但对密码泄露者完全无效——**9 个 DELETE 的保护强度实际由这个默认值决定**，应在文档里写死这个前提。

### #2 详情（BUG 排查独有，已核实代码分支存在）

`startAttempt` 在预留失败时（`service.go:385-390`）只做 `providerLease.Release()` / `breakerLease.Abandon()`，然后 `if errors.Is(err, budget.ErrExceeded) { return nil, err }`——这条分支**刻意不调用 `finalizeRequest`**，因为原先靠外层循环走完后在函数底部统一 finalize。`8868e85` 在 Chat/ChatStream/Embeddings 三处新增了直接返回，**跳过了底部那次 `finalizeRequest`**；而 `defer run.close()` 只释放 tokenGuard/limiter 租约，不发 `EventRequestFinalized`。

### V-1 · epoch 降级 — CONFIRMED，且实测比原报告更严重

证伪失败。断言 1~5 全部在代码里复现。关键的加强之处：

- **全量降级不依赖 checkpoint 陈旧**。验证角色特意用**全新、正确、刚推进过的** checkpoint（seq=5，覆盖全部 5 帧）做对照实验，`reconcileLedgerChainCheckpoint` 仍然返回 `nil` 放行——因为 `ok=false` 让 checkpoint 根本不被读取，**再新鲜也没用**。这是无条件绕过，不是窗口期问题。实测把 `reservation_micros_usd` 从 100 改成 999 后重放出 4995 micros（真实 500）。
- **下游比报告说的更弱**：`cmd/heimdall/main.go:720-724` 只把 report 打成 JSON 就 `return nil`，**退出码 0**。按退出码写监控脚本的运维完全看不到。全仓没有任何 metric/alert 消费 `ChecksumOnly`。
- **两个额外发现**：(a) 在诚实的 epoch-4 帧之后**追加**一个手工构造的 epoch-3 帧，`VerifyChain` 返回 `chainVerified=**true**`——连那个唯一的弱信号都不触发；(b) **篡改会被永久洗白**：全量降级后重启一次，新写的 epoch-4 帧以 `previousHash=0` 重新起链，第二次重启时 `VerifyChain` 返回 `chainVerified=true seq=7` 并把 checkpoint 推进到 7，**跨过伪造区，证据不可逆销毁**。

**被证伪的子断言**：原报告称"后缀降级同样全部放行"不对。checkpoint 新鲜时会被抓住（实测 `keep=2` 时报 `ledger chain does not match its trusted checkpoint`）。后缀降级只在 `checkpoint.Sequence <= 最后一个存活 epoch-4 帧的 sequence` 时通过；因 checkpoint 仅启动时推进，长跑实例确实处于该窗口，故**实践上成立、机制上有条件**。

已排除的拦截防御（都不成立）：`LedgerCompatibilityGate` 只读 bbolt 的 epoch 值、与 WAL 帧实际 epoch 零关联；backup manifest 不含链头；`status.RequireRecovery()` 只在 scan 返回 error 时触发而降级帧不产生 error；`PutLedgerChainCheckpoint` 的单调性只保护 checkpoint 本身而攻击者不碰 bbolt。**攻击者能力 (a)「仅 ledger.wal 写权限」即已足够。**

### V-3 · 预算超限泄漏 — CONFIRMED（机制）/ 归因 PARTIAL

写测试跑通了。预算 1 micro、发 25 次 `Chat`：

```
rejected=25 of 25, provider calls=0
ActiveRequests after 25 budget-rejected requests = 25
checkpoint payload bytes=10768, ActiveRequests after restore=25   ← 走完 Marshal/RestoreCheckpoint 仍是 25
```

### V-4 · Argon2id 放大 — PARTIAL：分支真实，归因与修法均被证伪

成立部分：5 个 handler 直连 `adminauth.VerifyPassword` 属实；中间件栈查完确认 `requireAdminSelfMutation` **没有任何限流**（`allowAdminRate` 只被 `loginAdmin` 和 setup 调用）；失败**确实零审计**（`admin_mfa.go` 全部 8 处审计都在成功路径上）；实测数字准确——单次 `VerifyPassword` = 64.01 MiB TotalAlloc / 52 ms，32 并发实测峰值 HeapAlloc 2048.57 MiB（精确 32×64 MiB，**无复用**）。

**四条被证伪**：
1. **不是 `read_only` 引入的**。同一路径对 administrator 完全同样敞开且早于角色特性存在。`read_only` 的产品文案是"可以查看全部配置与用量"——是**全可见审计员**角色，不是低信任沙箱，"预期发给外部低信任人员"的假设不成立。
2. **口令预言机是自指的**。5 处校验的都是**会话自己的**用户名，攻击者只能猜自己已知的口令；且猜出口令**不带来提权**（role 每请求从 store 读）。价值仅限凭据复用 + 该账号完全接管。
3. **不是新增的内存原语**。`loginAdmin` 未认证即可触发 argon2（含 `DummyVerify`），仅受 LoginRPM=5/IP/min 限制，多源 IP 即可复现同等量级。
4. **`verifyAdminStepUp` 本身也挡不住这个 DoS**：`stepUpExhausted` 在验证前检查、`recordStepUpFailure` 在验证后记录，典型 TOCTOU——100 个并发同时读到 attempts=0 全部进入 argon2。所以约 10 条 step-up 保护的端点**同样暴露**。

**双方都低估的一点**：`deploy/kubernetes/heimdall-aws-kms.yaml:55` 的 `limits: {memory: 512Mi}`——**8 个并发 argon2 就是 512 MiB**，直接 OOMKill。配合 `replicas: 1` + `Recreate`，10 个并发请求即可打掉整个网关。不需要 100 并发/6.4 GB。

**严重度定 P2 加固而非 P1**：默认 `admin_listen: 127.0.0.1:8081` 且非 loopback 必须开 TLS，攻击者需已持有有效 admin 会话 + 网络可达 admin 面。但**审计缺口独立值得修**——已认证会话下的口令暴力破解全程无痕，与 `docs/contracts/audit-integrity.md` 的取向直接冲突，这是本条里最实的部分。

**修法建议被推翻**：直接改走 `verifyAdminStepUp` 会造成 4 处语义回归——`changeAdminPassword` 现在不要求 TOTP（换了会破坏前端契约）；`deleteAdminMFAAuthenticator` 刻意用 `others`（排除待删认证器）验 TOTP，换成"验所有 active"是**削弱**；`disableAdminMFA` 支持恢复码替代 TOTP，step-up 无此分支会**直接破功能**；`regenerateAdminMFARecoveryCodes` 无条件要求 TOTP 而 step-up 在无 active 时跳过，是**放宽**。
正确做法拆成两件独立的事：(1) 抽出限流+失败审计的**包装器**，套在这 5 处**各自保留的** TOTP 语义外层；(2) 在 `internal/adminauth` 内给 argon2 加**并发信号量**（照抄 `runtime.go:548` 的 `metricsScrapes` 模式，有界队列 + 超时 503），同时覆盖 `VerifyPassword` 和 `DummyVerify`——这才是 DoS 的真修法，并顺带修掉 step-up 路径上的同一 TOCTOU。

### V-5a · 派生读模型毒化记账权威 — CONFIRMED，触发面比报告窄但机制更硬

断言链七条逐条核实**全部属实、无任何豁免**：`Replay` 对 visit 错误一律 `RequireRecovery()`（`log.go:349-372`，无 `errors.Is(err, context.Canceled)` 分支）；`scan` 原样透传不包装（`log.go:722-726`）；`RequireRecovery` 单向棘轮且 `MarkHealthyAfterVerifiedRecovery` **全仓零调用者（连测试都没有）**，唯一复位路径是进程重启；`CatchUp` visit 首行返回 `ctx.Err()`；`admin_usage.go:355` 直接透传 `request.Context()` 而**没有** `WithoutCancel`（仓库里这个模式只出现在 `runtime.go:908` 与 `adminauth/session.go:109,114`，usage 路径确实漏了）；`Append` 入口无条件拒绝非 healthy 状态而 `budget/manager.go:622` 是**每个网关请求的必经路径**；数据面**真的停**——`service.go:211-218` 的 `BeginRequestDetailed` 失败直接 `503 accounting_unavailable`，不是"探针红但流量照走"。

实测两组：
```
# 确定性触发：50 条事件 + 容量 1 的 lagging collector，replay 第 3 条时取消 ctx
CatchUp error: context canceled
ledger status after CatchUp: 3 (RecoveryRequired=true)
gateway BeginRequest after CatchUp: accounting is not healthy

# 纯真实时序：2 万条事件，用真实 replay 耗时的一半作为 deadline
full replay of 20000 records took 104.45ms (~190 records/ms)
CatchUp err=context deadline exceeded; status=3 (RecoveryRequired=true)
```

**成功证伪的三处（原报告需修正）**：
1. "刚重启后首次访问"这个前提**是错的**——`runtime.go:274-280` 在启动时就同步做了 `Replay(usageWatermark, usageAggregate.Apply)`，聚合在 collector 建立前已追平 WAL 头，重启后首次访问的 replay 后缀是 ~0 条。
2. **稳态下窗口极小**：聚合追平时 `Replay` 从 watermark 出发直接撞 EOF，**一次 visit 都不调用**，ctx 就算已取消也不会中毒。"随便关个页签就挂"不成立。
3. **10 秒后台 ctx 自触发不现实**：按实测 ~190 records/ms，撑爆 10s 需约 190 万条积压，而 checkpoint ticker 是 60s 一次，正常负载下积不到。

**但证伪失败的部分反而让结论更硬**：触发只需 **≥1 条待重放记录 + ctx 在 top gate 之后被取消**。`AnalyticsQueueCapacity=4096` 一旦被突发流量打满，`Run` 会因 lagging 停止 Apply、watermark 冻结、后缀随流量线性增长（10 万条积压 ≈ 0.5 秒窗口）。**更宽的窗口是 `applyMu` 串行化**：ctx 门在 `collector.go:69`、`applyMu.Lock()` 在 `:72`，而 `Lock()` 不感知 ctx——多个并发 admin 请求时后到者会在 `Lock()` 上阻塞**整个 leader 的 replay 时长**，进门时 ctx 早已取消。多开几个 Dashboard 页签再一起关，窗口不是微秒级而是"leader replay 全时长"。

**这直接违反 CLAUDE.md 的"derivatives must never be treated as sources of truth"**——派生只读路径可以单向污染记账权威状态，且无任何复位 API、无 admin 端点、无自愈，WAL 完好却全网关 503 直到重启。

### V-5b · 删光 WAL 绕过启动门禁 — CONFIRMED，比原描述更严重

**事实修正**：WAL 文件名是 **`ledger.wal`**（`<data_dir>/ledger/ledger.wal`），原报告写的 `usage.wal` 是错的。

分支核实：`ChainHead()` 的 `ok` 来源是 `chainVerifier.sawFrames`，只表示"本次扫描见过 epoch-4 帧"；`OpenWithOptions` 用 `os.O_CREATE|os.O_RDWR`，WAL 被删后**静默重建为空文件**，scan 干净返回。对照组 `reconcileAuditCheckpoint` 确实是无条件加载 + 比较，ledger 侧没有对齐——这条对照断言成立。

报告要求排查的其他拦截点**全部不拦**：`restoreUsageAggregate` 只校验 checkpoint 信封自洽、**从不与 WAL 比对**；启动 `Replay` 对空文件 `Seek` 越过 EOF 合法、返回干净 watermark；`RecoverPendingLeases` 从空 state 恢复无 pending；`LedgerCompatibilityGate` 只看 bbolt epoch 号与 WAL 无关。

实测两个场景都跑通：
```
# 场景 2（同时删掉 usage checkpoint，即崩溃前没来得及打点的常见情形）
chain checkpoint before wipe: seq=15 offset=9060
startup succeeded; accounting status=0
post-wipe settlement 0/1/2 accepted (each 0.3 USD against a 1.0 USD daily budget)
RESULT: CONFIRMED — full daily budget restored, gateway healthy
```
0.9 USD 已花的日预算被完全抹掉，网关持续健康服务、无任何告警。

**外加一个原报告没提到的二阶效应**（场景 1，保留 usage checkpoint）：聚合保留旧 watermark（seq=5/offset=3020），新 WAL 从 0 重写，重建到该偏移后 CatchUp 撞进帧中间——
```
CatchUp failed: ledger is corrupt at offset 3020: non-monotonic sequence
accounting status now: 3 (RecoveryRequired=true)
```
即"删 WAL"最终会在一分钟内（checkpoint ticker）把网关自己打成永久 503，**一个极难诊断的延迟爆炸**。

这正是 ADR 0016 chain checkpoint 明确宣称要防的 "log is shorter today" 场景（`runtime.go` 注释自己写着）。有 data dir 文件系统访问权的人可以一键重置全部预算与消费历史且不留痕迹。修法：`reconcileLedgerChainCheckpoint` 应**无条件**加载 checkpoint，只有 `checkpoint.Sequence == 0` 时才允许 `ok=false`，措辞与 audit 侧一致；另建议 `restoreUsageAggregate` 在 checkpoint watermark 超过 WAL 头时拒绝该 checkpoint（顺带消掉延迟爆炸）。
