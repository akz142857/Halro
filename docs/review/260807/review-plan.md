# Heimdall 评审方案（2026-08-07）

> 本文件是**方案**，不是报告本身。评审执行后的结论落在同目录 `260807.md`（格式参照 [`260805/260805.md`](../260805/260805.md)），整改进度落在 `progress.md`（参照 [`260805/progress.md`](../260805/progress.md)）。
> 评审框架定义见 [`docs/review/README.md`](../README.md)，本文件只做"这一轮该怎么跑"的具体化，不重复定义角色。

## 1. 背景与动因

上一轮全面评审（[260805](../260805/260805.md)，基线 `126fb32`）产出 23 项修复清单，已收尾：22 项完成、1 项（`internal/app` 拆 `adminapi`）量化评估后决定不做并关闭。所有改动已合并进 `main`，并打了首个 tag `v1.0.0-rc.1`。

但收尾过程中追加的改动量级不小于一轮新功能开发：

```
git diff --stat 126fb32 HEAD   →  281 files changed, 22870 insertions(+), 8391 deletions(-)
```

其中不只是"修 260805 指出的问题"，还夹带了三块上一轮评审**完全没见过**的新增/重构面：

1. **记账完整性升级**：Ledger 帧 epoch 4（HMAC + hash 链，[ADR 0016](../../adr/0016-ledger-frame-integrity.md)）、审计外部锚点（dead-man 拉取，[ADR 0015](../../adr/0015-audit-chain-external-anchoring.md)）——直接触及 CLAUDE.md 点名的"Ledger WAL 是记账权威"与"审计完整性"两条最高优先级不变量，且涉及新密钥派生链（`DeriveLedgerHMACKey`）与两套轮换路径。
2. **Admin 权限模型从无到有**：管理员/只读两级角色、破坏性删除的 step-up 二次认证（9 个端点）、多用户登录——从"过了 Admin 会话即全权限"（260805 S-P0 相关背景）变成有 RBAC，是新的信任边界，前端也随之改动（`817f7d9`、`1b33357`、`782b1ef` 等）。
3. **Usage/计费口径改动**：cost adjustments 功能先加入（ADR 0013）又在最新提交（`8868e85`）整体退役，Usage 页面随之重做；Parquet 导出降级为可选格式（[ADR 0017](../../adr/0017-usage-export-format.md)）。一个功能"加入又撤回"本身是需要专门确认撤得干不干净的信号——半路残留的读模型、迁移、前端引用都属于高风险点。

这三块都不是"改了一行 fix"，而是新子系统或信任边界的形状变化，值得当作独立评审对象，而不是全部塞进 `progress.md` 的验证记录里自证自评。

## 2. 本轮目标

不是从零打一轮全面评审，是**聚焦性复评**：

- **验证性**：确认 260805 的 23 项修复在真实合并后仍然成立、没有被后续提交悄悄削弱（例如 RBAC 落地是否重新打开了权限判断上的漏洞、fail-closed 门禁是否还在关键路径上）。
- **发现性**：对上述三块新增面做独立评审，视角与 260805 一致——角色互不知情、独立产出、证据必须带 `文件:行号`。
- **不重复**：已在 260805 走查过且本轮无改动的代码（如 `internal/domain/pricing_cost.go` 的 big.Int 计价、`safetransport` 拨号校验）不重新派角色通读，只在相关角色评审新代码时顺带确认接口/调用点没被破坏。

## 3. 范围界定

- **基线对比区间**：`126fb32`（260805 评审基线）→ `8868e85`（当前 `main` HEAD）。评审角色应优先通读 `git diff 126fb32 HEAD` 覆盖到的文件，而非重新通读全仓；全仓性结论（如"包结构是否合理"）仍允许角色按需扩大范围。
- **重点目录**：
  - `internal/ledger/`、`internal/vault/ledger.go`、`internal/store/bolt`（chain checkpoint 部分）——Ledger 完整性
  - `internal/app/audit_anchor*.go`、`internal/deadman/`（锚点拉取部分）、`internal/store/bolt/audit_anchor.go`——审计外部锚点
  - `internal/app/admin_role*.go`、`internal/adminauth/`、`web/src/pages/SettingsPage.tsx` 及账号管理相关组件——RBAC 与 step-up
  - `internal/usage/`（Parquet 可选化后）、`web/src/pages/UsagePage.tsx`（重做后）、cost adjustment 退役后是否有残留代码/表/文案
- **排除范围**：dependabot 依赖升级类提交（`9ea364a` 等一串 `build(deps)`）不单独评审，除非某角色在通读中发现依赖版本跳变引入了行为差异。

## 4. 角色选择

参照 README 选择指南的"大型功能合并前"档位（架构 + 核心逻辑 + 安全 + 测试盲区 + BUG），并按第 1 节列出的三块新增面做加法/减法：

### 本轮执行（7 个角色）

| 角色 | 档位 | 选择理由 | 本轮重点问题 |
|---|---|---|---|
| 核心逻辑 | 核心档 | Ledger epoch 4 是记账正确性的新一层，必须有独立视角复核不变量 | 链式 MAC 的密钥轮换是否真的不破坏历史帧可验证性；chain checkpoint fail-closed 门禁是否覆盖所有启动路径；cost adjustment 退役是否留下孤儿读模型/未清理的迁移 |
| 安全威胁建模（两个独立角色） | 核心档+专项档 | 沿用 260805 的双角色互证方法；RBAC 从无到有是全新信任边界，Ledger HMAC 密钥派生链是新攻击面 | RBAC 是否只挪了前端展示、后端鉴权点是否每个破坏性 mutation 都真正校验角色；step-up 二次认证的会话/超时语义是否有绕过窗口；`DeriveLedgerHMACKey` 是否重蹈 260805 S-P0-2 audit key 同域覆辙（ledger key 与 ledger 数据是否同域可推导）；审计外部锚点端点鉴权是否与 metrics token 正确隔离 |
| 测试盲区 | 核心档 | 260805 证明"中止路径裸奔"是真实 BUG 的成因；新子系统同样可能只测了 happy path | chain 校验的三态（authenticated/checksum-only/failed）是否都有负面测试；锚点拉取在 deadman 侧断网/端点不可达时的行为是否有测试；RBAC 权限降级（只读试图破坏性操作）是否有测试而不只是前端隐藏按钮 |
| BUG 排查 | 核心档 | 独立于安全/逻辑视角，专找有代码证据的具体缺陷 | 全仓，重点仓库 diff 覆盖的文件 |
| 架构设计 | 核心档 | 检查新子系统是否延续了既有架构纪律，还是绕过了既定分层 | Ledger HMAC 密钥管理是否复用 vault 现有信封模式还是另起一套；audit anchor 端点是否合理挂在 metrics 监听器而非新开一个监听面；`internal/app` 相关文件量在这一轮又涨了多少（P2-19 决定不拆之后，涨势是否失控） |
| 交互设计 | 专项档→本轮纳入 | RBAC 改变了前端可操作集合，Usage 页面整体重做，是本轮唯一有实质前端改动的两块 | 只读角色下按钮/表单的禁用态是否说明原因（260805 交互 #3 同类问题是否在新代码里重犯）；重做后的 Usage 页面是否延续了 260805 视觉/交互已发现的模式（模态框脏检查、创建成功反馈等）还是自成一派 |
| 视觉设计 | 专项档→本轮纳入 | 同上，且 260805 已发现"新模块各写一套模式"是系统性问题（如 `.alert-row`/`.resource-toolbar` 各写一份），需要确认 Usage 页面重做没有再添一个孤例 | 新增的角色管理 UI、Usage 页面是否复用既有 design-system token 还是引入新的裸值/新的间距手感 |

### 本轮不单独执行

| 角色 | 理由 |
|---|---|
| 可用性 | 260805 该角色发现的问题（`make start` 依赖 npm、`master.key` 提示缺失等）均已在 P1-8 修复，本轮无对应新增面，不重复通读 |
| 性能与容量 | 无压测环境；Ledger 帧从 24 字节头变 88 字节头、每帧多一次 MAC 计算，理论上有可测量的写路径开销，但需要压测数据而非读代码——记为**后续待办**，待有压测环境时补做，重点看 WAL 组提交吞吐是否因帧变大而显著下降 |
| API 兼容性契约 | 本轮未改动 OpenAI/Anthropic 兼容层 |
| 供应链与发布工程 | 本轮除依赖升级外未改 CI/构建；`v1.0.0-rc.1` 已打过标签，若下一步要发正式 `v1.0.0` 再触发此角色 |
| 数据迁移与升级 | 技术上应触发（migration 17/18、v3 gate 收紧），但已被"核心逻辑"角色的重点问题覆盖（chain checkpoint fail-closed、bbolt schema 迁移），不再单开一档避免重复评审同一批文件 |
| 可观测性 | 未改动 metrics/alert/runbook 定义本身（deadman 增加的锚点拉取算功能改动，已归入安全/核心逻辑角色的重点问题） |

## 5. 对抗验证

沿用 260805 的方法论沉淀（见 README「方法沉淀」一节）：发现型角色产出后，对最严重的 4~6 条 P0/P1（预期集中在 Ledger HMAC 密钥同域、RBAC 鉴权点遗漏、审计锚点端点鉴权隔离这几类）各派一个独立"证伪型"角色，默认 finding 为错，要求在代码里复现完整攻击链或找出已有拦截防御，裁决 CONFIRMED / REFUTED / PARTIAL。260805 的经验是 6 条最严重发现无一原样照收——本轮同样不假设发现型角色的结论直接可用。

## 6. 执行方式

- 7 个角色（含双安全角色）全部并行启动，互不知情，独立通读、独立产出，不共享中间判断。
- 每条发现必须带 `文件:行号`，区分【肯定/建议/问题/疑似BUG】，与 260805 报告格式一致以便交叉比对。
- 汇总时主动标注：(a) 跨角色交叉证实的问题；(b) 与 260805 结论矛盾或表明某项修复不完整的发现——这类要优先核实，因为意味着上一轮的"已完成"判断需要撤销。
- 报告结构沿用 260805：评分总览表 → 各角色分章 → 统一 BUG 清单 → 按 P0/P1/P2 分级修复清单 → 对抗验证章节。
- 输出文件：`docs/review/260807/260807.md`（报告，评审后不再改动）+ `docs/review/260807/progress.md`（整改活对照表，创建时从空表起步）。

## 7. 完成定义

本轮方案执行完成的标志：

1. `260807.md` 落地，7 个角色全部产出（安全角色为 2 份独立报告合并去重）。
