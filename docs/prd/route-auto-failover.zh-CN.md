# 路由自动切换：设计变更提案

## 修订说明

本文第一版的结论是「回退引擎已经建成，缺的只是控制台没把它暴露出来，因此这是一次纯前端
改动」。多角色评审推翻了这个结论，证据见[多目标别名今天保证什么](../guides/alias-failover.zh-CN.md)。
被推翻的具体判断：

- **不是纯配置操作。** 把两个单目标别名合并成一个双目标别名，会让该别名上的
  images / audio / batches / files / async 从可用变为 `409 ambiguous_resource_route`。
- **不是通用回退。** 401、4xx、500/502/504、任何歧义传输错误都不换目标。运维最想靠回退
  扛住的「主服务商凭据失效」恰好在不覆盖的那一半里。
- **不是零行为变更。** 三个准入闸门（Token Guard 按候选最高价准入、未定价候选否决整链、
  预算耗尽不换候选）都是在「一个别名等于一个目标」的前提下写的，多目标一出现就改变行为，
  而且改变的是**每一个**请求，不只是发生回退的那些。
- **不是纯 UI 可解释。** 「别名授权即授权其全部现在与将来的目标」这个语义，在合并别名之后
  会让运维失去今天事实上拥有的按服务商授权能力，且创建路由侧没有任何护栏。

所以本文重写为**设计变更提案**：先把必须做的决策列出来，再谈控制台。控制台改版排在决策
之后，因为在语义定下来之前做的任何标签，都会重演本文最初要修的那个问题——用一个让人安心
的标签覆盖一个并不存在的保证。

现状说明已拆分到独立文档，它可以立即用于指导配置，不依赖本文任何决策。

## 一、目标

让「一个别名多个目标」成为一种**可以被诚实描述**的运行模式：

1. 它在哪些协议面、哪些失败类别上真正提供切换，界面和文档说的与代码做的一致；
2. 启用它不会让别名在其他维度上悄悄变差（资源类端点、成本治理、可用性、授权面）；
3. 运维在配置时看得见代价，在配置后验证得了效果。

不在目标内：把回退扩展成一种通用的高可用机制。歧义结果不重发是账务保守性的刻意选择，
本文不提议改动它。

## 二、必须先做的决策

每一项都独立成立，可以分别裁决。推荐项是我的判断，不是既定结论。

### D1 · Phase 2 端点在多目标别名上的行为

**现状**：`inference_resources.go:22`、`inference_resources_store.go:217`、`:1113` 在候选数
≠ 1 时返回 409。这是 fail-closed 的正确直觉——资源类操作会在上游留下有状态对象
（文件、批次、异步作业），选错部署等于把对象建在了错误的账户里，且后续按
`ProviderID/DeploymentID/ProfileID/Region` 元组回查会找不到主人。

**问题**：这个判断是在别名恒等于单目标时写的，它今天的表现是「加一条兜底路由，图片接口
就挂了」，且没有任何配置期提示。

**选项**：

- **D1-a（推荐）**：保持 409，但在**配置期**拦截。给一个别名添加第二条启用路由时，若任何
  项目将该别名用于资源类操作（或干脆：只要别名已被任何项目授权），控制台与 Admin API
  必须明确告知「该别名将不能再用于 Phase 2 操作」并要求确认。代价最小，语义不变。
- **D1-b**：为资源类操作定义「主目标」——取优先级最高的候选，不回退。可用性不变，
  但引入了「同一个别名对不同操作有不同目标数」的隐式规则，且资源归属会随路由优先级
  调整而漂移。
- **D1-c**：允许资源类操作在多目标别名上按 `targets[0]` 执行并把部署固化进资源记录。
  改动最大，需要重新审视资源所有权契约。

**推荐 D1-a**：把它变成一次知情选择，而不是一次静默降级。

### D2 · Token Guard 的准入定价

**现状**：`captureTokenGuardPricingView`（`service.go:2439`）取候选集最高价作为本次请求的
预估成本，`RecheckCost` 只上调不下调，完成时不按实际成本回冲。

**问题**：加一个贵的兜底目标，会让该别名上**每一个**请求按最贵单价消耗成本窗口，包括
永远由便宜目标服务的那些。这是纯粹由「多配了一个目标」引起的治理面回归。

**选项**：

- **D2-a（推荐）**：准入仍按最高价（保守准入是对的，请求确实可能落到最贵的目标），但在
  `Complete` 时按**实际服务目标**的成本回冲差额。需要 Token Guard 支持向下调整，是
  `internal/tokenguard` 的实质改动。
- **D2-b**：准入改按优先级最高候选的价格。更贴近典型路径，但在真的发生回退时会低估，
  与 Token Guard 的 fail-closed 姿态冲突。
- **D2-c**：不改，只在控制台明示「Token Guard 将按候选集最高单价准入」。零代码，但把
  一个可修的缺陷固化成一条要求运维记住的规则。

**推荐 D2-a**：这是三个闸门里唯一一个既能保持 fail-closed 又能消除副作用的。

### D3 · 未定价 / 定价隔离的候选

**现状**：任一候选取不到覆盖的价格版本，`unknownPricePolicyEvidence`（`service.go:2506`）
让整个请求 409。对有日预算的项目，一条没配价的兜底路由会让别名的**全部**请求失败。

**问题**：加一个目标是为了提高可用性，结果降低了可用性——与提案前提直接相反。
且定价隔离在正常运维中可达（例如从旧备份恢复后重新激活了一个已排期的价格）。

**选项**：

- **D3-a（推荐）**：把未定价候选从候选集中**剔除**而不是否决整个请求；仅当剔除后候选集
  为空时才 409。这保持了「不在无成本治理的情况下计费」这条不变量——被剔除的目标永远不会
  被使用，因而不会产生无价格的计费。
- **D3-b**：保持现状，在控制台阻止把未定价或定价隔离的部署加为候选。护住了创建路径，
  但护不住「已在候选集里的部署事后被定价隔离」。
- **D3-c**：保持现状不动，仅文档说明。

**推荐 D3-a + D3-b 同时做**：前者兜住运行期，后者兜住配置期。

### D4 · 预算耗尽时是否尝试更便宜的候选

**现状**：`errors.Is(err, budget.ErrExceeded)` 在三条循环里都直接返回 403。代码注释给的
理由是「日预算属于项目不属于目标，所以换候选不改变答案」。

**问题**：这个前提在候选价格不同时是**假的**——预留金额按目标定价，贵目标的预留被拒时，
便宜目标的预留可能通过。表现为预算边缘「本可服务的请求收到 `budget_exceeded`」；叠加
`round_robin` 的轮转偏移，同一秒的两个相同请求会得到不同答案。

**选项**：

- **D4-a（推荐）**：`ErrExceeded` 时 `continue` 到下一个候选，仅当所有候选都被拒才返回
  403。语义更准确，且不会突破预算——每个候选各自走完整的预留准入。
- **D4-b**：保持现状，但把候选按价格升序试。改变了 `priority` 的含义，不推荐。
- **D4-c**：保持现状，更新那条注释使其不再声称一个已经不成立的前提。

**推荐 D4-a**；若不做，至少做 D4-c——一条陈述错误前提的注释会误导下一个读它的人。

### D5 · 别名授权的语义与创建侧护栏

**现状**：数据面授权只有 `slices.Contains(principal.Project.AllowedModels, model)`
（`service.go:231`），`Project` 上没有比别名更细的维度。删除路由有护栏
（`admin_providers.go:1743` 会拒绝删掉项目仍在使用的最后一条路由），**创建路由没有**——
`validateAdminRoute`（`:1548`）不查询项目。

**问题**：合并别名会让运维失去今天事实上拥有的按服务商授权能力；此后任何人给该别名加
一条路由，都静默把全部已授权项目扩展到新的凭据、区域与数据驻留姿态。

**选项**：

- **D5-a（推荐，必做）**：把语义写进文档与界面——「项目被授予一个别名，即被授予该别名下
  现在与将来的全部目标」；并给创建/启用路由加上删除侧的对称护栏：列出会因此被扩展的项目，
  要求显式确认，审计记录带上受影响项目列表。
- **D5-b**：在 `Project` 上增加目标级限制（允许的服务商/部署集合）。这是真正的解法，
  但属于授权模型变更，应单独立 ADR。
- **D5-c**：不动。

**推荐 D5-a 立即做，D5-b 记为待定 ADR**。这不是人体工学问题，是凭据隔离与数据驻留问题。

### D6 · 同别名重复部署与「启用但不路由」

两个较小但确定的缺口：

1. **没有任何校验禁止同一别名下两条路由指向同一个部署。** 控制台会显示两个目标，实际是
   一个故障域；断路器按路由 ID 分键，也不会合并它们。→ 建议在 `validateAdminRoute` 中拒绝，
   或至少在控制台阻断。
2. **策略归一化不一致导致「启用但不路由」。** Admin 侧把空策略归一为 `ordered` 再比较
   （`admin_providers.go:1563`），Registry 侧比较原始字符串（`provider.go:568`）。经 Admin API
   创建的空策略路由能通过校验，随后注册失败并被记为 `Dangling`，而控制台仍显示 Enabled。
   → 建议两侧统一归一化，并在路由列表标出被扣留的路由。

## 三、控制台改版（决策落定之后）

以下每一项都以 D1–D6 的结论为前提。**唯一可以现在就做的是 C1**。

**C1 · 修正误导性状态文案（不依赖任何决策，建议立即做）**

`web/src/pages/ProjectsPage.tsx:511` 按 `strategies.size === 1` 决定是否显示策略名，唯独
没有按目标数决定。单目标别名因此显示成「1 条已启用路由 · 顺序回退」——一个并不存在的
保证。改为：

- 有效候选数 = 1：显示「单一目标 · 无回退」，不显示策略名（单目标下它没有含义）。
- 有效候选数 ≥ 2：显示「N 个目标 · 顺序回退 / 轮询」。

**「有效候选数」不是启用路由数**。正确口径是：已启用路由 ∩ 部署已启用 ∩ 探活未失败
（`not_probed` 计入）。这三项前端都拿得到（`Deployment.enabled`、`Deployment.probe.state`）。
用启用路由数会在一个探活失败了两个部署的别名上显示「3 个目标 · 顺序回退」——把 G2 的错误
原样重演一层。

**C2 · 路由页别名输入改为组合框**，选中已有别名时就地显示该别名当前的目标与优先级，并按
D1/D5 的结论给出相应告知（将不能用于 Phase 2 / 将扩展哪些项目的可触达面）。

**C3 · 路由列表按别名分组**。组标题的策略取**优先级最高目标**的策略——这是引擎实际使用的
规则（`provider.go:621` 读 `targets[0].Strategy`），而不是「全体一致才显示」。混合策略组
本身应当告警。实现时保留 `<tr id="route-{id}">` 结构（现有测试按此定位），用每别名一个
`<tbody>` 分组。

**C4 · 覆盖面标注按协议面分列**，不是按别名给一个笼统的「N 级回退」。诚实的表述形如：
「Chat / 流式 / Embeddings：N 级顺序回退；原生 Messages：无回退；文件 / 批处理 / 异步：
不可用」。这条直接来自 D1 与原生路径的现实。

**C5 · 目标差异知情**：并列显示各目标的部署、服务商、单价与能力标记，并标出回退会失去的
能力项。两处技术要点：

- 能力差集要对齐 `filterSemanticCapabilities` / `filterGenerateProfileCompatibility` /
  `filterPrimitiveTargets` / `filterTokenCapabilities`（`service.go:2622-2664`），
  **不是** `filterByOperation`——后者只有操作粒度。
- 价格不能直接用 `Deployment.input_micros_per_million`，那是不含分时定价的基础费率；
  网关按 `SelectDeploymentPriceVersion` 选中的版本计费。要么标注「基础费率，不含分时定价」，
  要么按部署取价格版本。

**C6 · 尝试预算可达性提示**：需要 `gateway.max_total_attempts` 与
`retry.max_attempts_per_target`，而这两个值**不经过任何 Admin handler**
（只到 `runtime.go:425-426`）。因此本项**必须新增一个只读 Admin API 字段**——这是整个控制台
改版里唯一触碰 Go 的部分，第一版声称的「可由前端聚合」对它不成立。

文案要说「最坏情况下第 K 位之后不保证被尝试」，不能说「不会被尝试」：被断路器或并发闸门
挡住的目标消耗 0 次尝试预算，更靠后的目标仍可达（见 `TestOpenCircuitSkipsFailedTarget`）。
建议动作里要写明改这个值需要重启进程，即一次数据面中断，它与「减少目标数」不是对等选项。

**C7 · 用量页显示 `deployment_id`**。字段在每次尝试的载荷里已经有了，页面只把它放进了链接
href（`UsagePage.tsx:127`），可见文本是别名。没有这一列，回退无法在控制台被验证——对
「同一模型多部署」这种最安全的冗余配法，两个目标在页面上完全无法区分。

**C8 · 开发者工作台**标注别名形态。需要给 `DeveloperPage` 新增一个 `api.routes` 查询——
它当前只有 `projects` 与 `developerConfig`，`allowed_models` 是裸字符串数组。标注只能写在
`<option>` 文本里（`chat · 自动 · 3 目标`）。

## 六、验收

1. 单目标别名在项目弹窗、路由列表、开发者工作台三处均显示「单一目标 · 无回退」，
   不出现策略名。
2. 多目标别名显示的数字是**有效候选数**（已启用路由 ∩ 部署已启用 ∩ 探活未失败），
   不是启用路由数；探活失败一个部署后，数字随之下降。
3. 覆盖面按协议面分列显示，原生 Messages 与 Phase 2 操作的实际行为在界面上可读。
4. 给一个已被项目授权的别名添加第二条启用路由时，界面列出受影响项目并要求确认；
   审计记录包含该列表。
5. 同一别名下重复指向同一部署的路由被拒绝或明确阻断。
6. 一个候选缺少价格版本时，该候选被剔除而其余候选继续服务（D3-a 采纳后）；
   全部候选无价时才 409。
7. Token Guard 的成本窗口消耗与**实际服务目标**的成本一致（D2-a 采纳后）。
8. **回退验证按现状文档第八节的方法进行**：主目标保持启用且探活健康、返回 503，
   请求成功，账本中可见两条尝试（主目标失败 + 备目标成功，`fallback_count = 1`），
   客户端收到的 `model` 仍是别名。禁用路由或让探活失败**不构成**回退验证。
9. 用量页可直接看到每次尝试的 `deployment_id`。
10. 前端测试随文案改动更新而非删除；`internal/webui/dist` 与 `web/src` 同提交。

## 七、风险

- **回退覆盖面窄于直觉。** 401 / 4xx / 5xx / 歧义传输错误都不换目标。界面必须按错误类别
  说清楚，否则 C1 修掉的误导会在「N 级回退」这个标签上重新长出来。
- **跨厂商回退换掉的是模型身份。** 网关只保证请求被服务，不保证输出等价。这一层判断只能
  由运维做，方案靠 C5 的配置期提示让其知情。
- **成本上界随目标数上升。** 一次请求最坏会向多个上游各发一次并各自计费，
  `max_total_attempts` 是硬上限，C6 要让这个上限可见。
- **`round_robin` 的轮转在每次配置热加载后从 `targets[0]` 重新开始**
  （`Registry.Replace` 装入新的计数器映射），频繁改配置会让分摊比例偏离预期。
- **`Retry-After` 来自最后一个被尝试的目标**，与别名整体的可用性没有关系——主目标可能
  当下就是空闲的。
- **路由变更后激活失败会让运行时进入 stale 并拒绝全部数据面流量**，而 Admin 请求已经返回
  成功。每次路由变更后应检查 `halro_activation_stale`。

## 附录 · 为什么不引入「别名组」

即建立一个 `chat-auto`，成员是 `chat-aws`、`chat-deepseek`、`chat-openai`。第一版给的四条
否决理由里有两条经不起推敲，这里重写：

**成立的理由**：路由的 `public_model` 已经是分组键，再加一层引用会让同一个故障域有两种
表达方式，优先级、策略、探活剔除要各写一遍并保持一致；而且它不换来任何用一个别名多条
路由表达不了的能力。

**不成立的理由（第一版的说法，此处撤回）**：

- 「403 判定不再是常量时间的包含判断」——`MaxProjectAllowedModels = 256` 已经给它封了顶，
  组层查找同样有界。更重要的是，**方案 A 并没有回避这个问题，只是把答案默认掉了**：勾选
  一个别名就等于授权其全部现在与将来的目标（见 D5）。组的方案会强迫这个答案被写下来并
  评审，而现在它是隐式且不可评审的。
- 「账本与 Parquet 要扩字段，属于持久化契约变更」——两者已经携带
  `RouteID`/`DeploymentID`/`ProviderID`/`ProviderModel`/`AttemptNumber`/`RetryCount`/`FallbackCount`，
  再加一个字典列是常规改动；且本仓库 pre-1.0.0 的策略本就是就地改格式并提升版本号。

**被漏掉的、方向相反的论据**：要表达「项目 P 可以用 `chat`，但绝不能触达 OpenAI 的凭据」，
唯一的结构化办法就是一个比别名更细的绑定层。方案 A 没有这种表达，而且合并别名会**移除**
运维今天事实上拥有的那一个（一别名一服务商）。这不是人体工学需求，是凭据隔离与数据驻留
需求，已记入 D5-b 作为待定 ADR。
