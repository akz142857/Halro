# 内存有界状态：第一个发布的完成条件

2026-10-13 起草，同日用户确认。依据：[剩余范围审查](memory-bounded-scope-review.zh-CN.md) §3 和看板 §45.1 的裁定（只发 Standalone selected、单一引擎、重新初始化、物理储备移出、2 GiB）。

规则沿用看板 §40.16：

- 每项条件先登记再动手，事后不放宽；
- 证据是确定性测试加一次反向验证（撤掉修复，确认测试会失败）；
- 需要真实 Linux 的只跑一次确认，不做多次统计；
- 登记门槛前，先读它要判定的代码和数据。

## 0. 先要裁定的两件事

起草时核对代码，发现两处前提和 §45.1 的假设不一致。它们决定后面多项条件的写法，需要先定。

**0-1 selected 实例现在只能由迁移产生。** 创建 selected 实例的唯一路径是 `halro metadata migrate --from-backup … --activate-runtime`（`cmd/halro/metadata_migrate.go`）：先用原引擎 bootstrap 一个实例，做加密备份，再从备份迁移。测试夹具也是这样建的（`internal/app/selected_legacy_export_test.go` 的 `selectedLegacyExportFixture`）。仓库里没有“从空目录直接初始化 selected”的路径。所以“删除原引擎”和“重新初始化”都要求先新做一条初始化路径。两种做法：

- **A（推荐）直接初始化**：`halro init` 直接发布一组空的七根和原生日志，不经过原引擎和备份。这样原引擎可以整体删除，迁移命令随之删除。代价是新写一条初始化路径，并补上它的崩溃与重开测试。
- **B 内部复用迁移**：`init` 在内部先建原引擎实例、备份、再迁移。复用已验证的路径，但原引擎的 bootstrap 和备份写入代码必须保留，和“单一引擎”的裁定冲突。

**0-2 删除原引擎后，第一个发布里就没有 HA。** 现有 HA 跑在原引擎上，HA selected 已被后置。两种做法：

- **A（推荐）第一个发布不含 HA**：HA 启动在配置校验时明确拒绝，文档写明。HA selected 完成后作为第二个发布加回。
- **B 原引擎只给 HA 保留**：HA selected 完成后再删。这样两个引擎会继续并存一段时间，S1 的简化推迟。

**裁定（2026-10-13，用户）：0-1 选 A（直接初始化），0-2 选 A（第一个发布不含 HA）。** 下面的条件按此写。

**0-1 修订（同日，用户）。** 核对代码发现 0-1 的前提有误：selected 引擎自己就用“bbolt Metadata + 原生日志”作为交换格式。备份把 Metadata 导出成 bbolt 文件放进归档，`backup restore` 只还原交换格式，要再经激活才成为 selected，密钥轮换也从备份重建。所以建库和备份写入代码本来就要保留，方案 B“会留下原引擎代码”的说法不成立。改为：init 先写交换格式、打一份内部归档，再走已验证的激活路径；restore 改为解包后直接激活；`metadata migrate` 不再作为单独命令暴露，并入 init 和 restore。R-2 删除的是原引擎的运行路径和 `export-legacy`。R-1 的登记见看板 §46。

## 1. 结构改动（先做，后面的条件都在这个结构上判定）

| 编号 | 内容 | 完成条件 |
| --- | --- | --- |
| R-1 | 直接初始化 selected（0-1 A） | `halro init` 在空目录上产生可用的 Standalone selected 实例。测试覆盖三类：初始化后能启动、提交请求、关闭、重开；初始化过程中各阶段 SIGKILL 后重跑能完成，或明确拒绝且不留下半成品；非空目录拒绝 |
| R-2 | 删除原引擎运行路径 | 删除 `Runtime` 中 `selectedState == nil` 的原引擎分支、`memory_state_required` 开关（变成恒为真），以及 `metadata migrate`、`ha-*` 迁移子命令和 `export-legacy`。在原引擎数据目录上启动时，明确报错并给出重新初始化的指引，不尝试读取 |
| R-3 | HA 启动拒绝（0-2 A） | 配置里出现 HA 成员时，启动在打开任何数据之前拒绝，错误信息说明第一个发布不含 HA。HA 代码本身保留，后续发布要用 |
| R-4 | 配置收敛 | 去掉“零表示维持原路径”的语义：每个预算字段要么有由总量推导的默认值，要么是必填项，零值在校验时拒绝或换成推导值。完成判据：`config.example.yaml` 只需给出总 RAM、总磁盘等少数输入，就能通过校验并启动；`TestTheConfigurationReferenceDocumentsEveryKey` 等配置契约测试同步更新 |
| R-5 | 物理储备标为实验 | `physical_terminal_reserve` 保留，在配置文档和启动日志里标为实验功能；运维文档写明不开它时，真实 ENOSPC 下已接受请求的终结没有保证（§32 只验证到压力停止线） |

R-2 会大面积改测试：凡是先建原引擎再迁移的夹具，都要改用 R-1 的初始化路径。这部分工作量现在给不出可靠数字，R-1 完成后先盘点受影响的测试数再估。

## 2. 各项完成条件

“对应表”指：把原完成条件逐条列出，每条写上覆盖它的测试名，缺的补测试。对应表写进看板，作为该项的关闭证据。

| 项 | 完成条件 |
| --- | --- |
| D-02 存储布局 | 写一份 ADR，内容包括：已实现的布局（哪些状态在哪个文件，同库还是独立库）、锁顺序、写放大和 mmap 的已有观察、备份方式，并引用已有的 10 万 segment 对照证据。HA 影响写成“后续发布”。不再做新的选型基准 |
| D-03 认证协议 | 对照代码评审 `memory-state-authenticated-root-protocol.zh-CN.md`，写对应表。6 个性质每个都要有测试，各配一次反向验证：内容与键集合认证、位置、版本、发布、删除检测、恢复。角色恢复中只验 Standalone 重开，HA 后置 |
| D-04a + V-02 容量 | 运行前登记以下内容，然后在 Linux 2 GiB cgroup、隔离 ext4 上跑一次：<br>• 固定输入：历史规模（建议 10 万请求，由新实例直接写入，不经迁移）、并发 64、单请求大小、配置文件原文、Go 版本、镜像<br>• 数值门槛：cgroup 峰值 < 2 GiB 且有登记的余量；磁盘峰值；稳态 p99；冷重开时长；checkpoint 暂停时长<br>• 判据：一次运行全部达标。不达标就记录失败和归因，转入裁定，不改门槛 |

## 3. 发布前必须修的已知缺陷

| 缺陷 | 完成条件 |
| --- | --- |
| 管理审计批次在 ticket 结果未知时把所有者标记为退休（看板 §24） | 结果未知时所有者保持未退休，直到 ticket 被解决；测试覆盖“结果未知 → 后续操作解决 → 退休”，并做反向验证 |
| 单机压缩测试偶发 `context canceled`，原因未归因（看板 §23-2） | 找到原因并修复，或用确定性测试证明它只是测试夹具问题。原测试在 Linux 跑一次通过 |

审查 §4 的其余 5 项随 HA 或物理模式后置，不在第一个发布内。

## 4. 建议顺序

1. 裁定 0-1、0-2。
2. R-1（初始化）→ R-2、R-3（删除和拒绝）→ R-4、R-5（配置和文档）。这一步完成后跑一次完整门禁。
3. D-02、D-03 两份文档，以及 I-04、I-05、I-07～I-12、O-02、V-01 的对应表。这些主要是读代码、补测试，可以按项提交，攒到一起跑一次门禁。
4. §3 两个缺陷。
5. D-04a + V-02 一次 Linux 容量运行。
6. 完整门禁，用户确认后发布。
