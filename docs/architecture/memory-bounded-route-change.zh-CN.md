# 内存有界状态：换路线方案（草案）

2026-10-13 起草，待用户审阅。依据看板 §49～§53。

## 1. 为什么换

selected 引擎（七根认证 COW 状态）在真实负载下不成立：

- 所有账务写入串行通过同一条写入道，并发不能提速（§49.1）。
- 修掉锚点重复验证后，单线程仍比原引擎慢约 2 倍（§51.1）。
- 投影每个请求增长约 50 KB，checkpoint 回收不了；写满后停服，而且重启失败，调大上限也救不回来（§52）。

修好这些需要改 checkpoint 与回收的顺序、准入预留和启动重放三处协议，以天计，修完仍可能慢于原引擎。用户裁定换路线（§53）。

## 2. 原始问题还在

换路线不等于放弃。原问题是原引擎的常驻内存随历史增长（设计文档 §1～§2）：

| 来源 | 增长方式 | 量级（本地合成，设计文档 §1.2） |
| --- | --- | --- |
| Ledger 历史 map（`eventDigests`、`leaseRecords`、`settled`、治理索引） | 每个事件、每个 attempt 永久常驻 | 约 2.7 KB/请求，10 万请求约 276 MiB |
| Usage 明细与摘要（默认 30 天窗口） | 与吞吐 × 窗口成正比 | 1 请求/秒持续 30 天约 2.1 GiB 以上 |
| Snapshot 复制、导出中间数组、Governance checkpoint 拼接 | 峰值放大 | 10 万条 Usage 一次 Snapshot 约 85 MiB |
| segment 目录、价格 timeline、遗留恢复 slice | 随历史增长 | 较小，但无上限 |

生产现象：1 GiB 限制下多个任务 137 退出，调到 2 GiB 后运行在约 1.19 GiB（设计文档 §1.1）。

## 3. 建议路线

**原则。** 只在原引擎上做最小改动，让常驻内存不再随历史增长；不引入新的认证存储。每一步单独登记、单独验证，有可测的完成线。

**第一步：Usage 明细移出内存（收益最大）。** 明细和请求摘要写入磁盘（原引擎已有的 bbolt 或独立文件），内存只保留当前小时的汇总和有限写入缓冲；控制台分页、导出、checkpoint 改为从磁盘按页读。完成线：同一配置下 1 万和 10 万请求时，Usage 相关常驻内存差异不超过登记阈值。

**第二步：Ledger 历史 map 移到磁盘索引。** 去重摘要、已结算 attempt、历史 lease 改为磁盘索引 + 有限缓存；内存只保留活跃 lease、余额和活跃 WorkUnit。启动回放不再把历史重建成常驻对象。完成线同上（Ledger 部分）。

**第三步：去掉只为读水位而做的整份 Snapshot 和导出多份数组。** 改动小，可以和第一步一起做。

**之后再看：** segment 目录、价格 timeline、遗留恢复。按第一、二步之后的实测决定是否需要。

**验证方式。** 每步一个确定性测试（两个历史规模下常驻内存不随规模增长）加一次反向验证；最后在 Linux 2 GiB cgroup 下跑一次真实二进制负载（并发 16/64、10 万请求），和本次原引擎对照的吞吐（§50.1）比较，不能变慢超过登记的比例。

## 4. 分支怎么处理（需要用户裁定）

`memory-bounded-state` 相对 `main` 新增约 15.3 万行非测试 Go 代码，大部分属于 selected 引擎。两种处理：

- **A（推荐）从 `main` 新开分支。** 只挑出对原引擎也成立、已验证的修复（候选：`backup restore` 暂存回收、备份暂存回收、Usage 归档崩溃临时文件回收、macOS 主机压力源等，逐项核对是否适用于 `main` 的代码路径），再在原引擎上做第 3 节的三步。`memory-bounded-state` 保留为存档，不合入。符合“1.0 前不让错误的构造与替代者并存”。
- **B 合入整个分支，selected 默认关闭。** 保留全部工作，但把约 15 万行实验代码和它的配置、测试负担一起带进 `main`，门禁时间也随之翻倍（`internal/app` 单包约半小时）。
