## 3. 方案的主要问题

### 3.1 存储可用成本尚未证明，系统集成已经铺开

原方案 §4.0、§8.2 把 D-02 存储布局、D-03 认证协议、D-04 参数门槛作为关键依赖，实际已有大范围 Runtime、迁移、轮换、复制与物理储备实现，相关决策仍开放。允许原型先行合理，但应先有小型、完整业务切片的成本结论，再扩展整个系统。当前实现承担了自建认证 COW 存储、私有 scratch 树、根选择、回收及退出义务，已经超出普通持久化投影改造。

技术选择需要重新裁定，不应继续通过增加契约和测试来默认批准现有引擎。改用普通 bbolt 也不是自动成立的替代方案：它不能单独满足内容和键集合认证、可信增量重开的要求。

### 3.2 冷构建为低驻留付出的 IO 和分配代价缺乏上限

当前 scratch 没有 Open API，任何失败都会 poison 私有候选，必须从独立认证来源重建；与此同时，每次成功变更同步两个 FD，累计逻辑页读达到 16 MiB 又触发同步和整文件 DONTNEED 请求。源码边界见 `internal/scratchstate/store.go`、`pages.go`、`cache.go`、`block_stage.go`。

这提出一个需要验证的设计问题：不可恢复的私有 scratch 为什么需要这些频度的持久化屏障，页认证、实际 FD 复核和缓存回收是否造成重复 IO？现有 profile 支持将其列为优先调查项，但没有证明单一 Sync 或 DONTNEED 就是全部原因。修改前必须分别说明可见性、最终发布持久性、篡改检测和 cgroup 缓存控制的要求，不能直接删 Sync 或认证。

一万请求冷迁移约 17 分钟及 31.51 GB 累计分配说明成本已经显著。累计分配不是存活 heap，也不是磁盘使用量；低 heap 不能单独回答方案是否可用。只改变缓存或 syscall 次数，必须重新看整条链路时间和真实 IO。

### 3.3 内存、启动、满盘保证和生产接受被绑在同一“完成”中

消除历史驻留、可信增量启动、已接受请求在真实满盘时终结、全部 HA 角色物理信用、生产发布各有不同证明条件。物理终结涉及原生文件、Metadata、多个派生根、共同发布和每个必要 peer，确实有跨层成本；它不能被简化为一个逻辑 Disk permit。

这些目标都可以保留，但应该分别冻结和接受。不能靠“全部继续做”维持一个没有可预测结束点的工作流，也不能因一个可选物理模式尚未完成而掩盖其它模式的已验证进展。任何对外发布仍须满足该模式承诺的全部条件。

### 3.4 文档没有维护一份明确的当前架构决策

主方案共 1057 行，§8.1 从第 468 行延伸到第 835 行，大量历史日志与当前状态并列。主方案已记载新的 HA 七根接线，§8.3 仍有较早阶段描述；存储决策记录保留“最终候选尚未选定”等历史结论。读者需要自行重建时间线才能决定下一步。

原证据不应删除，但主文需要明确当前选定路径、模式、阻断项、替代方案与接受门槛。历史记录应作为证据索引。新增测试或边界不应不断改变同一顶层任务的含义。

### 3.5 执行反馈没有围绕成本与交付收口

此前“查明方案执行四天未完成的原因”聊天已指出构件接通过晚、过渡实现替换和频繁大范围验证；本轮发现当前业务接线已有进展，但容量收敛仍不足。将最新问题继续解释成“复杂、还差验证”不够。

长实验应持续报告实际阶段、完成事实数、输出文件增长、设备 IO 和停滞原因。不能只报告进程还活着，也不能等数小时后才得知磁盘环境不合格。尚未稳定的其它功能不应反复触发同一份容量基线的重编译和重跑。

## 5. 建议替换的近期实施路径

### 第一项交付：当前架构和成本裁定

固定一个完整编译输入的 selected Standalone 候选，沿真实备份验证、迁移、共同激活、业务读取、退出与新进程重开路径分段测量。先复用已有一千/一万样本；缺少归因时补窄实验，不先重跑全矩阵。

每段同时记录原生输入数、派生行数、累计分配、实际读写 bytes、Sync 次数/耗时、RAM 与磁盘峰值。空间记录包括目标文件系统 bytes/inodes、每个 scratch/root/备份/替换产物和底层 host backing；不能仅看配置 ceiling。RAM 配置、swap、cold/warm cache 和整个 seed/restart cgroup 口径明确固定。

先查重复完整扫描与重复建参考，再裁定 scratch 的索引操作、页/原 FD 复核、持久化和回收频度。一个优化只有在相同输入和职责下改善整链路成本、保持全部账务/认证差分时才进入候选。最新 syscall 对照只作为线索。

此交付必须形成保留当前引擎或更换冷构建布局的明确决定。替换方案需具体说明认证和增量恢复如何继续成立，不能仅提出“换数据库”。若相同安全语义下只能通过不可接受的时间或空间成本运行，应承认当前实现不合格并调整架构。

### 第二项交付：目标历史量的完整生命周期

运行前固定可接受的历史规模、业务成功吞吐/并发、p95/p99、迁移时间、普通重开时间、共同检查点暂停和最坏替换空间。尚未获得业务 SLO 时，明确给出工程建议值与采用理由；不等实验完成后再改门槛。

一万规模达到成本门槛，才升级到十万和后续规模。完整 fixture 的磁盘实际可用条件先核对；既有十万失败要补足分层归因，不能只扩大 image 或 ceiling 后宣称修复。最终需要迁移完成、实际业务、多个维护周期、真实原 owner 退出和新进程账务/Usage 一致，不能用只通过拒绝路径的压力测试代替容量。

每轮实验有固定墙钟预算、阶段进度与无进展诊断条件。超过预算时记录超限/诊断结果，按真实 owner 的关闭协议处理；退出未知继续保留义务，不能通过强制退费或随意 unlink 来节省等待。时间预算是实验决策门槛，不改变账务协议。

### 第三项交付：HA 与完整物理保证收口

在已裁定的存储格式上复用现有七根和 TLS 接线，分别关闭真实 HA 业务重开/角色切换、物理信用与公开 opening、在线续期、同组轮换/Seed 的具体缺口。功能模式与物理保证各自列清适用角色和验证结果，未接受的模式保持 guard。
