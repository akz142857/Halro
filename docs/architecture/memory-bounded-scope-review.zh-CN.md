# 内存有界状态：剩余范围审查

2026-10-13 记录。依据看板 §40.16 的安排：I-03 关闭后、开始 I-06 之前，审查剩余各项和状态模型，回答三件事：

1. 哪些项是发布前必需的；
2. 每项能否写成具体、可判定的完成条件；
3. 状态之间的交互能否合并或简化。

本文只给出建议和需要裁定的问题，不改任何任务的完成状态。后续范围由用户裁定。

## 1. 现状

- **任务计数**：25 项中 6 项完成、19 项开放。开放项中 D-01、D-04b、R-01 按用户指示暂缓，其余 16 项是本地工作。
- **代码规模**：本分支相对 `main`（`2425ae8e`），非测试 Go 代码从约 12.6 万行增到约 27.4 万行，新增约 15.3 万行。新增最多的包依次是 `internal/app`（3.6 万行）、`usage`（2.1 万行）、`ledger`（2.1 万行）、`authenticatedstate`（1.0 万行）、`replication`（1.0 万行）。
- **节奏**：只关闭 I-03 一项就用了 2026-10-08 到 10-13，其间跑了 19 轮完整门禁。最近两轮失败（gate 17 的空 `root.pending`、gate 18 的数据竞争）都是本分支以前就有的缺陷，在新测试里才暴露出来。
- **默认行为**：新引擎全部需要显式开启。`memory_state_required`、`physical_terminal_reserve` 默认都是 `false`，59 个资源预算字段大多是“零表示维持原路径”。不迁移、不配置时，运行的仍是 `main` 上的原引擎。

按这个节奏，19 项全部按原条件做完要以周计，而且没法给出可靠日期。所以本文的核心建议是：**先定一个发布范围，范围外的项明确后置，不再按“全部原条件”推进。**

## 2. 状态模型

### 2.1 现在有哪些状态维度

| 维度 | 取值 | 主要位置 |
| --- | --- | --- |
| 引擎 | 原引擎（bbolt + 内存历史）／selected 七根认证状态 | `Runtime.selectedState`、`haSelectedState`；`memory_state_required` |
| 迁移进度 | 未迁移／bootstrap／staging／中断（`memory-state.interrupted-*`）／已激活 | `metadata migrate --activate-runtime`、`memoryStateBootstrap` |
| 拓扑与角色 | Standalone／HA Primary／HA Replica，以及晋升、Stepdown、generation 切换 | `replication`、`statecut/ha_*` |
| 账务健康 | Healthy／Recovery 等 | `ledger.AccountingStatus` |
| 资源准入 | 8 个类别（Configuration、Active、Cache、IO、Background、Completion、Recovery、Control）× RAM/Disk/Unconfirmed 三个维度，加上 Recovery 储备、claim 上限和压力迟滞 | `resourcebudget`；59 个配置字段 |
| 物理终结储备 | 关／开（只支持 Standalone，HA 启动时拒绝） | `physical_terminal_reserve`，涉及 42 个非测试文件 |
| 根与文件所有权 | 七根、两个槽位（`revision % 2`）、`root.pending`、物理回执 `terminal.physical.0/1`、退役债务、持久清单 | `authenticatedstate`、`statecut`、`ownedfile`、`diskinventory` |

这些维度是交叉组合的。比如 `ledger/authenticated_usage_source.go:131` 这一行，就同时判断 `haSelected`、`Replica`、`haReadOnly`、lease、三个 durable 回调和 watermark。近几天门禁里暴露的缺陷，大多出在组合的边上：崩溃窗口、锁顺序、角色和物理模式同时开启的情形。

### 2.2 可以合并或简化的地方

**S1 只保留一个引擎。** 两个引擎并存，带来了“零值维持原路径”的双分支，也带来了 O-01、O-02 里与原引擎互转的全部工作。CLAUDE.md 写明 1.0 之前不保留兼容、错误的构造不与替代者并存。按这一条，selected 应该成为唯一引擎，原引擎的运行路径删除。前提是先回答现有数据怎么处理（见 S5）。

**S2 配置面从 59 个字段收敛。** 多数磁盘和 RAM 上限可以由少数输入推导：总 RAM、总磁盘、历史规模、并发、单请求大小。`persistent_inventory_disk_bytes` 已经改成由配置推导下限（看板 §20），这个做法可以推广。S1 成立后，“零表示原路径”的语义整体去掉。

**S3 物理终结储备移出发布范围。** 它只支持 Standalone，HA 启动拒绝。它还带着已知缺陷：

- 离线 `halro ledger verify` 对物理实例返回 `ErrRecovery`，即使从未 Roll（看板 §36）；
- Standalone 物理 Roll 在“重命名已持久、投影对齐未写入”之间崩溃后无法打开（续作交接 §3.3-12）；
- HA 物理 `BeforeRoll` 只要装了 peer credit 就拒绝，所以 HA 物理 Primary 永远不会 Roll（看板 §37）。

不开物理储备时，已接受请求的终结靠压力停止线（提前拒绝新工作）和 Recovery 储备保护。§32 在不开物理储备的 Standalone 上验证过：持续压力下新请求被拒、已接受请求完成。但 §32 只把磁盘填到停止线（约 64 MiB 可用），没有到真实 ENOSPC。所以取舍是：不开物理储备，磁盘被外部进程真正写满时，已接受请求的终结没有保证，只能靠停止线留出的余量。建议把物理储备保留为显式实验开关，不作为发布条件，并在运维文档里写明这一点；或者整体删除，以后需要时再按单独的设计做。

**S4 先发 Standalone，HA selected 后置。** HA selected 没有维护循环，没有定时封存、Usage 日期维护与窗口裁剪、定时 checkpoint（看板 §37），长期运行会不会重新出现增长还没验证。HA 成员的 Usage 维护 IO 下限约 1.5 GiB，已经超过 normal 池（看板 §36）。所以 HA 要发布，I-06、I-05/I-11 的 HA 部分，加上维护循环，都是必需的。Standalone 不受这些约束。分两步发布，可以把 HA 相关的一大块从第一个发布中移出去。

**S5 冷构建（M3）只跟“现有数据要不要迁移”有关。** 十万请求、1800 秒的冷迁移目标，是为了把已有历史迁进新引擎。如果现有实例改为重新初始化，冷构建只在投影损坏和备份恢复时用到，目标可以按实际历史规模重新定。但生产实例的 Ledger 是账务权威，重新初始化会丢历史，所以这只能由用户决定。

**S6 合并重叠的验收项。** D-04a（本地容量门槛）和 V-02（容量与性能验收）是同一次固定输入的 Linux 运行：一个负责登记门槛，一个负责跑。D-02 和 D-03 都是对已实现设计的书面裁定，可以各写一份 ADR 收口，不再做新的备选方案对比。

“发布必需”指第一个发布（建议为 Standalone selected）是否需要它。完成条件都按“先登记、事后不放宽、确定性测试加一次反向验证、需要 Linux 的只跑一次”来写（见看板 §40.16）。

## 4. 开放的已知缺陷

下面这些在第一个发布前要么修掉，要么写明属于不发布的模式：

1. `ha_memory_state_foundation.go` 约 734 行：在 `f.lifecycle` 下而不是 `f.mu` 下写 `closeErr`，而 `/ready` 在 `f.mu` 下读它（看板 §44）。仅限 HA。
2. 管理审计批次在 ticket 结果未知时，仍把批次所有者标记为退休（看板 §24）。
3. 单机压缩测试偶发 `context canceled`，原因没有归因（看板 §23-2）。
4. 离线 `halro ledger verify` 在物理实例上失败（看板 §36）。仅限物理模式。
5. Standalone 物理 Roll 的崩溃窗口（续作交接 §3.3-12）。仅限物理模式。
6. HA selected 没有维护循环，HA 物理 `BeforeRoll` 永远拒绝（看板 §37）。仅限 HA。
7. HA 成员的 Usage 维护 IO 下限超过 normal 池，Linux 容量剖面 `selectedCapacityBudget` 被拒（看板 §36）。仅限 HA。

如果按 S3、S4 裁定，第 1、4、5、6、7 项都随相应模式后置；Standalone 第一个发布只剩第 2、3 项。

## 5. 需要用户裁定的问题

1. **第一个发布的范围**：只发 Standalone selected（推荐），还是 Standalone 和 HA 一起发？
2. **引擎**：selected 成为唯一引擎、删除原引擎路径（推荐，符合 1.0 前的规则），还是保留两者，由配置开启？
3. **现有数据**：迁移（需要 O-01 和 M3 冷构建达标），还是重新初始化（需要接受旧 Ledger 历史不进入新引擎）？
4. **物理终结储备**：移出发布范围、保留为实验开关（推荐），删除，还是作为发布条件？
5. **容量目标**：维持原 2 GiB 逻辑预算，还是按 Standalone 的实测重定？

裁定之后，按第 3 节把发布范围内每一项的完成条件写进看板，再开始实施。
